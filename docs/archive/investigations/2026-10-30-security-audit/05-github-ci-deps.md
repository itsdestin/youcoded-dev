# 05 - GitHub, CI, release pipeline and dependencies

Auditor: supply-chain specialist. Read-only. Date 2026-10-30. Repos: youcoded-dev (workspace), youcoded, wecoded-marketplace, wecoded-themes (all public), youcoded-admin (private, no workflows). Raw scan files: `gl-*.json` and `audit-*.json` in the same folder (gitleaks output is redacted).

Bottom line: the release pipeline is in good shape. Signing identities are restricted to master and v* tags, there is no pull_request_target, and no PR-controlled text reaches a shell. The real gaps are (1) a single account holds all the power with no second check on master, (2) Dependabot alerts are OFF while `npm audit` shows 2 critical and 8 high production vulnerabilities in the desktop app, (3) third-party actions are pinned by tag, not commit.

## Findings

### F-01 | Medium | Production dependencies carry known critical/high advisories; Dependabot alerts and security updates are disabled
- Precondition: attacker supplies content the vulnerable library parses (a document, an MCP server, a remote HTTP peer).
- Evidence: `npm audit --omit=dev` in `youcoded/desktop`: 16 findings (2 critical, 8 high, 6 moderate). `gh api repos/itsdestin/youcoded` -> `dependabot_security_updates: disabled`; `dependabot/alerts` -> "Dependabot alerts are disabled" (same for marketplace, themes, workspace). Lockfile versions: dompurify 3.4.15, @modelcontextprotocol/sdk 1.30.0, proxy-addr 2.0.7.
- Detail:
  - dompurify (critical, DIRECT). Used in `desktop/src/renderer/components/artifact-views/sanitize-doc-html.ts` and `mascot/sanitize-rig-svg.ts` and the docx worker, i.e. for HTML/SVG from opened files and themes. The advisories cover IN_PLACE mode, `afterSanitize` hooks and SAFE_FOR_TEMPLATES; the code only uses an `afterSanitizeAttributes` hook (line 30) and no IN_PLACE / SAFE_FOR_TEMPLATES (rg checked), so likely not reachable as-is. Still, sanitizer is the last defence, so update. Confidence on reachability: medium.
  - proxy-addr (critical) is a transitive of express via the MCP SDK; only matters if the app runs an express server that trusts `X-Forwarded-For`. Not verified. Confidence low that it is reachable.
  - @modelcontextprotocol/sdk (high, DIRECT, used in `src/main/harness/mcp/mcp-client.ts`): OAuth client may send credentials to a server-chosen authorization server; HTTP transports follow cross-origin redirects. Relevant: a malicious MCP server a user adds could harvest OAuth credentials. Most plausible real impact of the set.
  - zod (high, direct, memory exhaustion), undici, tmp, brace-expansion, xmldom, fast-uri, body-parser: DoS/parsing, mostly low practical impact. exceljs->uuid moderate.
  - worker (marketplace): 1 moderate (hono 4.12.4-4.13.10). partykit (dev-deployed game server): 8 (6 high) but all via the `partykit` CLI, a deploy-time tool.
- Mitigations: `.github/dependabot.yml` exists with weekly npm/gradle/github-actions version updates (so bumps do get proposed); lockfiles committed everywhere.
- Fix: enable Dependabot alerts + security updates in all 4 public repos (free; Settings -> Code security); run `npm update` for dompurify, @modelcontextprotocol/sdk, zod, hono, then re-audit; enable CodeQL default setup (code-scanning currently "no analysis found").

### F-02 | Medium | Nothing stops a compromised owner account (or stolen token) from shipping a release alone
- Attacker/precondition: theft of Destin's GitHub session, PAT, or a malicious local tool with his `gh` token.
- Evidence: `branches/master/protection` on youcoded: `required_pull_request_reviews: null`, `enforce_admins: false`, only required check `build (ubuntu-latest)`; no rulesets (`[]`). wecoded-marketplace: no reviews, but enforce_admins true. wecoded-themes `main`: NOT protected (404). youcoded-dev master: NOT protected. Only collaborator is `itsdestin` (admin). `v*` tags are unprotected; one tag push triggers desktop-release.yml and android-release.yml which sign with all keys. The signing environments' branch policy (master and v*) does not help because the attacker would push master/a tag.
- Impact: attacker pushes a tag -> signed, notarized, manifest-signed malicious update for all users. This is the highest-consequence single point of failure, but it is a normal solo-maintainer situation and needs account takeover.
- Fix (cheap): (a) require 2FA with a hardware key/passkey on the account (not verifiable via API here - confirm); (b) add a tag ruleset on `v*` (restrict creation) and a `release` environment with Destin as required reviewer on the signing environments - a stolen token then cannot sign silently without a second approval click; (c) protect themes `main`. Do NOT enable "require PR review" blindly: with one collaborator it would block his own merges.

### F-03 | Low | Third-party actions pinned to a version tag, not a commit SHA; "require SHA pinning" off
- Evidence: all uses are tags: `actions/checkout@v7` (35x), `setup-node@v7`, `upload-artifact@v7`, `download-artifact@v8`, `gradle/actions/setup-gradle@v6`, `softprops/action-gh-release@v3` (holds contents:write + release upload in the signing job), `azure/login@v3` (receives OIDC token in windows-signing), `actions/github-script@v8`, etc. No 40-hex pins anywhere (rg). `actions/permissions` -> `sha_pinning_required: false`, `allowed_actions: all`.
- Attacker: compromise of a non-GitHub action repo (softprops, azure are the sensitive ones) retags to malicious code, runs inside the signing job (cf. tj-actions incident 2025).
- Mitigation: Dependabot github-actions ecosystem is configured, which will bump SHA pins comfortably.
- Fix: pin `softprops/action-gh-release`, `azure/login`, `gradle/actions` (and ideally everything) to full SHAs with a `# v3` comment; set `allowed_actions` to "selected" (GitHub-owned + those 3).

### F-04 | Low | Android release signing secrets are repo-level, not in a protected environment
- Evidence: `android-release.yml` reads `secrets.KEYSTORE_BASE64` / `KEYSTORE_PASSWORD` with no `environment:` (lines 103-108); repo secret list: KEYSTORE_BASE64, KEYSTORE_PASSWORD, PARTYKIT_*, UPDATE_SIGNING_KEY. Triggers include `workflow_dispatch` (any branch) so any branch workflow edited by a writer can read them. UPDATE_SIGNING_KEY (the ed25519 key that authenticates desktop updates) is also repo-level and read in `desktop-release.yml` (tag-only step) and `desktop-test-build.yml`.
- Contrast: Windows (Azure OIDC, federated credential bound to the windows-signing environment) and macOS (macos-signing) ARE restricted to master/v* (verified `deployment-branch-policies`: windows-signing: master, v*; macos-signing: master, v*).
- Impact: only matters if an attacker gains write access (see F-02); then they could push a branch workflow that exfiltrates the Android keystore and update key. Same precondition as F-02, so Low.
- Fix: move KEYSTORE_* and UPDATE_SIGNING_KEY into environments with the same master/v* rule (and required reviewer).

### F-05 | Low | Android Gradle: no dependency verification; unused jitpack.io repository
- Evidence: no `gradle/verification-metadata.xml`; `settings.gradle.kts:12` adds `maven("https://jitpack.io")` but `app/build.gradle.kts` has no `com.github.*` dependency (rg), so it is dead weight that widens where an artifact could be resolved from. Versions are pinned (e.g. `commons-compress:1.28.0`, wrapper gradle-9.7.1 with `validateDistributionUrl=true`); Dependabot gradle ecosystem on.
- Fix: delete the jitpack line; optionally add Gradle dependency verification (checksums).

### F-06 | Low | Workflow_dispatch inputs interpolated into shell (not exploitable by outsiders)
- Evidence: `wecoded-marketplace/.github/workflows/catalog-ingest.yml:69-71` (`${{ inputs.source }}` into `--source`), `youcoded/.github/actions/beta-version/action.yml:18` passes via env (good). Dispatch needs write access, so an attacker already has more than this. Fix: pass via `env:` anyway.

### F-07 | Low | Rebuild job in marketplace self-reports a required status check
- Evidence: `validate-plugin-pr.yml` "Commit updated marketplace files": creates a check run `bundled-version-bump` = success via API then pushes to master (contents:write, checks:write), to get around branch protection. Guarded: refuses if the commit touches non-listing files. It runs only on push/dispatch to master, after merge. The listing files are produced from third-party plugin repos (`scripts/sync.js` fetches external trees) - data, not executed code, but the token has write. Fine, but note it is a deliberate bypass of protection that relies on the file-list check. Info/Low.

### F-08 | Info | Update-signing-key private key location
- Docs say the private key lives in `~/system/youcoded-release-signing/` on Destin's machine and in the repo secret. Keep that folder out of any synced/backed-up-to-cloud location; not audited here.

### F-09 | Info | Gitleaks: no real secrets found in any repo's history
See Checked-and-OK. The 4,105 hits in the workspace are false positives (see below); worth adding a `.gitleaksignore`/allowlist so future real hits are not drowned out.

### F-10 | Info | Fork-PR approval policy could not be read
`actions/permissions/fork-pr-workflows-private-repos` is not available on public repos. Confirm in the UI (Settings -> Actions -> General -> "Approval for outside collaborators") that it is "Require approval for first-time contributors" or stricter. Practical risk is low because the PR-triggered workflows get a read-only token and no secrets (below).

## Checked and OK

- No `pull_request_target`, no `issue_comment`, no `issues`/`pull_request` text triggers in any of 11+4+2 workflows (rg of `on:` blocks). `workflow_run` appears once (site-deploy.yml, after "Desktop Release" success; job only has contents:read, pages:write, id-token:write and does not check out PR code).
- Script injection: rg for `github.event.(issue|comment|pull_request.title|body|head.ref)`, `github.head_ref` across all workflows -> zero. Only `${{ github.event.pull_request.base.sha / head.sha }}` (hex SHAs, not attacker-controlled text) are inlined (themes `validate-theme.yml`, marketplace `validate-plugin-pr.yml`).
- Default GITHUB_TOKEN is read-only in every repo: `actions/permissions/workflow` -> `default_workflow_permissions: read`, `can_approve_pull_request_reviews: false` (all 5 repos). Write permission is granted per job only in release/rebuild jobs triggered by tag/master/dispatch.
- PR workflows (desktop-ci, android-ci, worker-ci, validate-plugin-pr, validate-theme, workspace-ci, site-deploy PR) use plain `pull_request`: fork PRs get no secrets and a read token. android-ci sets `cache-read-only` for fork PRs so a fork cannot poison the Gradle cache. Drift/watch workflows that install untrusted packages deliberately skip npm cache (comments in cc-popup-drift, cc-startup-drift) and have `contents: read`.
- No self-hosted runners (all ubuntu/windows/macos-latest/macos-14; `actions/runners` total_count 0).
- Signing is gated: Windows (Azure Trusted Signing via OIDC, no password stored) and macOS (Developer ID + notarization) run only in `windows-signing` / `macos-signing` environments, whose branch policies admit only `master` and `v*` (verified via API). Release upload job (`desktop-release.yml` `upload`) runs only `if: startsWith(github.ref,'refs/tags/v')`. Branches/forks get unsigned builds with no secrets.
- Release integrity: Windows installer Authenticode-signed (`electron-builder.win-sign.yml`, azureSignOptions; publisher currently reads "Destin Moss" until LLC qualifies - no SmartScreen red-screen expected beyond early reputation building); macOS hardened runtime + notarize + stapled (`electron-builder.mac-sign.yml`, `notarize-mac-installers.mjs`); in-app updater verifies an ed25519-signed manifest with SHA-256/size per installer against a public key built into the app (`update-manifest-verify.ts`, `update-signing-key.ts`); manifest signing is non-fatal in CI but the updater refuses unsigned releases (fails closed). Linux packages are unsigned (AppImage/deb/rpm) but covered by the same manifest for in-app updates. Office add-on downloads pinned by URL + sha256 (`office-pin.json`).
- Android: release keystore + passwords come from secrets, files git-ignored (`*.jks`, `*.keystore`, `keystore.properties` in youcoded/.gitignore); only the publicly-known debug keystore is committed on purpose. No keystore/.pem/.p12/.env file ever added in youcoded history (`git log --diff-filter=A` check: none). Workspace `.gitignore` covers `.env`, `.env.*`.
- Repo settings: secret scanning + push protection ENABLED on all 4 public repos. Zero deploy keys (all repos). youcoded master: force-push and deletion disallowed, required status check. marketplace master: same plus enforce_admins. Webhooks: only a SourceForge release mirror on youcoded (`events: release`), a normal use. No code-scanning alerts API data (CodeQL not enabled; see F-01).
- Secrets in history (gitleaks, redacted, full history, `--source` each repo): youcoded-admin 0 (81 commits), wecoded-themes 0 (104 commits), youcoded 18, marketplace 276, workspace 4105 - all reviewed and false positives: youcoded = test fixtures (`'sk-live-123456'`, `Bearer wrong-key-1234`, `-----BEGIN PRIVATE KEY-----` stub in a test, `"key": "mcp-two-100x35"`); marketplace = 275 `sourceSha` git hashes in generated `index.json`/`skills/index.json` + 1 deliberate fixture (`plugin-with-secrets/.../fetch.js`, a fake `ghp_E...`); workspace = review-deck JSON `"key": ...` fields, perf-report session UUIDs (`"token": "<uuid>"` from throwaway dev instances), and design docs with placeholder tokens (`ghp_E...` example, `sk-or-v1-total...` placeholder, redactLog test strings). No live credential identified. (Caveat: I judged placeholders by shape; a note in docs says an OpenRouter key once sat untracked in `jev-demo/.env` and was then ignored - confirm it was never committed: no `.env` file appears in any repo's added-file history.) <!-- gitleaks:allow (quotes a test fixture name, not a key) -->
- Lockfiles committed for desktop, desktop/partykit, worker; every resolved URL in desktop's lock is the npm registry (no git/URL dependencies, no unpinned tarballs). Install scripts: electron, electron-winstaller, fsevents, koffi, node-pty only (expected). `postinstall` runs two repo-local patchers (`scripts/patch-node-pty.js`, `patch-xterm-webgl-mipmap.js`) - local files, not network; Dependabot ignores node-pty bumps to avoid silent patch no-ops.
- Electron 41.10.7 (package.json `^41.10.7`, lock 41.10.7) - current major line as of the audit; no known-CVE concern identified (did not fetch the web).
- Gradle wrapper pinned to 9.7.1 with distribution URL validation.
