# 04 - Supply chain: what code reaches a user's machine
Auditor: supply-chain specialist. Read-only static review. Paths relative to
/home/destin/youcoded-dev/worktrees/sessions/security-audit-2026-10-30/ (D = youcoded/desktop/src/main, R = youcoded/desktop/src/renderer).
No Critical or High findings. The self-update path is genuinely well built. The weak spots are (a) the single trust root "whatever is on wecoded-marketplace master", (b) the theme remote-stylesheet hole, (c) the signing key living in a plain GitHub secret.

## Findings

### SC-1  MEDIUM  Theme `google-font-url` loads any remote stylesheet, bypassing every theme CSS check
- Precondition: a theme in the community registry (or a hand-installed theme) sets `font.google-font-url` to an attacker URL. Reviewer approves it while the URL serves harmless CSS; attacker later changes what the URL serves.
- Steps: theme installs -> applyThemeFont sets `<link rel=stylesheet href=URL>` with no validation -> remote CSS now styles the whole app and can change after review. It can restyle/relabel/hide buttons (e.g. the permission Allow/Deny prompt), and every load is a tracking beacon (IP, time).
- Evidence: R/themes/theme-engine.ts:112-122 (url used verbatim, no host check). R/themes/theme-validator.ts:152-186 sanitizes only `custom_css`. wecoded-themes validate-theme.yml checks only custom_css, never font URL. No Content-Security-Policy on the main window: R/index.html has none, and grep of D for CSP finds none for the main window. Same gap: `background.value` of `https://...` passes through (R/themes/theme-asset-resolver.ts:19-27).
- Mitigations: today every published theme uses fonts.googleapis.com (grep of wecoded-themes/themes/*/manifest.json). CSS cannot run JS. Script-in-SVG is separately blocked (see OK list).
- Confidence: Confirmed (code path read end to end).
- Fix: in validateCommunityTheme and in theme-engine, allow only `https://fonts.googleapis.com/` (and drop non-theme-asset backgrounds); add the same rule to validate-theme.yml; add a CSP `style-src/img-src/font-src` allowlist to the main window; pin external fonts by bundling them into the theme instead.

### SC-2  LOW-MEDIUM  `sanitizeCSS` is a regex filter and is bypassable (and CI uses the same weak regex)
- Steps (tested with a copy of the regex in node): `background:image-set("https://e.example/b.png" 1x)` passes unchanged; `url(\68ttps://e.example/b.png)` (CSS escape) passes unchanged; `@\69mport "https://..."` passes the @import strip. Result: remote image beacons from custom_css.
- Evidence: R/themes/theme-validator.ts:152-170; wecoded-themes/.github/workflows/validate-theme.yml (python re.search patterns, same shape). Only applied at marketplace install, not to later registry changes.
- Impact: privacy beacon / tracking; with attribute selectors, limited data leakage from attribute values. No code execution.
- Confidence: Confirmed. Fix: parse CSS (e.g. a real CSS tokenizer) and allow only `url(theme-asset://...)`/`data:`; reject `image-set`, `src()`, `@import` after unescaping; CSP `img-src` closes it regardless.

### SC-3  MEDIUM  The update-signing private key is a plain repository secret, so "signed updates" do not protect against a compromise of the repo or CI
- Attacker/precondition: write access to itsdestin/youcoded (stolen maintainer login/token, or a malicious action update) - the exact threat the signature was added for.
- Steps: push a `v*` tag or edit desktop-release.yml -> job `upload` runs with `UPDATE_SIGNING_KEY` in env -> workflow prints/sends the key or signs a malicious build -> every installed app accepts it (key pinned in app, so no way to react short of shipping a release signed by the same stolen key).
- Evidence: youcoded/.github/workflows/desktop-release.yml:254-306 (job `upload` has no `environment:` gate, unlike windows-signing/macos-signing at :43; secret read at the "Sign release manifest" step). Signing failure is non-fatal and ships unsigned (the app then refuses that release, which is safe).
- Mitigations: signature still defeats tampering with release assets after the build and a hijacked CDN/redirect. Windows/macOS code-signing keys ARE environment-gated to master + v* tags. No pull_request_target anywhere (grep over all three repos).
- Related (Low): third-party actions pinned by mutable tag, not commit SHA: softprops/action-gh-release@v3 (in the very job that handles release files), azure/login@v3, gradle/actions/setup-gradle@v6, plus actions/*@vN across all repos. A hijacked tag runs in release/CI jobs.
- Confidence: Confirmed. Fix: move UPDATE_SIGNING_KEY into a protected GitHub Environment with required reviewer + tag/branch rules (or sign offline / with a hardware key or KMS and keep the key out of CI); pin third-party actions to full SHAs (dependabot already present); require 2FA and branch/tag protection on the repo. Document key-rotation/revocation (see SC-9).

### SC-4  MEDIUM  Our own plugins (and ALL third-party plugins when the Worker is down) install from "whatever is on master now" with no signature or pin, and run on every session
- Attacker/precondition: write access to itsdestin/wecoded-marketplace master (or a malicious merged community PR in a bundled plugin directory, or compromise of the repo owner account).
- Steps: bot or PR changes e.g. youcoded-inbox hooks-manifest.json / mcp-manifest.json -> every app launch runs reconcileBundledPlugins -> `git fetch` + `git reset --hard origin/master` of the cache clone -> copies into ~/.claude/marketplaces/youcoded/plugins -> hook-reconciler writes new hooks into ~/.claude/settings.json and mcp-reconciler writes MCP servers into ~/.claude.json -> Claude Code runs them on the next session, as the user, with no prompt.
- Evidence: D/skill-provider.ts:1042-1130 (reconcile at launch, :1240), D/plugin-installer.ts:240-263,282-316 (reset --hard origin/<branch>, 1h cache, no commit/signature check), D/hook-reconciler.ts:219-242 (adds `required` hooks), D/mcp-reconciler.ts:205-225 (adds `auto:true` servers). Only third-party entries are pinned, via the Worker catalog's `catalog.sourceCommit` (D/skill-provider.ts:333, scripts/catalog/sources/wecoded.mjs:250 - for `isOurs` entries sourceCommit is deliberately undefined). The fallback `index.json` has NO commit field at all (python count: 0 of 367 entries), so with the Worker down/CATALOG_ENABLED=0 every third-party `url`/`git-subdir` plugin installs at the upstream repo's current HEAD, unreviewed and with no capability list. Integration installs (D/integration-installer.ts:147) also pass no commit.
- Mitigations: third-party plugins from the catalog ARE pinned to the scanned commit (D/plugin-installer.ts:448-462,pinToCommit) - good: a listed community plugin cannot change after listing. Detail page shows a "What this can do" list before Install (R/components/marketplace/CapabilityList.tsx), computed from the same scanned files. Repo-side settings (branch protection / required reviews) cannot be verified from the code; only a `bundled-version-bump` required check is evident (validate-plugin-pr.yml:317-340).
- Confidence: Confirmed (mechanism). Whether master has required human review: Unverified.
- Fix: pin bundled plugins to a commit/tag baked into each app release (or signed with the same ed25519 key and verified before copy); fail closed (no install) when the catalog is unavailable for url/git-subdir sources, or at least show a warning; require reviews + signed commits on master of wecoded-marketplace; restrict who can touch bundled plugin directories (CODEOWNERS).

### SC-5  LOW-MEDIUM  Installed plugin manifests silently edit Claude Code's hook and MCP config; a plugin can overwrite another hook
- Steps: any installed plugin with hooks-manifest.json `required:true` entries gets them appended to ~/.claude/settings.json; with mcp-manifest.json `auto:true` gets stdio servers (arbitrary `command`/`args`/`env`) added to ~/.claude.json. In addition, if a manifest hook has the same script basename + matcher as an EXISTING hook (the user's or another plugin's, e.g. `session-start.sh`), the existing hook's command is REWRITTEN to the plugin's command.
- Evidence: D/hook-reconciler.ts:168-196 (findMatchingEntry basename match), :208-221 (command overwrite), :222-233 (add required). D/mcp-reconciler.ts:205-225. Consent: capability text shown before install, but nothing at the moment config files are modified, and nothing for hooks that match by name.
- Impact: installing a plugin = trusting it fully (inherent in Claude Code plugins). The extra risk is hijacking an existing hook and no per-plugin hook/MCP review step.
- Confidence: Confirmed. Fix: match hooks on full command path inside the plugin's own root, never on basename alone; show the exact hooks/MCP commands in the install confirmation; list plugin-added hooks/servers in a settings screen with off switches.

### SC-6  LOW  `postInstall` "trusted org" check is substring matching
- Evidence: D/plugin-installer.ts:122-134 `entry.sourceRef.includes('github.com/itsdestin/')`. A URL like `https://evil.example/github.com/itsdestin/x.git` or `https://github.com/evil/r?x=github.com/itsdestin/` passes. The command then runs via `bash -c` in the plugin dir (:127-141,:644).
- Preconditions: a registry/catalog entry carrying `postInstall` (none today: 0 entries in index.json/marketplace.json/overrides). Needs registry compromise anyway, so this is defence-in-depth that fails to defend.
- Confidence: Confirmed. Fix: parse the URL, require host === github.com and first path segment in allowlist, scheme https; or delete the feature (unused).

### SC-7  LOW  Prerequisite installer: GitHub CLI download has no checksum; Claude Code installer is `curl | sh`/`irm | iex`; predictable temp names
- Evidence: gh archive downloaded with TLS only, then unzip/tar and copied to PATH (D/prerequisite-installer.ts:1030-1065, version-pinned at :116 but no hash). Claude Code via vendor script (:1131 `irm https://claude.ai/install.ps1 | iex`, :1153 `curl -fsSL https://claude.ai/install.sh`). downloadFile follows redirects to any host (no allowlist) (:581-613). Temp files use fixed names in os.tmpdir() (e.g. :762, :808, :1033); on a shared Linux box a local user could pre-create them (kernel protected_regular usually blocks this).
- Mitigations (good): Node (all platforms) and portable Git are pinned by SHA-256 and checked BEFORE unpack/run (:97-110,:766,:814,:223); args passed via execFile (no shell injection); Windows System32 tools by absolute path.
- Confidence: Confirmed. Fix: add SHA-256 for gh (from the release's checksums file at the pinned version); download into a fresh mkdtemp dir; restrict redirect hosts. The Claude Code script is Anthropic's own and over TLS - acceptable, note as a trust dependency.

### SC-8  LOW  Announcement text is written to the terminal with raw control characters
- Steps: whoever can edit announcements.txt on youcoded master puts ESC sequences in the first line -> cache JSON -> statusline.sh prints `'\x1b[1;33m★ ' + message` raw, so a terminal escape (title change, OSC-8 fake link, possibly OSC-52 clipboard write if the terminal honours it) can be injected into every user's terminal. The in-app status bar renders it as text.
- Evidence: D/announcement-service.ts:52-65 (no stripping of control characters), youcoded/desktop/hook-scripts/statusline.sh:285-299.
- Precondition: write access to the youcoded repo (same bar as SC-3). Confidence: Likely (depends on terminal/Claude Code handling). Fix: strip C0/C1 control chars and ESC in parseAnnouncement; cap length.

### SC-9  LOW / INFO  Update rollback protection is relative to the running version only; no key rotation or revocation story
- A signed-but-old release newer than the installed one (e.g. a vulnerable 1.2.5 when running 1.2.0) is accepted if an attacker who controls GitHub release listings advertises it as "latest". Requires GitHub-level compromise plus an old vulnerable signed build. Evidence: D/update-manifest-verify.ts:171-176. Key is a single embedded ed25519 key (D/update-signing-key.ts); rotating needs a release signed with the old key. Fix: signed manifest could carry a "minimum safe version" / expiry timestamp; document the rotation drill.

### SC-10  LOW / INFO  Smaller items
- Plugin copy follows symlinks inside a cloned repo: copyDirSync uses copyFileSync (follows file symlinks) (D/plugin-installer.ts:165-176) so a git-subdir plugin can copy a local file such as ~/.ssh/id_rsa into its folder; `url` plugins keep symlinks in place, so a skill file can point at a private file that the model then reads. Needs a plugin the user already chose to install; use lstat and reject symlinks (and symlinks pointing outside the plugin root).
- git-subdir `subdir` is joined without a containment check (D/plugin-installer.ts:526-533). git's sparse-checkout normally refuses `../`, so likely unreachable; add isContainedIn.
- Theme install fetches `manifestUrl`/`assetUrls` from the registry without host/HTTPS restriction or hash check (D/theme-marketplace-provider.ts:166,195); trust root = registry (raw.githubusercontent main). Path traversal is blocked (:189-193). Add an https + host allowlist and verify the content hash that the publisher already computes (theme-content-hash.ts).
- Skill share links: `youcoded://skill/...` decode only creates a prompt skill from untrusted text (capped 2000 chars) (D/skill-provider.ts:736-760); plugin import is "not implemented", so no code path. Info: the prompt text is still prompt-injection material the user should see before saving.
- Workflow hygiene (no secrets exposed): validate-theme.yml interpolates directory names from the PR into shell/python (`for slug in ${{ steps.changed.outputs.themes }}`, python `'$MANIFEST'`); it runs on plain `pull_request` (fork PRs get no secrets, read-only token), so only a risk for same-repo branches. catalog-ingest.yml interpolates `${{ inputs.source }}` into a run line (workflow_dispatch needs write access). validate-plugin-pr.yml runs PR-supplied `npm test`/`node --test` on `pull_request` (no secrets for forks). update-registry.yml (push to main, contents:write) renders merged theme content in headless Chromium - fine unless a merged theme is hostile.
- Marketplace automatic scan (scripts/catalog/lib/capabilities.mjs) is regex heuristics that label, not block: obfuscated code or a split-up `curl|sh` would not be flagged. It is a convenience list, not a security gate.
- Android: no in-app updater and no network download of executables found (no REQUEST_INSTALL_PACKAGES; RuntimeInstaller.kt unpacks assets bundled in the APK). Android receives plugin/hook/MCP behaviour through the same desktop backend, so SC-4/SC-5 apply there too.

## Checked and OK (defences that hold)
- Desktop self-update verifies an ed25519 signature over the release manifest against a pinned public key BEFORE any installer runs: D/update-manifest-verify.ts:97-110 (verify), :160-194 (signature -> shape -> tag==manifest version -> not-newer-than-running refused -> size + SHA-256 of the exact file). Key embedded: D/update-signing-key.ts:13-16.
- Gate runs at every launch path, not just download: D/update-service.ts:299-303 (verifyBeforeLaunch), :423-445 (launchVerified refuses on any failure and deletes corrupt file), :593, :1001 (quit-time re-hash against freshly fetched signed file), :1109. A release with no manifest is refused (:272-275).
- HTTPS only and host allowlist (github.com, objects/release-assets.githubusercontent.com) on every redirect hop; max 5 redirects; byte cap on manifest/signature: D/update-installer.ts:28-45, D/update-service.ts:218-250, :525. Extension allowlist per OS (update-installer.ts:48-56). Dev "fake update" is gated by !app.isPackaged (:211-213).
- Downgrade/replay of old versions blocked (newer-than-running required, correct semver incl. betas): update-manifest-verify.ts:171-176,118-150. Stable users never see pre-releases: update-service.ts:49-57.
- Release pipeline: signing step verifies against the app's embedded key before publishing (desktop-release.yml:289-304); Windows/macOS signing secrets restricted to protected environments (desktop-release.yml:43). No `pull_request_target` and no PR-title/body/branch-name interpolation into `run:` in any of the three repos (grep).
- Local engine (llama.cpp) binaries: pinned version with a per-archive SHA-256 table, hash checked before unpack: D/engine/engine-pin.ts:18-70, D/engine/engine-acquisition.ts:373-395. Model weights: file names reduced with path.basename (no traversal), SHA-256 verified when the Hugging Face listing supplies one, atomic rename: D/models/model-downloader.ts:149-175; fixed host huggingface.co (hf-client.ts:22-27). Weights are data, not executed by YouCoded.
- Prerequisite installer pins and hash-checks Node and portable Git; uses execFile arrays (no shell interpolation); Windows PowerShell/tar by absolute path (prerequisite-installer.ts:97-110,223,766,814).
- Plugin installer: plugin id whitelisted `^[a-zA-Z0-9_-]+$` (plugin-installer.ts:55,583,659); HTTPS-only git URLs, so no ext::/file::/ssh (:441,468); `local` source containment check (:278,350); atomic stage-then-swap upgrades with rollback (:318-360); third-party plugins checked out at the catalog-scanned commit, not HEAD (:448-462); uninstall path containment (:668).
- Registry/runtime config is fetched over HTTPS only (raw.githubusercontent.com, Worker). curated-models.json rows are shape-checked (curated-catalog.ts:15-25); search-chain.json is enum-validated to exa/ddg/tavily so it cannot name a URL or command (harness/search/search-chain.ts:24-31); announcement is plain text (no URLs opened, no markup) except SC-8; none of these three can open a URL or run anything. (remote-config.ts is Tailscale/remote-access config, not a fetched config file.)
- Themes: `theme-asset://` handler allows only `[a-z0-9_-]` slugs, lexical AND realpath containment (symlink escape blocked): D/theme-protocol.ts:12-14,34-55. Install writes assets only inside the theme dir (theme-marketplace-provider.ts:189-193), 10 MB cap (:200). Themes cannot carry JS: no script field; mascot/companion SVGs fetched only from theme-asset:// or same-origin and go through XML parse -> tag/attr blocklist -> DOMPurify, failing closed (R/components/mascot/sanitize-rig-svg.ts:1-100; R/themes/theme-asset-resolver.ts:44-52); wecoded-themes CI also runs audit-svg-safety.mjs (validate-theme.yml end).
- Registry PR CI: plain `pull_request` (no secrets to forks); the privileged rebuild job runs only on push to master / manual dispatch and its commit step refuses to push anything but listing files (validate-plugin-pr.yml:250-340); secret-file and hard-coded-key scans are blocking (:80-135); no auto-merge anywhere; dependabot configured in both registries.
- Skill share links cannot install code (see SC-10).
