# Prior art for Glob/Grep tool design: what mature harnesses do

Research task: ground our fixes for five measured problems in our native harness's `Glob`/`Grep` tools
(`youcoded/desktop/src/main/harness/tools/glob.ts`, `grep.ts`) against what real agentic coding harnesses
actually do. Every claim below is cited; anything I couldn't confirm from a primary source is marked
**not found** rather than estimated.

## Six problems: root cause (ours) + recommendation, grounded in prior art

### 1. Glob silently doesn't expand braces

**Our root cause, confirmed by reading `youcoded/desktop/src/main/harness/tools/glob.ts`:** Glob is *not* backed by ripgrep or any glob library — it's a hand-rolled single-pass glob→regex converter (`fileGlobToRegex`). It handles `*`, `**`, `**/`, and `?`, but treats `{` and `}` as literal characters to escape (`'.+^${}()|[]\\'.includes(c)` → `rx += '\\' + c'`). So `*.{ts,kt,toml}` compiles to a regex matching the literal substring `.{ts,kt,toml}`, which no real filename contains — hence "No files matched" with zero signal that the syntax, not the search, is the problem.

**Prior art:** every harness surveyed that *has* a dedicated glob tool supports braces, and by two different mechanisms:
- **Claude Code** doesn't do glob matching in JS at all — it shells to `rg --files --glob <pattern>`, and ripgrep's own `globset`-crate glob engine supports `{a,b}` alternation as a first-class syntax element (not a rare edge case) [^cc-brace]. Verified independently against `globset`'s own docs: `{a,b}` is a documented core pattern; only *nesting* (`{a,{b,c}}`) is disallowed pre-ripgrep-15.0.0, and a well-known-looking "3+ items break" issue ([ripgrep#3018](https://github.com/BurntSushi/ripgrep/issues/3018)) was **closed `not_planned`** after the maintainer reproduced the reporter's exact 3-item case (`folder/{foo,bar,baz}`) and found it worked correctly — the original report was a CLI `--include`/`--exclude` interaction bug in the reporter's test harness, not a globset defect. So a straightforward `{ts,kt,toml}` is not expected to fail in ripgrep.
- **Gemini CLI** uses the npm `glob` package (built on `minimatch`), which enables brace expansion by default and gemini-cli does not disable it [^gem-brace].
- **Codex CLI** has no dedicated tool; it inherits whatever bare `rg` does, i.e. the same globset behavior as CC.
- **OpenCode** is architecturally identical to CC here — `rg --files --glob=<pattern>` via a shared ripgrep service, and its own tool docs use `"*.{ts,tsx}"` as the canonical example [^oc-brace] — a second independent confirmation that shelling to ripgrep's native glob engine is the standard way to get correct, unsurprising brace support.
- **Aider** and **Cline** have no glob tool at all, so the question doesn't apply to either.

**Recommendation: support braces, don't just detect-and-warn.** This is a genuine compatibility bug against Claude Code (our explicit default), not a matter of taste — CC supports the exact pattern shape that broke in our battery. The concrete fix is a library change: replace `fileGlobToRegex`'s hand-rolled converter with one of (a) shelling to the bundled ripgrep binary we already vendor for Grep (`@vscode/ripgrep`) via `rg --files --glob <pattern>`, matching CC's own architecture exactly and inheriting its brace support for free, or (b) if staying off ripgrep for Glob is deliberate, add brace-alternation handling to `fileGlobToRegex` directly (expand `{a,b,c}` into an alternation group `(?:a|b|c)` before the existing single-pass scan — non-nested only, matching CC's own pre-15.0.0 restriction, which is sufficient for the reported case). Given Grep already shells to bundled `rg`, option (a) also deletes the duplicate custom glob engine and its risk surface. Kimi's "detect and warn" idea is a reasonable *fallback* net (if an unrecognized construct like nested braces or `!()` extglob syntax appears, say so explicitly) but should not be the primary fix when the primary fix is cheap and CC-compatible. For that fallback net, OpenCode's pattern is worth copying directly: it distinguishes ripgrep exit code 1 (`items: []`, a genuine empty result) from exit code 2 with a `regex parse error`/`error parsing regex` stderr match (a distinct `Ripgrep.InvalidPatternError`) [^oc-zero] — the same exit-code/stderr split is available to us for free since we already shell to `rg` in Grep, and would apply to Glob too once Glob also shells to `rg` (see recommendation above). That is a strictly better version of "detect and warn": it doesn't need pattern-shape heuristics at all, it just reads ripgrep's own error signal.

### 2. Grep count mode reports a capped count as if it were a total

**Our root cause, confirmed by reading `grep.ts`:** the tool unconditionally passes `--max-count 500` to ripgrep regardless of `output_mode` (line 45: `const rgArgs = [..., '--max-count', '500']`). Ripgrep's `-m/--max-count` "limits the number of matching lines per file searched to NUM" — i.e. it stops the search itself, not just the printed output. So when `output_mode: 'count'` also sets `--count`, ripgrep is not under-reporting a real count it already computed; **it never counted past 500 in the first place.** There is no number to recover after the fact — the true count (2400, per Opus's follow-up) was never computed internally.

**Prior art:** Claude Code's docs state the count-mode total "covers every match even when `head_limit` or `offset` truncate the listed per-file entries" [^cc-docs] — i.e., CC treats count as a true, uncapped number and only caps what/how many *entries* are displayed, not the underlying count. This is consistent with the premise in the research brief: counting via `rg -c` without `-m` is cheap (ripgrep still has to scan the file either way; the only added cost is not stopping early, and no content is returned to inflate the response). The counter-example is instructive too: **OpenCode does exactly what we do wrong.** Its `metadata.count`/`matches` field reflects the length of its capped (`limit=100`) result list, not an independently computed total, and it labels the cap-hit case "(more matches available)" rather than giving a real number [^oc-count] — i.e., OpenCode has the identical "capped count presented as if authoritative" shape our battery flagged. No harness surveyed does the *capped-and-mislabeled* thing except OpenCode; CC is the only one that does count mode as a true exhaustive total.

**Recommendation:** stop applying `--max-count 500` when `output_mode === 'count'`. Run `rg --count` (or `--count-matches` if we want match-count rather than matching-line-count parity with CC) with no `-m` cap, so the number itself is always exhaustive; keep `head_limit`-style truncation only for how many per-file result *lines* are printed if the file list itself is huge (that's a display concern, separate from the number being wrong). Keep `--max-count 500` for `content` and `files_with_matches` modes, where it legitimately bounds work and output. This turns "misleading capped number with a disclaimer" into "correct number, always."

### 3. Grep content mode can flood the context

**Our root cause:** `caps: { maxChars: 30_000, maxLines: 250 }` (via `defineTool`'s generic `truncateOutput` wrapper) is a fixed post-hoc truncation applied after ripgrep already returned up to `500 matches/file × N files` of raw text — the expensive part (ripgrep producing and the tool buffering up to 200KB of stdout) has already happened by the time truncation kicks in.

**Prior art for auto-downgrade specifically:** none of the surveyed harnesses auto-downgrades `content`→`count`/`files_with_matches` based on match volume — Gemini CLI's `total_max_matches` (100, hard cap), CC's `head_limit` (250, hard cap), and OpenCode's `limit` (100, hard cap) are all pre-set caps, not adaptive volume-based mode switches. So "auto-downgrade to a *different mode*" is not an established pattern anywhere in this survey — it would be a novel design, not a copy. What *is* established and directly actionable, and closer to the spirit of the complaint: **Cline's `capSearchOutput`** does head/tail-preserving *middle* truncation (keep the start and end, elide the middle) with an explicit "narrow the pattern" notice at a 48,000-char ceiling [^cline-caps], rather than a naive head-cutoff — that's a real, already-shipped version of "smarter truncation instead of a wasted dump," just not a mode-switch. CC's per-line `--max-columns 500` cap (truncating *within* a matched line, independent of total match count) is a second mechanism we don't have — it bounds pathological single-line blowups (e.g. minified files) that a `maxLines`/`maxChars` cap alone doesn't catch cleanly. And Cline pushes `--max-count=1` at the ripgrep layer itself (first match per file only) [^cline-caps] — the most aggressive volume control in the survey, applied before any output is even generated rather than after.

**Recommendation:** three concrete, prior-art-backed changes, plus one flagged-as-novel option. (1) Add ripgrep's own `--max-columns 500` (or similar) to the Grep invocation so a single absurd line can't dominate the 30K-char budget — this is what CC does and is a one-line change. (2) Consider lowering the default match volume before truncation kicks in (e.g. tightening `--max-count`) for `content` mode specifically, taking a cue from Gemini's/OpenCode's stricter 100 default and Cline's `--max-count=1` vs. our 500/250 combo — these aren't all the same knob, but the comparison suggests our defaults are the most permissive of any harness surveyed. (3) Swap our current head-only truncation for something closer to Cline's head/tail-preserving `capSearchOutput` — a truncation notice that shows the start of the match list AND at least one tail sample is more informative than "here are the first 250 lines and then nothing," at no extra ripgrep cost. (4) The "auto-downgrade to count/files_with_matches when volume is high" idea from the battery has no prior-art backing in this survey — flag it to Destin as worth prototyping on its own merits, not as a "everyone does this" claim.

### 4. No context lines (-A/-B/-C) in Grep content mode

**Our root cause:** confirmed absent — `grep.ts`'s `inputSchema` is `{ pattern, path, glob, output_mode }` only; no context parameter exists, and the `rgArgs` builder never passes `-A`/`-B`/`-C`.

**Prior art:** every harness surveyed that wraps ripgrep exposes context lines directly:
- **Claude Code**: `-A`, `-B`, `-C` as named parameters, passed straight through as ripgrep flags (not renamed to `context`) [^cc-grep-schema].
- **Gemini CLI**: absent on the *base* `grep_search` tool, but compensated by an automatic behavior worth copying on its own (see §"worth copying" below) — its newer `grep_search_ripgrep` variant does expose explicit `context`/`before`/`after` params.
- **Codex CLI**: N/A structurally, but the model can and does pass `rg -A/-B/-C` itself via the shell tool — so functionally, Codex users already get this; we'd be behind even Codex's raw-shell fallback.
- **OpenCode** and **Cline** are the counter-examples, and instructive ones: OpenCode's `grep` tool has no context param at all [^oc-nocontext], and Cline's `search` tool hardcodes `contextLines = 2` at executor construction with zero model control [^cline-context]. Both read as unfinished rather than deliberate — Cline shipping a fixed, non-adjustable default is the same "the model can't get what it needs without a workaround" gap as our missing parameter, just resolved with a hardcoded guess instead of nothing. Neither is a model to follow here.

**Recommendation:** add `-A`, `-B`, `-C` as optional numeric parameters on our Grep tool, matching Claude Code's exact parameter names (not a synthesized `context` field) — this is a straight compatibility gap, not a design choice, since our tool surface is explicitly meant to mirror CC's. Wire them straight through to the `rg` invocation in `grep.ts` (`if (args['-C'] != null) rgArgs.push('-C', String(args['-C']))`, same for `-A`/`-B`). Low-risk, ripgrep already supports it natively, no new library needed.

### 5. Glob recursion semantics on directories

**Our root cause, confirmed by reading `glob.ts`:** the `walk()` function only tests **files** against the compiled regex (`if (e.isDirectory()) { ...recurse...; continue }` — directories are never matched, only ever recursed into). So a pattern like `**/*with spaces*` can only ever return files whose *name* matches, never a directory, and — critically — matching a directory by name does not imply anything about its contents unless the pattern itself extends past it (`**/*with spaces*/**`).

**Prior art:** this is not a bug relative to Claude Code — it's the same architecture. CC's Glob is `rg --files --glob <pattern>` [^cc-rg], and `rg --files` **only ever lists files**, never directories, by ripgrep's own design (ripgrep has no directory-listing mode). Gemini CLI's `glob.ts` is similarly built on the npm `glob` package used in its default file-only mode. So "a directory-shaped pattern doesn't automatically pull in its contents" is universal file-glob semantics across every dedicated glob tool surveyed, not something our harness does differently. Opus's "coin flip" framing is a real UX gap, but it's a gap in *expectation-setting*, not in behavior that diverges from prior art.

**Recommendation:** don't change the matching semantics (they already match CC). Fix the expectation gap in the tool's own description text instead — our current description is `'Find files by glob pattern (e.g. "src/**/*.ts"). Returns paths sorted by modification time, newest first.'`; add a clause like "matches file paths only — to list a directory's contents, end the pattern with `/**`," mirroring how CC's docs explicitly scope Glob to file-pattern matching by name (not directory browsing) [^cc-docs]. This is the same fix Kimi/Grok's brace complaint asked for in spirit — better upfront disclosure over silent surprising behavior — but here it's a docstring fix, not a code fix, since the underlying behavior is already correct and CC-consistent.

### 6. Parameter naming inconsistency (`path` on Glob vs. Grep)

**Checked directly against our own source, not just the battery's report:** in `glob.ts`, `path` is resolved via `resolveP(args.path ?? '.', ctx.cwd)` and used as the **root directory to walk**. In `grep.ts`, `path` is resolved via the identical `resolveP(args.path ?? '.', ctx.cwd)` and used as the **directory ripgrep searches under**. These are the *same* semantics in code — both are "search root directory," not "a base" vs. "a directory" as DeepSeek's framing implied. Neither schema has a `.describe()` string on `path` at all (`z.object({ pattern: z.string(), path: z.string().optional() })` for Glob; same shape for Grep), so a model has zero documentation to go on for either tool and may be inferring a distinction from behavior it never actually has — e.g. combining a `pattern` that itself contains path segments (`src/**/*.ts`) with a separately-specified `path` could look like two different roles even though the resolution logic is identical.

**Prior art for what CC actually does:** Claude Code's own docs describe `path` identically for both tools — Glob: "The directory to search in. If not specified, the current working directory will be used." Grep: "specifies search directory (defaults to current working directory)" [^cc-docs]. So **CC does not have this inconsistency**, and confirming our own code shows we don't structurally have it either — what's actually missing is the parameter documentation (`.describe()`) that would prevent a model from *inferring* an inconsistency that isn't there. This means the fix isn't a rename; it's adding descriptive text to both schemas, matching CC's practice of writing an explicit one-line description for every parameter (`pattern`, `path`, `glob`, `output_mode`, `-A`/`-B`/`-C` are all individually documented in CC's schema) [^cc-grep-schema].

**Recommendation:** add `.describe('The directory to search in (relative to the working directory). Defaults to the current directory.')` (or equivalent) to `path` on both `glob.ts` and `grep.ts` — same string, underscoring that they mean the same thing. This is cheap, directly CC-aligned, and turns "the finding is real in CC too" into a settled "no — CC has it, we already match CC in code, we were just missing the doc string that would have kept a model from assuming otherwise."

## Anything worth copying that nobody in our reviews asked for

- **Gemini CLI's auto-context injection** (`enrichWithAutoContext`): when a grep search returns very few matches (1, or 2–3), it automatically widens the returned window to ±50 or ±15 lines *without the model asking for context at all*, with an explicit comment citing a measured ~10% reduction in follow-up turns on SWE-bench [^gem-context]. This is a stronger version of problem #4's fix — instead of relying on the model to remember to pass `-C`, the tool infers "you probably want to see the body" from match sparsity itself. Worth prototyping as a complement to (not replacement for) adding explicit `-A/-B/-C` params: expose the explicit params for when the model wants precise control, but when a search returns a small number of hits with no context requested, default to some free additional context automatically.
- **CC's per-line `--max-columns` cap** is a genuinely different truncation axis than "total chars/lines" — it caps *width*, which nothing in our current `truncateOutput`/`caps` mechanism does. Already folded into the problem #3 recommendation above, but flagging separately because it's a small, cheap, orthogonal safety net (protects against one absurd minified-JS line blowing the budget even when total match count is otherwise reasonable).
- **Codex CLI's `original_token_count` field on truncated shell output** — even though Codex has no structured search tool, its shell tool's truncation response includes the *pre-truncation* size alongside the truncated content. That's the same instinct behind our `bounds`/`composeNotice` mechanism (per `.claude/rules/native-runtime.md`: "Tools DECLARE what they omitted") — worth checking that our count-mode fix (recommendation #2) and content-mode notices both surface an honest "here's how much there really was" number, not just "there's more."
- **OpenCode's exit-code-based error classification** (`Ripgrep.InvalidPatternError` on exit 2 + regex-parse-error stderr, vs. plain empty `items: []` on exit 1) [^oc-zero] is a clean, cheap pattern for exactly the class of problem the battery flagged for Glob (problem #1) — it's a general technique ("don't collapse a tool's distinct exit/error signals into one 'no results' string") that applies to Grep too, and costs nothing since we already parse `rg`'s exit code in `grep.ts` (it already special-cases exit 2 for `content`/`files_with_matches` — worth confirming `count` mode gets the same treatment once recommendation #2 changes its invocation).
- **Cline's head/tail-preserving truncation** (`capSearchOutput`, keep both ends instead of just the head) is a small, concrete pattern worth lifting wholesale into recommendation #3 above regardless of anything else in this document — a truncated-but-still-representative sample beats a truncated-and-arbitrarily-biased-toward-the-top-of-the-file one.
