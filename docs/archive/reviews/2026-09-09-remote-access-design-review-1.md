# Remote access batch 1 — technical design review, round 1

Reviewed: `docs/archive/specs/2026-09-09-remote-access-batch1-technical-design.md`
against `docs/active/specs/2026-09-09-remote-access-first-milestone.md` and app
HEAD `de69d60a` in this worktree. Paths below are workspace-relative; every line
number was opened, not carried over.

Locator check on the design's own "Today" claims: `remote-server.ts:174`,
`:389`, `:435`, `:468`, `:757`, `:2286`, `remote-config.ts:21-25`,
`remote-shim.ts:35`, `:88`, `:135`, `:150`, `:646` all resolve to the code the

## Findings

Triage by the implementing session, 2026-09-09: **all twenty accepted.** R1-1, R1-7,
R1-8, R1-9 and R1-12 were re-opened line by line before accepting; the rest were accepted
on the reviewer's cited evidence. Nothing was rejected and nothing was already handled.

- **R1-1 — Binding to loopback silently promotes every remote device to host-local privilege.** `youcoded/desktop/src/main/remote-server.ts:2272-2283` gates `remote:set-password` on `client.ip === '127.0.0.1' || '::1' || '::ffff:127.0.0.1'` (`:2274`). `client.ip` comes from `req.socket.remoteAddress` (`:748`). With §3's `listen(port, '127.0.0.1')` behind Tailscale Serve, every remote client arrives from 127.0.0.1, so the only "local connection" check in the file passes for all of them: any paired phone or browser can change the host password and, through `invalidateTokens()` (`:435-443`), throw every other device off. §3 does not mention this handler. Fix: replace the source-IP test with an explicit capability on the device record (host administration is the milestone's "restrict host administration and credentials explicitly"), and land that in the same batch as the bind change — not after it. — **accepted**

- **R1-2 — The same bind change collapses per-IP rate limiting and the device list's only identifier.** `remote-server.ts:751` rate-limits by `ip`, with `RATE_LIMIT_MAX_FAILURES = 5` per 60 s (`:80`, `:2764-2779`). Once every client is 127.0.0.1, that is one shared bucket: five bad password attempts from any one device lock out every device, and an attacker who can reach the port can deliberately lock out the owner. `getClientList()` (`:458-464`) also returns `ip` per client, which is what the Settings device rows show today — after the change every row reads 127.0.0.1. §3 mentions neither. Fix: key the limiter and the device rows on the device record (or on a forwarded identity Serve provides), and say which. — **accepted**

- **R1-3 — §3 has no client-side story, and every saved connection breaks on upgrade.** `youcoded/desktop/src/renderer/remote-shim.ts:780` hardcodes `targetUrl = ws://${host}:${port}/ws`; the saved-device record is `{name, host, port, password}` (`renderer/components/SettingsPanel.tsx:1908-1915`, port defaulting to 9900); the QR handler throws the scheme away and defaults the port to 9900 (`:1945-1953`); Android persists the same host/port/password shape (`youcoded/app/src/main/kotlin/com/youcoded/app/runtime/SessionService.kt:1784-1806`). A loopback-bound server makes every one of those stored targets unreachable, and there is no code path that can produce a `wss://<name>.<tailnet>.ts.net/ws` target. The design's migration paragraph covers host-side pairing records only. Fix: specify the canonical endpoint shape, the client change that emits it, and what happens to each existing saved device row and QR payload on upgrade. — **accepted**

- **R1-4 — The pairing-file migration is hand-waved and internally inconsistent.** `remote-server.ts:261-267` reads a flat array; `:805-806` mints a **fresh UUID on every successful password auth**, so `~/.claude/.remote-tokens.json` typically holds several entries per physical device, not one per device. "Migrated as one record named 'Existing device'" therefore merges unrelated credentials, and §2 simultaneously renames the file to `.remote-devices[.profile].json` without saying what reads the old path — on upgrade every device silently unpairs. "Whichever the migration test shows is safe" leaves the decision unmade in a document that is meant to be the implementation contract. Fix: state the shape detection (array = legacy), the read-old/write-new path, whether legacy entries become N records or a forced re-pair, and pick one. — **accepted**

- **R1-5 — The new credential format is unspecified in the one place it matters.** Today the token *is* the secret: `remote-server.ts:797` authenticates on `this.tokens.has(msg.token)`. §1 says "`id` is what the client sends; the secret is stored hashed", which either means the id alone still authenticates (no improvement — the id is in the device list UI and the auth message) or means the client also sends a secret, which changes the auth message, the browser's `localStorage` token and Android's stored record — none of which the design mentions. The hash is also unnamed: `remote-config.ts:11` uses bcrypt at 10 rounds (~100 ms per compare) inside the Electron **main** process, so a per-record scan on reconnect would block the UI process. Fix: give the auth message fields, state that lookup is by id (O(1), then one compare), and name the hash. — **accepted**

- **R1-6 — §4's removal list is incomplete; following it as written leaves a broken build and a live field.** Beyond the four sites named, `trustTailscale` also appears at `main/ipc-handlers.ts:1754,1757`; `main/preload.ts:840`; `renderer/remote-shim.ts:1254`; `renderer/components/SettingsPanel.tsx:81,1357,1722,2428`; `renderer/dev/workbench/mock-shim.ts:1684`; `main/remote-config.ts:36,45,56,75,87,125,132,138`. `isTailscaleIp()` (`remote-config.ts:103-112`) becomes dead code and will be reported by knip. `youcoded/app/src/main/kotlin/.../SessionService.kt:1508` still answers `remote:get-config` with `trustTailscale`, so the Android bridge keeps emitting a field the renderer no longer types. Existing tests assert it and will fail: `desktop/tests/remote-config.test.ts:49,58,66` and eleven fixture sites in `desktop/tests/remote-server.test.ts`. Fix: enumerate all of these, including the Kotlin line and the test updates. — **accepted**

- **R1-7 — §4 overstates today's exposure.** `trustTailscale` defaults to `false` (`remote-config.ts:56`) and only turns on via Settings → "Skip password on Tailscale" (`SettingsPanel.tsx:1722`, handler `:2428`). The bypass is real but opt-in, so "a saved `trustTailscale: true` is read once and discarded" affects only users who turned the toggle on. Fix: say so, so the user-facing note is accurate about who is affected. — **accepted**

- **R1-8 — §5's "Today" is wrong about what already exists.** `start()` already installs an `error` handler, rolls back and rejects with the real OS error (`remote-server.ts:368-395`); the Settings toggle path already catches it, reverts `enabled` and returns `{ error }` verbatim (`ipc-handlers.ts:1770-1787`); and `isRunning()` already exists (`remote-server.ts:279`) but has no caller anywhere in `main/` or `renderer/`. What is actually missing is **exposure**: `IPC.REMOTE_GET_CONFIG` (`ipc-handlers.ts:1741-1746`) returns `toSafeObject()` plus `clientCount` and no run state, so the indicator falls back to `config?.enabled && tailscale?.installed && tailscale?.connected` — `SettingsPanel.tsx:1372`, not the inherited 1262-1275 locator, which is now an unrelated status strip. Fix: restate §5 as "surface state that already exists over a named channel", name that channel and its payload, and say that the Android bridge's `remote:get-config` (`SessionService.kt:1502-1512`) must answer the new field too. — **accepted**

- **R1-9 — §5's named test partly exists and, as described, could pass without the fix.** `desktop/tests/remote-server.test.ts:410-414` already forces `EADDRINUSE` through the `listenBehavior` mock (`:20-45`) and asserts `start()` rejects. A new test that only re-asserts the rejection cannot fail for the absence of §5. Fix: assert the *reported* state — what `REMOTE_GET_CONFIG` returns after a failed start, and that it carries the OS reason. — **accepted**

- **R1-10 — §3's change breaks the existing test suite, and its named test cannot assert what it claims.** `desktop/tests/remote-server.test.ts:29-41` mocks `http.createServer` with `listen: vi.fn((_port, cb) => { …; cb?.(); })`. Changing the call to `server.listen(port, '127.0.0.1', cb)` makes `cb` the string `'127.0.0.1'`, and `cb?.()` throws — every test that calls `start()` fails, not just the new one. The suite also never binds a real socket, so "a test asserting the bound address is loopback" can only assert the argument passed to a mock. Fix: include the mock update in the design, and describe the assertion as an argument check (or specify a real-`http` test with an ephemeral port). — **accepted**

- **R1-11 — The §1/§2 tests as described would write to the live app's pairing store.** `remote-server.ts:174` builds `tokensPath` from `os.homedir()` inside the constructor and `saveTokens()` (`:270-276`) writes it. `desktop/tests/remote-server.test.ts` uses the real `fs` (`:3`, no `vi.mock('fs')`) and no current test drives the auth path, so nothing writes today. A test that "pairs, unpairs and restarts the server against the same file" added there would overwrite `~/.claude/.remote-tokens.json` — the file the running built app owns, which `.claude/rules/live-app-safety.md` puts off-limits. Fix: make the store path a constructor option (as `requestSnapshot` already is) and say so in §1/§2, so the tests point at a tmp dir. — **accepted**

- **R1-12 — §2's test cannot work as written.** `remote-config.ts:12` reads `const PROFILE = process.env.YOUCODED_PROFILE ?? ''` **once at module load**; `CONFIG_PATH()` closes over it. "Constructs two servers with different profiles" in one module instance yields the same path for both. The existing profile tests get around this with `process.env` + `vi.resetModules()` + re-import (`desktop/tests/remote-config.test.ts:229-282`). Fix: either have the shared path helper read `process.env` at call time, or specify the resetModules pattern the test must use. — **accepted**

- **R1-13 — §6's browser change creates an unbounded retry loop that trips the host's own lockout.** A revoked or wrong credential produces `auth:failed` **and** `recordFailedAttempt(ip)` (`remote-shim.ts` → `remote-server.ts:815-818`); `scheduleReconnect` retries on every failure (`remote-shim.ts:668-678`) with a 30 s ceiling. Removing the exhaustion escape without adding a stop condition means a browser whose device was unpaired retries forever, hits five failures in 60 s and takes the 4029 lockout (`:751`) — shared with every other device once R1-1's bind lands. §1 says a revoked device "is told it was unpaired" but nothing says the client stops. Fix: on a definitive unpaired/invalid-credential close, stop retrying, keep nothing but the disconnected state, and show the re-pair step. — **accepted**

- **R1-14 — §6's "platform-aware" fallback has no named signal, and the obvious one is wrong.** The existing local-bridge test is `location.protocol === 'file:' && !targetUrl` (`remote-shim.ts:549`, `:629`). An Android client connected to a *remote* host has `targetUrl` set, so that expression reports "not local" even though a real bridge exists — reusing it would deny Android the fallback the design wants to keep. Fix: name the condition explicitly (`location.protocol === 'file:'` alone, or a build-time platform flag). — **accepted**

- **R1-15 — §6's deadline fix does not cover the repeat risk it is aimed at.** A request already handed to `ws.send()` (`remote-shim.ts:121-123` only queues when *not* connected) is not in `pendingSendQueue`; when the socket drops mid-flight, only its `pending` entry times out. Deadlines on queued messages therefore cannot stop that class of repeat, and the design's answer — "surfaced as uncertain, with a safe next step" — names no mechanism: no per-request id echoed on reconnect, no server-side record of executed ids. This is the milestone's core acceptance requirement, not a detail. Fix: state how the client learns an in-flight request's outcome after reconnect, or state plainly that batch 1 only *reports* uncertainty and name the surface that does it. — **accepted**

- **R1-16 — "Bounded authentication/liveness" is a batch-1 scope item and the design does not address liveness at all.** Auth is bounded (`AUTH_TIMEOUT_MS = 5000`, `remote-server.ts:78`, `:771-773`), but there is no ping/pong, heartbeat or idle timeout anywhere in `remote-server.ts` — a client that disappears stays in `this.clients` and keeps receiving broadcasts. Serve adds a proxy hop, which makes half-open sockets more likely, not less. Fix: include a liveness bound, or say explicitly that it moves to a later batch and why that is safe. — **accepted**

- **R1-17 — No origin validation, and §3 makes its absence exploitable from the host's own browser.** The `WebSocketServer` is constructed without `verifyClient` (`remote-server.ts:321`) and nothing in the file inspects `Origin` or `Host`. WebSocket connections are not subject to CORS, so once the server is on 127.0.0.1 any page the user visits can open `ws://127.0.0.1:9900/ws` — and by R1-1 that connection counts as "local" for the password handler. The milestone lists origin validation in the same checkpoint bullet as the loopback bind. Fix: validate `Origin`/`Host` on upgrade in this batch. — **accepted**

- **R1-18 — §3 commits to Serve before the feasibility gate the milestone puts first.** The milestone's "First checkpoint — transport feasibility, before implementation" and the design's own "Still to prove" agree that WebSocket upgrade through Serve, header/query fidelity, idle behaviour, phone wake and route coexistence are unverified. §3 nonetheless specifies the bind change and the Serve route as decided work, and says nothing about who runs `tailscale serve`, with what privileges, on which host platforms, what happens when the CLI is absent or HTTPS certificates are not enabled for the tailnet, or how the app detects a failed Serve setup. Failing any of those, the bind change leaves remote access dead with no fallback. Fix: gate the bind change on those runtime checks, or ship it behind a setting whose default flips only after they pass, and specify the no-Serve failure state. — **accepted**

- **R1-19 — "Devices with names, where removing one really removes it" needs host-side surfaces the design never names.** `getClientList()` (`remote-server.ts:458-464`) returns only *connected* sockets as `{id, ip, connectedAt}`, and the Settings list is built from it (`SettingsPanel.tsx:2480-2484`, which calls `remote.disconnectClient`). A paired-but-offline device has no row to remove, and a revoked one has no socket to close. The design specifies no channel names, payload shape, preload entry or Android bridge parity for the new device list — and new `remote.*` channels are not caught by `desktop/tests/shim-parity.test.ts`, which only scans the preload's `session:` block (`:24`). Fix: name the channels and their payloads, and list the preload/shim/Kotlin sites that must move together. — **accepted**

- **R1-20 — §1's second named test is weaker than the risk it is meant to guard.** "Unpairing device A leaves device B connected" guards against a bug that does not exist today: `invalidateTokens()` (`remote-server.ts:435-443`) is called only on password change (`ipc-handlers.ts:1750`, `remote-server.ts:2280`), never from `disconnectClient` (`:468-478`). The durability risk is elsewhere — `saveTokens()` is called only when a credential is *minted* (`:760`, `:807`), so a design that sets `revokedAt` in memory and relies on the existing save points would lose the revocation on restart, and the test as described would still pass. Fix: have the test assert that after revoking A the server is restarted from the same file and **B's credential still authenticates while A's is refused**. — **accepted**
