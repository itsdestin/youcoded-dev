# Admin password UX review 2 — beta tester pass

Tested at `http://127.0.0.1:5233/?mode=workbench&child=1&view=tools`, "Admin password" section, against the simulated backend. Desktop width 1440px and phone width 390px. Screenshot paths are under `/tmp/claude-1000/-home-destin-youcoded-dev/eaa2bb68-654a-4cf4-a6ae-ec612e110464/scratchpad/shots/midnight/`.

- U1 accepted — Expected pressing Enter after typing my password to submit it, the same as clicking Confirm / Instead Enter does nothing at all — the card stays exactly as it was, no error, no loading, no change — while clicking Confirm visibly reacts (clears the field). A person used to hitting Enter in every other password box on their computer would think the app froze or didn't hear them. — "Enter your computer password" card — `wrong-card-retype.png` (Confirm-works reference) and `seq-enter-pressed.png` (Enter does nothing)

- U2 rejected (approved design R9: the banner stays until the next answer; changing it reopens approved UI) — Expected that once I start typing a new password after seeing "Wrong password," the old warning would clear or dim so I know I'm on a fresh try / Instead the gold "Wrong password / 2 tries left." box stays fully lit right above the box while I'm typing, and the Confirm button turns bright green (looking ready) at the same time. Two contradictory signals sit on screen together — "still wrong" and "good to go" — right before I'd press Confirm for real. — "bash-sudo-password-wrong" card — `wrong-card-retype.png`

- U3 rejected (the shared danger-outline Button's disabled state, used app-wide; filed on the roadmap rather than restyled here) — The red "Stopping…" label (after pressing Stop on the running-as-admin card) is hard to read — measured contrast 3.98:1, below the 4.5:1 minimum for text that size. Everything else I looked at on these cards passed contrast checks; this is the one place text got noticeably harder to read while something was actively changing. — "Ran a command · in the background" (running-as-admin) card, Stop button — `seq-stop-clicked.png`

- U4 rejected (owner-settled Full auto wording, same as review 1 U4) — The card that says "Full auto still stops here — this runs with full control of your computer" uses the term "Full auto" with zero explanation on the card itself. I don't know what "Full auto" means in this app (some kind of autonomous mode?) and the card gives me no way to find out. A college student with no prior context would be equally lost. Suggested shorter, plainer wording: "Even when it's running many steps on its own, it still stops here — this command would fully control your computer." — "bash-sudo-awaiting-approval-fullauto" card — `phone-approval.png`

- U5 rejected (a gallery artefact: in the app only one of the two cards ever appears, per mode) — The two "stop before an admin command" cards sit side by side and are visually identical except for one sentence of body text (everything else — title, command, buttons — is the same). Nothing on the card marks them as two different situations (like a badge for "autopilot mode"). Seeing them stacked like this, my first reaction was "did this text get duplicated by mistake," not "these are two different scenarios." — both approval cards — `pw-empty.png`

- U6 rejected (Destin chose to show the exact command, R7; the assistant's plain summary is in the card header) — The raw command shown to me — `sudo pacman -S --needed rocm-hip-runtime hipblas rocblas` — is Linux package-manager syntax. As someone who (per this test) has never coded, I don't know what `pacman`, `--needed`, `rocm-hip-runtime`, `hipblas`, or `rocblas` mean. I'm being asked to hand over my computer password to run a line I can't read at all. A plain-language line above it — like "Installs graphics drivers your local AI models need" (which is close to what the card's title already says) — would tell me what I'm approving without also showing the cryptic command. If the exact command matters to anyone, it could be tucked behind a "show details" toggle instead of shown by default.

- U7 rejected (approved on decks R2-3/R4-1: the password card shows the step sudo runs) — Small inconsistency: the "stop before an admin command" cards show the full command with `sudo` in front (`sudo pacman -S ...`), but the password-entry cards for the exact same action show it without `sudo` (`pacman -S ...`). Not a big deal on its own, but if I were checking that the password screen is asking about the same thing I just approved, the command text doesn't quite match. — compare `pw-empty.png` (approval cards) against the password cards below them in the same image

- U8 rejected (approved wording, R11 names the script) — "Asked partway through install.sh" names a file (`install.sh`) most non-developers won't recognize as "a setup script." Everything else on that card is in plain English; this one word choice stands out. Suggested: "Asked partway through setup."

- U9 rejected (Destin removed extra text from the first card, R2-3) (positive, worth keeping/expanding) — The line "Only type your password if you expected this step" on the mid-script password card is the single most reassuring thing on any of these cards — it directly tells me how to spot a trick. It only appears on that one card, though; the very first, plain password card doesn't carry any version of that same reassurance, even though that's exactly where a first-time user needs it most.

- U10 rejected (existing header truncation used by every tool card; not this feature) — Minor, phone width (390px) only: the header row on every card ("Running a command · '...'") truncates the quoted description early, e.g. down to `"Install the A…"`. This may be an existing pattern used everywhere in the app, not specific to these cards, so flagging it lightly — I could not find a way to read the full text without widening the window (no tooltip, and clicking the row didn't expand it in my testing). — `phone-approval.png`

## Things that worked as expected (no finding, listed for completeness)
- Show/hide password eye button correctly toggles masked dots to plain text and back.
- Confirm is disabled (dimmed) while the password field is empty, and becomes enabled as soon as I type anything — checked in code (`disabled: true/false`) across all four password cards.
- Clicking "Stop" on the running-as-admin card gives immediate feedback ("Stopping…") and the elapsed timer visibly ticks up in real time.
- "Run it" / "Skip it" and the raw "Confirm" click do nothing further because this is a static simulated backend — expected, not reported as a bug per the test brief.
- No layout clipping, overlap, or unreadable text found at 390px width on any of the seven admin-password cards I could bring into view.

## Could I complete the task, and what confused me most
Yes — I could read every card, click every button asked of it (password field, eye toggle, Enter, Confirm, Run it, Skip it, Stop), and I never hit a dead end. The single most confusing moment was U2: retyping a password on the "wrong password, 2 tries left" card left the old red warning fully lit at the same time the Confirm button turned bright green, as if the app were telling me two opposite things — "that failed" and "you're good to go" — in the same breath, right before I'd hand over my real password.
