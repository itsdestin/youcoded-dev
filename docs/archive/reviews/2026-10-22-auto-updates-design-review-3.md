# Review 3 — auto-updates technical design rev 3 (adversarial)

Paths are under youcoded/desktop unless noted. Mac and Windows behaviour is from platform knowledge, not run here.

- F1 — blocker — The Restart prompt can be answered "yes" by the app's own quit. `shutdownApp()` calls `settlePendingCloseRequests()` → `closeRequests.settleAll`, which resolves EVERY pending request (including the update prompt with its own key) as `{ close:true, reopen:true }` — the same shape as a Yes. Design §4 step 2 says "any quit starting while the prompt is open ⇒ not install", but the awaiting code cannot tell that settle from a real Yes, so a menu Quit / Cmd+Q / SIGTERM during the prompt continues into step 3 (Mac password box, `'install-relaunch'` mark, Linux pkexec) in the middle of a shutdown. — evidence: src/main/close-request-manager.ts:162-168 (KEEP_TRACKED), main.ts:1936-1941 (settle at top of shutdownApp). — Fix: after the prompt resolves, re-check `shuttingDown` (or give settleAll a distinct "app-quitting" result for update requests) and return `{ restarting:false }` before any step 3 work; pin it in a test.

- F2 — blocker — A Mac root helper started by Restart outlives a held or abandoned Restart and then acts on the NEXT exit of any kind. Design §4 step 3 says it "simply waits for the next exit". That next exit may be a plain quit (user chose Discard and quit, or just quit later), a crash or a SIGTERM: the helper swaps and `open`s the new app, so a plain Quit relaunches the app, installs with the switch off, skips the exit-hook brake / attempt-record / failure-count gates, and installs even if the release was pulled meanwhile. It also polls a pid with no timeout and no cancel path (pid reuse). — evidence: design §4 table (macOS needs password row) and step 3; app-restart.ts:79-86 (a held restart is forgotten, nothing can recall a root helper). — Fix: give the helper a handshake: it waits for a "go" token (file or fd the exit hook writes only for `'install-relaunch'`) and a deadline, and exits without swapping if the token never arrives; or start it only from the exit hook (one password box then needs the prompt answered earlier — use a pre-authorised short-lived helper that still needs the token).

- F3 — major — The existing interactive install path will now double-fire. `update-service.ts` `launch()` ends with `setTimeout(() => app.quit(), 500)`, which goes through `before-quit` → `gatedQuit` with no restart requested — exactly the design's definition of "a person's quit" (§4 "When a quit installs"). With a `pending` file and the switch on, that quit would also spawn the quiet installer on top of the interactive installer / disk image the user just launched (Windows per-machine, Mac password fallback after a cancel, manual fallback, Linux pkexec). The same applies to the Mac "cancel ⇒ open the disk image" fallback if the user then quits. — evidence: src/main/update-service.ts:171; design §4 "When a quit installs". — Fix: `launch()` and every fallback must mark the exit action `'none'` (an explicit "install already handled" flag), and the quit-install intent must be opt-in set by menu/Cmd+Q/window-all-closed callers, not inferred from "no restart requested".

- F4 — major — Work that cannot finish inside `will-quit` is placed there. The process exits as soon as the `will-quit` handlers return (and `app.exit` after the watchdog), so async work started there may be cut off. Linux AppImage "copy the file beside the running AppImage, verify, rename" (180 MB copy + hash) is listed as running "from will-quit"; the attempt record "written at the moment of spawn" and any async `fs.promises` write there likewise races process exit. The design also says every new path is async and the blocking-call allowlist does not grow, which conflicts with needing a synchronous write/rename at exit. — evidence: design §4 table (AppImage row), exit-hook paragraph, Performance section; app-restart.ts:62-67 (`onWillQuit` is synchronous, nothing awaits). — Fix: do the copy + verify in the prepare step (or earlier, right after download verifies), leaving only a synchronous `renameSync`/`spawn` + a small synchronous attempt write at exit, and say those few sync calls are the allowlisted exception.

- F5 — major — Mac staging cannot fit in the 5 s prepare cap. §4 says prepare "runs the brake and the hash re-check and leaves a ready-to-spawn plan", but the macOS row requires `hdiutil attach`, `ditto` of a ~300–400 MB app, `codesign --verify --deep --strict -R`, detach — routinely well over 5 s. Where staging runs is unspecified for quit install: inside prepare ⇒ it times out and the quit never installs on slower disks (silent, every time, with a 5 s hang on each quit); at will-quit ⇒ it is cut off (F4). — evidence: design §4 macOS staging paragraph vs "prepareInstall … capped at 5 s". — Fix: stage on the Mac right after the download verifies (background, once, recorded in `pending`), re-verify only the staged copy's signature/hash in prepare, and keep the cap for the brake + hash only.

- F6 — major — Restart untracks sessions before the unsaved-files gate. §4 step 3 says "Untrack sessions if `reopen` is false … then quit through the normal path", but the gate (`refuseQuitForUnsaved`) can then hold the quit; the sessions stay running yet are no longer tracked, so a later crash/quit loses their Welcome-back offer, and the restart is "forgotten". — evidence: design §4 step 3; app-restart.ts:79-86 (gate runs inside gatedQuit after the request). — Fix: untrack inside the shutdown step after the gate passed (carry `reopen` as the pending exit-action's data), never before.

- F7 — major — A restart that the post-teardown refusal "drops to a plain quit" has no rule for the install actions. `refusedAfterTeardown` clears `relaunchOnQuit` and sets `restartDropped`; with the new `'install-relaunch'` action the design doesn't say whether it becomes `'install'` (quiet install, no relaunch, on a path where password/Mac conditions were never re-checked), `'none'`, or stays and relaunches. On Windows that decides whether `--force-run` fires. — evidence: app-restart.ts:88-93; design §4 exit-hook paragraph. — Fix: state it: a dropped `'install-relaunch'` becomes `'none'` (or `'install'` only if every quit-install condition holds), and add the case to the exit-hook tests.

- F8 — minor — Prepare's 5 s cap can add a visible 5 s freeze to every quit with an update pending. Prepare is "inside runShutdown, in parallel", but runShutdown's first step is an awaited ≤1 s flush before the parallel steps start, and the final `Promise.race` waits for the listed services; if prepare is joined, a blackholed network (captive portal, VPN down) holds an otherwise instant quit for the full 5 s with windows still open and nothing on screen; if it is not joined, prepare may be unfinished at will-quit and the plan silently drops (no explanation). — evidence: main.ts:1943-1957 (sequential flush), 1991-1996 (join list); design §4 exit-hook paragraph, E12 triage. — Fix: start prepare in `gatedQuit` before the flush, join it in the final race with a shorter cap (2–3 s), and cache a recent successful brake result (e.g. 10 min) so a quit shortly after a good check does not re-fetch.

- F9 — minor — The failure-count test and the success rule disagree with a Restart that is held. `attempt.json` is written "at spawn", but for the Mac root helper the spawn happens before teardown/gate (step 3), while the swap happens later (or never, F2); the next-launch rule "running version ≥ attempted ⇒ success" would count a helper that is still waiting or was abandoned as a failed attempt. — evidence: design §4 step 3 (attempt record) vs Restart step 3. — Fix: write the attempt record from the exit hook (when the helper is actually released), not when the password box returns.

## Triage (implementing session, 2026-10-22)

All nine accepted; fixes are in the design's "Rev 4 amendments" section. Round cap (three) reached — no round 4.

- F1 accepted — update prompts are settled as Cancel by `settleAll`, and step 3 re-checks that no shutdown has begun.
- F2 accepted — the Mac helper waits for a "go" file the exit hook writes; no go file when our process exits ⇒ it cleans up and does nothing; 24 h deadline.
- F3 accepted — quit install is opt-in: only a quit not raised by our own code; `launch()`, app-restart and every internal `app.quit()` mark the quit internal.
- F4 accepted — everything slow happens before exit; the exit hook only does a synchronous rename/spawn/small write.
- F5 accepted — Mac staging and AppImage copy happen right after the download verifies, not during quit.
- F6 accepted — sessions are untracked only after the unsaved-files gate passes.
- F7 accepted — a restart dropped to a quit keeps the install and drops the relaunch (no `--force-run`).
- F8 accepted — the brake result is cached for 10 minutes and refreshed when the popup shows Ready; quit joins it with a 3 s cap.
- F9 accepted — the attempt record is written by the exit hook.
