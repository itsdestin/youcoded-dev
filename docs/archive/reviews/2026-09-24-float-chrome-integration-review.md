# Float chrome — integration review

Read-only review of `session/theme-minimal-chrome` (`git diff origin/master...HEAD`),
scoped to the questions the requesting session asked: consistency with existing
chrome styles, reduced-effects/accessibility behaviour, primitive reuse, plausible
breakage, and what's still missing for `float` to be a shippable, user-selectable
option. A separate prior review (`docs/archive/reviews/2026-09-24-float-chrome-code-review.md`)
already covers `use-wallpaper-header-ink.ts` performance (F1–F5, all "accepted, fixed
in `e720e771e`" per that doc's own triage) — confirmed still true by reading the
current hook (coalesced resize, band-limited `getImageData`, cached decode, gated
observers). This review does not re-litigate those; it covers different ground.

## 1. Consistency with existing themes/chrome styles

- **I1 — OK, `theme-types.ts`/`theme-engine.ts` layout-attr plumbing.** `ChromeStyle` gains `'float'` alongside `'default' | 'floating'` (`desktop/src/renderer/themes/theme-types.ts:79`), and `buildLayoutAttrs` sets `data-chrome-style` off `layout['chrome-style']` exactly as it does for `'floating'` (`desktop/src/renderer/themes/theme-engine.ts:144-151`, `applyThemeToDom` line 660). No parallel attribute or code path — reuses the existing mechanism. Confirmed by reading the diff and the surrounding function.
- **I2 — OK (documented deviation), `chrome-glass` gating.** Every other chrome style hides `.chrome-glass` via `display: none` (`globals.css:2164-2167`, `[data-chrome-style='floating'] .chrome-glass`). `float` deliberately does NOT reuse that rule — instead it collapses the clip-path to a zero-area polygon and keeps `background/backdrop-filter: none !important` (`globals.css:2169-2186`). The comment explains why: `display:none` still let a clip-path-bearing element paint (a promoted-stacking-context hairline bug measured 2026-09-20), and the element must stay in the tree because it owns `--top-chrome-bottom`/`--bottom-chrome-height` custom properties the rest of the layout reads. This is a real, working-around-a-browser-bug deviation, not sloppiness — but it means `youcoded/docs/renderer-chrome.md:12` and `.claude/rules/react-renderer.md` ("`chrome-glass` is `display:none` in floating-chrome modes... Mirror the gating for any new always-floating element") are now **incomplete/misleading** for a future editor who follows that rule verbatim on a chrome-glass-adjacent change. See I15 (doc drift) below.
- **I3 — PROBLEM, blur/opacity tokens diverge from the app's one mechanism.** Every existing translucent surface (`chrome-glass`, `.settings-drawer`, `.layer-scrim`, bubbles, `.glass-overlay`, floating-chrome header/status/input in `theme-engine.ts:792-815`) gets its `background-color` from `color-mix(..., var(--panels-opacity, 1) * 100%, ...)` in static CSS, and its `backdrop-filter` from a **JS-injected literal** (`theme-engine.ts` `glassEl.textContent`, built from the live `panelsBlur` value) gated on `!reducedEffects && panelsBlur > 0`. `float`'s per-control surfaces (`float-chrome.css:187-226`) instead hardcode `background: color-mix(in srgb, var(--inset) 16%, transparent) !important` (fixed 16%, not `--panels-opacity`) and `backdrop-filter: blur(6px)`/`blur(16px) !important` as literals baked into the static stylesheet — never touching `panelsBlur`, `reducedEffects`, or the theme-engine's glass injector at all. The large surfaces (`.framed-shell > .drawer-pane`, `.screen-pane`, `.session-menu.glass-overlay`) DO reuse `--panels-opacity` for fill (`--float-sheet-fill`, `float-chrome.css:477`) but still use hardcoded blur literals that `!important`-override whatever the theme-engine already injected for `.glass-overlay`. This is a parallel, ad-hoc mechanism for the one thing (blur) the app has a single, carefully gated JS pipeline for — see Q2 for the concrete accessibility consequence. Confirmed by reading `theme-engine.ts:746-832` (no `'float'` selector anywhere in the glass injector — `float-chrome-pops.test.ts:74-77` pins this on purpose: *"the theme engine injects nothing float-specific"*) against `float-chrome.css`'s literal `!important` blur rules.
- **I4 — OK, isolation is real and tested.** `float-chrome-pops.test.ts` mechanically parses `float-chrome.css` and asserts every top-level selector list is gated on `[data-chrome-style='float']` (one documented exception: the hidden base `.chat-edge-fade` rule), and separately asserts `applyThemeToDom` sets no float-only attribute for a `'default'`/`'floating'` theme. This is the strongest evidence for the branch's own hard requirement ("zero effect on other themes"). Confirmed by reading the test file end to end.

## 2. Reduced-effects and accessibility toggles

- **I5 — PROBLEM, float's blur ignores "Reduced effects" entirely.** `reducedEffects` is surfaced as `[data-reduced-effects]` on `<html>` (`theme-engine.ts:620-622`) and is the gate every other blur in the app respects (`theme-engine.ts:749`: `if (hasBackgroundLayer(bg) && !reducedEffects && panelsBlur > 0)` before injecting ANY `backdrop-filter`). Searching `float-chrome.css` for `data-reduced-effects` finds exactly **one** match — gating the session-dot breathing *animation* (`float-chrome.css:373`, plus the `prefers-reduced-motion` twin at line 376). None of float's five `backdrop-filter` declarations (chips/buttons `blur(6px)` line 218; composer `blur(16px)` line 224; session-menu `blur(6px)` line 416; drawer-pane `blur(16px)` line 497; screen-pane `blur(16px)` line 532) are gated on `[data-reduced-effects]` in any form. Turning on "Reduced effects" strips blur from every other surface in the app but leaves every float-chrome surface blurred exactly as before. Confirmed by `rg -n "reduced-effects" float-chrome.css theme-engine.ts` (single hit, animation-only) and by reading each blur rule's selector list.
- **I6 — PROBLEM, the panel-blur slider has zero effect under float.** The Appearance popup's blur slider drives `panelsBlur`, which only reaches the DOM through the theme-engine's JS-injected literal (`theme-engine.ts:813`: `blur(${panelsBlur}px)`). Because float's surfaces never appear in that injector's selector list (see I3), setting the blur slider to 0 — which elsewhere means "no blur, ever" (`panelsBlur > 0` is a hard gate on whether the glass stylesheet is populated at all, `theme-engine.ts:749`) — has **no effect** on float's chips, header buttons, composer, session menu, drawer pane, or screen pane; they stay hardcoded at 6px/16px regardless. Confirmed by the same evidence as I5/I3 plus `float-chrome-pops.test.ts:114-120`, which explicitly pins `backdrop-filter: blur(16px)`/`blur(6px)` as literal constants in the stylesheet (not as a runtime-variable read).
- **I7 — PROBLEM (partial), the panel-opacity slider affects only the large float surfaces, not the controls.** `--panels-opacity` IS threaded into `--float-sheet-fill` for the drawer pane/screen pane (`float-chrome.css:477`), so that slider does move those two surfaces' fill. But the per-control fill used by header buttons, quick chips, status chips, session strip, and the composer form is the fixed `color-mix(in srgb, var(--inset) 16%, transparent)` (`float-chrome.css:197`) — no `--panels-opacity` reference anywhere in that rule. A user who turns panel opacity down (or up) expecting it to affect "the chrome" sees roughly half of float's surfaces respond and the other half (arguably the more visible half — every button and the message box) stay fixed at 16%.
- **I8 — OK, `prefers-reduced-motion` (OS-level).** The one animation float adds (wallpaper-tuned status-dot breathing) is gated by both the app's own reduced-effects attribute AND `@media (prefers-reduced-motion: reduce)` (`float-chrome.css:376-380`), matching the app's existing dual-gate pattern elsewhere (`globals.css:958`, `:802` etc. use the same `[data-reduced-effects]` + a matching OS media-query pattern).
- **I9 — OK, the edge fade itself carries no blur/motion to gate.** `ChatEdgeFade` (`desktop/src/renderer/components/ChatEdgeFade.tsx`) is a static masked `background: var(--canvas)` div — no `backdrop-filter`, no `animation`/`transition`. Nothing here needs a reduced-effects or reduced-motion gate; confirmed by reading the component and its CSS (`float-chrome.css:143-180`).
- **I10 — GAP, the wallpaper-ink sampler is not reduced-effects-aware, though it may not need to be.** `useWallpaperHeaderInk`'s `eligible()` check (`use-wallpaper-header-ink.ts:107`) is purely `chromeStyle === 'float'` plus an image background — it runs (decode + canvas sample) regardless of `reducedEffects`. Since it doesn't itself add blur or motion (it derives colours for otherwise-static text/icons), this is arguably correct as-is, but it does mean the canvas-sampling cost (already reviewed for perf in the sibling code-review doc) is not one of the costs "Reduced effects" lets a user opt out of.

## 3. Primitives and shared components

- **I11 — OK, component-side changes are class hooks on existing markup, not hand-rolled surfaces.** `HeaderBar.tsx`, `QuickChips.tsx`, `ScreenBand.tsx`, `SessionStrip.tsx`, `SessionTagsChip.tsx`, `GamePanel.tsx`, `TerminalView.tsx` each add exactly one class name (`quick-chip`, `status-chip`, `caption-buttons`, `session-dot`/`data-status`, `header-controls-left/-right`, `game-panel`, `terminal-wallpaper`) to markup that already existed, still going through `Tooltip`, `ON_INSET_CONTROL`/`HEADER_ICON_BUTTON` (`control-states.ts`), and the existing `.glass-overlay` class for the session menu. `float-chrome-pops.test.ts:87-96` pins every one of these class additions verbatim. No new hand-rolled button/pill/overlay primitive. Confirmed by reading the full component diff.
- **I12 — PROBLEM, per-element `backdrop-filter` on repeated controls — the exact paint-bug class `react-renderer.md` names.** `react-renderer.md`: *"`.layer-surface` on a REPEATED element (grid tile, list row) is a paint bug — N tiles = N backdrop-filters... (shipped twice: `516411a5`, `1f68a7f0`)."* `float-chrome.css:209-220` applies `backdrop-filter: blur(6px) saturate(1.1) !important` to an `:is(...)` list that includes `.quick-chip` (an unbounded, user-configurable list of chips, `QuickChips.tsx:73-84`), `.header-bar > .header-controls-left/-right > ... button` (roughly 6–10 simultaneous header icons), and `.status-bar > button, .status-chip` (several simultaneous status chips) — every matching element gets its OWN independent backdrop-filter/compositing layer. Tellingly, the SAME file's author explicitly avoided this pattern one section later, with a comment naming the exact rule: `float-chrome.css:493-495`, *"One blur for the whole pane — its rows and cards below get none (a filter per repeated card is the paint bug react-renderer.md warns about)."* The drawer-pane/screen-pane treatment (single blur on the container, plain fill on children) follows the rule; the header/chip/status-chip treatment does not. Confirmed by reading both selector lists and the drawer-pane comment acknowledging the rule by name. Not measured live (no profiler run in this review — same caveat the sibling perf review states for its findings), so severity is unconfirmed, but the pattern itself is a textbook match for a class of bug that has shipped twice before.
- **I13 — OK, Overlay/`.glass-overlay` primitive is reused, not replaced.** The session menu keeps its `.glass-overlay` class and the `<Scrim>`/portal machinery (`SessionStrip.tsx` diff, `className="session-menu glass-overlay overlay-no-drag ..."`); float-chrome.css only restyles it via the `.session-menu` hook, it doesn't bypass the primitive. Same for `.scroll-fade` (session-menu list) — float restyles via existing data attributes (`data-fade-top`/`data-fade-bottom`) rather than inventing a new fade mechanism.
- **I14 — GAP, `ChatEdgeFade` is a new masking mechanism, justified but not reusing `.scroll-fade`.** The component's own comment explains why: masking the scrollport directly would make it a backdrop root and break bubble-level `backdrop-filter` sampling of the wallpaper — a real, documented (2026-09-18 marker comment in `theme-engine.ts:738-745`) constraint, not an oversight. It mounts unconditionally for every visible chat tab regardless of theme/chrome-style (`ChatView.tsx:1076`, `{visible && <ChatEdgeFade .../>}`), staying `display: none` via the base `.chat-edge-fade { display: none; }` rule (`float-chrome.css:142`) for every non-float style. Two extra always-hidden divs per visible tab is cheap, but it is a new element mounted for every theme to serve one chrome style — narrowly inside the letter of `renderer-lists.md`'s "nothing the user cannot see is built," though the cost here is negligible compared to what that rule is actually guarding against (large lists).

## 4. What might break

- **I15 — PROBLEM (doc drift, not app behaviour), stale chrome-glass guidance.** `youcoded/docs/renderer-chrome.md:12` and the same sentence duplicated into `.claude/rules/react-renderer.md` both say *"`chrome-glass` is `display:none` in floating-chrome modes... Mirror the gating for any new always-floating element."* `float` does NOT mirror that gating (I2) — for a documented, sound reason — but neither doc mentions `float` or the exception at all. A future session reading only the always-loaded rule file (not this branch's code) would apply `display:none` to a new always-floating element and could reintroduce the exact stacking-context/hairline bug this branch's own comment says was already hit once (`globals.css:2169-2173`, "measured 2026-09-20"). Confirmed: `rg -n "chrome-style|floating" youcoded/docs/renderer-chrome.md` returns only the two `'floating'`-only lines; neither file contains `'float'`.
- **I16 — PLAUSIBLE, solid/gradient (non-wallpaper) themes selecting `float` get untuned, low-differentiation chip fills.** `useWallpaperHeaderInk`'s `eligible()` requires `background?.type === 'image'` (`use-wallpaper-header-ink.ts:63,107`) — a solid or gradient-background theme never runs the sampler, so header icon/text ink and bottom-control ink never get tuned; they fall back to the theme's plain token colours. Separately, the per-control 16% fill (I3/I7) applies unconditionally (not gated on `[data-wallpaper]` — only the blur is), so a solid theme's buttons/chips get a faint, unblurred, low-opacity tint over a flat canvas with no image to add contrast variation. Whether this reads fine or reads as barely-there UI depends on how close the theme's `--canvas` and `--inset` tokens are — not verified visually in this review (no dev instance was launched, per the live-app-safety/task scope). `desktop/scripts/audit-theme-contrast.mjs` has no chrome-style awareness (`rg` found zero hits), so nothing would catch a bad combination at theme-authoring time either. Marked PLAUSIBLE, not confirmed.
- **I17 — PLAUSIBLE, chat-edge-fade's fixed pixel offset vs. dynamically-sized bottom strips.** The fade's bottom boundary is a static `--float-fade-end: 27px` measured against the window edge (`float-chrome.css:153-165`) and does not reference `--queued-strip-height` or `--model-status-height` — the two CSS vars the rest of the chat view (`globals.css:713,722,757` etc.) already uses to grow the bottom-chrome reservation when a queued-message strip or model-status strip appears above the composer. If either strip is showing while float chrome is active, the transcript's fade-out band may no longer align with the actual top of the now-taller bottom cluster (messages could fade before reaching it, or remain visible underneath it). Not run live; flagged from reading `ChatView.tsx:900-1005` (where those two vars are computed) against `float-chrome.css`'s mask math, which never reads them.
- **I18 — OK, narrow/phone widths.** No new breakpoint is introduced; `float-chrome.css` contains zero `@media (max-width...)` rules. The header goes `position: absolute` full-width (`float-chrome.css:124-130`) which is compatible with the existing `640px`/`700px` collapse logic in `HeaderBar.tsx`/`globals.css` (untouched by this branch). The one narrow-relevant addition, `.wide-view-toggle { flex-shrink: 0; }` (`float-chrome.css:115-117`), is explicitly there to fix a header-measurement regression, not introduce one.
- **I19 — OK, Android/remote browser and macOS traffic lights.** The terminal's float treatment is explicitly gated `html[data-platform="electron"]` (`float-chrome.css:549,565,570`) — Android/remote keep today's terminal look, per the file's own comment ("Desktop only: on phones the message box stays under the terminal..."). No Kotlin/Android-native file references `chrome-style` at all (`rg` in `app/src` returns nothing) — this is a pure shared-webview/CSS concern, so Android parity is automatic once the shared bundle rebuilds. Traffic lights aren't touched by this branch (`MacTrafficLights` logic unchanged in the diff).
- **I20 — OK, terminal PTY/fit-addon sizing on chrome-style switch.** `TerminalView.tsx` already has a `ResizeObserver` on the terminal container (`TerminalView.tsx:484`) that calls `fitAddon.fit()` on any box-size change; float's CSS-driven repositioning of `.terminal-overlay-scroll` (insets, `top`/`left`/`right`/`bottom`) will trigger that observer like any other layout change, so a runtime chrome-style switch should re-fit correctly. Not run live.
- **I21 — OK, buddy window(s).** `buddy.css` has no `.header-bar`/`.chrome-wrapper`/`.status-bar`/`.chat-edge-fade` selectors at all — buddy windows don't render those components, so most of `float-chrome.css` simply has nothing to match there. The one component both files target, `.input-bar-container`, is already protected: `buddy.css`'s `body[data-mode="buddy-chat"] .input-bar-container` selector has one more specificity point (the `body` type selector) than float's `[data-chrome-style='float'] .input-bar-container`, so buddy's `!important` override wins regardless of source order — the same protection that already covers `'floating'` (buddy.css's own comment says as much for `'floating'`, though it does not mention `'float'` by name — a minor doc-staleness note, not a functional risk).
- **I22 — OK, theme switching at runtime into/out of float.** `applyThemeToDom` clears all `LAYOUT_ATTRS` (including `data-chrome-style`) before reapplying (`theme-engine.ts:657-662`), and the wallpaper-ink hook's own `MutationObserver` on `data-chrome-style` (`use-wallpaper-header-ink.ts:311`) clears its writes the instant the attribute changes away from `'float'` (`sample()` calls `clear()` when `!eligible()`). No stale-attribute residue expected.

## 5. What's still missing for `float` to be a real, user-selectable option

- **I23 — Not missing: no theme is shipping it yet, and nothing blocks one from doing so.** `rg -n "chrome-style" wecoded-themes/themes/*/manifest.json` shows no theme currently sets `"chrome-style": "float"` — expected, since this is new. `wecoded-themes` has no JSON-schema or validator file that enumerates allowed `chrome-style` values (`rg -n "chrome-style" wecoded-themes -g '*.json' -g '*.js' -g '*.mjs' -g '*.ts'` outside the manifests themselves returns nothing) — so no registry-side allowlist needs updating before a theme author can use it.
- **I24 — Not missing: the theme-builder plugin already has first-class support.** `wecoded-marketplace/wecoded-themes-plugin/skills/theme-builder/` (a sibling repo, outside this branch's diff) already has a `"Minimalist"` Kit preset (`scripts/kit-presets.json:72`, `chrome-style: "float"`), documents it in `SKILL.md:172` ("Minimalist (`chrome-style: "float"` — the wrapping surfaces go away entirely...)"), mirrors the look in its own `theme-preview.css:1308-1382`, and `scripts/sync-check.cjs` explicitly tracks the float-chrome fork's sync against the app's `globals.css` (`scripts/sync-check.cjs:141-166`, comments dated 2026-09-20). This looks like it was built in a companion session/PR to this branch. **Not independently re-verified for byte-for-byte sync against this branch's current `float-chrome.css`/`globals.css`** in this review (that plugin repo is a shared checkout and out of scope to modify; `sync-check.cjs` itself would need to be run to confirm, which this review did not do).
- **I25 — GAP, `desktop/docs/theme-spec.md` documents neither `'floating'` nor `'float'`.** `rg -n "chrome-style" youcoded/desktop/docs/theme-spec.md` returns nothing — pre-existing gap (not introduced by this branch), but this branch is a second chrome-style option landing on top of an already-undocumented one.
- **I26 — GAP, stale/incomplete `chrome-glass` guidance in always-loaded rules.** Restated from I15: `youcoded/docs/renderer-chrome.md` and `.claude/rules/react-renderer.md` both give a `display:none` instruction for "any new always-floating element" that `float` itself does not follow, without noting the exception.
- **I27 — GAP, no MAP.md entry for the new subsystem files.** `docs/MAP.md`'s "React renderer / chrome" row lists `globals.css`, `App.tsx`, `HeaderBar.tsx`, `SessionStrip.tsx`, etc., but not `float-chrome.css`, `use-wallpaper-header-ink.ts`, `wallpaper-header-ink.ts`, `ChatEdgeFade.tsx`, or the three new test files. Per this workspace's own convention ("Start non-trivial project work at `docs/MAP.md`"), a reviewer or future session has no indexed path to this subsystem beyond finding it by grep, as this review did.
- **I28 — Not missing: no Appearance/Settings UI gap.** Chrome style is not independently user-selectable in `SettingsPanel.tsx`/`theme-context.tsx` for `'floating'` either — it's a manifest-only property themes bundle. `float` is consistent with that existing precedent, so there is no new settings-surface gap to fill.
- **I29 — GAP, no CI contrast/readability check is chrome-style-aware.** Neither `desktop/scripts/audit-theme-contrast.mjs` nor `wecoded-themes/scripts/audit-contrast.mjs` references `chrome-style` at all — relevant given I16 (untuned solid/gradient themes under float).
- **I30 — Not missing: tests exist and are meaningfully scoped.** `desktop/tests/float-chrome-pops.test.ts` (isolation + approved-look pins), `wallpaper-header-ink.test.ts` (pure colour-math unit tests), `wallpaper-header-runtime.test.tsx` (hook integration, including the F1–F5 perf fixes from the sibling review). No test in any of the three exercises reduced-effects or the panels-blur/opacity sliders against float's surfaces (consistent with I5–I7 being real gaps rather than merely untested ones).

## Top priorities

1. **I5/I6 (PROBLEM):** Wire float's `backdrop-filter` rules into the theme-engine's existing reduced-effects/`panelsBlur`-gated injection (or add an equivalent static `[data-reduced-effects]`/`panelsBlur`-aware gate) so "Reduced effects" and the blur slider actually do something under this chrome style, matching every other surface in the app.
2. **I12 (PROBLEM):** Collapse the per-control `backdrop-filter` on `.quick-chip`/header buttons/status chips into a shared-container blur (the same pattern the branch's own drawer-pane/screen-pane rules already use, and the same pattern the file's own comment cites as the fix) to avoid N-simultaneous-compositing-layers on an unbounded/repeated element set.
3. **I15/I26 (doc drift):** Add a `float`-aware caveat to `renderer-chrome.md` and `react-renderer.md`'s `chrome-glass` rule so the next always-floating element doesn't get pointed at the bug this branch already fixed once.
4. **I7 (PROBLEM, smaller):** Either wire the panel-opacity slider into the per-control 16% fill too, or document that it's deliberately fixed — right now it's an inconsistent half-response that's easy to read as a bug.
5. **I16/I29 (PLAUSIBLE + GAP):** Before any theme actually ships `chrome-style: "float"` on a solid or gradient background, visually check contrast/legibility of the untuned chip surfaces — nothing in CI would catch a bad one.
