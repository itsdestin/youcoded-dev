## Gate: safe design before a source change

Inspected `desktop/src/main/harness/shell-registry.ts` (`spawnDetached` lines 141–145, `killTree` lines 151–175, `start`/`adopt` lines 262–285, `ShellRegistry.kill` line 530), `desktop/src/main/harness/tools/bash.ts` (spawn line 559, killTree callers lines 950, 997), `tests/shell-registry.test.ts`, `tests/shell-registry-win-kill.test.ts` and `tests/shell-audit-disposable.test.ts`. The detached POSIX Bash process is both the Node child and process-group leader. `killTree` sends `SIGTERM` to `-pid` immediately, then only sends delayed `SIGKILL` when `child.exitCode === null && child.signalCode === null`. If the leader exits on TERM and another group member ignores TERM, that member survives. The audit probe reproduces the defect but deliberately **asserts survival**; it uses a live detached child and a timed delay and is not a desired-behavior regression. It was preserved rather than inverted to require an unsafe implementation.

The simple change (remove the leader-status guard and call `process.kill(-pid, 'SIGKILL')` after two seconds) is explicitly forbidden by the C2 contract: after the original group disappears, the PGID can be reused, and a negative numeric PID may designate unrelated work. Likewise `/proc` starttime/PGID checks, even via asynchronous bounded reads, have a **check-to-signal interval** in which the last original member can exit and its PGID can become available for reuse. Rechecking twice only narrows this window; it does not eliminate it. The existing `signal()` helper's positive leader-PID fallback is also unacceptable for delayed escalation once that number may have been recycled. No async `/proc` recheck was installed as a purported safety guarantee.

Read-only platform inspection: `uname -s` returned `Linux`, `node -p 'process.version'` returned `v26.4.0`, `stat -c '%A %U %G' /sys/fs/cgroup` returned `dr-xr-xr-x root root`. `python3` reports `os.pidfd_open` and `signal.pidfd_send_signal` available; the latter's docstring says **“Send a signal to a process referred to by a pid file descriptor.”** That is a stable reference to *one process*, not a reference/signalling primitive for an entire POSIX process group including newly created descendants. The present Node `process.kill` accepts numeric PID/PGID, not a stable group handle. A captured member pidfd plus rechecked `/proc` membership cannot make a subsequent negative-PGID signal atomic; sending via member pidfds instead would change the contract to a snapshot of individual processes and fail to cover later group members. Non-Linux POSIX support cannot be inferred from Linux's pidfds. Windows `taskkill /PID /T /F` path was left unchanged, not claimed to have been exercised on Windows.

**Possible designs requiring separate safety review before implementation:** (1) a stable, owned *group-lifetime anchor* created together with each detached group, held alive until after the escalation decision, with a protocol preserving Bash exit/output/handoff semantics and proving no anchor PID/PGID recycle before the group signal; this changes launch and lifecycle across `ShellRegistry.start` and both `tools/bash.ts` call sites and must be proved on supported platforms. (2) A platform-owned isolation handle (e.g. properly owned process container/job) with a kernel-atomic group stop and fail-closed unsupported-platform path, if such a facility is available in the shipped runtime; this is not currently wired. (3) A separately specified best-effort snapshot kill using stable per-process handles, explicitly **not** called whole-group cleanup and not a substitute for C2's current acceptance criteria. None can be silently replaced by numeric-PGID probes or positive PID fallback. Until an ownership design is established, **skip unsafe delayed escalation rather than accidentally signal unrelated work**; current code still contains the pre-existing unsafe conditional path, so this report does not claim C2 is fixed or the old implementation is generally safe.
