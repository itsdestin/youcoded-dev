# Review 2 — auto-updates technical design rev 2 (adversarial)

Paths are under youcoded/desktop unless noted. Mac and Windows behaviour is from platform knowledge, not run here (unverified where stated).

- E1 — blocker — Restart-to-update calls `shutdownApp({ installUpdate:false })` directly. That skips `before-quit` and `gatedQuit`, so the unsaved-files gate (`refuseQuitForUnsaved`) never runs and the later watchdog/unsaved refusal logic is bypassed: edits are lost. Worse, the platform step (Windows NSIS `--force-run`, Linux pkexec) has ALREADY been started before the quit, so if the gate would have refused, the installer still kills the app. — evidence: design §4 "Restart to update" step 3; src/main/main.ts before-quit/gatedQuit (~2037-2050); src/main/app-restart.ts:94-101 (gate only on the before-quit route). — Fix: Restart must go through `requestRestart`/`app.quit()` so the gate runs, and the installer spawn must happen only after the gate passed and teardown finished (from `will-quit`), same as the quit path.

- E2 — major — The install spawn in `will-quit` is skipped on every exit that bypasses it: the 10 s watchdog calls `app.exit(0)` ("exit() skips will-quit"), and SIGTERM does too. The design never says what happens then; a hung window silently drops the update while `attempt.json` may or may not have been written. — evidence: src/main/app-restart.ts:112-121 (`onWillQuit(d.relaunch); d.exit()` — the existing code has to special-case this for restarts); design §4 "When a quit installs". — Fix: route the install spawn through the same helper the watchdog uses (like `onWillQuit`), or write `attempt.json` only at the moment of spawn and state that a skipped spawn is "not tried".

- E3 — major — Quit-time install condition is "`pending` exists", not "`pending.version === latest` for the current channel". A person on beta who switches the beta switch off (or whose newer stable is pulled so the stable listing offers an older release) still has a pending beta file that is newer than the offered stable; quitting would silently install a pre-release onto a stable-channel install. §5 only brakes on a 404. — evidence: design §4 "When a quit installs" (Conditions); §3 (`downloaded` is tied to latest, install is not); update-service.ts `setBetaChannel` (re-check changes `latest`). — Fix: require `pending.version === status.latest` (fresh, current channel) and drop `pending` when the channel changes; also delete `pending` at startup if running version >= pending.version.

- E4 — major — Windows "per-machine install" detection by "install folder not writable" is unreliable: Node's `fs.access(W_OK)` on Windows only checks the read-only attribute, not ACLs, so Program Files reports writable. A per-machine install would then be treated as per-user and a hidden `/S` installer would raise a UAC prompt on the secure desktop at quit/logoff, or fail silently. (unverified for this exact case, but documented Node behaviour) — evidence: design §3 Windows bullet; D24 triage. — Fix: detect by path (exe under `%ProgramFiles%`/`%ProgramFiles(x86)%`) and/or the uninstall registry hive (HKLM vs HKCU), not by an access check.

- E5 — major — Mac password path runs a root helper whose inputs live in user-writable places: the staged app in `$TMPDIR` is verified as the user, then moved into /Applications as root. Any user-level process can swap the staged bundle (or the helper script, if it is written to disk) between `codesign --verify` and the root swap — a local privilege/persistence path. The script's location is not specified. — evidence: design §4 macOS staging paragraph and "needs password" row. — Fix: pass the script text inline in the osascript command (nothing on disk), stage into a mode-700 directory, and have the root helper re-verify (below) after `chown root` on the staged copy, before the swap.

- E6 — major — `codesign --verify --deep --strict` only proves the staged app is validly signed by SOMEONE; any ad-hoc or attacker-signed bundle passes. The DMG hash is checked earlier, but the staged copy is not tied to our signing identity. — evidence: design §4 macOS staging (D11 fix). — Fix: verify with a requirement (`codesign -R` / designated requirement equal to the running app's, or Team ID match for release builds); keep the ad-hoc case explicit (ad-hoc builds only match their own cdhash, so state that updates of ad-hoc builds stay manual).

- E7 — major — Restart on Windows spawns the installer before teardown. Teardown can take up to ~6 s (Office drain 5 s, sessions) while NSIS's running-app check kills `YouCoded.exe` after a few retries, i.e. mid-teardown: Office recovery journals and the welcome-back flush may be cut. D6 was fixed only for the quit path. — evidence: design §4 table "Restart to update" Windows cell + "run the platform step ... then quit"; src/main/main.ts:1936-2031. — Fix: same ordering as quit (teardown, then spawn from will-quit with relaunch flag); the "restarting:true" answer can return before the spawn.

- E8 — major — Failure loops: when an install fails (antivirus, locked file, App Management), `pending` is kept and `autoInstall` stays on, so EVERY following quit re-spawns the installer (Windows flashes/holds the exit, Mac asks again) indefinitely. Only a log line is written. — evidence: design §4 step 3 ("keep `pending` so the popup is simply Ready again"). — Fix: count failed attempts in `attempt.json`; after 2 failures stop quit-installs for that version (Restart still works) and say so in the log.

- E9 — major — AppImage installs where the folder is not writable (/opt, immutable-distro, read-only mounts) are never marked: `needs_password` excludes AppImage, so the app downloads 180 MB in the background, shows Ready, and fails silently at every quit (`appimage-not-writable`) while the copy-beside-target step in D20 needs the directory writable too. — evidence: design §3 "Never AppImage"; update-installer.ts:555-566 error mapping. — Fix: probe the AppImage directory (async `access` + a temp-file create) at startup and, when not writable, do not background-download/quit-install; leave the Restart/manual path with the existing error.

- E10 — minor — Restart-flow spec: `pending.json` is read from a user-writable file at launch and its `filePath`, `manifestUrl` and `signatureUrl` are trusted for the install (the design's own data shape even calls the field `file` vs `filePath` in §2). A tampered record can point the installer at any path or an old signed manifest. Hash and version checks limit damage, but the path should not be trusted. — evidence: design §2 (record) vs Data shape; §4 step 2. — Fix: derive the path from `update-cache/` + the manifest's asset name, validate containment, and unify the field name.

- E11 — minor — The 404-means-pulled rule has no mechanism: `fetchUrlToBuffer` rejects every non-200 with the same `network-failed` error and the status code only in the message string, so the caller cannot distinguish 404 from a 5xx/redirect-host 404. A misparse either deletes a good file (5xx treated as pulled) or never brakes. — evidence: src/main/update-service.ts:~129-135 (`status ${code}` text only). — Fix: add a `httpStatus` field to the error and test 404, 403, 500 and a 404 on the redirect hop separately.

- E12 — minor — Quit-time brake needs the network; offline or captive-portal quits never install, and `attempt.json` is not written, so nothing explains why Ready never turns into installed. With a 5 s cap on every quit this also adds up to 5 s of tail latency to a plain quit while online but slow (the cap runs in parallel with the 6 s teardown, so it only hurts when teardown is short — closing with no sessions). — evidence: design §5, §4 conditions. — Fix: start the brake fetch early (at the quit decision, before teardown) and keep it parallel; state in the contract that offline quits do not install.

- E13 — minor — Status delivery: `downloaded` and `needs_password` are set from async work, but `getUpdateStatus()` is read by the periodic status poll; the design does not say what pushes a change when a background download finishes while the popup is open. If the poll interval is long the popup sits at "Downloading… 100%" or the pill stays stale. — evidence: design §3 and §2 ("arrives as `downloaded` through the status push"); src/main/ipc-handlers.ts:1184 (poll-based read). — Fix: emit a status push explicitly on pending set/cleared and in the dedupe test pin that `downloaded` flips cause a push.

- E14 — minor — Test plan gaps for rev 2: no test for the watchdog/`app.exit` path (E2), channel switch with a pending beta (E3), repeated install failure (E8), or Restart passing through the unsaved-files gate (E1).

## Triage (implementing session, 2026-10-22)

- E1 accepted — Restart goes through the normal quit path (unsaved-files check included); nothing is spawned before teardown.
- E2 accepted — the spawn moves into the shared quit-exit helper that both `will-quit` and the watchdog's `app.exit` path pass through; the attempt record is written at the moment of spawn.
- E3 accepted — a quit installs only when `pending.version === latest`; changing the beta channel clears `pending`.
- E4 accepted — per-machine Windows install detected by the install path being under `%ProgramFiles%`/`%ProgramFiles(x86)%`, not by `fs.access`.
- E5 accepted — the root helper is passed inline (fixed script text, paths as arguments), staging is in a mode-700 folder, and the helper re-verifies the staged app after taking ownership.
- E6 accepted — the staged app is checked against the running app's own designated requirement (`codesign --verify -R`).
- E7 accepted — same fix as E1: Windows Restart spawns after teardown.
- E8 accepted — failed attempts are counted per version; after two, quits stop installing that version (Restart still works).
- E9 accepted — an unwritable AppImage is probed at startup: no background download and no quit install.
- E10 accepted — the file path is derived from the cache folder + the signed asset name, never read from `pending.json`; field names unified.
- E11 accepted — fetch errors carry the HTTP status; 404 on the final hop means pulled.
- E12 accepted — the brake fetch starts when the quit begins; offline quits do not install (stated).
- E13 accepted — status is pushed when `pending` is set or cleared.
- E14 accepted — tests added.
