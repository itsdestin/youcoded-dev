> **Superseded in part (2026-09-28, PR-review Q-5):** the "refuse the change when rules cannot fit" behaviour described below was replaced — rules that cannot fit are now shown shortened once and the model re-plans. See the PR-review amendments in `../design/2026-09-26-native-harness/native-harness.decisions.md`. The rest of this record stands.

Scope: only the B4 aggregate-guidance omission edge, in the preserved uncommitted app worktree. No commits, live-app access, paid inference, C2 work or Q10 changes.

## Why and interface

`fit-rule-group.ts` now returns `{ contents, omitted }` from `fitRuleGroupDelivery`: an omission-only fallback, a per-rule minimum notice, or `fitInjection`'s notice-only result identifies rules whose **body was not supplied**. `fitRuleGroup` retains its existing display-text return shape. `ruleFitRefusal` builds a bounded, actionable not-run result naming up to three omitted sources and the remaining count; a larger model context is needed before retrying that file change. It does **not** claim that merely calling Read discharges the rule requirement.

`rule-delivery.ts` marks only substantively delivered rules as injected, including B3 exact retained-history matches. A post-Read notice with no rule body remains visible once but cannot mark that rule delivered; a later Write/Edit is refused if the body cannot fit. The driver (`harness-session.ts`) checks for omissions **before** replan: pairs every announced call with existing completed results and truthful not-run results through `supersedeToolGroup`, then ends the turn. It does not send an automatic request to retry a rule the model never received. With a fit, its existing B4 fresh-request path and permission checks remain unchanged; a partial-but-substantive fitted rule remains delivered. System prompt and profile budget are untouched.
