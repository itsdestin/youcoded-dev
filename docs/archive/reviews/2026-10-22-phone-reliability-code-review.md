# Code review: phone reliability branch (`session/remote-access-audit`, 13 commits)

Reviewer: fresh agent, 2026-10-22. Read-only; nothing edited, committed or run against the installed app.

## Verify summary

`bash scripts/verify.sh .../youcoded` : OK. Types (src and tests), related tests plus 82 source-scanning guards, knip, lint, design lint, ast-grep, screens-open, journeys all PASS. Not covered by verify: Android (`./gradlew test`), Worker. Machine load was high (14 to 22) during the run.

Overall: the main design holds together. The protocol additions are all opt-in (`pieces`, `refillPush` flags sent by the page; an old page never gets a `remote:piece` frame or a `session:refill` push), so "old page, new computer" mostly works. Defects below are mostly in edge handling. Findings are ranked by severity.

## Findings

- F1 (medium, confidence high) , `desktop/src/renderer/state/submit-outgoing.ts:~262-280` (`settleSavedQueueSends`) against `desktop/src/main/ipc/queue.ts:10-14` : **A new page talking to a computer that predates `lookup` puts already-delivered messages back in the message box.** An old computer's strict schema rejects the `lookup` action and answers `{status:'rejected', message:'Invalid queue action.'}`. The settle code treats anything that is not `lookup`/`unavailable` as "not sure", dispatches `RESTORE_UNSENT_EVENT`, clears the saved send and toasts "may not have reached your computer". Scenario: phone (Android app updated from the store) pairs with a laptop still on the previous release; a send's answer is lost but the computer did accept it; on reconnect the words reappear in the box with a toast, and a tap on Send delivers it twice (the saved sendId, the only duplicate guard, was just deleted). Confirmed by reading the zod union (`.strict()` on a discriminated union with no `lookup`) and the settle branches. Fix direction: treat `rejected` with no `lookup` support, or any reply that is not `lookup`/`unavailable`, as "cannot tell": keep the saved send and say nothing.

- F2 (medium, confidence high) , `desktop/src/main/remote-server.ts:~358-390` (`start`), `:~561` (`startAfterWake`), `:~546` (`waitForTailscale`) : **`start()` has no in-flight guard, and this branch adds two more callers.** `running` only becomes true inside `server.listen`'s callback, after `await detectTailscale()`. If the 20 s retry timer's `start()` is mid-detect when the laptop resumes (or the `resume` event fires twice, which Electron does on some wake paths), two `listen()` calls run. `clearTailscaleWait()` in `startAfterWake` cannot cancel a timer callback that already fired. The second one either hits EADDRINUSE, whose `onError` calls `this.stop(true)` and tears down the shared `httpServer`/`wss`/subscriptions the first listener is using while the first server keeps listening orphaned (panel then reads "not running" while a port is bound), or double-subscribes `pty-output`/`session-exit` handlers so a phone receives every terminal chunk twice. Confirmed by reading `start`/`listen`/`stop(true)`. Fix direction: one shared `starting` promise returned to every caller.

- F3 (medium, confidence medium) , `desktop/src/renderer/App.tsx` `onRefill` effect (~line 1774) with `desktop/src/main/remote-server.ts:~993` (`dropAudience`) : **The "refill just this conversation" replacement for the hang-up has no retry and no strip.** The old hang-up forced a full reconnect, whose fills go through `reportFillRound` and the new `refillRetry`. The new `session:refill` handler is `void firstPages.refill(sid, {fresh:true})` : its outcome is ignored. A fill expires because the phone's link was slow or stalled, so the refill is likely to hit the same trouble; if it fails, the conversation keeps its hole (the reason hang-up was chosen: "or they would silently keep a copy with a hole in it"), the strip says nothing, and `refillRetry` is never started. Also refills a conversation the person has since left, which re-subscribes the phone to it. Fix direction: route the push through the same round helper (outcome into `reportFillRound` and `refillRetry.start`), and skip ids not in `remoteWatch.watchedIds()`.

- F4 (medium, confidence medium) , `desktop/src/renderer/remote-shim.ts:~1524` (`replaced`), `:~2024` (`online` listener), `:~1700` (`checkConnectionAfterWake`) : **Two tabs of one phone browser can take the connection from the visible tab.** A tab closed with 4011 stops reconnecting, but `checkConnectionAfterWake` still reconnects a `disconnected` tab with a saved token, and the `online` event fires in every tab, hidden ones included. After a network blip both tabs run `reconnectNow`; whichever connects last wins, which can be the hidden tab, leaving the tab in front on the "Open in another tab, Reload" card. Conversely, simply focusing the replaced tab silently takes the connection back (the card disappears), contradicting the "coming back would take it back again, forever" comment (it is bounded by user action, not infinite). Fix direction: after a `replaced` close set a flag that `checkConnectionAfterWake`/`online` respect until reload. Related, **old page against the new computer**: a page that predates 4011 (a tab left open across an update) treats it as an ordinary drop and reconnects in about a second; two such tabs replace each other forever, each flap costing a refill. Low likelihood (needs two stale tabs).

- F5 (medium-low, confidence medium) , `desktop/src/renderer/state/first-page-loader.ts:115-117,170-172,208` (`unCount`) : **A first load that fails deterministically is no longer capped.** `FIRST_PAGE_MAX_RUNS` existed so a session that cannot load stops being retried by every live event. The catch around `deps.open` now refunds the run for every throw, but the same catch also covers "a bridge with no host record" (per its own comment), a deterministic failure on desktop and Android-local too. Each live event for that session will call `load` again: IPC round trip plus `HISTORY_PAGE_REQUESTED`/`HISTORY_PAGE_FAILED` dispatches, unbounded. Fix direction: refund only when the rejection is a connection/timeout error from the remote shim, not any throw. Marked PLAUSIBLE (did not reproduce a persistent throw).

- F6 (medium-low, confidence medium) , `desktop/src/renderer/state/submit-outgoing.ts:~260` (`reply?.status === 'unavailable'` branch) : **An unsent message is silently dropped when the queue says `unavailable`.** `unavailable` means "no binding for this session right now" (`claude-queue-runtime.ts:114`), which is true for a conversation that is gone but also for one whose binding has not been recreated yet (computer just restarted, phone settling at start via `useSendReconcile`'s mount call). The saved send is cleared with no restore and no notice, so the words are lost. PLAUSIBLE: depends on startup ordering on the computer.

- F7 (low, confidence medium) , `desktop/src/renderer/state/submit-outgoing.ts` `settleSavedQueueSends`, `desktop/src/renderer/hooks/useSendReconcile.ts:26` : **Lookups are sequential and awaited inside the reconcile loop.** On a frozen computer each lookup can wait out a request timeout, so `reconcileSends` (which settles message bubbles) is delayed by N times the timeout. Also a send that failed visibly already restores its text in the catch block while its saved copy remains; a later settle will restore it a second time (if the box was emptied meanwhile) with the "didn't reach" toast.

- F8 (low, confidence medium) , `desktop/src/main/ipc/session.ts:144,408` (`ptyCutServed`) : **The set is never pruned on disconnect.** Entries are removed only by the next ordinary open on the same audience and session. The page always pairs the two, so leakage is a few bytes, but a ptyOnly whose ordinary open never arrives (dropped connection, error before the handler) leaves an entry forever. Also: the early answer is ignored by the page when `openedHere.has(sid)` is true (a second open on the same connection, e.g. Refresh), and the ordinary open no longer carries the terminal; the page then draws no terminal cut on a refill. Pre-existing for the `ptyEarly` case, new if the first early answer failed.

- F9 (low, confidence high) , `desktop/src/renderer/remote-gate.tsx` `tryComputer`, refused branch : **Wrong cause shown.** Any `refused` sign-in (including `no-password-configured`, `rate-limited`-style reasons) produces "X didn't accept the saved password. Update it in Settings". The sign-in reasons that mean a bad password are `invalid-credentials`/`revoked`/`unknown`; the rest are different faults (project rule: never invent an error cause). Also the last-computer record is not forgotten on refusal, so the toast repeats at every launch.

- F10 (low, confidence medium) , `desktop/src/renderer/components/ChatView.tsx` reconnecting strip : the Android "Use this phone only" escape exists only inside an open conversation's strip. On the Android app, once connected and then dropped, a person on any other screen (no conversation open, Settings, Resume) has no way out of a computer that stays unreachable, since the automatic fall back to the phone's runtime was removed.

- F11 (low, confidence low) , `desktop/src/renderer/remote-gate.tsx` `choosePhoneOnly`/`tryComputer` : pressing "Use this phone only" while a connect attempt is mid-flight mounts the app on the phone's runtime immediately, then the late success runs `disconnectFromHost` : a brief flash of the remote mode and a second runtime switch.

- F12 (low, confidence medium) , `desktop/src/renderer/remote-shim.ts` heartbeat: `HEARTBEAT_REPLY_MS` 5 s to 20 s plus removal of the `HIDDEN_TOO_LONG_MS` shortcut. A truly dead socket (iOS Safari freezing a backgrounded tab so its socket is half-dead but the page still believes it is open) now takes 10 s after waking, or 12 s plus 20 s while in front, before it is replaced; a Send tapped in that window goes into a dead socket and fails at its request timeout. This is the intended trade-off, noted so the owner knows what the "Waiting for your computer" path costs when the cause is the phone, not the laptop.

## Checked and fine

- Pieces: server splits only when the page announced `pieces`, never on the Android loopback (`!this.local`), pieces are sent in one synchronous loop, reassembly keyed by id, cleared on each new connection, stale generation guarded. A cut inside an emoji is escaped by `JSON.stringify` and restored by join (the test covers it). No old-page or old-computer mismatch: the flag is the page's, absent flag means whole frames. Only `respond()` answers are split; large broadcast pushes (e.g. `pty:output`) still go as single frames, which is fine but means the "every piece is a sign of life" claim covers load answers only.
- Device replacement: `owner`/`local` excluded, per-device scoping correct, `removeClient` is idempotent so the old socket's later `close` event does not double-count, stale-socket handlers are guarded by `isCurrent()` so a late 4011 on an abandoned socket cannot disturb the new one.
- Android paired mode treats 4011 as an ordinary drop (reconnects), correct for a single-page app.
- Reconnect "never gives up": backoff caps at 60 s, key-dead refusals still fall back on Android and clear queued sends and the last-computer record.
- `perMessageDeflate`: off on loopback, threshold 1024, no context takeover; reasonable.
- Refill retry: generation counter cancels stale rounds, pauses while hidden, bounded to five tries; test is a real behavioural test (fake timers).
- The `lookup` action itself (`claude-queue-runtime.ts`): read-only, checks the queueId first, matches by sendId against items and tombstones; the renderer demands an epoch match before trusting "found". Tombstones are cleared when the epoch rotates, but then the epoch differs and the code takes the hedged path.
- New tests exercise real behaviour (server connection tests drive a real `RemoteServer` with fake sockets; the pieces test splits inside an emoji). The deleted `remote-recovery` source-text test asserted the removed behaviour and is rightly gone.
