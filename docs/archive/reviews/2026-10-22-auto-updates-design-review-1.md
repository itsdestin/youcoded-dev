# Review 1 — auto-updates technical design (adversarial)

Paths are under youcoded/desktop unless noted. Mac and Windows behaviour is from knowledge of those platforms and electron-builder, not run here; items marked (unverified) need a test on real hardware.

- D1 — blocker — The brake's re-check cannot tell "release was pulled" from "check failed". `fetchLatestRelease()` returns `void` and swallows every error (network, timeout, rate limit). `parseReleaseResponse` also keeps the OLD `cachedUpdateStatus` whenever `readReleaseStatus` returns null (a rate-limit body has no tag). A forced re-check that fails therefore leaves the stale cache saying "update available, same version", and §5 would install. Also GitHub's unauthenticated API allows 60 calls/hour per IP, so a forced check on every quit and Restart will hit it on shared networks. — evidence: src/main/update-service.ts:55-95 (`resolve()` on error/timeout; `else if (!cachedUpdateStatus)`), update-release-status.ts:155-157 (null on no tag). — Fix: add a result-returning `checkNow()` (ok / failed / status), treat anything but a fresh, parsed answer as "do not install this time", and make the manifest fetch itself the primary brake (404 on the signed manifest URL means pulled; that goes to the release CDN, not the rate-limited API).

- D2 — major — The brake section names the wrong files. The release assets are `youcoded-release.json` and `youcoded-release.json.sig`, not `manifest.json` / `manifest.json.sig`. An admin following §5 would delete nothing and the brake would not engage. — evidence: src/main/update-release-status.ts:171-172; update-manifest-verify.ts header; design §5. — Fix: correct the names in §5 and in the youcoded-admin procedure; add a test that the procedure's file names equal the constants the app reads.

- D3 — major — "Mark not latest" does not brake beta-channel installs. On the beta channel `selectRelease` picks the HIGHEST version among all non-draft releases, ignoring GitHub's "latest" flag. Only deleting the manifest (or the release) stops a beta. The doc presents both as equivalent. — evidence: update-release-status.ts:123-150. — Fix: state that the manifest deletion is the one reliable brake for both channels; "not latest" is stable-only.

- D4 — major — Windows OS-shutdown detection does not exist as designed. `powerMonitor` `'shutdown'` fires on Linux and macOS only, not Windows; main.ts has no `session-end` / `query-session-end` handler (rg found none). On a Windows logoff/shutdown the quit goes through `before-quit`/`window-all-closed` and would be treated as "a person's quit", spawning the installer into an OS shutdown (the half-written-app case §4 says it avoids). — evidence: src/main/main.ts:2010-2040 (only window-all-closed, before-quit, SIGTERM/SIGINT); design §4 quit-time rules. — Fix: on Windows listen to BrowserWindow `session-end` (and app `'session-end'`) to set a `systemShutdown` flag; skip install when set.

- D5 — major — `runShutdown()` cannot tell the quit route. `shutdownApp()` is the same function for before-quit and SIGTERM/SIGINT, and for app-restart.ts relaunches. The design adds "only a person's quit" without saying how the flag gets there. Worse, `app.relaunch()` flows (restart for other features, `onWillQuit(() => app.relaunch())`) would run a quit-time installer while the relaunched copy starts from a half-replaced folder. — evidence: src/main/main.ts:1936-1941, 2018-2031, 2037-2040; app-restart.ts. — Fix: pass an explicit `shutdownApp({ installUpdate })`; allow it only from window-all-closed / menu quit / Cmd+Q with no pending relaunch, and refuse when `onWillQuit` has a relaunch queued.

- D6 — major — Windows installer is started while the app is still alive, and NSIS's own running-app check will act on it. electron-builder's NSIS template, in silent mode, tries `taskkill` on `YouCoded.exe`, then force-kills after retries; it matches by image name, so a second YouCoded process (a dev instance or another profile) can be killed too (unverified). The spawn also happens "at the end of runShutdown", before `will-quit` and before the watchdog exit, so the child sees a live app for a moment. — evidence: design §4 table row Windows; src/main/main.ts:2018-2031 (quit continues after runShutdown); update-installer.ts:528-529 (current launch relies on NSIS's own window, not silent). — Fix: spawn from `will-quit` (or immediately before `app.exit`) after teardown, and have the installer start with a short wait; test with two running instances and decide whether to accept the kill.

- D7 — major — Silent quit-install gives no feedback and invites a collision. After a quit-install the person sees nothing for the 10-30 s the installer runs; reopening YouCoded during that window launches an old or half-written copy that NSIS then force-kills (or that locks files so the install fails silently). The design says nothing about failure: no log, no next-launch notice. — evidence: design §4, no failure path for quit-time; update-installer.ts:749-760 has detached spawn with no outcome capture. — Fix: write a small `update-pending.json` before spawning (version, time); on next launch, if the version is still old, surface a "last update didn't finish" notice and clear the cached file; optionally hold a lock file the next launch waits on for a few seconds.

- D8 — major — macOS password path swaps the bundle BEFORE quitting, leaving a running old process on a new bundle. Any process Electron starts after the swap (a new window's renderer, GPU restart, utility process, spellcheck) loads the NEW helper app and frameworks against the OLD main binary: a known crash pattern. The window includes the sessions teardown (up to ~7 s). — evidence: design §4 table macOS-needs-password and step 3 ("password step BEFORE quitting"). — Fix: ask for the password up front but run the swap after exit: one `osascript … with administrator privileges` that launches a root background script which waits for our pid, swaps, then (for Restart) opens the app as the logged-in user. Cancel still leaves the app running.

- D9 — major — macOS admin swap changes ownership and can destroy the app. (a) `ditto`/`mv` as root leaves the new bundle root-owned, so the writable check fails forever after and every later update asks for a password. (b) The target is `path.resolve(exe,'../../..')` with `rm -rf` run as root; in a dev run, a translocated app (opened from Downloads: App Translocation gives a read-only randomised path), or a renamed bundle that path is wrong. (c) AppleScript string quoting of paths is unspecified. — evidence: design §3 and §4 macOS rows. — Fix: refuse unless `app.isPackaged` and the bundle name is `YouCoded.app` and the path is not under `/AppTranslocation/`; `chown -R` to the original owner after the swap; pass paths as positional args to a fixed script (`do shell script quoted form of …`), never interpolate.

- D10 — major — macOS swap has no rollback. "mv old aside → mv staged in → rm -rf old" with no recovery: if the second move fails (disk, permission, a file lock) the person is left with no app at the path. Also hidden staging folder `.YouCoded-update-<version>.app` beside the bundle is left behind (about 300 MB) if the helper never runs, with no startup sweep. — evidence: design §4, Data shape. — Fix: helper script moves old back on any failure and logs; startup deletes stale `.YouCoded-update-*` siblings and `$TMPDIR/youcoded-update-*`.

- D11 — major — macOS App Management protection (Sequoia and later) may block a detached `/bin/sh` helper, or root `osascript`, from replacing another signed app bundle without an "App Management" grant; the prompt would appear with a confusing identity and the quit-time (no UI) path would just fail (unverified). Also a swapped-in app is not checked: the plan relies only on the DMG hash. — evidence: design §4 macOS rows. — Fix: test on a clean macOS 15/26 account before committing; after staging, run `codesign --verify --deep --strict` and `spctl -a -t exec` on the staged `.app` (cheap, catches a bad DMG) and fall back to opening the DMG on any failure.

- D12 — major — Quit-time/Restart install trusts the in-memory "verified" flag and an on-disk file the user (or any user-level process) can change afterwards. §4 says it re-checks the brake but not that the file's hash is recomputed immediately before use. Verification at download time, install minutes or days later, from `userData/update-cache` (user-writable) is a time-of-check/time-of-use gap; `launch()` today verifies right before launching. — evidence: design §2 step 3 / §4 / §5; update-service.ts:196-217 (`verifyBeforeLaunch` is the current gate right before launch). — Fix: `installVerified` must call the existing `verifyBeforeLaunch`/`verifyDownloadedUpdate` (full hash) on the exact path it then executes, and hand that path (not any renderer value) to the installer.

- D13 — major — Cache and verification are tied to the CURRENT status, so a newer release breaks an earlier download. `verifyBeforeLaunch` reads `cachedUpdateStatus.tag/manifest_url`; if 1.3.2 is published while 1.3.1 sits downloaded, the 1.3.1 file fails with "no manifest entry" and (for `verify-failed`) is deleted. §5 says to delete and not install, so a person on a fast release cadence can quit repeatedly and never update, and each new release restarts a 180 MB download. — evidence: update-service.ts:196-217; design §5 ("latest no longer equals the downloaded version → delete"). — Fix: either install the file that was verified against its own tag's manifest (store tag + manifest URLs with `verified`), or at least don't delete a still-valid older file until the newer one has verified.

- D14 — major — Race: background download vs popup download vs stale-cleanup. `startDownload` coalesces only when the URL matches; a different URL (a new release) while one is running rejects `busy`, and the popup's `download()` can hit that while ensureDownloaded owns the job; the design does not say what the popup does (it needs the same `UpdateDownloadResult` the coalesced promise gives, and `jobId`s differ for cancel). Also the popup's Cancel would cancel the background job, and `cancelDownload` is not distinguished. Separately ensureDownloaded after a cancel retries only on the next 30-min check (fine) but "Update now" then silently re-downloads. — evidence: update-installer.ts:222-246 (startDownload), update-service.ts:225-230. — Fix: route ALL downloads through one `ensureDownloaded()` promise owned by the service; popup `download()` awaits it; define Cancel (stops auto-download until next check) and a `busy` mapping.

- D15 — major — `cleanupStaleDownloads` ordering. It runs at startup (main.ts:1459) before any release check, and the design's fix ("skip the file matching current `latest`") needs a `latest` that is not known yet at that moment (cache starts as current version). Result: a 25-hour-old, already-verified download is deleted at each launch and re-downloaded. — evidence: src/main/main.ts:1455-1460; update-installer.ts:351-370. — Fix: do the sweep after the first successful check (or key off the highest version in the cache dir newer than the running version); also stop sweeping at 24 h by mtime for the file we plan to install.

- D16 — major — Android/parity claim is wrong. The design says the backend "reports unsupported" and the renderer capability check hides the rows because the method "is absent or rejects". The shim's own comment says Android answers `{ok:false, unsupported:true}` — a RESOLVED value, not a rejection; `useAutoInstall` would read `.enabled` as undefined and may show a broken switch. The design also hasn't said the two new channels are added to the open (phone-allowed) set that `channel-table-families.test.ts` pins. — evidence: src/renderer/remote-shim.ts:2470-2478; tests/channel-table-families.test.ts:306. — Fix: make the get channel return an explicit `{ supported:false }` on Android/unpackaged and have the hook treat that as null; update the pinned list in the same change.

- D17 — minor — A remote browser (phone) can turn auto-install on or off for the desktop, because the settings channels are not `desktopOnly`. The beta channel set the precedent, but install behaviour is more consequential (restarts the computer's app on quit). Setting ON also triggers a download of ~180 MB on the host. — evidence: design §1; ipc/update.ts:20-29. — Fix: decide deliberately; at minimum, call it out in the contract and keep `restart-to-update` `desktopOnly` (already planned).

- D18 — major — Main-thread blocking not fully addressed. Beyond the sync helpers the design acknowledges, `verifyDownloadedUpdate` itself calls `fs.statSync` and runs on a timer path; the existing AppImage branch uses `chmodSync/renameSync/copyFileSync` (and a 180 MB `copyFileSync` on EXDEV) and `launchInstaller` is reused by `installVerified` at quit; `UpdateSettings.read()` is a sync file read called on every check and now every quit decision. The ratchet test bans additions. — evidence: update-manifest-verify.ts (`fs.statSync(filePath)`), update-installer.ts:552-563, update-settings.ts:33-41; .claude/rules/performance.md rule 1. — Fix: convert these to `fs.promises`, cache `autoInstall` in memory (write-through on set), and keep the allowlist from growing.

- D19 — minor — Startup download timing. §2 runs `ensureDownloaded()` "at startup", competing with session restore and the first-paint chores; a 180 MB download plus a SHA-256 over the whole file happen while the app is being opened. — evidence: design §2; main.ts startup chores around line 1455. — Fix: defer to idle (e.g. 60 s after first window ready, or after first check), hash with a stream at low priority, and skip when on battery saver is not detectable (already noted) but at least not at the same time as session restore.

- D20 — major — Linux AppImage in-place replacement when the downloaded file is on another filesystem: the EXDEV fallback does `copyFileSync` onto the RUNNING AppImage path, which opens it for writing while it is executed (ETXTBSY, or corruption of the mounted image). This was tolerable when the person pressed a button and saw the failure; at quit it fails silently or damages the install. — evidence: update-installer.ts:555-566. — Fix: copy to a temp file beside the target (same directory), then `rename` over it; verify the copy's hash before the rename.

- D21 — minor — Quit-install when the process gets "stuck": the 5 s brake cap runs in parallel with a 6 s teardown wait; if the person force-quits or the watchdog in `quitAfterTeardown` fires before the spawn, the update silently does not install (acceptable) but the verified file stays and §2's "not retried" logic has no state for "tried at quit". — evidence: main.ts:2018-2031, 1936-1941. — Fix: record the attempt (D7's pending file) so the next launch can distinguish "never tried" from "failed".

- D22 — major — Restart flow: the close prompt can be bypassed or double-fired. `closeRequests.request()` is keyed per windowId and `settleAll()` resolves pending prompts as `{close:true, reopen:true}` when ANY quit starts; if the person hits Cmd+Q / the OS quits while the "Restart to update?" prompt is open, the update quit goes ahead with sessions kept tracked, and the update install runs because it's now "a person's quit". Also the update prompt reuses a pending ordinary close prompt for the main window (design §4 step 1 says "no stacking"), which would answer the update question with the wording of a window-close, and a "No" answer would CLOSE nothing but the answer is shared. — evidence: close-request-manager.ts:100-103, 156-166 (reuse and settleAll); design §4 Restart step 1. — Fix: give the update request its own key (not the window's close slot), and treat a `settleAll` during an update request as Cancel for the update (the generic quit proceeds without installing unless the person chose Yes).

- D23 — minor — `restartToUpdate` counts "active sessions across all windows" but the answer is asked of the MAIN window only; sessions owned by secondary windows get untracked/destroyed on `close:true, reopen:false` without those windows' own prompts. Behaviour is probably intended, but it is not stated. — evidence: design §4 Restart steps 1-2; close-request-manager.ts `applyCloseAnswer`. — Fix: state it in the contract's risk line, or ask each window.

- D24 — minor — Windows NSIS assumptions: `/S --updated --force-run` is electron-updater's convention and works only if the installer is the electron-builder one-click per-user build (yml sets no `oneClick`/`perMachine`, so the default per-user applies — OK), but a machine that was ever installed per-machine (older build or manual choice) will raise a UAC prompt from a hidden background installer at quit. The design says "never Windows" for passwords without checking the install location. — evidence: electron-builder.yml:20-28 (no oneClick/perMachine); design §3. — Fix: detect install under `Program Files` (or non-writable exe dir) and treat as needs_password / manual, like macOS.

- D25 — minor — Spawn survival: children are `detached` + `unref`ed, but on Windows a child started by an app running inside a job object that kills on close (some launchers, Task Scheduler) dies with the app, and on Linux a systemd user scope kills the process group unless `setsid`. `spawnDetached` passes `detached: true` which gives a new session on Linux/macOS, so those two are fine; the Windows job-object case is not covered. — evidence: update-installer.ts:749-760. — Fix: on Windows add `windowsHide:false`, and `CREATE_BREAKAWAY_FROM_JOB`-style spawn if feasible, or accept and document.

- D26 — minor — The setting is shared by the dev instance and the installed app through the same `~/.youcoded/config.json`. Gating on `app.isPackaged` protects the dev instance from installing, but a packaged side-by-side test build (e.g. the release-test channel or an older installed copy) will also read "autoInstall" and may download over a metered link while the person thinks it's off. — evidence: update-service.ts:33-37 (comment on shared config); design §1-2. — Fix: accept, but pin with a test that unpackaged never downloads.

- D27 — minor — Test plan gaps. Nothing tests: the failure path of `readReleaseStatus` null (D1), the race of two `startDownload` callers with different URLs (D14), the cleanup-before-first-check order (D15), the SIGTERM-vs-before-quit flag plumbing (D5), relaunch-queued quits (D5), the Windows session-end (D4), Mac helper script content with paths containing quotes/spaces (D9), and rollback (D10). — evidence: design "Tests (pins)". — Fix: add the listed cases.

## Triage (implementing session, 2026-10-22)

- D1 accepted — the signed release file is the primary brake (fetched from the release download host, not the rate-limited API); the re-check returns a result and anything but a fresh, parsed answer means "do not install this time".
- D2 accepted — names corrected to `youcoded-release.json` / `.sig`; the admin procedure names come from the same constants (test).
- D3 accepted — deleting the signed release file is THE brake for both channels; "not latest" is stable-only and optional.
- D4 accepted — Windows `session-end` sets the system-shutdown flag.
- D5 accepted — explicit `installUpdate` intent passed into shutdown; refused when a relaunch is queued by anything else.
- D6 accepted — spawn from `will-quit`, after teardown. Two-instance kill: the dev instance runs as `electron.exe`, so only a second installed copy could be hit; accepted and documented.
- D7 accepted in part — a pending record is written and read on next launch (log + the file is kept/redone so the popup is simply Ready again). No "last update didn't finish" notice: that is new UI no deck approved.
- D8 accepted — Mac swaps always run after our process exits; the password is asked up front.
- D9 accepted — refuse unless packaged, bundle named `YouCoded.app`, not translocated; restore ownership after a root swap; paths passed as arguments, never interpolated.
- D10 accepted — helper rolls back on failure; startup sweeps stale staging folders.
- D11 accepted — `codesign --verify --deep --strict` on the staged app; any failure falls back to opening the disk image. A real-Mac test is a release gate (no Mac here).
- D12 accepted — full hash re-verified on the exact path immediately before it is run.
- D13 accepted — a download remembers its own tag and signed-file URLs; an older verified file stays until a newer one has verified.
- D14 accepted — one service-owned `ensureDownloaded()` promise; the popup awaits it.
- D15 accepted — the stale sweep runs after the first check and never deletes the verified pending file.
- D16 accepted — get returns `{ supported:false }` where there is no updater; the hook treats it as null; pinned channel list updated.
- D17 rejected — the phone already flips the beta channel on the same host; R1 asks for one setting that stays in sync everywhere. Restart stays desktop-only.
- D18 accepted — async fs on every new path, `autoInstall` cached in memory with write-through.
- D19 accepted — the first background download waits until a minute after the first window is ready.
- D20 accepted — copy beside the target, then rename over it.
- D21 accepted — folded into D7's pending record.
- D22 accepted — the update prompt gets its own request key; a quit during it counts as Cancel for the update.
- D23 accepted — documented: the prompt counts every window's sessions and one answer covers them all.
- D24 accepted — a per-machine install (exe folder not writable) never installs at quit; Restart lets the installer raise Windows' own permission prompt.
- D25 accepted — documented as a known limit (Windows job objects).
- D26 accepted — pinned: an unpackaged build never downloads.
- D27 accepted — tests added to the plan.
