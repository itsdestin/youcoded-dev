## Findings

### R2-1 The Android/remote gate is backwards: `targetUrl` is null in a remote browser tab, so the mic ships there
severity: blocker
claim: "the shim exposes `voice` when the connection is `android-local` (the `targetUrl` gate that `android.*` already uses, hoisted to the namespace) and leaves it `undefined` for a remote-desktop connection (Q-7)" (R1-1's disposition).
evidence: `targetUrl` is not "am I Android" — it is "am I pointed at a paired remote desktop". `remote-shim.ts:42` `let targetUrl: string | null = null;`, set only by `connectToHost()` (`:651`) and by the localStorage restore in `installShim()` (`:782`). A plain **remote browser tab** never takes either path: `getWsUrl()` (`:64-79`) falls through to `` `${proto}//${location.host}/ws` `` precisely *because* `targetUrl` is null. The shim's own Android test is written differently everywhere it actually matters: `:420` and `:500` both read `const isLocalBridge = location.protocol === 'file:' && !targetUrl;`. So "expose `voice` when `!targetUrl`" is true in the browser client and the mic renders there. (The `android.*` methods get away with the loose gate only because their remote branch returns a harmless default; a namespace that is *present* is not harmless — `useVoiceInput` gates the whole feature on `!!bridge`.)
consequence: contract **R7** ("In a remote browser tab there is no mic button") fails on every remote browser — the exact row Q-7 was decided to protect, and the one the design calls "the one intentional gap". `voice:start` then goes over the WebSocket to the desktop's `remote-server.ts`, whose `handleMessage` has no `voice:*` case, so the user gets a hang or an unexplained failure rather than an absent button. Second, smaller half: hoisting the gate to the **namespace** evaluates it once at `installShim()`, while `targetUrl` changes at runtime (`connectToHost` / `disconnectFromHost` / the reconnect fallback at `:531`), and `useVoiceInput` captures the bridge **once at mount** (`useState(() => window.claude?.voice)`) — so an Android user who pairs to a desktop mid-session keeps a live mic that now talks to a host with no handlers.
fix: gate on the shim's own Android predicate, `location.protocol === 'file:' && !targetUrl` (the `:420`/`:500` form), not on `!targetUrl` alone; state in the design that the namespace is decided at `installShim()` and therefore that a *runtime* switch to a remote desktop must also make `voice.start` refuse (or that the mic hides on connection-mode change, which `platform.ts`'s `setConnectionMode` already broadcasts). Add the browser case to `ipc-channels.test.ts` as an assertion about the *predicate*, not about the string being present.
disposition: accepted — the gate is the shim's own Android predicate (`location.protocol === 'file:' && !targetUrl`), decided at installShim; a runtime switch to a remote desktop hides the mic via setConnectionMode. The parity test asserts the predicate, not the string.

### R2-2 R1-11's fix and R1-15's fix cancel each other out: `require.resolve` cannot see a package in userData
severity: blocker
claim: the worker "loads the addon by its resolved path" — R1-11's disposition names `require.resolve('sherpa-onnx-<platform>-<arch>/sherpa-onnx.node')` — while R1-15's disposition moves that package out of the installer entirely, into `<userData>/voice/`, and the design keeps "`sherpa-onnx-node@1.13.7`'s JS wrappers" for the API.
evidence: `require.resolve(<pkg>/<file>)` walks `node_modules` from the requiring file upward. After R1-15 there is no `sherpa-onnx-linux-x64` in any `node_modules` — `electron-builder.yml`'s `files: node_modules/**/*` ships what `npm ci` installed, and the design's whole point is that nothing native is installed. The call throws `MODULE_NOT_FOUND`, which the design then forwards verbatim as the user-facing reason — accurate, and useless. The JS wrappers make it worse: `sherpa-onnx-node/addon.js` (read from the published tarball) hard-codes five `require()` candidates, every one of them a bare package specifier or a relative path inside its own package; none can reach `<userData>/voice/`. `non-streaming-asr.js`, `types.js` etc. all go through `addon.js`.
consequence: the addon never loads on any platform, so the feature is dead in the first build — and the failure appears only in a packaged app or a userData-based dev run, never in a checkout where `npm ci` happens to have installed the package, so it can pass a developer's smoke test and fail for every user.
fix: the design must say the worker `require()`s an **absolute path** — `require(path.join(voiceRoot, 'runtime', 'package', 'sherpa-onnx.node'))` — and how the JS wrappers get pointed at that handle: either fetch the wrappers, unpack them beside the platform package so their relative `require('./sherpa-onnx.node')` candidate resolves, or drop the wrappers and call the N-API surface directly. Pin this with a test that loads the addon from a temp dir with no `node_modules` on the path.
disposition: accepted — and it is the round-1 pair that cancelled: the worker `require()`s an ABSOLUTE path into `<userData>/voice/runtime/package/`, the JS wrappers are unpacked beside the addon so their relative candidate resolves, pinned by a test that loads from a temp dir with no node_modules on the path.

### R2-3 The npm tarball's `package/` prefix and its sibling shared libraries are not in the layout plan
severity: major
claim: "unpack into a `.unpacking` sibling → `.complete` marker written last → rename into place", "the exact shape of `engine/engine-acquisition.ts`", for "BOTH things the feature needs".
evidence: npm tarballs are rooted at `package/`, not at the archive root — `tar -tvf sherpa-onnx-linux-x64-1.13.7.tgz` gives `package/sherpa-onnx.node`, `package/libonnxruntime.so` (26.4 MB), `package/libsherpa-onnx-c-api.so`, `package/libsherpa-onnx-cxx-api.so`, `package/index.js`, `package/package.json`. Windows is the same shape with `.dll`s; darwin with `.dylib`s. `engine-acquisition.install()` handles exactly this with a pinned `binaryRelPath` and a post-unpack existence check ("the pinned layout in engine-pin.ts is stale") — the design's `voice-pin.ts` is described as holding only "`dist.integrity` per platform, four entries" and never mentions a relative path. Round 1 established (its own preamble) that the `.node` finds its siblings by `RUNPATH $ORIGIN` / `@loader_path` — which is true **only if the four files stay in one directory**; any flattening or per-file move breaks the dlopen and produces exactly the misleading loader message R1-11 was raised about.
consequence: a silent layout assumption in the one step that has already burned this repo once (the `engine-pin.ts` WHY comment records `build/bin/llama-server` as "a stale guess"), plus no post-unpack existence check, so a wrong guess surfaces at first tap as a dlopen error instead of at install time.
fix: pin the in-archive path per platform the way `engine-pin.ts` does (`package/sherpa-onnx.node`), keep all four files in one directory, and reuse `engine-acquisition`'s "the pinned layout is stale" existence check verbatim. State that the four entries are two-per-platform (integrity **and** relative path). Note also that `sherpa-onnx-win-ia32` exists on the registry but `sherpa-onnx-win-arm64` does not (`npm view` → E404), which is the real reason `win-arm64` — not `win-ia32` — is the unsupported platform the design should name.
disposition: accepted — per-platform pins carry integrity AND the in-archive relative path (`package/sherpa-onnx.node`), all four files stay in one directory, engine-acquisition's stale-layout existence check is reused verbatim, and the unsupported platform is `win-arm64` (not `win-ia32`, which exists).

### R2-4 The card prints 487 MB, which is neither R8's approved number nor the true total
severity: major
claim: "The first-run card keeps R8's approved copy exactly" (§What was decided) and, four paragraphs later, "The download's real number is 487 MB; the card prints that" (§Risks).
evidence: contract row **R8** pins "'Speak your messages', two sentences, **464 MB**, Not now and Download"; the built UI carries it (`mock-shim.ts` `sizeMb: 464`, `VoiceButton.tsx` "One-time download: {readiness.sizeMb} MB"). The design contradicts itself in one document, and both numbers are now wrong anyway: after R1-15 the first tap downloads the model **plus** a platform package — `dist.unpackedSize` 32.7 MB (linux-x64) / 23.0 (win-x64) / 34.0 (darwin-arm64) / 37.5 (darwin-x64), 8.7–10.8 MB compressed — so the honest total is ~498 MB, and the design's own "percentage over the combined byte total" already knows that.
consequence: the same failure R1-12 was dispositioned on — approved copy changed outside a deck — reintroduced by a different edit. A user watching a bar that is denominated in a number no card ever showed is the "reads as stuck" complaint the fix was meant to remove.
fix: pick one number, make it the true combined total, and take it through the one-step decide deck that R1-12's disposition already schedules (it is the same card, the same sentence, and Destin is already being asked about that card's copy). Until then the design must not assert both "keeps R8 exactly" and "prints 487".
disposition: accepted — the design asserts no number; the true combined total and the card's sentence both go to the one-step decide deck R1-12 already schedules.

### R2-5 The Enter guard is written into `send()`, which silently turns the Send button — and the "Send anyway" retry — into a stop
severity: major
claim: "Both send paths (`send()` and the global-keydown route through `sendRef`) check the phase: listening → `stop()` and return."
evidence: `send()` is not one of two paths, it is the *shared bottom* of at least four. `InputBar.tsx:637-650` `handleSubmit` — the `<form>`'s submit handler — ends in `send()`, and the Send button is `type="submit"` (`:936-940`). `:408` `sendRef.current(true)` is the "Send anyway" retry fired from a toast after the pending-prompt gate refused. `:283-288` is the global-keydown route. Putting the guard inside `send()` therefore also governs a mouse/touch tap on Send and the retry.
consequence: two behaviours nobody signed. (1) Tapping **Send** while the mic is open does not send — it stops the mic; the user must tap Send twice. Contract R3 lists the stops as "a second tap, Enter, the strip's Stop, or about two quiet seconds" — Send is not among them, and Destin drives this app by touch, where Send is the natural end of a dictated message. (2) If a pending-prompt toast is on screen and the user opens the mic, "Send anyway" silently stops the mic and drops the send it was retrying, with no toast and no second chance.
fix: guard at the *keyboard* sites (the textarea's `onKeyDown` Enter branch and the global handler), not inside `send()`; or guard inside `send()` but exempt `force === true` and give the Send button its own explicit behaviour, decided on the deck — "Send while listening stops and sends" is the shape a touch user expects and is a different promise from Enter's.
disposition: accepted — the guard lives at the two keyboard sites (the textarea's Enter branch and the global handler), never inside `send()`, so the Send button and the Send-anyway retry are untouched.

### R2-6 An `AudioWorklet` cannot call `window.claude.voice.sendAudio`
severity: major
claim: "an `AudioWorklet` that posts Int16 PCM every 100 ms to `window.claude.voice.sendAudio(chunk)`."
evidence: worklet code runs in `AudioWorkletGlobalScope` on the audio rendering thread — no `window`, no `document`, no `postMessage` to the page except through its own `MessagePort` (`this.port.postMessage`). It is also loaded by URL through `audioContext.audioWorklet.addModule(url)`, so the processor must be a *separate module file* that the Vite build emits and that resolves under both the dev server and the packaged `file://` renderer — which is build plumbing the design does not mention anywhere (nothing else in `desktop/src/renderer` ships a worklet today).
consequence: the one sentence describing how audio leaves the microphone cannot be implemented as written; a builder either discovers this and improvises the relay (fine, but unreviewed), or reaches for the deprecated `ScriptProcessorNode`, which runs on the main thread and drops frames under load — the exact stutter the utility process exists to avoid.
fix: say it properly: a `voice-worklet.js` module emitted as its own chunk (or a `Blob`/data URL built at runtime, which sidesteps the packaging question entirely), `processor.port.onmessage` on the renderer side relaying each Int16 chunk to `window.claude.voice.sendAudio`, and the RMS computed in the worklet and shipped in the same message so the meter costs nothing extra. Then say which of the two module-loading routes is chosen, because the packaged `file://` case is where it breaks.
disposition: accepted — a `voice-worklet.js` built at runtime as a Blob URL (sidesteps the packaged file:// question), posting Int16 chunks AND the RMS in one message through `processor.port.onmessage`, which the renderer relays to `sendAudio`.

### R2-7 The `finishing` watchdog can destroy a good utterance and blame the engine for it
severity: major
claim: "Watchdog (R1-9): 5 s in `finishing` with no terminal event → a local `error` ('The speech engine stopped answering.') and back to idle", together with "The hook drops `partial`/`final` while `phaseRef` is idle" (R1-6).
evidence: the two rules compose badly on exactly the slow machine both were written for. `stop` triggers "one last pass on the open segment"; the design's own cost table has a 24 s segment at 733 ms (2 threads) and warns the laptops the findings targeted are slower; add a cold recogniser after the ten-minute unload (measured construction 0.83–0.94 s *here*, "longer on the laptops"), a 641 MB model read from a cold spinning disk, and any queued pass the 200 ms-gap scheduler has in flight. When the watchdog wins that race, the hook goes to `idle`; the real `final` then arrives a moment later and is **dropped by the idle rule**.
consequence: the user's dictated sentence disappears — the box keeps only whatever was committed before the last pass — and the card blames the engine for a failure that did not happen. "The speech engine stopped answering" is a hardcoded assertion about a cause the renderer never verified, which is `docs/error-message-standards.md`'s canonical anti-pattern (the same shape as the llama.cpp "its build may not run on this machine" message that doc exists because of).
fix: the watchdog must not be a fixed 5 s renderer timer racing a variable-length pass. Have `VoiceService` ack the `stop` with an expected-work signal (or simply push a `readiness`/heartbeat while a pass runs) and start the watchdog only when the worker has gone quiet; make a late `final` after a watchdog error still deliver its text rather than being dropped; and if the message stays, drop the invented cause — "Voice stopped before it finished." plus the two actions of the standard's general shape.
disposition: accepted — VoiceService heartbeats while a pass runs and the watchdog starts only after the worker goes quiet; a late `final` still delivers its text; the message loses its invented cause and uses the general shape.

### R2-8 `readiness.state: 'unpacking'` has no card, so the progress card vanishes for the minute the fix was written to explain
severity: major
claim: R1-15's disposition, "the unpack phase gets its own label"; the design adds "`readiness.state: 'unpacking'`" to `voice-types.ts` and says "the card must say so instead of sitting at a full bar".
evidence: adding a member to the `VoiceReadiness` union does not draw anything. `VoiceButton.tsx` builds `card` from four branches — `error`, `needs-download`, `downloading`, `unavailable`. An `unpacking` readiness matches none, so `card` is `null`, and the render is `{open && card && createPortal(...)}`: the "Getting voice ready" panel **disappears** at the moment the download completes and does not come back until `ready`. The tap-to-reopen path does not help — `handleClick` toggles `open`, and `card` is still null. `ProgressBar percent` also has no value to show: bzip2 gives no progress signal, and the design does not say what the union member carries.
consequence: the user taps Download, watches a bar to 100 %, and the card vanishes for the tens of seconds the half-gigabyte unpack takes — a worse reading of "stuck" than the full bar it replaced, and R9's "when it finishes, a note says 'Voice is ready'" is the only thing that ever comes back.
fix: name the UI change in the design, not just the type change: a fifth `VoiceButton` branch for `unpacking` with an indeterminate bar and the label, the union member's exact shape (`{state:'unpacking'; engine: string}`), the workbench fake extended to emit it (it is the surface Destin reviews), and a line in the test list. Note this makes `VoiceReadiness` a five-state union that the Android shim also produces — Android never unpacks, which is fine, but the type should say so.
disposition: accepted — `unpacking` gets its own VoiceButton branch (indeterminate bar + label), an exact union shape, the workbench fake emits it, and it joins the test list; the type notes Android never produces it.

### R2-9 The grey tail's fate at a commit, and the mid-word hard cut, are unspecified against R2's promise
severity: major
claim: "The result of each pass splits into `committed` (all but the last two words) and `tail`"; "a segment commits at any ≥ 0.8 s pause once it is past 5 s, and is hard-cut at 15 s even mid-word (a hard cut may split a word; the next segment's first pass hears the rest, and the join is a space)".
evidence: contract **R2** promises "the newest few show grey until they **settle**, then turn solid" — a state transition per word. The design defines the tail only *within* a pass and never says what happens to the two grey words when the segment they belong to commits and its audio is dropped: they cannot be re-heard (the next segment's audio does not contain them), so either they are promoted to solid without ever being re-decoded (fine, but then "settle" means "the segment closed", which is worth saying) or they are lost. The hard cut is worse and the design admits it in passing: a word split at 15 s is decoded as two fragments in two different segments and joined with a space — permanently, because the earlier segment is already committed. `InputBar.tsx`'s merge (`setText(voiceBaseRef.current + committed)`) has no notion of segments at all; it replaces everything after the base with whatever `committed` string arrives, so the segment joining has to happen in the worker and be shipped as one cumulative `committed` — also unstated.
consequence: a user dictating a long unbroken sentence — the design's own "normal when dictating" case — gets a visible mangled word ("recogni tion") in settled text they must hand-fix, and R2 grades as pass/fail on a deck where the reviewer is watching exactly this transition.
fix: state the segment→text contract explicitly: `committed` is cumulative across segments, the tail is promoted on commit, and a hard cut is taken at the **quietest 100 ms frame in the last second** rather than exactly at 15 s (an energy minimum is nearly free — it is the same RMS the silence stop already computes) so the split lands between words in almost every real case. Put "a hard cut never splits a word when any sub-threshold frame exists in the last second" in `voice-rehear.test.ts`.
disposition: accepted — committed is cumulative across segments and the tail is promoted on commit; the hard cut is taken at the quietest 100 ms frame in the last second (the RMS the silence stop already computes), with the no-split-when-a-quiet-frame-exists case pinned in voice-rehear.test.ts.

### R2-10 Node's `fetch` ignores the system proxy, so the corporate and offline cases both report "fetch failed"
severity: major
claim: `voice-assets.ts` uses "the exact shape of `engine/engine-acquisition.ts`", now against two hosts (registry.npmjs.org and objects.githubusercontent.com).
evidence: `engine-acquisition.ts` takes `private fetchImpl: typeof fetch = fetch` — the global undici fetch, which honours neither `HTTP_PROXY`/`HTTPS_PROXY` nor the OS proxy configuration, unlike Electron's `net.fetch`. `rg -n 'net\.fetch' src/main` returns nothing anywhere in the app. Its error handling covers HTTP status (`the server responded with HTTP ${res.status}`) but a transport failure never reaches that line: undici throws `TypeError: fetch failed` and hides the real reason (`ENOTFOUND`, `ECONNREFUSED`, proxy 407, TLS interception) in `err.cause`, which nothing unwraps.
consequence: on a school or corporate network — the design's stated audience is students and professionals — the one-time download fails and the card says "fetch failed". That is neither of the two allowed shapes in `docs/error-message-standards.md`: not specific (the real cause is one property away and is being discarded) and not the general shape (no Report bug / Diagnose with Claude actions). The blast radius doubled when R1-15 added a second host, and adding npm means an air-gapped or registry-restricted machine now fails where a single GitHub host might have succeeded.
fix: use `net.fetch` (or thread the proxy through) for both downloads, unwrap `err.cause` into the message, and render the failure through `<ErrorState mode="general">` when no cause survives. This is a change to `engine-acquisition`'s shape, so say so in the design rather than inheriting the defect by reference.
disposition: accepted — `net.fetch` for both downloads, `err.cause` unwrapped into the message, `<ErrorState mode="general">` when no cause survives; stated as a change to engine-acquisition's shape rather than inherited by reference.

### R2-11 Readiness composition is described unconditionally, and Android is the surface it breaks
severity: major
claim: "Readiness is composed, not read (R1-4): `useVoiceInput.status()` and `recheck()` merge the probe over main's model status — `unavailable` from the probe wins over `ready` from the model folder", alongside "`voice:download` and `voice:mic-access` reply not-implemented" on Android and "Android's shim omits `sendAudio`".
evidence: the composition rule has no platform condition anywhere in the design, and `useVoiceInput` is one hook shared by the Electron renderer, the Android WebView and the workbench (`react-renderer.md`: "This code runs in BOTH the Electron renderer AND a bundled Android WebView"). On Android the probe's two halves are both wrong: `voice:mic-access` answers not-implemented, and `navigator.mediaDevices.enumerateDevices()` in a WebView that has never been granted `RECORD_AUDIO` is not a reliable source of truth about the phone's microphone — while the authoritative answer (`isRecognitionAvailable()` plus the launcher's result) is the very thing main's status already returns and the probe is defined to override. The workbench fake has the same gap by construction: `createVoiceMock` (mock-shim.ts:1982) exposes exactly `status/download/start/stop/cancel/onEvent` — no `micAccess` — and the compare panes are the surface Destin's approval was recorded against.
consequence: the phone can show "**No microphone was found on this computer.**" — wrong verdict, wrong noun — over a working recogniser, killing R6; and the workbench panes stop matching the app unless the fake grows the new methods.
fix: say the composition is desktop-only and how the renderer knows (`typeof bridge.micAccess === 'function'`, the same "only calls what is present" test the design already uses for `sendAudio`), and that on Android `status()` is authoritative. Extend `createVoiceMock` with `micAccess` and `sendAudio` in the same change, and add the platform split to `useVoiceInput.test.ts`.
disposition: accepted — composition is desktop-only, detected by `typeof bridge.micAccess === 'function'` (the same present-or-absent test as sendAudio); on Android `status()` is authoritative. The fake gains micAccess and sendAudio; the platform split joins useVoiceInput.test.ts.

### R2-12 `formatBytes` is not the model manager's helper — it is a private function in an unrelated main-process file
severity: minor
claim: "Sizes are printed in the unit the rest of the app uses (`formatBytes`, the same helper the model manager uses)."
evidence: `rg -n 'formatBytes' src tests` in `youcoded/desktop` returns exactly two lines, both in `src/main/project-context.ts` (`:116` the declaration, `:145` its only call) — a **non-exported** helper (`rg -n 'export .*formatBytes'` → no match) that formats file sizes for the project-context file list. The model manager does not use it. The renderer, which is where this card lives, has no shared size formatter at all: `SessionDrawer.tsx:1282` `formatSize`, `ResumeBrowser.tsx:41` `formatSize`, `PartialFileBanner.tsx:6` and `BinaryFallback.tsx:14` each hand-roll `/ (1024*1024)`.
consequence: a name in a design that a builder will try to import and not find — and the sentence quietly settles a real question (MiB vs MB) by pointing at a function that answers MiB, while R2-4's "487 MB" is the decimal number. The two together mean the card can print a bar denominated in one unit and a total in the other.
fix: drop the false attribution; either add a shared renderer helper (and say the four hand-rolled ones are out of scope) or state the unit literally in the design. Whatever is chosen must agree with the number R2-4 settles.
disposition: accepted — the false attribution goes; the design states the unit literally and it must agree with the number R2-4 settles.

### R2-13 `dist.integrity` is base64 sha512; the verify path being copied is hex sha256
severity: minor
claim: "pinned `dist.integrity` per platform, four entries", using "the exact shape of `engine/engine-acquisition.ts`: download → verify → unpack".
evidence: `npm view sherpa-onnx-linux-x64@1.13.7 dist.integrity` → `sha512-npmxn5WwmAmlthgBhmbZ...==` (base64 sha512, the SRI format). `engine-acquisition.ts` verifies with `sha256File()` — `crypto.createHash('sha256')` compared as lowercase hex against `asset.sha256`. The two are not interchangeable, and the model's pin genuinely *is* hex sha256, so `voice-assets.ts` needs both algorithms and both encodings in the same verify step.
consequence: a small but real fork in the "exact shape" the design leans on, easy to get subtly wrong (comparing a base64 digest case-sensitively, or silently truncating), in the step whose whole job is to detect corruption.
fix: one sentence in the design: the verifier takes `{algo, encoding, digest}` and the npm entries carry sha512/base64 while the model carries sha256/hex — or normalise the npm pins to sha256 hex, computed once and recorded with the command that produced them (a pin nobody can reproduce is worse than the format mismatch).
disposition: accepted — the verifier takes {algo, encoding, digest}; npm pins stay sha512/base64 as published, the model stays sha256/hex, and each pin records the command that produced it.

### R2-14 Nothing says who kills the worker, or which window gets `voice:event`
severity: minor
claim: "Unloads the worker after ten idle minutes"; "`voice:event` push to the requesting window".
evidence: the ten-minute idle timer is the only lifecycle the design states — there is no `before-quit`, no window-closed, and no second-window story, and `rg -n utilityProcess src/main` still returns nothing (this is the app's first one, so there is no house pattern to inherit; `session-manager.ts:161-172` shows what the existing worker spawn does bother to handle). "The requesting window" is a single `webContents`: sending to a destroyed one throws, and the app can have more than one window.
consequence: at best untidy (a 1.14 GB process and an open microphone outliving the window that asked for them); at worst an unhandled throw in main when a window closes mid-dictation, and a dev instance that leaves an orphan holding the mic between reloads — the same class of leftover the workspace already polices for Vite servers.
fix: state it: `start` records the requesting `webContents.id`; a `destroyed`/`closed` window cancels the session and unloads; `app.on('before-quit')` kills the worker; a second window's `start` while another is listening is refused with a real reason. One line each, and one case in `voice-service.test.ts` (the suite already promises "exactly one terminal event per start" — window death is one more path into it).
disposition: accepted — start records the requesting webContents.id; a destroyed window cancels and unloads; before-quit kills the worker; a second window's start while listening is refused with a real reason; one case each in voice-service.test.ts.

### R2-15 Space-hold leaks a stuck-open mic when the key-up never arrives
severity: minor
claim: R18/R19's mechanism, and the test list's "Space held 250 ms in an empty box starts, release stops".
evidence: `InputBar.tsx:867-870` — the only stop for walkie-talkie mode is the textarea's `onKeyUp`. If focus leaves the textarea while Space is down (the idle-blur timer at `:310-325`, an Alt-Tab, a click on another pane, the window losing focus), the `keyup` lands somewhere else and `spaceHeld.current` stays `true` with the mic open. Nothing in the design or the hook has a blur/visibility fallback, and the design's test list codifies only the happy path.

disposition: accepted — blur and visibilitychange while spaceHeld also stop the mic, with the case added to InputBar.test.tsx.

### R2-16 The bridge grows two desktop-only methods without amending the parity rule's closed exception list
severity: minor
claim: "Added by this build: `sendAudio(chunk: ArrayBuffer): void` and `micAccess(): Promise<…>` on the bridge (desktop only; Android's shim omits `sendAudio`…)"; "`ipc-channels.test.ts` records `voice:*` as present in all three surfaces, with remote-desktop as the named exception".
