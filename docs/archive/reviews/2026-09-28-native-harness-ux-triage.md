## U1 — submitted native question was shown as expired

**Cause established in the workbench, not a native-runtime failure.** The review fixture `fixtures/bubbles/questions-native.jsonl` supplies a static `tool_use`/`permission_request` through `fixture-loader.ts`. That replay does **not** register the request in `reply-script.ts`'s live `pending` map. `mock-shim.ts`'s `session.respondToPermission` previously called only `resolvePermission(id)`, which returned `false` for `native-d4-visual`. `AskUserQuestionCard.handleSubmit` therefore called `onFailed`; that dispatches `PERMISSION_EXPIRED` with `delivery-failed`, and `chat-reducer.ts` writes “This request closed before an answer reached it.” The static card retained raw INPUT and had no tool result — exactly the review screenshot. This does **not** show that an actual native response failed: production `ipc-handlers.ts` routes `permission:respond` to `nativeHost.respondPermission` → `PermissionBroker.respond`, which resolves the waiting driver with `updatedInput`; the driver records a paired tool result from `formatAnswers`. Production `PermissionResolved` purges the ask buffer; `PermissionExpired` on cancellation is a separate path. Existing `harness-session-loop.test.ts`, `native-permission-broker.test.ts`, `ask-user-question-tool.test.ts` pin those individual paths, not paid inference or a live run.

**Accepted narrow fidelity fix:** `mock-shim.ts` recognizes only the seeded `native-d4-visual` request when `seed=bubbles-questions-native`. A valid two-answer allow consumes it once, emits a real-shaped `tool-result` on the fixture's `d4-native-ask` ID with both distinct answers and optional note, then a `turn-complete` because the canned fixture has no model continuation. Dismiss on that same fixture also consumes it once, emitting the driver's existing question-dismissed result and stop reason rather than falsely expiring it; no other fixture request is intercepted. Any other request still follows the existing `resolvePermission` path. This is not a new product receipt or transport change; it prevents a successful fixture Submit from falsely looking expired or leaving a permanent Thinking chip. No renderer/reducer/broker production code changed. The fixture's result is canned and is **not proof** that a real provider consumed the answers.
