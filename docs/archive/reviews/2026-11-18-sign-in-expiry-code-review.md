## Findings (most severe first)

- F1 **accepted** — — desktop/src/renderer/state/provider-sign-in-store.ts:44,95 (+ SignInNotices.tsx useSignInCard `back`) — the per-provider phase is never reset: after one successful sign-in in an app run it stays `signed-in` forever, so the NEXT expiry (or any later ChatGPT/OpenRouter error card) draws the green "Sign in successful. Send another message to continue." with no button instead of the red expired card; a `failed` phase likewise sticks ("Signing in didn't finish.") on an unrelated later card. Only `cancelSignIn` or `opened===false` set IDLE — confirmed by reading every `set(...)` call in the store and the only reader branch (`back = state.phase === 'signed-in'`); same stale value also feeds Settings notices (`signInNotice` returns null for `signed-in`) so Settings hides a fresh expiry too.
- F2 **accepted** — — desktop/src/renderer/components/AssistantTurnBubble.tsx:~449 (`assistantTurnPropsAreEqual`) — the memo comparator ignores the new `latest` prop, so when the person sends another message the old reply's `latest` flips true to false but the bubble does not re-render: the "Your Claude sign-in has expired" card (with its Sign in button) stays on screen instead of disappearing (promise 1). Confirmed by call chain: ChatTimelineRow's default memo re-renders on the prop change, then the bubble's custom comparator returns true because `turn`, ids and maps are unchanged. The added test (`AssistantTurnBubble.test.tsx`) renders `latest=false` from the start, never a true-to-false flip, so it cannot catch this.
- F3 **accepted** — skip the check for local endpoints; — desktop/src/main/harness/harness-session.ts:4497 with provider-failure.ts:77 (`NETWORK_CODES` includes ECONNREFUSED/ECONNRESET) — a local-model or LAN-endpoint failure (Ollama stopped, server down) while the computer happens to be offline now ends at once with the red "No internet connection." card and skips the retry ladder, blaming the connection for a problem that is the local server. The check is made for any `network`-coded step failure regardless of whether the provider is local/on this machine; confirmed by reading withRetry (no provider-type guard). Local models are marketed as offline use, so this is the exact "invented cause" the error standards forbid. Suggest skipping the check when the endpoint is local (`isLocalEndpoint`) or the code is ECONNREFUSED.
- F4 **accepted** — "required" gets its own sentence; — desktop/src/renderer/components/AttentionBanner.tsx:139 — `chatgpt-signin-required` (never signed in, `CHATGPT_SIGN_IN_REQUIRED_MESSAGE`) is routed to the same card as `-expired`, so a person who simply has not connected ChatGPT is told "Your ChatGPT sign-in has expired." Confirmed in provider-error-code.ts (two distinct codes) and ProviderSignInCard (one `expiredLine` for chatgpt). Wording is wrong for that case.
- F5 **accepted** — — desktop/src/renderer/hooks/useExpiredSignIns.ts + SignInNotices.tsx — `recheckExpiredSignIns()` has exactly one caller (the Claude card on mount). A ChatGPT/OpenRouter reply failure, an OpenRouter sign-in or key paste done in Settings (OpenRouterBlock uses its own local `startSignIn`, not the shared store, so the `phases` dependency never fires), or a pasted new key never re-reads, so the gear's red dot stays lit until the app restarts (or goes unlit late for a new ChatGPT expiry). Promise 5 says checks happen "when a reply fails" and the dot "must clear itself". Confirmed by `rg recheckExpiredSignIns` (one call site) and the OpenRouterBlock diff.
- F6 **accepted** — — desktop/src/renderer/state/provider-sign-in-store.ts:75 with claude-sign-in.ts:67 — while a Claude sign-in is open, the renderer polls `claude-code:status {refresh:true}` every 1.5 s and main's `finish()` polls with `invalidate()` every 2 s: each one spawns a `claude auth status` subprocess (up to 8 s each), so two overlapping spawn loops for up to 10 minutes. Not a main-thread block, but needless process churn (performance.md per-event cost). Confirmed by reading both loops; `refresh:true` drops the cache every time. Suggest the renderer poll without `refresh` (main already invalidates).
- F7 **accepted** — — desktop/src/main/first-run.ts:~460 (`stoppedForNoInternet`) — the check runs before any state update, so on a slow-failing network the person presses a sign-in button and sees nothing for up to 5 s (the DNS timeout) with no spinner; also it does not re-check `authRound` after the await, so Cancel pressed during the wait is not honoured (it still writes the offline state). PLAUSIBLE: low impact; I did not time a real offline DNS failure.
- F8 **rejected** — unverified that the CLI ever omits loginExpiresAt (it reports one today); an in-app sign-in or restart clears it. — desktop/src/main/providers/claude-account.ts:~140 (`withExpiry` with `failedLogin === ''`) — for a login with no end time, a remembered refusal never clears when the person signs in again outside the app (terminal `/login`): the stamp stays `''`, so the account reads expired until `clearAuthFailure()` (only called by the in-app sign-in) or restart. PLAUSIBLE: depends on the CLI omitting `loginExpiresAt`, which I could not confirm; not reproduced.
- F9 **rejected** — by design: the person did sign in since; the card says so and leaves on the next send (Destin approved R2-3). — desktop/src/renderer/components/SignInNotices.tsx:~95 (`LiveClaudeSignInNotice`) — on reopening an old chat whose last reply is a stale `authentication_failed` line, `alreadyBack` shows a green "Sign in successful. Send another message to continue." although the person never signed in during this view, and the `recheckExpiredSignIns()` mount effect runs a status spawn. PLAUSIBLE UX oddity, not a crash; by-design per the card text but worth Destin's eye.
- F10 **accepted** (dead tones) / **rejected** (routing OpenRouter Settings through the store: its own state machine already blocks a second tab from Settings; the chat+Settings double tab needs both open at once) — — desktop/src/renderer/components/ChatNoticeBubble.tsx:21-28 — `warning` and `quiet` tones (and their comments) are used by nobody on the branch (only `danger`, `success` are passed). Small dead surface; knip does not see union members. Also store comment claims all surfaces "move together", yet OpenRouter Settings bypasses the store (see F5), so two browser tabs can be opened (chat card + Settings).
