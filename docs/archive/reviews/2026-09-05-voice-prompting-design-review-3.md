## Findings

### R3-1 `setConnectionMode` does not rebuild `window.claude`, so R2-1's runtime half is unfixed — the phone keeps a live mic after pairing to a desktop
severity: blocker
claim: "The namespace is decided at `installShim()`, so a runtime switch to a remote desktop hides the mic through `setConnectionMode`, which already broadcasts." (§The shim, and the one intentional gap — R2-1's disposition.)
evidence: `setConnectionMode` does not touch `window.claude` at all. `renderer/platform.ts:26-30` is four lines: it assigns a module-level `_connectionMode` and calls the listeners. `window.claude` is assigned exactly once, at `remote-shim.ts:790` inside `installShim()`, and nothing reassigns it (`rg -n 'setConnectionMode' src` → six call sites, all in `remote-shim.ts`, none of which rebuild the object; `remote-shim.ts:659` inside `connectToHost` is the pairing one). The only listener that matters is `App.tsx:1972`, which flushes session state and re-lists sessions — it does not remount the shim. And even a remount would not help: `useVoiceInput.ts` captures the namespace with `useState(() => window.claude?.voice)` under a WHY comment that says the capture is deliberate, and `voice` is a plain object property that a namespace-level predicate created once at boot. On Android `installShim()` runs with `location.protocol === 'file:'` and a `targetUrl` it has just cleared (`:775-778`), so the predicate is true and the namespace is created; `connectToHost()` later sets `targetUrl` (`:651`) but the object is already on `window`.
consequence: exactly the second half R2-1 named, still live: an Android user who pairs to a remote desktop mid-session keeps a mic button, and `voice:start` goes over the WebSocket to a `remote-server.ts` with no `voice:*` case — a hang or an unexplained failure. Contract **R7** ("voice ships on desktop and Android only") passes at boot and fails after one pairing. The design records this as resolved, which is worse than recording it as open: the next session reads the sentence and does not look.
fix: the gate cannot be a one-time namespace decision if it also has to react. Either (a) keep the namespace decided once AND make each `voice.*` method refuse at call time when `targetUrl` is set — the per-call shape `android.*` already uses at `:1437-1445` — with `status()` answering `unavailable` with the Q-7 reason so the card explains itself, or (b) make `supported` reactive: `useVoiceInput` subscribes to `onConnectionModeChange` and drops the bridge on `'remote'`, which means giving up the mount-once capture and saying so in that comment. Whichever is chosen, delete the sentence that says `setConnectionMode` hides the mic.
disposition: accepted — option (a): the namespace is still decided once, and every `voice.*` method refuses at call time when `targetUrl` is set (the per-call shape `android.*` already uses), with `status()` answering `unavailable` carrying the Q-7 reason so the card explains itself. The sentence claiming setConnectionMode hides the mic is deleted.

### R3-2 The heartbeat-gated watchdog reinstates R1-9's forever-`finishing` mic: a worker that wedges without exiting is now unbounded by design
severity: blocker
claim: "**Heartbeat instead of a blind timer** (R2-7): while a pass is running **the service pushes a heartbeat**, so the renderer's watchdog starts only once the worker has gone quiet"; and "`voice-service.ts` … **guarantees exactly one terminal event per `start`** (R1-9): a worker `exit` or `error`, a load failure, or a pass that throws becomes `error`".
evidence: the heartbeat's source is the service, and the service's evidence that "a pass is running" is that it dispatched one and has not heard back. Every listed terminal path requires the worker to *report* something: `exit`, `error`, a load failure, a throw. A worker that is alive and not answering matches none of them — and that is not a hypothetical here. The design's own numbers make it the likely failure: one loaded recogniser is **1.14 GB RSS** (R1-13) on machines the findings describe as 4 GB laptops also running a local chat model, and the design already names that combination as "a known bad combination". A process swapping against a 641 MB model, or a `decodeAsync` that never calls back, keeps the service in "a pass is running" forever, so the heartbeat never stops, so the renderer's watchdog — which the fix defined as "starts only once the worker has gone quiet" — never arms. There is no upper bound anywhere in the design, even though the design *has* the number to write one: a pass is bounded by segment length, and the measured worst case is 733 ms for 24 s of audio at 2 threads, against a hard cut at ~15 s.
consequence: R2-7 traded a watchdog that fired too early for one that can never fire. The visible result is R1-9's original bug, verbatim: `phase` stays `finishing`, `VoiceButton` renders `disabled={disabled || phase === 'finishing'}` so the mic is dead for the rest of the app's life, `useVoiceInput.start` refuses because `phaseRef.current !== 'idle'`, and `voiceCanStart` (`InputBar.tsx:160`) is false so Space-hold silently does nothing too. The user's dictated sentence is also gone. Only an app restart recovers, and no error is ever shown — which is the one outcome `docs/error-message-standards.md` has no shape for.
fix: keep the heartbeat, add a ceiling. The heartbeat must carry a *deadline the service can defend* — e.g. the worker acknowledges each pass with the segment length, the service derives an expected cost from the measured curve already in the design, and a pass that overruns it by some multiple ends the session: kill the worker, emit the one terminal `error` R1-9 promises, and say what actually happened ("Voice stopped: the speech engine did not answer for 30 seconds and was closed") — specific and true, no invented cause. Add the case to `voice-service.test.ts`, which already promises "exactly one terminal event per start": a worker that neither exits nor answers is one more path into that suite, and it is the only one the current list omits.

disposition: accepted — and it is the second fix-restores-the-bug pair of this review. The worker acknowledges each pass with its segment length, the service derives the expected cost from the measured curve already in the design, and an overrun by a multiple kills the worker and emits the one terminal error with what actually happened. The wedged-worker path joins voice-service.test.ts.

### R3-3 Settled words provably change: the re-hear loop rewrites `committed`, which R2 and `voice-types.ts` both promise it will not
severity: major
claim: "**the segment→text contract, stated** (R2-9): `committed` is **cumulative across segments** and the tail is **promoted into it on commit**, so the grey never disappears or repeats"; `shared/voice-types.ts`: "`committed` will not change again"; contract **R2**: "the newest few show grey until they **settle**, then turn solid."
evidence: R2-9's fix makes `committed` stable *across* segment boundaries and says nothing about stability *within* an open segment — and within a segment every pass re-decodes the whole thing (R1-7: `OfflineStream` has no incremental mode). Nothing constrains a re-decode to leave its prefix alone. Measured it with the round-1 rig against the real pinned model (`sherpa-onnx-nemo-parakeet-tdt-0.6b-v3-int8`, 4 threads, growing 1-second prefixes of a real utterance, then comparing pass *k*'s `committed` — "all but the last two words", the design's own split — against pass *k+1*'s prefix):

```
 1s | And so
 2s | And so my fellow American
 3s | And so, my fellow Americans.
 4s | And so, my fellow Americans ask
 5s | And so, my fellow Americans, ask not
…
2s -> 3s : CHANGED
    was: And so my
    now: And so, my
```

One rewrite in ten transitions on a clean studio recording. The churn is punctuation, which is exactly what Parakeet TDT v3 adds and exactly what later context decides: "American" → "Americans." → "Americans," all happened while that word sat behind the two-word grey tail, i.e. in solid black text. Hesitant real-world dictation gives the model more to revise, not less.
consequence: R2 is `checkedBy: deck` and grades pass/fail on precisely this transition — Destin will be watching solid text and will see commas appear and disappear in it. `InputBar.tsx:129` `setText(voiceBaseRef.current + committed)` replaces everything after the base on every partial, so a rewrite is rendered immediately and silently. And the guard the design lists cannot catch any of this: `voice-rehear.test.ts` drives "a scripted fake recogniser", which by construction returns prefix-stable text, so the suite will be green on a promise the real engine breaks.
fix: decide which promise survives and write that one down. Either widen the grey window so it covers what actually moves (hold back the last N words *or* everything since the last full stop — the measurement above says punctuation revisions reach at least three words back), or drop the "settled words never change" wording from `voice-types.ts` and take a corrected R2 sentence to the acceptance deck, since it is a promise to the user and the copy is Destin's. Whichever is chosen, `voice-rehear.test.ts` needs one case driven by *recorded real output* (the ladder above is 11 lines of fixture) rather than a scripted fake, or the guard guards nothing.
disposition: accepted — and it is a REOPEN, not a build decision: measured against the real model, solid text gains and loses commas, so the approved R2 sentence is not true of the engine we chose. Destin decides on a decide deck BEFORE the build (widen the grey window, or change the promise); voice-rehear.test.ts gains a case driven by recorded real output, since a scripted fake is prefix-stable by construction and can never catch this.

### R3-4 R2-11 made only the readiness half desktop-only: the start path still opens a microphone the Android WebView auto-denies, and reports it in the desktop's words
severity: major
claim: "**Readiness composition is desktop-only** (R1-4, R2-11)… **On Android `status()` is authoritative** and nothing is composed, or the phone would be told 'No microphone was found on this **computer**' while its recogniser works" — alongside, with no platform qualification, "`open()` calls `getUserMedia(…)`", "A start-time `NotFoundError` / `NotAllowedError` becomes `setReadiness({state: 'unavailable', reason})`… access `denied` → V-8 verbatim", and "**Phase flips to `listening` only after `open()` resolved** (R1-4)".
evidence: the composition rule got a platform gate; the capture rule did not, and both live in the one hook the Android WebView runs (`react-renderer.md`: the renderer runs in BOTH surfaces). `getUserMedia` is not a bridge method, so the design's "the renderer calls only what is present" test does not cover it. In the Android WebView it fails by default: the only `WebChromeClient` in the app is `ui/WebViewHost.kt:145`, and it overrides `onConsoleMessage` and nothing else (`rg -n 'onPermissionRequest|WebChromeClient' app/src/main/kotlin` → one hit, that one). A WebView whose chrome client does not override `onPermissionRequest` denies every media request, so `getUserMedia` rejects with `NotAllowedError` — before `RECORD_AUDIO` is even reached, and independently of R1-3's manifest fix.
consequence: the design's own mapping then prints V-8 on a phone: "Microphone access was refused by **your computer**. Allow it for YouCoded in **your system's privacy settings**, then check again." Wrong verdict, wrong noun, no way to act on it — the identical failure R2-11 was filed and accepted to remove, arriving through the door that fix left open. And because "phase flips to `listening` only after `open()` resolved", the strip never appears, so contract **R6** fails on every phone even after R1-3 and R1-10 land.
fix: gate the capture the same way the composition is gated — one sentence saying `voice-capture.open()` runs only where the bridge offers `sendAudio`, that on Android `start()` is the bridge call alone and the phase flips when it resolves, and that the start-time `NotFoundError`/`NotAllowedError` mapping is desktop-only. Add the Android start path to `useVoiceInput.test.ts` beside the readiness split that is already listed there.
disposition: accepted — the capture is gated the same way the composition is: `voice-capture.open()` runs only where the bridge offers `sendAudio`; on Android `start()` is the bridge call alone and the phase flips when it resolves; the NotFound/NotAllowed mapping is desktop-only. The Android start path joins useVoiceInput.test.ts.

### R3-5 `net.fetch` has no `err.cause`, so R2-10's two halves cancel: the fix that finds the reason is paired with a rule that throws it away
severity: major
claim: "**`net.fetch`, not global `fetch`** (R2-10), so system proxies are honoured, and `err.cause` is unwrapped into the message — Node's `fetch` reports a corporate proxy and an offline machine identically as 'fetch failed'… **Where no cause survives, the card is `<ErrorState mode="general">`**."
evidence: `err.cause` is undici's shape, not Chromium's. Electron's `net.fetch` rejects with the `ClientRequest` error object untouched — `lib/browser/api/net-fetch.ts`: `r.on('error', (err) => { p.reject(err); })`, with no `cause` set anywhere in that file. So on `net.fetch` the cause is *always* absent, the unwrap step is dead code, and the stated fallback fires on **every** transport failure — discarding whatever Chromium put in `err.message`, which is the one thing `net.fetch` was adopted to obtain. Two smaller consequences of the same swap, neither stated: `net.fetch`'s signature is `fetch(input: (string) | (GlobalRequest), init?: RequestInit & {bypassCustomProtocolHandlers?: boolean})` (`node_modules/electron/electron.d.ts:10132`), which is **not** assignable to `engine-acquisition.ts:39`'s `private fetchImpl: typeof fetch` — `typeof fetch` accepts a `URL`, `net.fetch` does not — so this is a real fork in the "exact shape", not a drop-in; and `net` "can be used only after the application emits the `ready` event", which a download triggered from a user tap always satisfies but which the design should not leave to luck if anything ever pre-warms.
consequence: the design believes it has bought a specific reason for the failure that costs students and office workers their download, and has instead guaranteed the reasonless card for all of them — including the plain offline case, where the honest sentence was one property away. Contract **R12** ("the reason on that card is always the one the computer reported") is the promise being spent.
fix: state the shape that matches the API actually chosen: `net.fetch` rejects with an error whose `message` is the reason — surface `err.message` verbatim as the card's detail, keep `err.cause` only as a fallback for whatever path still uses Node's `fetch`, and reserve `<ErrorState mode="general">` for a failure with no message at all. Say that `voice-assets.ts` declares its own fetch field rather than reusing `engine-acquisition`'s `typeof fetch` slot.
disposition: accepted — `net.fetch` rejects with the reason in `err.message`, so that is what the card shows verbatim; `err.cause` stays only as a fallback for a path still on Node's fetch; voice-assets declares its own fetch field rather than reusing engine-acquisition's `typeof fetch` slot.

### R3-7 R2-15's blur guard is keyed on `spaceHeld`, which is false for the 250 ms in which the leak actually happens
severity: minor
claim: "**Space-hold releases on more than key-up** (R2-15): `blur` on the textarea and `window` `blur` / `visibilitychange` **while `spaceHeld` is set** also stop the mic, or an alt-tab mid-hold leaves it open until the silence stop inserts text nobody asked for."
evidence: `spaceHeld.current` is not set when the key goes down — it is set 250 ms later, inside the timer callback, one line before the mic starts (`InputBar.tsx:838-841`: `spaceHoldTimer.current = window.setTimeout(() => { spaceHoldTimer.current = null; spaceHeld.current = true; startVoice(); }, 250)`). A guard conditioned on `spaceHeld` therefore does nothing during the hold's first quarter second — and that is a live window, because the timer is not cancelled by losing focus either: `onKeyUp` is on the textarea (`:866-870`) and is the only place that clears it.
consequence: press Space in an empty box and Alt-Tab within 250 ms — the timer fires in the background, the mic opens with focus elsewhere, no key-up ever reaches the textarea, and the blur that already happened was ignored because `spaceHeld` was still false. The mic stays open until the two-second silence stop, which then inserts whatever the room said into the box. That is R2-15's own consequence sentence, reproduced by its fix.
fix: the guard's condition is "a space-hold is in flight", not "`spaceHeld` is set": on blur/`visibilitychange`, clear `spaceHoldTimer` **and** stop if `spaceHeld`. Add the second case to the `InputBar.test.tsx` line that already lists "focus leaving mid-hold stops the mic": focus leaving *before* the 250 ms elapses must leave the mic closed.
disposition: accepted — the guard's condition is 'a hold is in flight': on blur and visibilitychange, clear spaceHoldTimer AND stop if spaceHeld; the before-250 ms case joins the InputBar test line.

### R3-11 This is the app's first `.tar.bz2`, and the unpack step it inherits verbatim is documented — and was verified — for `.zip` and `.tar.gz` only
severity: minor
claim: "`voice-assets.ts` — acquires both halves … in `engine/engine-acquisition.ts`'s shape … **Two changes to that shape, both stated rather than inherited**" (the two being `net.fetch` and the verifier); and "`sherpa-onnx-nemo-parakeet-tdt-0.6b-v3-int8.**tar.bz2**"; and "`unpacking` (bzip2 is single-threaded; half a gigabyte takes tens of seconds)".
evidence: the inherited unpack is one line, `execFileAsync(systemTar(), ['-xf', archivePath, '-C', partialDir])` (`engine-acquisition.ts:148`), under a WHY comment that enumerates what it was verified against: "System bsdtar handles BOTH shapes: .zip (Windows builds) and .tar.gz — no unzip dependency to bundle." bzip2 is not in that list, and it is not free the way gzip is: **GNU tar delegates bzip2 to an external binary**. Measured on this machine (`tar (GNU tar) 1.35`): `tar -xf t.tar.bz2` succeeds normally, but with the compressor hidden it fails with `tar (child): lbzip2: Cannot exec: No such file or directory` / `Error is not recoverable`, exit 2. Two knock-ons the design states as fact: the "single-threaded, tens of seconds" figure is wrong on any machine where tar picks `lbzip2`/`pbzip2` (this one), and `systemTar()`'s Windows branch — System32's bsdtar — is a build the repo has only ever exercised on `.zip` and `.tar.gz`.
consequence: on a Linux machine without a bzip2 implementation, a 487 MB download completes, verifies, and then fails at the unpack with a tar child-process message; the failure costs the whole download because it is discovered last. On Windows it is unverified rather than wrong — but "unverified" in the one step where a wrong guess has already burned this repo once (R2-3's `engine-pin.ts` stale-layout precedent) deserves a sentence, not silence.
fix: name the unpack as the **third** stated change to `engine-acquisition`'s shape rather than letting it ride as inherited: say which decompressor is used, run the one-line check on each platform before the build starts (`tar -xf` a small `.tar.bz2` on Windows' System32 tar and on a bzip2-less Linux container), and either commit to `systemTar()` with a checked failure message or decompress bzip2 in-process. Fix the "single-threaded" sentence, which is a property of `bzip2(1)`, not of the format.
disposition: accepted — the unpack is named as the THIRD stated change to engine-acquisition's shape: the decompressor is checked on each platform before the build starts, with a checked failure message, or bzip2 is decompressed in-process. The 'single-threaded' sentence is corrected (that is bzip2(1), not the format).
