# Website analytics — technical design

Historical design; see the [rollout closure record](../design/2026-09-14-site-marketing-analytics/README.md) for final authorization, delivery state and verification limits. Original gates below record the design stage, not a new approval request.

## Authority and scope

Implements [the signed contract](../design/2026-09-14-site-marketing-analytics/site-analytics.contract.json), R1–R15. `site-analytics.contract.answers.json` records C = yes, submitted 2026-09-15; the requester also records chat approval to build. This document is the technical proposal, not evidence of implemented behavior or acceptance. Companion: [implementation plan](../plans/2026-09-15-site-analytics-implementation.md).

Use the existing marketplace Worker and D1 for **daily aggregates with page snapshots in the same 90-day history**. Do not use Analytics Engine for website measurements. No app telemetry, device-hash, IPC, theme/embed, release, or download behavior redesign. No paid evaluation, deployment, credential inspection, or public activation is authorized by this documentation task.

Startup preserved this session rather than merging its 20 incoming workspace commits. Relevant incoming landing guidance adds generated per-theme embed posters and `whenEmbedPainted()`; analytics must not change that lifecycle. Other incoming work concerns first-run/model-picker/permission-card work. The complete startup inventory and relevant guidance diff were inspected; no integration was performed.

## Existing seams and choice

- `wecoded-marketplace/worker/src/index.ts`: Hono routes, strict/public-read CORS dispatch, daily maintenance. Website ingestion needs its own narrow branch, not a broadening of authenticated CORS.
- Worker `wrangler.toml`: existing `DB`, `APP_ANALYTICS`, custom `api.youcoded.ai` domain and still-enabled legacy workers.dev host. `src/lib/rate-limit.ts` is a non-atomic Cache API counter. Older worker-backend guidance says the custom domain is absent; current configuration contradicts that historical statement. Neither configuration nor per-colo caching proves an effective global abuse limit.
- `src/admin/analytics.ts`, `auth/admin-middleware.ts`, `auth/admin.ts`: reuse authentication and owner authorization, not the app's AE queries or dimensions.
- `youcoded-admin/skills/analytics/dashboard/{index.html,website.mjs,website-helpers.mjs,server.mjs}`: approved Website/App preview, daily row helper, copy builder, credential-holding loopback proxy. Production proxy currently excludes `website`; fixtures alone answer that request. Existing helper accepts arbitrary trimmed labels up to 160 characters.
- `youcoded/docs/index.html`: `openModal`, `downloadKeyFor`, `resetDownloadButton`, and final `downloadBtn` click handler are the integration points. The modal can point to the releases list when an installer cannot be resolved. iOS has no download. Existing Mac GPU detection is for selecting an installer: analytics must neither invoke it nor send its result as a device dimension.

**WHY D1:** adding cumulative maxima and their deltas in one database transaction produces exact integer visit counts and once-per-visit outcomes for accepted journeys, without keeping a 90-day event trail. AE's sampled event stream and weighted sums do not establish exact deduplicated page outcomes; no proof for exact distinct counts/ratios exists here. Reusing app AE or approximating distinct visits would change the approved metric. D1 reuses a binding and migration/test pipeline, with no new analytics subscription. It is not a claim that usage is free: allowance, request cost, row reads/writes, indexes, storage and backup retention remain activation gates.

## Measurement semantics (R1–R3, R7–R8, R10–R14)

| Value | Definition |
|---|---|
| Visit | One accepted top-level landing document load, random page-only identifier; reload and a second tab create new visits. Not a person, session across pages, or app device. |
| Instructions opened | Number of visits whose install instructions were opened at least once, not number of modal opens. Count the visible iOS information modal too; it cannot produce an installer click. |
| Download clicks | Every accepted final installer-link activation, including repeats after reopening/changing variant. Not card opens, release-list fallback navigation, download completion, or installation. |
| Clicked visits | Visits with at least one accepted installer click across all target platforms. |
| Visits’ click rate | Sum(clicked visits) / sum(visits), never clicks / visits, never average of row percentages; zero visits displays an em dash. |
| Platform | Installer target: Windows, macOS, Linux, Android. Mac architecture and Linux package variants collapse to these four. No inferred visitor OS, GPU, geography or device field. |

All outcomes belong to the visit's initial UTC date, even when a later click crosses midnight. Counts remain provisional while those visits can update. “Three months” means the approved 7/30/90-day controls and a rolling **90 UTC-date window including today**, not calendar-quarter or year retention. Query cutoff applies even if pruning is late. New measurement cannot reconstruct historical traffic.

Date, source and campaign filter all website totals, trend, campaign table and platform breakdown. Platform filters **only** the platform breakdown, not totals, rates, trend or campaign table. Preserve the approved helper's share denominator: selected platform rows divided by their selected total (one nonzero selected platform shows 100%). All-platform shares divide by all platform clicks. Keep App filters and geography restrictions unchanged.

Client page state persists only in JS memory, including through back/forward cache restoration of the same document. Never write a journey identifier to cookies, localStorage, sessionStorage, URL, service worker, IndexedDB or app state. No background recovery after reload. One document remains one visit until close/reload while its original visit day is retained; once that day leaves the 90-day window, stop measuring rather than create another visit.

**Reviewer wording check (R3):** “without identifying unique people or tracking them across days” means no persistent returning-visitor identity across days, reloads or documents. It does not mean the server cannot correlate updates from the same still-open page across midnight. The server needs a page nonce and cumulative snapshot for exact once-per-page counts and retry deduplication, not a persistent browser identity. Policy must state this distinction explicitly; the removed short cutoff was a self-imposed constraint, not a signed requirement.

## Attribution and owner-created links (R5–R7, R15)

“Approved labels” means **source/campaign pairs explicitly registered by the owner through Copy link**. There is no public registration and no per-campaign deployment.

- Retain the builder's fixed `https://youcoded.ai/` destination and live `utm_source` / `utm_campaign` preview. Validation is identical in builder, proxy and Worker: trim; each label 1–160 UTF-16 code units and at most 640 UTF-8 bytes; reject control characters (including DEL/C1), unpaired surrogates, and reserved display sentinels. Preserve case and punctuation, including `/#?`, through URL encoding; do not invent a slug restriction that breaks the approved helper. Recommend non-personal post names in the hint.
- `POST /admin/analytics/website-campaigns` registers the exact pair idempotently, under existing admin auth plus owner allowlist. Unique pair, immutable labels, server timestamp. Initial total capacity is 1,000 registered pairs, configurable rather than permanent exhaustion; retain 30 new pairs per UTC day. Document the increase path: review storage/cost, raise the validated capacity setting through an authorized configuration change, and verify registration above the old limit without changing existing pairs. At capacity, refuse only new pairs with an actionable capacity message; idempotent registration of existing pairs still succeeds. Registry metadata is owner configuration, not visitor history; keep it so old shared links work without redeployment. Campaign results still disappear after 90 days; zero-traffic registry entries do not populate report filters.
- Copy link captures the pair and initiates a promised `ClipboardItem` write during the user gesture where supported; resolve its text only after successful registration. Do not await registration and assume clipboard activation survives. On unsupported/failed clipboard access, successful registration exposes the frozen link with a second explicit Copy action and selectable manual-copy fallback. Registration failure never reports ready/copied. Live preview remains instant; edits during registration cannot change the captured link. Test delayed registration, both clipboard paths and failure states.
- Ingestion accepts only exact registered pairs. Invalid, missing, duplicate or unknown UTM pairs become untagged; never persist rejected label text. Other query parameters and the full landing URL are never submitted. The pair is frozen on initial load, so sharing a labeled link elsewhere retains its original campaign.
- Parse `document.referrer` locally; send only a lower-case hostname. Reject IP literals, localhost/private names, credentials, ports, paths, query/fragment syntax and invalid DNS names server-side; strip trailing dot, canonicalize IDN with URL parsing. Store no full referring URL. Same-site or missing referrer becomes empty. Bound hostname bytes to 253.
- Store campaign source separately from `referrer_domain`. Display/filter source is registered source when tagged, otherwise referrer domain, otherwise `Direct / unknown`. Do not replace a carried campaign label with its new referral site. Retain the independent referring-domain dimension for provenance; do not add an unapproved referrer drilldown UI.
- Bound referrer cardinality to 128 admitted domains per day; subsequent new domains map to `Other referring sites`. Bound aggregate cells to 1,000/day, rejecting new cells beyond that rather than merging different campaigns. Allocation must be transactional. Record only aggregate rejection counts and disclose collection limits, not fabricated visit totals.

## Public protocol and exact updates

New routes: `POST /site-analytics/start` and `POST /site-analytics/update`. Only schema version 1 is accepted. These are cumulative page snapshots, not an arbitrary event bus.

Start body: version, cryptographic 128-bit random page nonce, page-created Unix time, candidate source/campaign pair, referring hostname, instructions boolean, and four cumulative nonnegative integer download counts. Update body: version, signed page capability, instructions boolean and the same counters. Unknown fields are errors. Client time is used only for the replay admission window; server time sets the reporting day and expiration. Initial page-created time must be within five minutes of server time; a skewed clock loses measurement, not functionality.

On accepted start, derive the snapshot `pageKey = HMAC(server secret, "site-analytics:page-key:" + raw nonce)` and persist only that irreversible key; the raw random nonce remains only in client memory and transient request processing. Return a server-signed capability binding pageKey, admitted attribution, server start/day and expiration—never the raw nonce. Use a new server-only HMAC secret; never ship signing keys or admin credentials. A retry derives the same pageKey, returns the same capability/immutable attribution and cannot insert another visit. Start lookup must check the original five-minute admission window before creating any missing record. A duplicate start cannot mutate dimensions or extend expiration. After five minutes the client cannot restart admission; abandon failed starts. A valid update must find its original snapshot: **never upsert a missing update into a new visit**.

Snapshot lifetime: retain within the same rolling 90 UTC-date history as aggregates. Capability expiry is the UTC boundary when the original visit day leaves that window; no refresh-on-use. Accept updates while that day is retained, including across midnight and beyond one day. Once expired, return 410 and stop the client, never start a replacement visit. Maintenance deletes expired snapshots and aggregates. A pruned nonce cannot be resurrected by an old start because its original timestamp is outside five minutes, or by an update because updates cannot insert. A malicious fresh nonce represents fabricated traffic; idempotency is not bot authentication.

Each snapshot holds only the derived pageKey, frozen cell key, start/expiry, instructions boolean and four counts. The raw nonce is forbidden from database storage, logs and capabilities; no event log exists. The derived key is scoped to one page and retention window, not a person or cross-page identity; its use does not claim that hashing removes all correlation. Merge each counter with `max(old, incoming)` and instructions with OR. Derived clicked flag is `sum(downloads) > 0`. Per-page cap: 100 total final clicks; enforce this on both the incoming vector and the merged maxima inside the transaction (conflicting reordered vectors must not bypass the cap). Reject excess snapshots, never silently clamp while claiming full counts. Duplicate and reordered snapshots converge; repeated actual clicks increment the local cumulative counter, whereas transport retries resend it unchanged.

Use SQLite **AFTER INSERT / AFTER UPDATE triggers** in the new D1 migration to add visit/outcome/platform deltas to the daily cell in the same atomic SQL statement as the snapshot insert/update. UPDATE fires only when a maximum actually advances. A trigger or quota failure rolls back both snapshot and aggregate; never read old values in JS and later write an independent delta. DELETE of an expired snapshot must not subtract retained aggregate counts. Parameter-bind values and enforce schema CHECK constraints. Test D1 trigger support, rollback and concurrent duplicate starts with the actual Workers test pool before implementation is accepted.

Client sends start once on load, then changed cumulative snapshots with a 250 ms coalescing window, at most one request in flight. Keep only the latest pending state; on success send any newer state. Each attempt has a finite 8-second deadline covering fetch and response reading: abort on timeout, release the single-flight slot even if transport never settles, and ignore late completions using an attempt token. Retry the same nonce/capability and cumulative snapshot at most twice with backoff; retain newer pending state for the next send. At most 128 send attempts/page, never a timer heartbeat. Test never-settling transport, late replies, retry exhaustion and lost start/update acknowledgments after server commit; retries must not duplicate counts or discard newer state. Final click/visibility-hidden uses bounded `fetch(..., {keepalive:true, credentials:'omit', referrerPolicy:'no-referrer'})`; no unload blocking or dependency on delivery. A later cumulative update repairs a missed earlier outcome. No-JS, blockers, aborted requests, bots, and limits affect coverage: “exact” means exact aggregation of accepted snapshots, not complete human traffic.

## Storage, security and cost gates

New migration tables: `site_campaigns`, `site_journeys`, `site_daily` (day + campaign pair ID/untagged + admitted domain; visits, instructions, clicked visits, four click integers), `site_daily_domains`, and small day-level budget/health rows. Index journey expiry and daily date/dimensions. No joins to accounts, app identifiers, or geographic tables; campaign registration authorization does not become a visitor dimension.

`SITE_ANALYTICS_ENABLED` must equal `"1"`; absent/other values mean OFF. Commit production default `"0"`. OFF routes stop before parsing bodies or touching D1; existing reports may remain readable with explicit disabled status. Public host must be exactly `api.youcoded.ai`, HTTPS; reject the legacy workers.dev host for these routes only. Require exact `Origin: https://youcoded.ai`, reject absent/null/alternate origins and credentials, no public query parameters. Site-specific OPTIONS allows only POST and Content-Type with no credentials. Do not rely on CORS alone: enforce inside handlers. Local test origins exist only in test configuration.

Require JSON, streaming body cap 4 KiB even without Content-Length, exact fields/types, finite safe integers, bounded capability length and constant-size counters. Reject arbitrary event names, raw URL, UA, IP, geography and device fields. Do not echo rejected bodies or secret-bearing errors. Catch website route failures before the global error logger can print payload/SQL-bound values; log only fixed error codes and aggregate counts. Requests use a constant URL and `no-referrer`; credentials stay in server-side signing configuration and the existing owner proxy.

Use edge abuse controls on the custom domain as the first request-volume defense, and transactional D1 daily budgets as a second bound: initially 10,000 accepted starts, 50,000 state-changing updates, 1,000 cells and 128 domains per UTC day. Quota checks and reservations belong in the same transaction/triggers as changes; duplicates consume no state-change quota. Closed budgets reject without further row writes. Cache/per-colo counters may shed load but are not correctness or billing guarantees. Forged Origin and fresh nonces remain possible. Rejected requests still incur Worker/read costs: these caps alone are **not a monetary ceiling**.

Before enabling, owner must approve a recorded account-specific allowance/cost estimate, edge rate-rule availability/effectiveness and budget alerts. Verify limits on the custom domain in an authorized isolated environment, not production. Estimate workload from starts + changed snapshots, including trigger/index writes and read scans; measure D1 `meta` row counts on a seeded local workload rather than assuming one write per request. Budget denial is a collection gap, never a zero-traffic conclusion.

Use the existing daily maintenance schedule for website cleanup: DELETE journeys, daily aggregates and day/domain/budget rows older than the same 90-date cutoff. Queries and updates enforce that cutoff independently of cleanup. Track sweep success and non-identifying rejection/budget status; alert and recover failed cleanup. **D1 has no proven automatic per-row TTL here:** scheduled deletion can be delayed by an outage. Before activation, verify cleanup/recovery and document Cloudflare backups/Time Travel and observability retention. Policy must distinguish the 90-day retention of all website analytics records in the active database from provider backup expiry and operational deletion delays; do not promise instantaneous physical deletion or an unverified backup deadline. No separate sub-day retention gate or hourly infrastructure is required.

## Dashboard API, privacy and remaining review

`GET /admin/analytics/website` requires `requireAdminAuth` and `requireAdminAccount`. Return schema version, current UTC `end`, retention/collection start, enabled/health status and daily aggregate rows matching `summarize`: `day, source, campaign, referrerDomain, visits, instructions, clickedVisits, downloads`. Platform keys match the existing UI (Windows, macOS, Linux, Android). No raw journey endpoint, even for admins. Query only the retained window. Cap rows at 90,000 by the cell budget; use keyset pages of 1,000 with a fixed end date and key ordering, never truncate silently. Dashboard loads all pages before rendering and rejects failed/incompatible pages; concurrent active-day updates are provisional, not a frozen multi-request snapshot. Start a fresh full load on Refresh.

Extend the loopback proxy only for GET website and POST website-campaigns, with bounded params/body and methods. Keep upstream credentials server-side; reject unexpected Host and cross-origin writes, require same-origin JSON and a per-process CSRF token for registration. Bind 127.0.0.1; no generic authenticated passthrough. Use no-store responses and safe errors. Preserve preview fixtures as preview-only and add local fake registration for review tests; never call production from a fixture.

Website UI validates integer rows and invariants before rendering: instructions/clickedVisits <= visits, clickedVisits <= total clicks; unknown platform keys rejected. Loading, empty, disabled, validation failure and server failure are distinct. Reuse existing error/status presentation; known HTTP status may be shown under Technical details with Retry, but never infer “expired login”, “offline” or “no visitors” from an unknown failure.
