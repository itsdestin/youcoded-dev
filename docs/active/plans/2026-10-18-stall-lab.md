# Stall impact measurements and performance-lab coverage

## Authorized outcome

Measure hardware detection, XLSX, HTML, CSV, DOCX, large path lists and watcher startup; improve the existing performance lab so these workloads and measurement blind spots are not silently omitted. Preserve the already verified viewer/diff/index fixes. This phase changes lab tooling, not the remaining production behaviors merely because a stress case exposes them.

## Confirmed lab gaps

- `scenario-artifacts.mjs` currently exercises code, Markdown and self-contained HTML, with a 400000-byte large fixture. It does not establish XLSX/DOCX/CSV or asset-heavy HTML coverage.
- `attributeStall` currently declares main blocked from low renderer long-task time. The session's actual legacy diff control blocked rendering/input for 11.7s while that observer reported zero. Absence of a long-task entry is not proof of an idle renderer.
- Renderer-started IPC pings do not record time before their callback runs. A renderer block between pings can therefore leave fast round trips; scheduling delay needs its own signal.
- Build fingerprinting documents a hole for content changes inside already-untracked directories. New fixture/probe code must not silently reuse stale builds.

## Measurement contract

Every case records: case ID, workload shape, exact fixture bytes/hash, target/runtime/build provenance, first-use versus repeated-use state, operation outcome, operation duration, renderer timer/frame delays, IPC round trips, independently observed main-loop delay where available, input-response evidence, and memory peak. 2. Add reusable independent loop sampling, with initial-tick and ongoing-gap accounting. Validate with no-op, known main block, renderer block (including the long-task-observer blind spot), and slow-but-nonblocking controls. A control that is not detected invalidates the run.

5. Wire the new scenarios through existing run/report/comparison validation and document exact coverage. Preserve individual severe samples; a median must not erase a single long freeze. Reports distinguish measured budget breaches from lab/probe failure.
6. Run bounded smoke ladders first, then increase only where memory/time headroom permits. Record actual impact and prioritize remaining app fixes from results, without quietly changing the app during the measurement pass.

### Document adapter revision 2 (implementation; runtime acceptance pending)

The adapter/report/CLI share `DOCUMENT_CONTROL_TYPES` in `scripts/perf-lab/document-input.mjs`: noop, renderer-block, main-block, slow-async, and a fifth renderer-congestion control. Renderer-block now waits asynchronously for 200 ms before a 400 ms synchronous block, exercising input coverage after file-wait-like latency without adding a redundant sixth control. Congestion uses 24 bounded ~30 ms tasks separated by yields; calibration requires aggregate timer excess and multiple late inputs as well as observed short-task work, not merely one task exceeding 50 ms. Opposite-thread negative controls distinguish main-loop blocking from renderer-loop blocking. Thresholds are instrument calibration policy, not yet validated on this machine in this revision.

Input is an independently scheduled inert F24 train from before action through readiness plus a bounded tail (50 ms slots, at most 256 samples / 12 seconds / 16 outstanding keydown commands, followed by one keyup). Controller stalls/backpressure skip slots without catch-up bursts; skipped, missing, overflowed or exhausted coverage fails closed. Ordered tokens correlate raw controller planned/actual/ack times with captured trusted DOM receipts and the unique active session. Pre/post monotonic clock exchanges retain offset brackets with a declared 1 ms drift allowance and at most 25 ms alignment error; a latency interval crossing the 250 ms budget is inconclusive, never silently healthy. `input.latencyMs` is retained as the conservative upper bound of controller-dispatch-to-DOM routing, including browser/main routing, **not** renderer-only delay. Epoch subtraction fields cannot honestly be retained and are replaced by raw monotonic timings and bounds.

Loop probes add constant-space `totalExcessMs` and `delayedSamples` for sub-50 ms congestion. Timer excess is not CPU busy time; IPC `totalStallMs` remains a sum of completed round-trip excess, not union elapsed blocking or inferred main-thread occupancy. Required finite metrics, stopped probes, full input coverage, build provenance and shared five-control discrimination are rechecked by reports. Revision-1 document baselines are incompatible and must be remeasured. Source hashes use the executed checkout; the executable path and owned main identity must agree with the runner build, build stamp and current source fingerprint. The existing stamp does not attest packaged bytes, a separate stated limitation. Per-measurement independent cleanup attempts every acquired resource, preserves primary and cleanup errors, and a cleanup failure stops the owned boot. No runtime launch, rebuild or stress run is part of this implementation verification; bounded runtime acceptance still needs independent safety review and parent authorization.

### Result semantics

- **Healthy:** valid evidence and the applicable, declared budgets passed.
- **Measured but slow:** valid evidence with preserved budget breaches.
- **Measurement failed/incomplete:** expected samples, completion, clocks, provenance or cleanup evidence were not established.
- **Not covered/unsupported:** named capability or workload was not measured, with its reason.

A completed command is not proof of a successful experiment. Summed RSS is a conservative process-family safety measure, not unique physical memory or proof of a leak. Natural and forced-GC trajectories stay separate. rAF and two-frame waits are scheduling evidence, not physical display timing. Hardware-virtual presentation does not establish scanout, and whole-system/domain power is not attributable app watts.

## Safety and acceptance details

Each risky case has an external wall-time watchdog and bounded memory growth, outside the process being exercised. Kill only the rig-owned family; a failed cleanup stops further launches. Limit generated expansion as well as compressed bytes. Invalid input, wrong viewer, missing samples, observer failure, timeout and process exit cannot be credited as fast performance.

Use current fixture/runtime identities and record background load. Default virtual-display results are software-rendering evidence, not proof about the production GPU/compositor. All added unit tests use deterministic clocks/data; runtime budgets are measured policy outcomes, not flaky wall-clock unit assertions.

Acceptance: lab tests and calibration controls pass; performance breaches remain visible rather than being tuned away; relevant workspace tests/anchor audit and app checks for any touched app tooling pass. An explicit unavailable/unsafe reason is required for missing evidence, but does NOT by itself satisfy completion of a required capability. No merge or installed-app change is authorized by this plan.

### Mandatory candidate-comparison workflow

- A short documented entry point accepts two explicitly identified app candidates and runs the same selected workload/measurement configuration against both. Head-to-head means a fair comparison, not simultaneous competing stress runs.
- Provide a quick targeted iteration path and a full acceptance path, with preflight identifying prerequisites, expected work and bounds. Reuse verified unchanged builds/fixtures instead of rebuilding unnecessarily; no bespoke scripts or manual report assembly for ordinary reruns.
- Record exact candidate/build identities, instrument revision, workload/fixture identity, machine/platform context, repetitions and raw samples. Incompatible runs must be marked incomparable, never silently ranked.
- Produce one readable comparison showing both values, absolute/relative changes where meaningful, variability, worst cases, regressions, improvements and inconclusive/missing results. Link the evidence; do not hide a required measurement behind one aggregate score.
- Allow changing a candidate and rerunning a chosen workload without losing earlier results. Changing the instrument or fixture requires matched remeasurement rather than comparison against stale evidence.
- Demonstrate the workflow with two isolated candidates, an unchanged-candidate repeat to expose noise, and known-change controls proving detection. Record observed run duration; do not promise a timing target before measuring it.
- Completion includes reviewed code, executable concise instructions, preserved provenance/results and a verified practical rerun experience—not merely standalone diagnostic modules or passing unit tests.
