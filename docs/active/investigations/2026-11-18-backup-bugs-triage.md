## Part 1. The four decided items

### Shared facts that matter for items 1 and 2

- **The phone has no backup code of its own.** `app/src/main/kotlin` has no sync/backup file (`git ls-tree origin/master -- app` lists none). The phone runs the same Node backend as the computer (`main/headless/headless-boot.ts:293` `new SyncService()`, `:302` `startSyncSpaces(...)`). The stale comments that say "the phone app's own backup service (SyncService.kt pushGithub)" (`SyncSetupWizard.tsx:16-18`, `:216`) and "on Android, rclone is bundled in Bootstrap" (`sync-setup-handlers.ts:154`) describe the old native-Kotlin era. CONFIRMED.
- **The phone's runtime has neither `rclone` nor `gh`.** The packaged Linux runtime's package list (`app/runtime/alpine-lock.json`) has git, nodejs, bash, ripgrep... and no rclone, no gh, no rsync; `rg rclone app/` returns nothing. CONFIRMED from the lock file; UNVERIFIED on a real device.
- **The backend cannot tell it is on a phone from `process.platform`** (it says "linux"; see the WHY at `headless-boot.ts:304`). A backend-side guard therefore needs an explicit flag passed from `headless-boot.ts` (it has no way to know otherwise). The renderer does know: `isAndroid()` (`renderer/platform.ts:65`), `isRemoteMode()` (`:117`), and `deviceNoun() === 'phone'` (= Android app AND talking to its own backend, `:79`).
- **Important correction to the review's story for item 1.** The review says a phone user "picks GitHub, signs in, makes a repo, taps finish". On a phone the wizard's prerequisite step needs `gh` (`SyncSetupWizard.tsx:639-640`, `:673`); with no `gh` in the runtime the user is stuck on "GitHub tools: missing" with an install button that cannot work. So on a current phone the false "finished" most likely cannot be reached through the wizard. The lying-success code path is real (below), but the more likely experience is a dead end, and any phone user who really has a GitHub or Drive entry probably got it from the old native-Kotlin app (migrated config). UNVERIFIED on a device. This does not change the decision (hide), only the wording of what existing users see.

- `sync-setup-handlers.ts:156-196` `installRclone()`: `win32` winget, `darwin` brew, **everything else** (including the phone) `bash -c 'curl -fsSL https://rclone.org/install.sh | sudo bash'` (`:183`). No Android branch. The wizard offers Drive on every platform (`SyncSetupWizard.tsx:215`), the prerequisite step shows "Cloud sync tool: missing" with an Install button (`:691`, `:711`), and a failure shows the raw error plus "Install manually" (rclone.org, `:737`).
- **Every place the UI offers it:** (a) wizard type picker `:215`; (b) **the inline picker in the Backup & sync card** `SyncPanel.tsx:1657-1676`: two buttons, "Google Drive" (`:1661`) and "iCloud" (`:1669`), shown whenever the "Keep a second copy" switch is on and there are no destinations. This one is not gated at all and also offers **iCloud on a phone and on Linux** (the wizard's own picker hides it there, `SyncSetupWizard.tsx:~228`). (c) the "Add a backup" button (`:1689`) opens the wizard picker; (d) failure warnings with "Sign in again" / "Reconnect Google Drive" (`sync-error-classifier.ts:~120-135`); (e) the `RCLONE_MISSING` warning's "Install rclone" opens rclone.org (`:307-319`), useless on a phone; (f) `sync:setup:install-rclone` is a channel open to a phone (`ipc/sync.ts:94`, `tests/sync-channels.test.ts:63` pins "all open to a phone"). A phone paired to a computer, or a phone's web browser, drives the **computer's** rclone, so Drive must stay available there.
- **Gate to use.** "Drive works here" = not (`isAndroid() && !isRemoteMode()`) = not `deviceNoun() === 'phone'`. Put it next to `githubBackupWorks` in one tiny shared helper (`backupTypesAvailableHere()`), and use it in the wizard picker, the inline picker, and the row rendering. This is the existing pattern (`githubBackupWorks`, the `!checkIsAndroid()` iCloud gate at `SyncSetupWizard.tsx:~228`).
- **iCloud on Android today.** The wizard picker hides it. The inline picker offers it; choosing it runs the prerequisite scan which only looks for `~/Library/Mobile Documents/...`, `~/iCloudDrive`, `~/Apple/CloudDocs` (`sync-setup-handlers.ts:~130-145`), none exist in the phone runtime, so the user lands on instructions about signing in with an Apple ID that cannot apply (`SyncSetupWizard.tsx:777`). A dead end, not harm. The same gate should apply (hide iCloud on a phone; on Linux the inline picker is a separate small bug: use the picker's existing `detectDesktopOS() !== 'linux'` test).
- **What an existing phone user sees after hiding.** Only people migrated from the old app can have a Drive entry. Also make `installRclone()` refuse on the phone (same flag) instead of `curl | sudo bash`.
- **Fix plan (S-M).** Files: `SyncSetupWizard.tsx` (picker + helper), `SyncPanel.tsx` (inline picker `:1657-1676`; `unsupported` row `:1559`; notice text `:1634`), `sync-service.ts` (skip drive on phone in the `instances` filter at `:1041-1043`; clear the warning), `sync-setup-handlers.ts` (`installRclone` refusal), `headless/headless-boot.ts` (pass flag). (2) A phone that is hidden loses its only off-device backup path of any kind if the user relied on a migrated Drive entry: say so in the notice and point at cross-device sync/mesh. ### Item 3. "Back up now" copies settings and skills only: CONFIRMED (and slightly worse than described)

- **What it copies.** `forceSync()`/`pushBackend()` (`sync-state.ts:647-692`) call only `SyncService.push({ force: true })`. That copies the personal set: per-project memory, CLAUDE.md, encyclopedia, user skills, plans/specs, settings, keybindings, mcp, history, conversation index (`sync-service.ts:~695-770`, force bypasses the once-a-day gate at `:~1057`). Conversations and project files are on purpose not in it (`sync-service.ts:~739-743`); they travel only through `DailyBackup.runIfDue` (`sync-spaces/daily-backup.ts:51-85`), called only at launch and on the hourly timer (`sync-spaces/service.ts:270-276`), gated by one marker per device (`~/.claude/.spaces-backup-marker`, `isBackupDue`: "marker != today's UTC date"). The marker is not per destination: add a Drive at 3 pm after today's run and it gets no conversations until tomorrow's first hourly tick. A paused destination (`syncEnabled:false`) never gets them at all (`backup-targets.ts:~8-12`), though "Upload now" is offered on it.
- **Every place that starts a backup.** "Back up all now" (`SyncPanel.tsx:1702`, `handleForceSync :634` -> `sync.force`), row menu "Upload now" (`:1617`, `handlePushBackend :672`), a warning's "Try again" (`handleFixAction` `retry`, `:~742-750`), the wizard's first upload (`SyncPanel.tsx:1088`), and the hourly timer. No assistant tool or command starts one.
- **Fix plan (M).** Add `DailyBackup.runNow(spaces, targets, log, { onlyType/base? })`: ignore the marker, ignore the in-memory `done` set for the requested targets, copy, prune, and only write the marker when every active target landed (so a forced one-destination run never "closes the day" for the others). Expose `syncSpacesBackupNow(backendId?)` from `sync-spaces/service.ts` (it already owns `backup`, `activeSpaces()` and the targets). `sync-state.ts` can call it directly because it already imports `./sync-spaces/service` (line 29). That needs no `main.ts` edit (main.ts is at its line budget) and both doors get it because both call `startSyncSpaces`. `forceSync`/`pushBackend` then run personal push, then spaces, and report failure if **either** fails. A paused target requested by id (Upload now) is included explicitly (that is what a manual tap means) even though the timer skips it. Also add the missing single-flight guard (D-11): one in-flight run; a second caller waits for it rather than starting a copy of the same spaces. Tests: `DailyBackup.runNow` copies despite a same-day marker; does not write the marker if one target failed; paused target included when asked; overlapping calls run once; `forceSync` returns `success:false` when only the spaces half fails; the wizard first upload covers conversations the same day.
- **What could go wrong (the part to decide).**
  1. **Slow and big.** `rclone copy` of a whole Personal space + every project folder; first upload to a new Drive can be many GB. Each space copy has a 10-minute kill (`RCLONE_TIMEOUT`, `daily-backup.ts:12`); a space over that fails with a TIMEOUT warning and finishes on later runs (rclone resumes per file). The button already says "Backing up..." and disables itself; the wizard's first upload today awaits the personal push only and would now sit for minutes. Option A: keep awaiting (honest, simple, long). Option B: wizard's first upload starts the copy and returns at once; the new row shows "Uploading..." and any failure lands as the usual red box. B needs a visible "in progress" state for the spaces half, which does not exist yet (the spaces half only logs; D-7 and D-13 are the same gap), so B is bigger. Recommendation: A for "Back up all now"/"Upload now"; for the wizard's first upload ask you (it changes what you see).
  2. **A phone/browser talking to a computer will time out.** `remote-shim.ts:474` default request timeout is 30 s; `force` has a 10-minute override (`:2763`) but `pushBackend` (`:2770`) does not. Once these calls get slow, a paired phone or remote browser reports "Couldn't confirm the upload finished" while it is still running. Give `pushBackend` the same override (renderer-only change; the Android WebView uses this shim).
  3. **Metered connections.** No setting is enforced: `SYNC_WIFI_ONLY` is stored (`sync-state.ts:136,544`) but nothing reads it (`rg` over `desktop/src` and `app/src`). A laptop on a phone hotspot would upload everything on one tap. After item 2 no phone does this itself (phone Drive/iCloud hidden), so the exposure is laptops; card #258 is the existing "what a phone syncs on mobile data" item. Consider a one-line confirm ("This may upload a lot of data") only if you want it; it is a visible change.
  4. **Overlap with the hourly timer.** `runBackup` has no re-entry guard today (D-11). A manual run while the timer is mid-copy would double the upload. The guard above fixes both.
  5. **Locks.** `DailyBackup` does not use the personal push lock; the two write different remote folders (`Backup/<date>/personal` vs `Backup/spaces/<date>`), so they do not collide on the remote. The lock bugs in D-18/B-3 do not affect it.
  6. **Honesty after the change.** Remote errors from this half must reach the existing red box under the row, or "finished" would become a new lie. `DailyBackup` failures today only go to the log (no panel warning); the work must classify them the way `recordBackendFailure` does.
  7. Existing text at `SyncPanel.tsx:85-86` ("Forces an immediate copy to your additional backups") becomes true; no copy change needed.

### Item 4. "Sign in again" for an expired Drive backup makes a second entry: CONFIRMED

- `sync-error-classifier.ts:~120-135` `AUTH_EXPIRED` (and `CONFIG_MISSING :113-122`) set fix action `open-sync-setup` with `payload.backendId`. `SyncPanel.tsx:724-732` `handleFixAction` stores `wizardPreselect = { id, type }` and opens the wizard. Wizard: `preselectedBackendId` only picks the first step and the copy (`isReconnect`, `SyncSetupWizard.tsx:324`); after auth it goes to the Configure page (folder + label) and `onComplete` (`:389`) -> `SyncPanel.tsx:1072` `claude.sync.addBackend(instance)`; `updateBackend` is never called by the wizard. `authGdrive` (`sync-setup-handlers.ts:225-259`) looks at existing remotes and takes `gdrive2` when `gdrive` exists (`:238`), so the new sign-in lands in a new remote while the old entry keeps `rcloneRemote:'gdrive'` and keeps failing. The wizard text even says "Sign in with the same Google account... A different account would start a new backup instead of continuing this one" (`:~985`), which is not what the code does.
- **Every place the UI offers it.** The red warning box's button in Backup & sync (`SyncPanel.tsx` warnings list, `:~1745`); the same button on `CONFIG_MISSING` ("Reconnect Google Drive"), `PERMISSION_DENIED` ("Open sync settings"), and the iCloud/GitHub analogues (`sync-error-classifier.ts:204, 228, 249`); the status bar chip opens Settings (`App.tsx:3426`), no direct fix. No assistant tool/command.
- **Fix plan (M).** (1) `authGdrive(existingRemote?: string)`: when the wizard is in reconnect mode pass the entry's current `config.rcloneRemote` and refresh the token in place instead of picking a new name. Per `rclone config update --help` on this machine: "If the remote uses OAuth the token will be updated"; `rclone config reconnect <remote>:` also exists ("normally means going through the interactive oauth flow again"). Which of the two behaves best with no terminal attached is **UNVERIFIED** (I did not run them against a real Google login; that needs a throwaway remote on a dev machine; the existing `config create` call relies on rclone auto-answering questions, `--help` says the default is taken unless `--non-interactive`). If the remote is gone entirely (`CONFIG_MISSING`), fall back to `config create` with the **same** name. (2) New channel or a parameter on the existing one: a parameter on `sync:setup:auth-gdrive` is cheapest, but the channel types in `shared/sync-channel-types.ts`, `shared/backend-contract.ts`, `preload.ts:~1686 area`, `remote-shim.ts`, `workbench/mock-shim.ts:2544` and `ipc/sync.ts:96` all need the new argument (the IPC parity test will catch a miss). (3) Wizard: in reconnect mode finish after auth: skip the Configure page, do not call `addBackend`; call `updateBackend(id, { config: { rcloneRemote } })` only if the name changed, then `pushBackend(id)` to prove it works, which clears the failure on success (`pushDrive` -> `clearBackendFailures`, `sync-service.ts:~793`). Verify the id still exists before writing (stale id). (4) Treat `PERMISSION_DENIED` separately: signing in again does not fix "the folder is read-only"; keep it routed to Edit settings, not the re-auth wizard. (5) Tests: wizard test (reconnect completes with the backend count unchanged and no Configure page); `authGdrive('gdrive')` reuses the name and never creates `gdrive2` (stub `safeExec`); a failing re-auth leaves the entry as it was.
- **What could go wrong.** Users who already hit this have two Drive rows (the working `gdrive2` one and the broken `gdrive` one); nothing auto-cleans them. Offering a one-time "remove the old one?" is a visible addition (needs approval). If the user signs in with a different Google account, the same remote now uploads to a different Drive, and old snapshots stay in the old account: the existing warning text covers this. The reconnect of a remote shared by two entries (two entries pointing at the same remote name, possible by hand) repairs both; fine. Browser sign-in can still be stuck for 5 minutes (D-21).

### Surprises and corrections to the review

1. **The inline picker at `SyncPanel.tsx:1657-1676` offers iCloud on Android and Linux**, and Drive on Android, with no platform gate at all. The review only talked about the wizard picker. Any "hide on phone" fix that touches only the wizard misses this entry point.
2. **Item 1's "silent success" probably cannot happen on a current phone** because `gh` is not in the phone runtime, so the wizard stops at its prerequisite step. The lying code path is still real and still worth closing, and any entry a user already has most likely came from the old native-Kotlin app. UNVERIFIED on a device.
3. **Existing phone Drive entries today produce a permanent red "rclone isn't installed" warning every hour.** Hiding the option without also making the backend skip them leaves that warning and the red status dot. This is the main hidden consequence of item 2.
4. **The backend cannot detect a phone** (`process.platform` is "linux" there). Any backend-side skip/refuse needs an explicit flag from `headless-boot.ts`.
5. **`pushBackend` has a 30 s timeout over remote access** (`remote-shim.ts:474, :2770`) while `force` has 10 minutes. Item 3 makes pushes slow, so a paired phone or browser would report a false failure unless that is lengthened.
6. **`SYNC_WIFI_ONLY` is stored but never read** anywhere (`sync-state.ts:136, 544`): a "Wi-Fi only" choice, if it exists in some UI, does nothing. (No UI for it found on this branch; the field comment says "Android only", a leftover of the old Kotlin app.)
7. **B-1 (Windows never overwrites) is much smaller than the review says** because snapshots go into a new dated folder each day.
8. **`sync-state.ts` already imports `sync-spaces/service`** (line 29), so item 3 needs no `main.ts` change, which matters because `main.ts` is at its line budget.
9. **Pinned test to keep:** `tests/sync-service.test.ts:497-512` expects `{success:true, errors:0, backends:[]}` for a github-only push. Put the "unsupported = failure" logic in `pushBackend`, not `SyncService.push`.
10. **Item 4's fix has an untested core:** whether `rclone config update <remote>` (or `reconnect`) refreshes a Google token with no terminal. Plan a throwaway-remote test on a dev machine before building; I could not do it read-only.
