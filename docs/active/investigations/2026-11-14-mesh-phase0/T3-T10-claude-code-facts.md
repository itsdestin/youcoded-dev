# T3 + T10 (Linux part): what Claude Code 2.1.325 does when a chat is moved by hand

## 1. Verdict

**PARTIAL, leaning PASS.** On one computer, a chat file placed by hand in another project folder resumes with the same id, appends to the same file, follows up a helper, re-reads a saved output, repeats back a hook note, and edits a file in the new folder correctly (T10 Linux half: PASS). Not proven: a *second home folder that is signed in* (could only prove it is found and loaded before the sign-in check fails), Windows/Android-written chats, and anything that depends on the other device's home path differing. Three design statements are wrong or fragile (sections 4.1 to 4.4).

## 2. What was done

- 26 `claude` invocations (limit ~40): 24 real `-p --model haiku` runs, 1 no-sign-in run (never reached the model), 1 dummy-token run (401). `claude --help`, `setup-token --help` and `--version` do not count.
- Throwaway projects `projA, projB(removed), projC, projH, projM, projN, projP, talk` under `/tmp/claude-1000/-home-destin-youcoded-dev/1d94ee8c-71e6-4c05-afdb-68b45dbe9211/scratchpad/t3/` (not under git, so the workspace CLAUDE.md did not load).
- Prototype folder `docs/active/prototypes/2026-11-14-mesh-phase0/T3/`: `cc.sh` (runs the real `claude` with the app's nested-run variables `CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_DESKTOP_*`, `CLAUDE_PID` and `CLAUDE_CODE_SUBAGENT_MODEL` removed), `env.sh` (paths, slug helper), `lines.py` (one-row-per-line transcript summary, prints no chat text), `hook-ctx.sh` (context hook), `slow.sh` (22 s PreToolUse hold for the overlap test), `talk-note.sh` (talk-only note hook).
- Re-run recipe for any fact: `. T3/env.sh; T3/cc.sh <folder> -p --model haiku --output-format json [--resume <id>] "<prompt>"`, then `python3 T3/lines.py <slugdir>/<id>.jsonl`. Slug = every non-alphanumeric to `-` (matches `slug-encoding.ts`).
- Destin's global hooks fired for every run (SessionStart: the superpowers plugin hook and `~/system/hooks/session-start.sh`, a brain status printout; Stop hook summary). They only add `hook_success` / `hook_additional_context` attachment lines to the transcript; I saw no other side effect. The shared `~/.claude.json` gained one project entry for my `projC` path (Claude Code wrote it; I did not touch the file, it is held by the live app). It is harmless and can be left or removed by Destin's next maintenance.

## 3. Findings (each with a written YES/NO)

**F1. `--resume <id>` keeps the id and appends to the same file: YES.**
Session `1648fc3b` created at 55 lines / 300,240 bytes after run 2; the first 292,914 bytes (the original 43 lines) were byte-identical after the resume (`cmp` on the prefix), `session_id` in the result unchanged, no second file in the slug folder. New user line's `parentUuid` is the previous leaf's uuid, so the chain continues. The file is very noisy: 292,914 bytes for a one-tool, one-sentence chat, mostly `attachment` (187 KB), `api-request-blob` (54 KB) and `api-request-shape` (39 KB) lines. Each prompt appends about 10 to 25 bookkeeping lines (`session-owner`, `atis-latch`, `last-prompt`, `tools-used`, `cost-state`, `mode`, `queue-operation`).

**F2. Resume from a different folder: YES, and the file does not even have to be moved.**
- Resume from a *different* folder with the file left in the old slug folder: Claude Code found it and appended to the original file in the original slug folder (55 to 68 lines). Resume from `/usr/share` (a folder unrelated to anywhere) also found it by id, created no new slug folder (27 project folders before and after), appended 14 lines. So lookup is by session id across all slug folders of that config dir, not by the current folder's slug. (UNVERIFIED: what happens if the same id exists in two slug folders; see 4.3.)
- Old lines keep their old `cwd` byte-for-byte; new lines carry the current folder (checked: user line cwd ends `…/projB`, then `…/projC`, `…/usr/share`). Claude Code does nothing about the recorded `cwd` and does not need that folder to exist (T10 setup: old folder `projA` renamed away).
- **T10 test**: chat read `note.txt` in `projA`; folder renamed away; transcript moved (`mv`) into the slug folder for `projC` (copy of project with the file); resumed from `projC` with `--permission-mode acceptEdits` and told to edit `note.txt`. Result: `projC/note.txt` changed `alpha`→`gamma`; `projA.gone/note.txt` unchanged; the model reported the new absolute path. YES.
- The model's earlier tool calls keep the *old* absolute paths in their inputs (read of `…/projA/note.txt`); it used the new folder correctly because the current folder is stated in the fresh `environment` attachment.

**F3. Fork on resume (`--resume <id> --fork-session`): new id YES; rewrites all earlier lines YES; bytes identical NO.**
Original 99 lines; fork file 77 lines with a new id (`5dbc4d74`). Original file unchanged (`cmp` clean). Byte-identical lines between the two files: 0 of 77 (also 0 positionally). Per conversation line (50 shared uuids): `sessionId` differs on 50, `cwd` differs on 35 (old lines' `cwd` is rewritten to the *current* folder), `promptId` differs on 7. Uuids and `parentUuid` are kept (50 of 50 shared). Bookkeeping lines are deduplicated (api-request 7→1, last-prompt 7→2, queue-operation 8→2, session-owner 4→2, cost-state 4→1) and a new `mode` line is added at the top, so the fork is not a line-for-line copy either (99 vs 77 plus 4 new conversation lines for the new turn). Consequence for 5.3: a forked version cannot be stored as "my lines after the split point plus a pointer to the parent"; it has to store all its own lines. Shared uuids would allow dedupe by uuid if ever wanted.

**F4. Talk-only: YES, with a note. Flags alone are not enough to stop attempts.**
Three runs resuming the same Edit-heavy chat in an empty scratch folder `talk/`, with `--permission-mode` set so only the flags could stop it:
1. `--disallowedTools "Edit Write Bash NotebookEdit MultiEdit PowerShell"`, `acceptEdits`: no write attempted; tried `Glob` and `Read` of the old absolute path; the Read was refused (outside the scratch folder, listed in `permission_denials`). File unchanged.
2. `--tools ""` (all tools off), `bypassPermissions`: tried `Edit` once; got `<tool_use_error>No such tool available: Edit. Edit is disabled for this session, in subagents as well as here.` File unchanged; reply said it could not.
3. `--tools ""` plus a UserPromptSubmit hook note in the scratch folder's `.claude/settings.json` ("this chat is now talk-only… do not attempt any tool"): 0 tool attempts, reply explained it could not. One sample each, so "refrains" is shown for the note case only once; the flag-only cases clearly *try* and fail harmlessly.
Recommended flags: `--tools ""` (removes every built-in tool; MCP tools need `--strict-mcp-config` too, untested) plus the note. `--disallowedTools` leaves Read/Glob/Grep, which are then confined to the scratch folder in print mode (UNVERIFIED in interactive mode).

**F5. Prompt hook adds context the model sees: YES; it IS written to the transcript.**
Hook set only in the throwaway project's `.claude/settings.json` (UserPromptSubmit, JSON `hookSpecificOutput.additionalContext`). Recorded as two things: a `type:"attachment"` line with `attachment.type:"hook_additional_context"` (`content:[note text]`, `hookName:"UserPromptSubmit"`, `hookEvent`), and the same line carries `rendered:[{content:"<system-reminder>…"}]`, `renderedRole:"system"`. It comes right after the user line (line 14 in the test). The model repeated the codeword. App display: `transcript-watcher.ts` reads `attachment` lines only for `queued_command` (lines 423 and 432 of that file), so no bubble is drawn (UNVERIFIED in the rendered UI). `hook_success` attachments also record the hook command, stdout and duration. Not a user-visible line, but a line in Claude Code's file: it travels with the chat.

**F8. End of a reply:**
- Assistant lines carry `message.stop_reason`. Claude Code writes ONE LINE PER CONTENT BLOCK (thinking, text and each tool_use are separate lines sharing `message.id` and `requestId`) and the same `stop_reason` is copied onto every block line of that message. Example: a thinking line (`…:00.572Z`) and its text line (`…:01.367Z`) both say `end_turn`, 0.8 s apart. A reader that fires on "first line with `end_turn`" fires on the thinking block before the text exists in the file.
- After the last assistant line: `system` `stop_hook_summary` (present when Stop hooks exist), then `last-prompt`, `cost-state`.
- Interactive sessions additionally write `system` `subtype:"turn_duration"` (`durationMs`, `messageCount`, `pendingBackgroundAgentCount`). Measured on one real 51 MB interactive file: 121 `turn_duration`, 120 `stop_hook_summary`, in 120 of 121 cases right after an `end_turn` assistant line plus `stop_hook_summary`. Print mode wrote no `turn_duration`. So `turn_duration` is not usable as the reply-end marker for chats created by non-interactive runs, and `stop_reason` must be taken from the LAST block line of the message (or the first non-assistant line after it).
- The app's own rule (`transcript-watcher.ts:351`): emit `turn-complete` for any stop reason except `tool_use`.

**F9. `/compact` and `/clear`:**
- `/compact` (print mode, manual): same id, same file, **appended only** (166 to 192 lines, 1,103,109 to 1,218,342 bytes; first 1,103,109 bytes byte-identical). Adds `system` `compact_boundary` (`compactMetadata`: `trigger:"manual"`, `preTokens`, `preservedSegment`), then a user line with `isCompactSummary:true`. Matches the "never removed a line" statement in 3.1. (The file did not shrink; a shrink could still come from other paths. T2 owns that.)
- `/clear`: **mints a new id** (`80b4ae76`) and a new file (10 lines: mode, session-owner, hook attachments, the command, a `system` `local_command`). Nothing in the new file mentions the old id (`grep -c` 0). The old file got 3 bookkeeping lines appended and its prefix is intact.

**F10. `cleanupPeriodDays`: read from the 2.1.325 binary, not observed.**
Default 30 (`zUe=30`). A cut-off date = now minus N days; a `<id>.jsonl` is deleted when its **file modification time** is older than the cut-off, together with its session folder (`tool-results`, `subagents`, …) and the `.ccr-tip.json` / `.precompact.json` sidecars; legacy `todos` and other old folders are swept too. Value 0 returns "no cleanup" in the code, though a message in the binary says "must be at least 1". Cleanup is skipped when settings are invalid or remote settings are unknowable ("a later process … runs the cleanup"), so it runs inside Claude Code processes at start-up; exact trigger moment UNVERIFIED. **A copy placed by the mesh gets a fresh modification time, which restarts the clock on that device; a copy whose mtime is preserved by `cp -p` or `touch -d` will be deleted at the old age.** The app's seed of 365 days exists (`cc-dependencies.md`, retention entry); it is written into the shared `~/.claude/settings.json`. `claude purge` also deletes a project's data. The binary also names sibling files next to a `.jsonl` that Claude Code manages (`.desktop-released.json`, `.dir-sync.json`, `.cloud-worktrees.json`, `bridge-pointer.json`, `.cast`); none appeared in my runs or in `find ~/.claude/projects -maxdepth 2 -type f -not -name '*.jsonl'` (only a `.tar.gz` backup).

**F11. Two live processes resuming the same id: lines do not corrupt, but the chat forks and the late process writes after the early one.**
Process 1 resumed and was held mid-tool-call for 22 s by a PreToolUse hook; process 2 started 4 s into the hold, finished in 7 s, process 1 finished 16 s later (all 112 to 126 lines parsed as valid JSON; no duplicated or torn lines). Result in the file, in time order: p1 user line → p1 tool_use (`a2cbd`) → **p2's resume wrote its own tool_result for p1's unfinished tool call** (text "No response requested.") → p2 prompt and reply `TWO-DONE` → **p1 wrote a second tool_result for the same tool_use (`a2cbd` has 2 children)** → p1 reply `ONE-DONE`. So the transcript becomes a tree inside one append-only file with interleaved writers; the final reply on disk belongs to the process that finished last, not the one that started last. (An earlier attempt with `sleep 25` showed the model refuses long sleeps, so the hold had to come from a hook.) Relevant to "old host keeps writing": expect the old host's tail to contain lines whose `parentUuid` points at a line another process already extended.

**F12. Second home folder (`CLAUDE_CONFIG_DIR`): finds and loads the chat, then stops at sign-in.**
Fresh config dir containing only `projects/<slug>/<id>.jsonl` (copy of a throwaway chat): `claude -p --resume <id>` returned in 487 ms with `session_id` unchanged, the previous cumulative cost (0.14 USD, restored from the last `cost-state` line), `result:"Not logged in · Please run /login"`, `is_error:true`, `terminal_reason:"api_error"`. It **did load the session** (cost restored, same id) and it **appended 24 lines to the copied file**, including the failed prompt and a synthetic assistant error line (`stop_reason:"stop_sequence"`), so a failed resume pollutes the chat copy. It created a fresh `.claude.json` (new `machineID`, `userID`), `backups/`, `plugins/`, `sessions/`; it read no credentials. Credential mechanism: `CLAUDE_CODE_OAUTH_TOKEN` (and `…_FILE_DESCRIPTOR`, `…_REFRESH_TOKEN`) are read by the 2.1.325 binary, produced by `claude setup-token` ("long-lived authentication token (requires Claude subscription)"; `--help` shows no options). With a deliberately fake token the run reached the API and failed with `401 OAuth access token is invalid`, which shows the env var path is used instead of the credentials file. I did not run `setup-token` and did not test a real token. The first line of every chat is `session-owner` with the account and organization uuid, and a `credential_org` attachment exists; whether resuming under a different account is accepted is UNVERIFIED.

## 4. What this changes in the design

**4.1 Section 5.4, "The divider and the notes to the assistant" (and 3.1 last paragraph).** The sentence "so nothing is written into Claude Code's file (T3)" is false. Proposed: "Claude Code chats get the note as hook context on the next prompt. Claude Code records it as a `hook_additional_context` attachment line in its own file, so the note travels with the chat, is replayed on every later resume and need only be sent once (sending it with every prompt would add a line each time). The app does not draw that line."

**4.2 Section 5.3 Identity, third bullet.** Replace "unless Claude Code's fork rewrote them (T3), in which case it stores them all" with "Claude Code's fork rewrites every earlier line (new `sessionId`, `cwd` rewritten to the current folder, new `promptId`, bookkeeping lines deduplicated), so a forked version stores all its lines; lines keep their uuids." (T3 verified.)

**4.3 Section 5.4, Becoming host.** Add: "Claude Code looks a chat up by id across all project folders of that home folder, so the working file can sit in the slug folder of the local project folder (kept as designed). A kept-aside old copy must be moved out of `~/.claude/projects` (or renamed so it does not end in `.jsonl`); a second file with the same id in another project folder would make the lookup ambiguous (untested). Check that Claude Code is signed in on this device before the first resume: a resume without sign-in loads the chat and writes a failed turn into it. Set the file's modification time to the moment of placement (the clean-up deletes by modification time)."

**4.4 Section 5.3 Extras table (and 3.1).**
- To-do list row: `~/.claude/todos/` does not exist; use `~/.claude/tasks/<sessionId>/` (N.json, `.lock`, `.highwatermark`), keyed by session id.
- Add `<slugdir>/<sessionId>/workflows/`.
- Saved long outputs and the plan are referenced by ABSOLUTE path in the chat lines (`persistedOutputPath`, "Full output saved to: …", `plan_mode.planFilePath`). The store may not rewrite lines (hash chain), so on a device with a different home path or slug the model's first read fails (recovered by luck in F7) and a missing plan file is not recreated. Proposed: becoming host also (a) places the plan file at `~/.claude/plans/<slug>.md` on the new device, and (b) sends the assistant a note via 4.1's hook: "Earlier saved outputs and plans from this chat are now under <new path>." The plan text is also in the chat's `Write` line, so the app can regenerate the plan file from the transcript if it was not copied.
- Add `file-history/<sessionId>/` as not required for resume (verified by absence in print mode; interactive rewind needs it, UNVERIFIED).

**4.5 Section 5.3 "An index of reply ends".** State the marker: the last assistant line of a message whose `stop_reason` is not `tool_use` (blocks of one message repeat the value; use `message.id` grouping or the next non-assistant line); `stop_hook_summary`/`turn_duration` are not reliable markers (absent in print mode).

**4.6 Section 5.4, Talk-only.** Name the mechanism: `--tools ""` plus a hook note, not flags alone (attempts still happen with flags alone, F4), and resume works from any folder, so a scratch folder is fine (T10).

**4.7 Section 12.2 (risk 2).** Soften: resume across folders and file placement work; the remaining Claude Code risks are sign-in per device (`CLAUDE_CODE_OAUTH_TOKEN`), absolute paths in extras, and a failed resume writing junk lines.

**4.8 Section 5.4 "old host keeps writing" (F11).** Evidence for the existing rule: two writers on one file produce a tree with interleaved valid lines and a second tool result for the same call. Nothing to change if the control-log/tail rules already treat that as a second version; T13 should include a line whose `parentUuid` points at an already-extended line.

## 6. Could not test here

- A real second signed-in home folder or device: only "found and loaded, then stopped at sign-in" (F12). No real token was available or created; account-mismatch behavior unknown.
- Windows-written chat on Linux or Android. From `youcoded/desktop/src/main/slug-encoding.ts` (read, not run on Windows): `ccProjectSlug` turns every non-alphanumeric into `-` (so `C:\Users\x\proj` becomes `C--Users-x-proj`), uppercases a drive letter as app-side input normalization, and for slugs over 200 characters appends a base-36 hash of the original path (JS UTF-16 units; the Kotlin mirror widens to Long). Because Claude Code looks chats up by id, a slug mismatch between devices does not by itself break `--resume` (verified on Linux), but app code that derives the slug (`resolve-local-project.ts`, listing, memory) could. Specifically unknown: (a) the recorded `cwd` and tool-input paths with backslashes and drive letters being replayed to the model on Linux/Android (probably harmless as old lines are untouched, untested); (b) whether Claude Code on Windows/Android looks up across slug folders the same way; (c) Android's home and `CLAUDE_CONFIG_DIR` layout; (d) case-insensitive path behavior on Windows/macOS; (e) path-length effects at 200+ characters with non-ASCII characters (hash input).
- Interactive mode (TUI): reply-end `turn_duration`, plan recovery on resume and task tools were read from existing real transcripts or print-mode behavior only.
- The same id existing in two slug folders; MCP tools under `--tools ""`; `claude --bg`/`--fork-session` combined with a moved chat.

## 7. Proposed additions for `youcoded/docs/cc-dependencies.md` (not applied)

### Moving a chat between folders and devices (mesh sync) — measured 2026-11-14, CC 2.1.325, Linux
- **Files:** (planned) mesh chat store and `becomeHost`; today none.
- **Depends on:** (1) `claude --resume <id>` finds the transcript by id across every `~/.claude/projects/<slug>/` of the config dir, keeps the id, and appends to the same file; new lines carry the current `cwd`, old lines are untouched. (2) `--fork-session` mints a new id and rewrites every line (`sessionId`, `cwd`, `promptId`; 0 byte-identical lines). (3) `--tools ""` removes all built-in tools; a model may still try one and gets "No such tool available". (4) A UserPromptSubmit hook's `additionalContext` is stored as an `attachment` line `hook_additional_context` (also `hook_success`) and replayed on resume. (5) Saved long outputs: `<slugdir>/<sessionId>/tool-results/*.txt`, absolute path in the line text and `toolUseResult.persistedOutputPath`; helper transcripts `<slugdir>/<sessionId>/subagents/agent-<id>.jsonl` + `.meta.json`, continuable with SendMessage after a move; plans `~/.claude/plans/<slug>.md` with absolute `plan_mode.planFilePath`; tasks `~/.claude/tasks/<sessionId>/<n>.json`; no `~/.claude/todos`. (6) Assistant lines are one per content block, each carrying the message's `stop_reason`; `turn_duration` only in interactive sessions. (7) `/compact` appends (`compact_boundary` + `isCompactSummary`); `/clear` mints a new id and file. (8) Two processes resuming one id interleave whole lines and fork the parent chain. (9) `cleanupPeriodDays` (default 30) deletes by file mtime, with the session folder. (10) A not-signed-in resume loads the chat, then appends a failed prompt and a synthetic error line; `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`) is the env-based sign-in.
- **Break symptom:** A moved chat is not found (lookup becomes slug-scoped), forks reuse bytes or stop rewriting `cwd`, hook context stops being recorded (notes lost on the next host), extras land elsewhere (follow-up of helpers/plans fails), `stop_reason` copied only to the last block (reply-end timing changes), or tasks move out of `~/.claude/tasks`.
- **Detection:** the Phase 0 T3 prototype (`docs/active/prototypes/2026-11-14-mesh-phase0/T3/`) re-run on each Claude Code bump; review trigger: CHANGELOG lines on session lookup, `--resume`, `--fork-session`, hooks output storage, `tool-results`/`plans`/`tasks` layout, or `cleanupPeriodDays`.
