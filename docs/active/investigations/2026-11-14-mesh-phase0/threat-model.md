# YouCoded Mesh — threat model

Scope: `docs/active/design/2026-11-07-mesh-sync/design.md` (read in full) plus the app code it builds on (checked in
`youcoded/desktop/src/main/`). Method: STRIDE per component (Spoofing, Tampering, Repudiation, Information
disclosure, Denial of service, Elevation of privilege), against OWASP ASVS/MASVS-style requirements. No prototype was run;
everything marked **Code** was read in the worktree, everything marked **Design** is the design's own claim and is
untested.

**Verdict: PARTIAL.** The design's cryptographic skeleton (signed roster, sealed frames, hash chains, "a keeper is never
authority") is sound and better than most. But the model it states in section 8, "every paired device is fully trusted",
is too coarse in four places, and each one is a real hole: (1) a watcher can reach raw terminal input and permission-free
session creation on the host (Code, section 4.6 below); (2) live events and heartbeats are not signed (6.3); (3) any paired
device can write lines into any chat, and those lines become the assistant's "memory" when the chat is next resumed
(6.3 `answer`, 5.3); (4) the project carrier applies another device's files to disk with no path, symlink, case-folding or
config-file checks, where one crafted file (`.claude/settings.json`, `~/.claude/settings.json` via extras) is command
execution. Nothing here needs a redesign. Each is fixed by a rule the builders can test. Count of threats below: 112 rows,
of which 15 are Critical, 56 High, 32 Medium, 9 Low.

## 0. How to read the tables

- **Stopped?** Yes (cite section), Partly (what is missing), No (design is silent).
- **Sev:** Crit = silent data loss, code execution, or total compromise by someone outside the set (or by a set member
  beyond what Destin accepted); High = confidentiality or integrity breach or sustained denial; Med = bounded harm or needs
  a second failure; Low = annoyance or hygiene.
- **MUST** lines are testable requirements. IDs (e.g. `MUST S-3`) are for the builders and auditors to cite. A later
  auditor checks each MUST with the test named or implied.

## 1. Assets

| # | Asset | Where it lives | Why it matters |
|---|---|---|---|
| A1 | Chat contents, including secrets pasted or printed into chats (API keys, `cat .env` output, tokens in tool results) | Every device's chat store (plaintext on disk), relay (sealed), interim GitHub backup (plaintext in a private repo, today), unlocked cloud backups | Chats are the product. A chat is a durable record of everything the user did and saw. |
| A2 | Project files | Every device that turned sync on for the project; relay (sealed bundles); GitHub backup branches | Source, documents, client work. Also a code-execution surface (see A6). |
| A3 | The set secret and every generation of it | Every device (`safeStorage` / Keystore shim); never a server (8.1) | Whoever holds a generation can read every frame sealed under it, forever (no ratchet). |
| A4 | Device signing and key-agreement private keys | Each device | Impersonation of that device; roster add/remove power. |
| A5 | The roster (who is in the set) | Signed log on every device; hashed ids and public keys on relay | Controls everything else. |
| A6 | **The ability to run commands on a host**: a watcher types into a chat whose assistant can run Bash, edit files, and answer its own permission prompts | The host device's process, plus its files and credentials (`~/.ssh`, cloud CLIs, browsers' sessions) | By design reachable from every paired device (2.1). The most valuable asset on a developer's computer. |
| A7 | The host's permission posture: permission mode, `skipPermissions`, "always allow" rules, hooks, settings | Host-local settings and `~/.claude/settings.json` | Defines what A6 can do without a human. |
| A8 | Metadata: IPs, timing, sizes, counts of devices/chats, public keys, hashed ids, chat group names | Relay, Cloudflare, network | Reveals when and where the user works, how much, on what; with token-sized live frames, sometimes what was said (see L-4). |
| A9 | Availability of sync and of the relay | Cloudflare free plan | Users stop receiving chats; potential data stuck on one device. |
| A10 | The user's finished work: replies and file edits that exist on exactly one device for some time | Single device until acknowledged | Covered in `data-loss-review.md`. |
| A11 | Pairing codes and QR payloads | Screen, camera, typed text, possibly logs | A one-time capability to join the set. |

## 2. Actors

| # | Actor | Capability assumed | In scope? |
|---|---|---|---|
| T1 | **Curious relay operator** (YouCoded, or Cloudflare staff/systems) | Reads everything the relay stores or sees: ciphertext, sizes, timing, IPs, public keys, hashed ids, unsealed `received` counters and group names. | Yes |
| T2 | **Hostile relay operator / compromised relay** | T1 plus: delays, drops, reorders, replays, rolls back state, withholds roster updates from chosen devices, tells two devices they both won a register, erases a set, admits unknown clients. Cannot forge signatures or break the cipher. | Yes (design 5.6, T16) |
| T3 | **Network attacker** (ISP, hotel, coffee-shop wifi) | Sees and alters traffic to the relay. TLS applies. | Yes |
| T4 | **Same-wifi attacker** | Sees mDNS announcements, can connect to the direct listener, can spoof announcements, can be a LAN port scanner, can sit between two devices that discover each other. | Yes (6, own review required) |
| T5 | **Thief, unlocked device** (stolen mid-use, or unlocked by coercion) | Everything on the device: keys, stores, can add/remove devices, can type into chats on others. | Accepted by design (8), but the blast radius is not bounded; see S-, R- rows |
| T6 | **Thief, locked device** | Device at rest. Disk encryption and OS lock apply. Desktop without disk encryption: reads stores directly. Linux without a keyring: `safeStorage` keys are protected only by a hardcoded password (Electron docs, below). | Yes |
| T7 | **Removed device** | Holds the set secret up to the last generation it received, a roster, every chat it had, and valid signatures from before removal. Tries to reconnect, rejoin, replay, or race the removal. | Yes |
| T8 | **Malicious paired device** (a device whose owner turned bad, or malware on a paired device) | Valid signatures and keys. Design says "fully trusted". We bound it. | Yes, bounded (this model) |
| T9 | **Shoulder surfer or camera watching a pairing code** | Sees the QR or typed code for the minutes it lives. | Yes |
| T10 | **Malicious web page / local process on a device** | Web page: cross-origin WebSocket and `fetch` to loopback and LAN addresses, DNS rebinding. Local process: same-user file access, loopback connections, IPC. | Yes for page and for non-same-user processes. A same-user process can read the stores and keys; this cannot be stopped by the app (state honestly). |
| T11 | **A peer of the user's choice who is not the user** (spouse, employee with a device on the set) | A legitimate roster member the user later regrets. Same as T8 plus intent. | Yes, covered by T8 rows |
| T12 | **Compromised app update / supply chain** | Total. | **Out of scope.** Say so in the product's security page. An attacker who ships the app code owns every key. Mitigations live elsewhere (signed releases, release process in `youcoded-admin`). |
| T13 | **Anonymous internet abuser of the relay** (no sign-in) | Free requests, many addresses, many keys. | Yes |

## 3. Trust boundaries

```
 [User] -- OS unlock prompt (local UI gate, NOT a cryptographic gate) -- [App process: main]
 [App main] -- IPC -- [Renderer: app window | Pages | embedded browser]      (boundary B1)
 [App main] -- channel table (door: desktop | remote | peer) -- [handlers]   (boundary B2: where peer calls enter)
 [App main] -- filesystem -- [~/.claude, project folders, mesh store]        (boundary B3: peer bytes become files)
 [App main] -- spawn -- [Claude Code / native runtime / git]                 (boundary B4: files become commands)
 [Device] <== sealed+signed frames ==> [Device]       via: LAN direct | super-host | relay    (boundary B5)
 [Device] <== TLS ==> [Cloudflare edge] -- [Relay Durable Object]                              (boundary B6)
 [Device] ---- plaintext chats and files ---- [GitHub interim lane / cloud backup]             (boundary B7: outside the E2E promise)
```

The design draws B5 and B6 well. It does not draw B2, B3 and B4, and the worst holes are there.

## 4. Component tables

Tables give each row: threat (STRIDE letter), whether the design already stops it, severity, requirement.

### 4.1 Pairing (5.1 pairing, 4.3 A, walk-through D)

| ID | Threat | Stopped? | Sev | MUST |
|---|---|---|---|---|
| P-1 | **S** Relay or network attacker man-in-the-middles the key exchange | Yes (5.1: PAKE, relay "assumed hostile", 8.5). Depends on T5 library choice. | High | MUST P-1: pairing uses an audited PAKE (e.g. SPAKE2/CPace/OPAQUE-style) and a test with a recording relay that mutates every pairing message must end in "no pair, no secret revealed". The QR path binds the existing device's key fingerprint into the transcript. |
| P-2 | **S/E** Attacker on the relay guesses the typed code | Partly. 5.1: three attempts then burn. | High | MUST P-2: typed code total entropy and attempt limit are chosen so that expected success for an attacker with three guesses per code is at most 1 in 10^5 (Magic Wormhole's published model: one guess per code, "1 in 65,536" for its default, https://magic-wormhole.readthedocs.io/en/latest/welcome.html). Counting happens on the existing device and survives restart. |
| P-3 | **D** Anyone who learns the meeting point id burns the three attempts, so the real device cannot pair | No. The typed code "carries the meeting point and a short secret". | Med | MUST P-3: the meeting point id is a separate random value of at least 64 bits, not derived from the short secret. An attempt counts against the code only after the PAKE message authenticates as *a participant who knows the secret*; a connection that never completes the first PAKE round is dropped and counts nothing per code (rate limited per address instead). |
| P-4 | **S** Shoulder surfer or camera pairs first. The existing device then shows "Add this device?" with a name the attacker chose, and the user taps yes | Partly. 5.1: name is shown after authentication, but the name is chosen by the code holder, which is the attacker (the design says so). | High | MUST P-4: the code is single use. If a second party connects to a meeting point that has already authenticated one joiner, the existing device shows "Someone else tried to use this code" and cancels the pairing. Both screens show a short authentication string (six words or digits) derived from the PAKE transcript that the user must see match, before "Add this device?" can be confirmed. The prompt shows platform and first-seen network type, not just a free-text name. |
| P-5 | **S** Device name spoofing and display tricks (bidi override, 200-character names, look-alike "Destin's phone") | No. | Med | MUST P-5: device names from peers are length-capped (40), stripped of control and bidi characters, and shown with the platform and short key fingerprint in the same line on every add/remove prompt. |
| P-6 | **E** A deep link, clipboard or URL scheme starts pairing from a web page or another app | No. | High | MUST P-6: pairing starts only from the in-app scanner or typed code on the Devices screen, after the user opens that screen. No `youcoded://` URL, clipboard watcher or notification action may start or complete pairing. Test: grep that no registered URL handler reaches the pairing code. |
| P-7 | **E** *Joining two sets* (5.1): the scanning device signs an `add` for each of its former companions without those companions' consent, merging two users' data. A user tricked into scanning an attacker's QR hands over their whole set | Partly. The screen "names every device that will end up together". | **Crit** | MUST P-7: joining two sets requires unlock and an explicit confirmation on **both** sides, each screen listing every device of both sets with name, platform, fingerprint. A companion that is not present gets a prompt on its next start ("Your devices joined another set that includes: ..."), may refuse, and refusal leaves it in the old set with a fresh roster. A set must never merge on one side's tap. The product copy states: "everything on every listed device becomes readable to every other." |
| P-8 | **I** The existing device reveals set secret before the user confirms | Yes (5.1: set secret sent only after "yes"). | High | MUST P-8: test that no frame sealed under the set secret leaves the existing device before the confirmation event. |
| P-9 | **D** The pairing pipe is free general-purpose relaying | Partly (5.6 limits). | Med | MUST P-9: a meeting point carries at most 64 KiB total and lives at most the code's lifetime; per-address rate limit; no data after both sides disconnect. |
| P-10 | **E** The OS unlock before add/remove is only a local UI gate. Malware (T10 same user) or anyone with the unlocked process can sign an add or remove without the prompt | No. | High | MUST P-10: keep the signing key that authorises roster `add`/`remove`/`rename` (the "admin key") separate from the key that signs frames, and store it where the platform can require user presence (Android Keystore `setUserAuthenticationRequired`, macOS Keychain access control or Secure Enclave, Windows Hello/KeyCredential). Where a platform cannot, the Devices screen says "adding or removing devices on this computer is not protected by your fingerprint/PIN" (this is O4/T11). |
| P-11 | **R** No record on other devices of who paired what, if the entry is dropped | Yes (5.1 roster entries are signed, 2.4 "Laptop was added by Phone"). | Low | MUST P-11: every `add`/`remove` shows a persistent in-app notice on every other device until dismissed, and stays in a viewable log. |
| P-12 | **D** Brute attempts at the *existing device's listener* during local pairing | Partly (same counter). | Med | MUST P-12: the same attempt counter and burn rule apply to the local meeting point; the listener refuses connections with an `Origin` header (a web page), and limits one pairing session at a time. |

### 4.2 Roster, generations, removal (5.1, walk-through D)

| ID | Threat | Stopped? | Sev | MUST |
|---|---|---|---|---|
| R-1 | **T** Removed device forges entries dated before the cut-off | Partly. Entries name what they have seen (order never from clocks), cut-off from witnesses. A removed device can still pick `seen` pointers freely. | High | MUST R-1: cut-off entries are validated against the removed device's own last roster-signed head: an entry from a removed device is valid only if the device had **never been told** of the removal in any signed message, and it names (via `seen`) no entry that postdates the removal. Test: forge `seen` lists; expect void. |
| R-2 | **E** *The cut-off can be extended by the attacker.* Cut-off = furthest point any remaining device held when it learned of the removal. The removed device keeps pushing signed `claim`/`takeover`/`deleted` entries to any remaining device that has not yet heard (a hostile relay can delay the removal notice indefinitely to a chosen device). That device then signs a `witness` covering them, so they stand | No. | **Crit** | MUST R-2: (a) removal notices go on every path at once (mailbox, direct, live lane) and a device that has heard of the removal from any peer never witnesses later arrivals; (b) a witness covers only entries the witness had **received before** it first saw the removal, proven by the entry's receive record, not by claim; (c) no entry from a removed device that changes host, deletes, or edits the roster is ever honoured past the *removal entry's own* position, only plain lines and summaries are eligible for witness extension; (d) a device whose roster head is older than 24 hours with no peer confirmation shows "may be out of date" and refuses peer `call`s that delete, create sessions, or change roster. |
| R-3 | **E** *Mutual removal decided by "in the set longer".* A thief of the oldest device, unlocked, removes the owner's newer phone and wins the tie, and the owner loses the race by design | No (it is the stated rule). | **Crit** | MUST R-3: mutual removals never resolve by age or arrival order. Both removals stand: both devices become removed, any third device stands, and with exactly two devices the set dissolves into two sets of one, each keeping what it holds, and pairing again (after unlock) re-joins them. Test: two devices remove each other concurrently in every message order; outcomes identical. State the residual risk in the security page: a thief with an unlocked device can remove the others. Consider (Destin) an optional recovery rule: with three or more devices, removing a device requires a second device's confirmation (Tailscale tailnet lock requires multiple signing nodes to co-sign key revocation, https://tailscale.com/kb/1226/tailnet-lock). |
| R-4 | **I** *No forward secrecy.* One static set secret per generation protects every frame sealed under it, including everything the relay stored in the last 30 days (and anything Cloudflare or a network attacker captured at any time). Compromise of any one device, or removal of a device that quietly copied frames, exposes all of them | No (it is the design). | High | MUST R-4: the security page states plainly: "protects against a server or network reading your data today; it does not protect past traffic if a device is later stolen." Optionally derive per-sender chain keys from the generation key with a ratchet. MLS gives forward secrecy and post-compromise security by updating keys regularly (https://www.rfc-editor.org/rfc/rfc9420.html, sections on FS/PCS and Remove). At minimum, rotate generation on a schedule (for example monthly, from any device) so exposure windows are bounded. |
| R-5 | **I** Removed device reads frames sealed under the old generation until relay refuses it, and sees frames sent by devices that have not yet learned of the removal | Partly (8.6 "from the first frame sealed under the next generation"). | High | MUST R-5: a device that learns of a removal seals nothing more under the old generation. A device that has not learned yet keeps sealing under it (unavoidable) and the removing device lists, in the removal screen, "devices that had not yet confirmed" so the user knows the real exposure window. The relay refuses the removed key's connection within one round trip of holding the removal; test with the removed device already connected. |
| R-6 | **T** A removed device is re-admitted by a stale roster after the relay erased an idle room (90 days) | Partly. | Med | MUST R-6: when a room is re-registered, relay accepts only the roster chain that extends (or equals) the longest chain any connecting roster device presents, and bans any key a `remove` in that chain names. Test: erase, re-register with a stale prefix from the removed device and a full chain from a good device; removed device refused. |
| R-7 | **D** Parked entries (unknown signer) pile up unbounded | No ("parked, never refused"). | Med | MUST R-7: parked entries are bounded per sender (for example 8 MB and 30 days) and only accepted when sealed under a generation this device holds. T12's "none lost" applies to entries within that bound. |
| R-8 | **E** Reinstall replaces the old entry for the same machine id "with no extra question" (5.1) | No. | High | MUST R-8: a re-pair by the same machine id still requires the existing-device confirmation and unlock and shows "this looks like Laptop reinstalled"; its old keys are revoked as of the new `add`, and chats it hosted become hostless until it proves possession of the store (see data loss D-12). Otherwise an attacker who learns a machine id (hashed ids visible on the relay, see Y-6) can claim a device's slot. |
| R-9 | **S** Hashed device id linkability | Partly. | Med | See Y-6. |
| R-10 | **R** "Unseen for 30 days" is computed from local clocks | Partly. | Low | MUST R-10: offer is shown only on a device whose own clock agrees with the relay's within an hour (see X-5), and removal is never automatic (already true, 2.4). |
| R-11 | **E** A paired device alters the relay address for the set (keeper swap) | No. | Med | MUST R-11: relay address and keeper choice changes are signed roster-level entries, need unlock, and raise the same notice as `add`. |

### 4.3 Link layer (5.2, 6.3)

| ID | Threat | Stopped? | Sev | MUST |
|---|---|---|---|---|
| L-1 | **T** Relay rewrites the *outside* fields (`to`, `group`, `seq`) of a sealed frame, moving a `chat:A` frame into `chat:B` or into another device's mailbox | No. Outside fields are "readable by a keeper" and nothing says they are bound to the ciphertext. | High | MUST L-1: the sealed AEAD uses the outside header (`v`, `set`, `group`, `to`) as associated data, and the signed inner `body` repeats the group. A receiver rejects a frame whose inner group differs. Test with a relay that swaps fields. |
| L-2 | **T/S** Nonce reuse: all devices share one generation key, ChaCha20-Poly1305 has a 96-bit nonce | No (5.1 says only "keys derived from it"). | **Crit** | MUST L-2: per-sender, per-session subkeys by HKDF from (generation key, device id, session id). The nonce is that sender's counter. A unit test proves that two devices encrypting the same counter use different keys; a static check bans random 96-bit nonces under a shared key. |
| L-3 | **T** Replay of sealed frames: across sessions, devices, sets, after a sender's state loss | Partly (5.1 duplicate rule `(sender, session, counter)`). | High | MUST L-3: the AEAD key binds `set` and `generation`; each receiver keeps, per (sender, session), the highest counter and window, persisted; a *new session id from a sender after its roster entry says "reinstalled"* starts a fresh record, but a **previously seen session id never starts fresh**. Records are kept as long as the sender is on the roster plus 30 days. |
| L-4 | **I** *Token-length side channel.* Live words are batched about every quarter second; ciphertext length tracks plaintext length. Researchers recovered the content of 29% of encrypted AI-assistant responses and the topic of 55% from packet sizes alone (Weiss et al., "What Was Your Prompt?", https://arxiv.org/abs/2403.09751). The relay operator and the network see exactly these sizes | No. | High | MUST L-4: live-lane frames are padded to a fixed bucket size (for example 256 bytes, then powers of two) and sent on a fixed cadence while a reply streams, with dummy frames. Test: ciphertext sizes of two replies with different text but equal length buckets are equal. Durable `lines` frames for finished replies are less sensitive but are padded to buckets as well. |
| L-5 | **I** Group names (`chat:<version>`, `project:<id>`) reveal raw runtime session ids and provider to the relay | No. | Med | MUST L-5: group names on the wire are `HMAC(set secret, id)` truncated, never raw ids or prefixes such as `claude:`. The relay sees counts, not provider mix. |
| L-6 | **T** `live-event` and `beat` carry no signature (6.3 marks `*` only on durable frames, calls, acks). Any holder of the generation key, including a removed device, can forge host events, a fake "assistant" reply, a fake permission prompt, or fake heartbeats that suppress the "host offline" notice | No. | **Crit** | MUST L-6: every `live-event` and `beat` is authenticated. Per-batch Ed25519 signatures (four per second is cheap) or a pairwise MAC from the X25519 agreement keys. A watcher ignores any live event whose signer is not `decide().host` for the named host entry. Test: a non-host member forges an event for a hosted chat. |
| L-7 | **D** Flood with oversized or unknown-kind frames ("unknown kinds are kept and passed on", 5.11) | No. | Med | MUST L-7: maximum frame size, maximum unknown-kind bytes stored per sender, and rate limits per sender and per path. Unknown kinds are kept up to a bound, not forever. |
| L-8 | **T** Downgrade of version negotiation: `hello` is unsealed or unsigned | Partly. | Med | MUST L-8: `hello` is inside a sealed, signed frame; the relay cannot alter app/mesh versions. A minimum mesh protocol version is enforced by the roster-level `format` entry, not by the peer's claim. |
| L-9 | **I** Plaintext fallback paths (HTTP to the relay, debug sockets) | No. | Med | MUST L-9: relay connections are `wss://` only with certificate validation; a build-time test fails if any `ws://` or `http://` relay URL is accepted outside loopback test rigs. |

### 4.4 Relay: authentication, rooms, registers, mailboxes, meeting points (5.6, 6.4)

| ID | Threat | Stopped? | Sev | MUST |
|---|---|---|---|---|
| Y-1 | **I** Relay learns plaintext | Yes (8, S4 shim test that no byte decrypts). | High | MUST Y-1: keep the S4 test and run it in CI against the real Worker bundle; add a static check that the Worker does not import crypto key code (S4). |
| Y-2 | **S** Room name = hash of the first device's public key; the QR carries "the key fingerprint". If those are the same value, anyone who sees the QR learns the room name and can poke it | Partly. | Med | MUST Y-2: room id is a separate random value or an HMAC of the public key with a secret from the set; nothing printed or displayed is the room id. |
| Y-3 | **E** Challenge-response replay or reflection | Partly (6.4 `auth`). | High | MUST Y-3: the challenge is random, single use, expires in 30 seconds, and the signed message includes room, relay hostname, connection id and the challenge. Test replay across connections and across rooms. |
| Y-4 | **T** *Relay rollback or restore.* Durable Object storage restored to an older snapshot reissues `seq` numbers to different frames. A device that "has seq 57" skips the new seq 57 and silently misses a frame | Partly (5.6: "never accepts a head older than one it has seen"). | High | MUST Y-4: `seq` is a transport hint only. Completeness is judged by hash chains and head tables, never by `seq`. Test (T16): relay restored to an earlier snapshot, then new frames; all devices converge or show "two versions". |
| Y-5 | **T** Relay withholds roster updates from a chosen device (eclipse) | Partly. | High | See R-2(d). MUST Y-5: devices compare roster heads over every path they have, and a mismatch seen on any path blocks serving until reconciled (already in 5.1 "exchange roster heads first"). |
| Y-6 | **I** Hashed device ids are linkable: a one-way hash of the machine id is stable across sets, across reinstalls, and across anything else that hashes the same value | Partly (5.1). | Med | MUST Y-6: the relay never sees a hash of the machine id. Each set uses a random per-set device id assigned at `add`. Reinstall matching (R-8) uses a value sealed in the roster, not the wire id. Test: two sets paired from the same machine produce unrelated relay-visible ids. If the machine id is hardware-derived (not a random UUID), confirm it is not brute-forceable (T21-style check): a hash of a guessable value is not anonymous. |
| Y-7 | **D** *Quota exhaustion without sign-in.* Workers Free allows 100,000 requests a day (https://developers.cloudflare.com/workers/platform/limits/); once exceeded, Cloudflare returns Error 1027 to everyone. One attacker needs to send 100,000 cheap requests; every user's sync stops | No. | **Crit** (availability) | MUST Y-7: before launch, a paid plan (or a protective layer) is in place and a rate limit per address and per key exists at the edge, in front of any Durable Object. No Durable Object is instantiated before a valid signature (stateless Worker verification of signed challenges). Document the cost cap and a kill switch. Also: the allow-list during the build (5.6) stays until this is done. |
| Y-8 | **D** Attacker makes unlimited sets, each holding 1 GB for up to 90 days (5.6 limits: per-address new-set rate, 1 GB per set) | Partly. Per-address limits fail against rotating IPv6 addresses and botnets; per-set 1 GB times many sets is unbounded. | High | MUST Y-8: a global storage ceiling and a proof-of-work or token requirement for creating a set; an unproven set gets a small quota (for example 20 MB) that grows only when a second device authenticates and after N days; unverified sets are purged after 7 idle days. Per-address limits must not lock out users behind shared campus or mobile-carrier NAT (use soft limits plus proof-of-work). |
| Y-9 | **D** A hostile or buggy device fills its own set with `hold` frames to push other devices' waiting data out via the 1 GB "release least recently used" rule | Partly. | Med | MUST Y-9: a single device may not push another device's group out of the set; release prefers the writer's own oldest groups and never releases a group whose lines no device has acknowledged without the "Relay full" notice (5.6 already announces). |
| Y-10 | **T** `received` counters are unsealed claims; a device (or an old removed one before the relay sees the removal) can claim to have received everything, making the relay drop frames others still need | Partly. | High | MUST Y-10: `received` is signed by the claiming device and verified by the relay against the roster; after a removal, the removed key's counters are ignored and cannot trigger drops. |
| Y-11 | **I** IPs, timing, counts, sizes, active hours, public keys seen by Cloudflare and us | No (stated in 2.4 and 8 promise; accepted). | Med | MUST Y-11: the privacy page lists exactly these; relay logs do not retain IPs beyond rate-limit windows (24 hours) where the platform allows; no per-user analytics joined to relay identifiers. |
| Y-12 | **D/E** Register compare-and-swap abuse: a roster device (or removed device pre-relay-knowledge) overwrites `tip:<project>` with junk to put every project into "diverged" | Partly (5.7 "a bad tip raises diverged"). | High | MUST Y-12: a tip that does not connect to local history is **ignored and logged**, not turned into "diverged" (that state appears only when two devices that are current roster members present genuinely unrelated histories). ### 4.6 Session proxy and forwarded calls (5.5, 6.3 `call`, 4.3 B)

This is the highest-risk component. Facts from the code, read in this worktree:

- `ipc/session.ts:280` `session:input` is **raw terminal input**: `sessionManager.sendInput(sessionId, text)`. Raw keystrokes to Claude Code's terminal include Shift+Tab (cycle permission mode, which can reach "bypass permissions"), `!` bash mode, slash commands such as `/permissions`.
- `ipc/session.ts:201` `session:create` passes its payload to `createSession` **unfiltered** (the code's own comment says so). The create options include `skipPermissions`, `cwd`, `resumeSessionId`, `provider`, `model` (`shared/backend-contract.ts:1051`). The existing `remoteGuard` blocks only `provider: 'shell'`.
- `ipc/permissions.ts:21` `permission:respond` accepts `decision` as an arbitrary object; the "Allow for this chat" rule is persisted (`permissionStore`) and revocation exists but nothing limits who can grant.
- `channel-table.ts:~195` `serveRemoteChannel`: **default allow** (a channel is open to a phone unless marked `desktopOnly` or `remoteAllowed: false`). The design's S6 parity test says "every session-scoped channel is `peerAllowed`, or has a refusal message", which is also fail-open for any channel added later.

### 4.8 Project carrier (5.7, 4.2, 3.6) — git bundles as an attack surface

Existing hardening (Code, `sync-spaces/git-transport.ts:62-71`): every git call carries `core.hooksPath=<nonexistent>`,

## 6. What "end-to-end encrypted" may honestly claim

Allowed, once the MUSTs for L-1, L-2, L-6, C-1, P-1/P-4/P-7 are met and the pre-Phase-7 audit has closed its findings (8):

> "Your chats and project files are encrypted on your devices with keys that never leave them. YouCoded's servers and
> Cloudflare store only encrypted data and cannot read it."

Not allowed, and why:

| Phrase | Why not |
|---|---|
| "Zero-knowledge", "YouCoded can't see anything about you" | The relay sees IPs, timing, sizes, device and chat counts, public keys, group counts, `received` counters (A8). With padding (L-4) token sizes are hidden; without it, content leaks. |
| "Forward secret" / "past messages stay safe if a device is stolen" | One static secret per generation; the relay holds up to 30 days of frames under it (R-4). |
| "A removed device can't read anything" | It reads everything sealed before the first frame under the next generation, and what unaware devices keep sending until they learn (R-5). |
| "Safe if your phone is stolen" | A stolen unlocked device holds the keys and can remove the others (8 "Limits"). A locked device on a platform without a hardware key store is only as safe as the disk. |
| "Your backups are private" | The interim GitHub lane is plaintext; cloud backups are unlocked by default (2.10). |
| "Audited" | Only after the audit is done and findings are closed. |
| "Nobody can run commands on your computer" | Paired devices can type into a chat on a host whose assistant can run commands (A6). Bounded by S-1 to S-6, not eliminated. |

Published practice to compare with: Signal's group design keeps membership out of the server's view
(https://signal.org/blog/signal-private-group-system/); Matrix clients check device keys and signatures and let the user
block or verify each device (https://matrix.org/docs/matrix-concepts/end-to-end-encryption/); MLS gives forward secrecy and
post-compromise security by regular key updates and removal that excludes the removed member from the next epoch
(https://www.rfc-editor.org/rfc/rfc9420.html); Tailscale tailnet lock requires nodes to be signed by trusted signing keys
so a compromised coordination server cannot add nodes, with the stated caveat of trust on first use
(https://tailscale.com/kb/1226/tailnet-lock). The Mesh's first-pairing step (PAKE with a hostile relay) has the same shape as
Magic Wormhole (https://magic-wormhole.readthedocs.io/en/latest/welcome.html). The design follows these in spirit and
differs in having no ratchet and live events without signatures.

STRIDE: https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats (not fetched; used as the
method name). OWASP ASVS: https://owasp.org/www-project-application-security-verification-standard/ and MASVS:
https://mas.owasp.org/MASVS/ (not fetched; the audit before Phase 7 should be written against these, which resolves the
unconfirmed reading in design section 8).

## 7. Needs Destin (things a user would experience)

1. **Can another device tell your computer "always allow"?** Today, if a permission box appears and you tap "Allow always" on
   the phone, the computer remembers it for good. Recommendation: from another device you can only allow once or say no;
   "always" must be tapped on the computer itself. Pro: a stolen or misused phone cannot quietly widen what the computer
   may do. Con: one extra trip to the computer. Not recommended against.
2. **A "let other devices type here" switch per chat**, off automatically when the computer is set to skip permission
   boxes. Pro: a computer that never asks can't be driven from anywhere else by accident. Con: one more setting. Recommended.
3. **Extra tap for risky approvals from a phone** (commands that change files outside the project or download and run
   something). Pro: phone screens make careless approvals easy. Con: slower. Recommended.
4. **"Keep this chat on this device only"** for chats where you pasted a password or key. Pro: the only way to keep a secret
   out of every other device and every backup. Con: that chat is lost if the device is lost, and cannot be continued
   elsewhere. Recommended as optional.
5. **Project files that can run things** (`.claude` folder, `.mcp.json`, `.vscode`, Pages). Arriving from another device,
   they are held for you to look at instead of replacing yours. Pro: removes the most direct path from a stolen or removed
   device to commands on your computer. Con: a changed hook or setting does not reach your other computers by itself.
   Recommended.
6. **If two devices remove each other at once, both are removed.** Pro: a thief holding your oldest device cannot win the
   race. Con: a legitimate removal tapped at the same moment as another leaves both outside until you re-pair. Recommended.
7. **A short matching code on both screens when pairing.** Pro: stops a watcher from slipping in first. Con: one more
   step. Recommended.
