**SUPERSEDED 2026-09-27 (same day, later in the session):** Destin decided Excel comments use ONLY
modern threaded comments, never old-style Notes, as the product's write format (design doc's own
changelog, this date). This spike's whole subject — the legacy-Note OOXML shape `exceljs`'s write
path produces — is no longer what T18/T19 build toward; the product never creates a legacy Note at
all going forward (an existing one in a file is still read far enough to refuse `'cell-has-note'`,
never parsed for its own content). The new format's equivalent spike work (threaded comments'
`xl/threadedComments/`+`xl/persons/` shape, researched from real Excel-365 and Google Sheets files
rather than from desktop's own writer output) lives in the design doc's §4.2 and in
`shared-fixtures/doc-comments/xlsx-threaded-reference/`. This document is kept for history —
`xlsx-note-reference/` (the fixture this spike produced) is likewise kept, unmodified, as a
reference for what a genuine legacy Note looks like (still relevant: the product must recognize and
leave one untouched, §4.1), not deleted.

# xlsx legacy-Note OOXML format — spike findings (T18)

T18 (Android xlsx comment reading, doc-comments build) required capturing exactly
what `exceljs` (the library desktop's `xlsx-comments.ts` write path uses) writes to
disk for a legacy cell Note, so T19 (the Kotlin writer, not built by this task) has a
concrete byte-level target instead of an open-ended OOXML spec to reverse-engineer.
This is that capture's findings. The machine-readable, checked-in version of this
same material lives in the `youcoded` app repo at
`shared-fixtures/doc-comments/xlsx-note-reference/` (raw XML parts + `manifest.json`
+ the actual `.xlsx`), generated by
`desktop/tests/fixtures/doc-comments/generate-xlsx-note-reference.mjs` and kept
honest by a re-diff self-check, `desktop/tests/xlsx-note-reference-drift.test.ts`,
that runs on every `npm test`/CI (review 2, F17's own instruction — this is a
"documented, watched risk," not a frozen assumption).

**Method**: rather than reading `exceljs`'s source and guessing, the reference was
captured by actually running desktop's real `addXlsxComment` (the T13 write path,
`desktop/src/main/doc-comments/xlsx-comments.ts`) against a minimal one-sheet, one-
populated-cell workbook, then unzipping the result and reading the literal bytes.
Every claim below is either a direct quote of that captured output or a citation to
the exact `exceljs@4.4.0` source line that explains WHY it looks that way (both
confirmed against `desktop/node_modules/exceljs`, the version this build ships).

## The four pieces (§4.3a's own naming), confirmed

### (a) The VML preamble/namespaces, verbatim

`xl/drawings/vmlDrawing1.vml` (a NEW workbook's first note) is:

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<xml xmlns:v="urn:schemas-microsoft-com:vml" xmlns:o="urn:schemas-microsoft-com:office:office" xmlns:x="urn:schemas-microsoft-com:office:excel"><o:shapelayout v:ext="edit"><o:idmap v:ext="edit" data="1"/></o:shapelayout><v:shapetype id="_x0000_t202" coordsize="21600,21600" o:spt="202" path="m,l,21600r21600,l21600,xe"><v:stroke joinstyle="miter"/><v:path gradientshapeok="t" o:connecttype="rect"/></v:shapetype><v:shape id="_x0000_s1025" type="#_x0000_t202" style="position:absolute; margin-left:105.3pt;margin-top:10.5pt;width:97.8pt;height:59.1pt;z-index:1;visibility:hidden" fillcolor="infoBackground [80]" strokecolor="none [81]" o:insetmode="auto"><v:fill color2="infoBackground [80]"/><v:shadow color="none [81]" obscured="t"/><v:path o:connecttype="none"/><v:textbox style="mso-direction-alt:auto" inset="1.3mm,1.3mm,2.5mm,2.5mm"><div style="text-align:left"/></v:textbox><x:ClientData ObjectType="Note"><x:MoveWithCells/><x:SizeWithCells/><x:Anchor>1, 6, 0, 14, 3, 2, 4, 16</x:Anchor><x:Locked>True</x:Locked><x:AutoFill>False</x:AutoFill><x:LockText>True</x:LockText><x:Row>0</x:Row><x:Column>0</x:Column></x:ClientData></v:shape></xml>
```

Structure, confirmed against `lib/xlsx/xform/comment/vml-notes-xform.js`:
1. `<o:shapelayout>`/`<o:idmap>` — written ONCE per file, unconditionally, before any
   comment shape.
2. `<v:shapetype id="_x0000_t202" ...>` — also written ONCE, unconditionally, shared
   by every note shape in the file (a reusable VML "class").
3. One `<v:shape id="_x0000_sNNNN" ...>` per note. `id` starts at `_x0000_s1025` for
   the first note in a file and increments by 1 for each subsequent note **on the
   same worksheet** (confirmed by adding a second note to an already-noted sheet —
   `_x0000_s1026` followed). `<x:Row>`/`<x:Column>` are the note's cell address,
   **0-indexed** (A1 → Row 0, Column 0) — Kotlin's writer must convert from a 1-based
   cell reference.
4. Root element is bare `<xml>` (not `<v:shapes>` or similar) with the three fixed
   namespace declarations `xmlns:v`/`xmlns:o`/`xmlns:x` — exactly as §4.3a's own
   framing already named.

### (b) `legacyDrawing`'s position after `extLst`

`xl/worksheets/sheet1.xml`'s LAST child, confirmed both by direct capture and by
reading `worksheet-xform.js`'s `render()` (lines ~345-351): `this.map.extLst.render(
xmlStream, model)` is called, and immediately after it — with NOTHING rendered in
between or after — the code loops `model.rels` and emits `<legacyDrawing r:id="…"/>`
for the `VmlDrawing`-typed relationship. This plain fixture never emits a real
`<extLst>` at all (no data validation/conditional formatting extension features are
present), so the directly-observable fact is: **`<legacyDrawing>` is the LAST element
in `<worksheet>`, full stop** — when an `<extLst>` IS present (a feature this spike's
minimal fixture doesn't exercise), it sits immediately before `<legacyDrawing>`
rather than after it. A from-scratch Kotlin writer that naively appends
`<legacyDrawing>` before the closing `</worksheet>` tag gets this right for the
common case; it only needs the extLst-ordering rule if it ALSO ever writes an
`<extLst>` of its own (T19 was not observed to need this — flagging for whoever
builds it).

### (c) The vml Content-Types `Default` entry — non-`+xml`, confirmed exact string

`[Content_Types].xml` contains, among the usual `Default`/`Override` entries:

```xml
<Default Extension="vml" ContentType="application/vnd.openxmlformats-officedocument.vmlDrawing"/>
```

Confirmed by `content-types-xform.js` and by direct capture — **no `+xml` suffix**,
unlike `xl/comments1.xml`'s own entry:

```xml
<Override PartName="/xl/comments1.xml" ContentType="application/vnd.openxmlformats-officedocument.spreadsheetml.comments+xml"/>
```

Both strings are captured verbatim in `shared-fixtures/doc-comments/xlsx-note-
reference/manifest.json` (`contentTypes.vmlDefaultContentType` /
`contentTypes.commentsOverrideContentType`) so a Kotlin writer's own
`[Content_Types].xml` mutation can assert against the exact string rather than a
hand-retyped copy.

### (d) Both worksheet-rels entries, same relative order

`xl/worksheets/_rels/sheet1.xml.rels`:

```xml
<Relationships xmlns="http://schemas.openxmlformats.org/package/2006/relationships"><Relationship Id="rId1" Type="http://schemas.openxmlformats.org/officeDocument/2006/relationships/comments" Target="../comments1.xml"/><Relationship Id="rId2" Type="http://schemas.openxmlformats.org/officeDocument/2006/relationships/vmlDrawing" Target="../drawings/vmlDrawing1.vml"/></Relationships>
```

**Two separate `Relationship` elements** (never a combined one), in this order:
Comments (`rId1`) first, then VmlDrawing (`rId2`). Both `Target`s are relative to
`xl/worksheets/` (the rels file's own directory) — `../comments1.xml` resolves to
`xl/comments1.xml`, `../drawings/vmlDrawing1.vml` resolves to
`xl/drawings/vmlDrawing1.vml`. Confirmed against `worksheet-xform.js:170-179`.

## Additional findings, not named by §4.3a's own "four pieces" framing but load-bearing for both T18 (read) and T19 (write)

### `comments<N>.xml`'s structure

```xml
<comments xmlns="http://schemas.openxmlformats.org/spreadsheetml/2006/main"><authors><author>Author</author></authors><commentList><comment ref="A1" authorId="0"><text><r><t>You: A brand new note.</t></r></text></comment></commentList></comments>
```

- **`<authors>` always contains exactly ONE `<author>`, and its text is always the
  literal string `"Author"`** — never a real name. Confirmed in
  `comments-xform.js`: `// TODO: support authors properly` /
  `xmlStream.leafNode('author', null, 'Author')`. `authorId="0"` is likewise
  hardcoded on every `<comment>` element, regardless of how many comments exist.
  This is WHY desktop's own reader/writer (§4.1, `xlsx-comments.ts`) puts the real
  author's name as the FIRST LINE of the note's own `<text>` body instead of reading
  it from OOXML's own author mechanism — that mechanism carries no real information
  in this app's files, ever.
- **Note text is a sequence of `<r>` ("run") elements, each with a `<t>` leaf** — a
  plain-string `cell.note = "..."` produces exactly ONE `<r>` for the WHOLE string
  (confirmed: `note.js`'s `Note` class wraps a plain string as
  `{texts: [{text: theWholeString}]}`, and `comment-xform.js` renders one `<r>` per
  `texts[]` entry). A multi-turn transcript (reply threads, `\n\n`-joined per §4.1)
  is therefore still ONE run with embedded LITERAL newline characters in its `<t>`
  content — never split into multiple runs by paragraph. **A reader must concatenate
  every `<r><t>` under `<text>` in document order** to reconstruct the full body
  (this matters if some OTHER tool, e.g. real Excel, wrote a genuinely multi-run
  note — e.g. bold text mid-sentence — which this app's own writer never produces
  but a foreign note legitimately might).
- **`<t xml:space="preserve">` is added whenever the text starts/ends with
  whitespace OR contains a newline** (confirmed, `text-xform.js`:
  `/^\s|\n|\s$/.test(model)`). Since this app's own multi-turn transcripts almost
  always contain `\n\n`, `xml:space="preserve"` is present on nearly every note this
  app's writer produces. **This does not matter for a READER** (T18's scope) — any
  standards-conformant XML parser, including Android's `javax.xml.parsers` DOM
  builder, preserves whitespace in text content regardless of whether
  `xml:space="preserve"` is declared; the attribute is a hint for XML EDITORS that
  might otherwise collapse/trim whitespace, not a parsing requirement. It DOES
  matter for T19's writer if byte-for-byte fidelity with exceljs's own output is a
  goal (documented here for that task, not acted on by this one).
- The zero-width space (U+200B) and checkmark (U+2713) in the app's resolve marker
  (§4.1's `​✓ Resolved`) are written as literal UTF-8 bytes inside `<t>`, with no XML
  entity escaping needed or applied (confirmed byte-for-byte in the captured
  `comments1.xml` when the fixture included a resolved note) — an ordinary XML
  parser round-trips them with no special handling required on the READ side either.

### Worksheet id / part numbering (load-bearing for T18's `id` field, `x-${worksheetId}-${cell}`)

- **`comments<N>.xml`/`vmlDrawing<N>.vml` are numbered by the WORKSHEET's position
  in `xl/workbook.xml`'s own `<sheets>` list (its `sheetId` attribute), not by "the
  Nth worksheet that happens to have a note."** Confirmed: a two-sheet workbook
  where only the SECOND sheet has a note still produces `xl/comments2.xml`/
  `xl/drawings/vmlDrawing2.vml` (never `comments1.xml`) — the number tracks the
  worksheet, not a running count of commented sheets.
- **`worksheet.id`** (the field desktop's `xlsx-comments.ts` embeds in every comment
  id, `x-${worksheet.id}-${cell.address}`) **comes from `<sheet sheetId="N" .../>`
  in `xl/workbook.xml` when a workbook is LOADED from disk** — confirmed in
  `lib/xlsx/xform/book/workbook-xform.js`'s `reconcile()`: `worksheet.id =
  sheet.id`, and `sheet-xform.js`'s `parseOpen` sets `id: parseInt(node.attributes.
  sheetId, 10)`. On a FRESHLY built (never-saved) workbook, `id` is assigned
  sequentially as sheets are added (`workbook.js`: `nextId = this._worksheets.length
  || 1`) — which happens to equal `sheetId` for any workbook exceljs itself wrote,
  since it renders `sheetId: model.id` right back out. **For T18's Kotlin reader,
  this means: read the worksheet id from `<sheet sheetId="…">`'s attribute value,
  never from the sheet's POSITION in the `<sheets>` list** — they are the same
  number for every fixture this build ships, but are not guaranteed to be for an
  arbitrary foreign `.xlsx` a user opens (e.g. one where a sheet was deleted and
  re-added in a different tool, leaving a gap in `sheetId` values). Getting this
  wrong would silently produce different comment `id`s than desktop's own reader for
  the exact same file.
- Resolving which worksheet PART (`xl/worksheets/sheetN.xml`) belongs to which
  `<sheet>` entry in `workbook.xml` requires following its `r:id` through `xl/_rels/
  workbook.xml.rels` (`Target` is relative to `xl/`, e.g. `worksheets/sheet1.xml` →
  `xl/worksheets/sheet1.xml`) — **never assume the Nth `<sheet>` element maps to
  `sheetN.xml`.** In every fixture captured here it does, but the relationship, not
  positional convention, is the only way OOXML actually declares this mapping.
- Finding a worksheet's comments part requires its OWN rels file, `xl/worksheets/
  _rels/sheetN.xml.rels` (name derived from the worksheet part's own filename), and
  looking for the `Relationship` whose `Type` ends in `.../relationships/comments`
  — never a fixed `commentsN.xml` naming guess, even though it happens to line up
  with the sheet's own filename number in every captured case.

## What this means for T18 (already applied in this task's Kotlin reader)

- `XlsxComments.kt`'s reader walks `xl/workbook.xml` → `<sheets>` for
  `{sheetId, name, r:id}`, resolves each `r:id` through `xl/_rels/workbook.xml.rels`
  to a worksheet part path, then that worksheet's own `_rels/sheetN.xml.rels` for its
  comments-relationship target — never a hardcoded `commentsN.xml` guess.
- Comment/reply id generation exactly mirrors desktop: `x-${sheetIdAttribute}-
  ${cellRef}`, using the `sheetId` XML attribute, not list position.
- Note body reconstruction concatenates every `<r><t>` text node under a `<comment>`'s
  `<text>` element, in document order — never assumes a single run.
- `<authors>` is read only to the extent of confirming the part parses; its content
  (always literally `"Author"`) carries no information this reader uses, matching
  §4.1's own committed decision that the real author lives in the note BODY's first
  line, not OOXML's own author slot.

## What this means for T19 (Kotlin writer — out of this task's scope, captured here so it doesn't have to re-derive any of it)

- The checked-in reference (`shared-fixtures/doc-comments/xlsx-note-reference/`) is
  the literal byte target for "add the first note to a worksheet with none yet."
  `manifest.json` gives the two content-type strings and the worksheet-rels order as
  machine-checkable values, not prose to retype.
- `<v:shape id="_x0000_sNNNN">` numbering increments per-worksheet starting at 1025 —
  a SECOND note on an already-noted worksheet needs `id="_x0000_s1026"`, discovered
  by scanning the existing `vmlDrawing<N>.vml` for the highest `_x0000_s` suffix
  already in use (mirroring how desktop's own `w:id` uniqueness rule works for docx,
  §3.3 review 1 F6) — never assumed to start over at 1025.
- `<x:Row>`/`<x:Column>` in the VML shape are 0-indexed; a cell reference like `"B2"`
  is Row 1, Column 1.
- `legacyDrawing` is emitted once per worksheet (one `<legacyDrawing r:id="…"/>`),
  even though a worksheet can carry many notes — all of a worksheet's notes share
  ONE `comments<N>.xml` and ONE `vmlDrawing<N>.vml`/`legacyDrawing` reference; adding
  a second note to an already-noted worksheet means appending a `<comment>` to the
  EXISTING `commentList` and a `<v:shape>` to the EXISTING `vmlDrawing<N>.vml`, not
  minting new parts.
- The drift self-check (`desktop/tests/xlsx-note-reference-drift.test.ts`) is the
  mechanism that will catch it if any of the above stops being true on a future
  `exceljs` bump — T19 should read (not duplicate) that test's own fixture-building
  helper (`tests/fixtures/doc-comments/xlsx-note-parts.mjs`) if it ever needs to
  re-capture a richer scenario (e.g. a second note on an already-noted sheet) rather
  than hand-building a new one.
