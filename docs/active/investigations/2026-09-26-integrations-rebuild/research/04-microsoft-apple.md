# Microsoft & Apple Integration Research — 2026-09-26

## PART A — MICROSOFT

### A1. Multi-tenant Entra app registration as a public client (desktop, PKCE/loopback or device code)

**Registration itself: free.** Creating an Entra app registration costs nothing and does not require a paid Azure subscription — you can create a free Entra ID tenant (via a Microsoft/Azure free account) and register apps in it at no charge. Ongoing use of OAuth2 credentials (client ID, PKCE flow) is free indefinitely as long as the tenant/app registration stays active.
Source: https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app , https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-create-new-tenant , https://learn.microsoft.com/en-us/azure/cost-management-billing/manage/microsoft-entra-id-free

**Setup**: register as "Public client/native (mobile & desktop)", enable "Allow public client flows", add a loopback (`http://localhost`) or custom redirect URI, use Authorization Code + PKCE (no client secret) or device code flow for headless. Supported account type "Accounts in any organizational directory and personal Microsoft accounts" gives the `common` authority (multi-tenant + personal).
Sources: https://learn.microsoft.com/en-us/entra/identity-platform/howto-convert-app-to-be-multi-tenant , https://learn.microsoft.com/en-us/graph/auth-register-app-v2

**Personal account caveat (important, found in Softeria's own docs)**: using the generic `common` authority for MSA (outlook.com/hotmail) accounts can cause refresh tokens to be rejected after ~1 hour; Softeria's README says personal accounts should explicitly use the `consumers` authority instead of `common`. This is a real gotcha for a "sign in with any Microsoft account" flow — we'd likely need to branch authority (`consumers` vs `organizations`) based on account type, not just use `common` everywhere.
Source: https://github.com/Softeria/ms-365-mcp-server (README, fetched)

**Publisher verification — what's required, is it free, what breaks if skipped:**
- Verification itself has no direct fee, but it requires enrolling in the **Microsoft AI Cloud Partner Program (formerly "MPN" — Microsoft Partner Network)** via partner.microsoft.com, completing **business verification** (a real legal-entity check, similar in kind to what tripped up the LLC's Azure Trusted Signing application), obtaining a Partner Global Account (PGA) + Partner ID, then linking that Partner ID to the Entra app registration whose **publisher domain** must match a DNS-verified domain on the account or tenant.
- Required roles: Application Administrator/Cloud Application Administrator in Entra, plus CPP Partner Admin/Account Admin in Partner Center.
- Region-specific MPN IDs are NOT accepted — must be the global partner account.
- **If skipped:** since Nov 2020, Microsoft enforces "risk-based step-up consent" by default on newly registered multi-tenant apps requesting anything beyond basic sign-in/profile. Practically: (a) users in tenants with default security settings will hit a **"not verified" warning** before consenting — many will bail; (b) many work/school (Entra) tenants are configured to **block user consent entirely for unverified apps**, forcing an IT admin to grant tenant-wide admin consent before any employee can connect their account — this is a real adoption barrier for a consumer-facing app that a work user might want to try; (c) personal Microsoft accounts (outlook.com) are **not gated by tenant consent policy** — they always see a personal "Let this app access your info?" screen, verified or not, so verification mainly matters for the work/school half of Part A, not the personal half.
- Because our owner's LLC reportedly struggled with Microsoft's business-verification process for code-signing (Azure Trusted Signing), the same underlying verification pipeline (legal entity, domain, sometimes D&B/D-U-N-S-style checks) is a plausible recurring obstacle — this should be treated as a real risk to budget time for, not a rubber stamp.
Sources: https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview , https://developer.nylas.com/docs/provider-guides/microsoft/verification-guide/ (third-party SaaS walkthrough, very close analog to our situation) , https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/user-admin-consent-overview , https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-consent-requests

**Net for Part A:** one multi-tenant public-client app registration (free, ~minutes) gets personal + work accounts working technically. Publisher verification is optional to get *something* working (personal accounts always work; some lenient work tenants allow it too) but is effectively required to reach locked-down business tenants without an IT admin's help, and it runs through the same business-verification machinery that has already given the LLC trouble once.

### A2. Existing MCP servers / CLIs and their auth

- **Softeria ms-365-mcp-server** (Node, Graph API wrapper): ships a **built-in Softeria-owned Entra app** (client ID not published in the README, described only as "the default Softeria app" with a "lean, fixed permission set") so a user can start immediately without registering their own app. Supports both personal (MSA, `consumers`) and work/school (`--org-mode` flag) accounts. Lets you swap in your own `MS365_MCP_CLIENT_ID`/`CLIENT_SECRET`/`TENANT_ID` for enterprise/headless deployments needing pre-approved permissions, or hand it an externally-obtained `MS365_MCP_OAUTH_TOKEN`. This is architecturally exactly the "ride someone else's public client" pattern.
  Source: https://github.com/Softeria/ms-365-mcp-server
- **Microsoft's own "Work IQ" MCP/CLI** (`microsoft/work-iq`): official, reached GA June 16 2026. Very different shape from what we want — it requires a **Microsoft 365 Copilot license** per user, is governed/toggled by the tenant's M365 admin center, and is read-only by default unless an admin turns on writes. Not viable as our integration path since most personal/consumer users won't have a Copilot license.
  Sources: https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/work-iq/mcp/overview , https://github.com/microsoft/work-iq
- **pnp/cli-microsoft365** (m365 CLI): the community PnP tool. Note a hard breaking change — Microsoft **deleted the old shared "PnP Management Shell" multi-tenant app on 2024-09-09**; that well-known client ID no longer works, and users of that CLI must now register their own Entra app per tenant. This is a cautionary tale: riding a shared/well-known client ID is not durable — Microsoft can and has killed one outright.
  Source: search results citing github.com/pnp/cli-microsoft365 history
- **Well-known Microsoft first-party public client IDs** exist and are technically usable by anyone via device-code/PKCE flows without registering your own app — e.g. Azure PowerShell's `1950a258-227b-4e31-a9cf-717495945fc2`, and Microsoft Graph CLI/"Graph Command Line Tools" `14d82eec-204b-4c2f-b7e8-296a70dab67e`. **Risk/ToS**: these are Microsoft's own first-party client IDs, intended for Microsoft's own tools; nothing in the search results found explicit third-party ToS permission to impersonate them in another product, and the PnP shutdown above shows Microsoft will retire an ID it doesn't consider "yours" without notice. Using someone else's client ID as a permanent strategy is fragile and could look like impersonation/consent-phishing if not disclosed to users — Softeria's approach (own branded app, clearly Softeria's, offered as a default) is the safer version of this pattern; hot-wiring Azure PowerShell's ID would not be.
  Sources: search results (constants/o365sprayer, InternalAllTheThings Azure AD access-and-tokens reference), https://learn.microsoft.com/en-us/graph/cli/app-only

### A3. Brokers — Composio / Pipedream / Arcade

- **Composio**: offers a managed OAuth app for Microsoft Teams (sign in with normal MS account, approve access); markets 250+ integrations with rich API coverage claims, but the search results only confirm Teams explicitly — Outlook/Calendar/OneDrive coverage wasn't independently confirmed in this pass (unverified — check Composio's own toolkit docs before relying on it).
- **Pipedream Connect**: confirmed dedicated integrations for **Microsoft Outlook Email**, **Microsoft Outlook Calendar**, and **Microsoft 365**, all interoperable with Microsoft Teams tools in one MCP session. Backed by Pipedream's much larger (2,500+ app) catalog/OAuth-proxy infrastructure.
  Source: https://pipedream.com/apps/microsoft-outlook/integrations/microsoft-teams , https://pipedream.com/apps/microsoft-outlook-calendar/integrations/microsoft-teams
- **Arcade.dev**: has explicit, named toolkits — "Microsoft Outlook Mail" (Graph Mail API: read/compose/send/search/organize, personal + shared/delegated mailboxes) and "Microsoft Outlook Calendar" (Graph Calendar, OAuth2 delegated). Arcade centrally manages the Microsoft Graph OAuth app, token acquisition/refresh, and per-user scopes — i.e., Arcade eats the publisher-verification/app-registration problem for us in exchange for running through their hosted OAuth broker (and their pricing/dependency).
  Sources: https://docs.arcade.dev/en/resources/integrations/productivity/microsoft-outlook-mail , https://docs.arcade.dev/en/resources/integrations/productivity/microsoft-outlook-calendar , https://www.arcade.dev/blog/microsoft-office-365-mcp-servers-launch/

All three brokers effectively let us skip registering/verifying our own Entra app by riding their already-verified one — at the cost of a broker subscription/usage fee and a dependency on a third party sitting between the user and their Microsoft data.

### A4. Non-OAuth paths

- **IMAP/SMTP for Outlook.com/personal mailboxes**: **Basic auth (including app passwords) is being killed.** Microsoft's phased SMTP AUTH Basic-auth rejection began March 1 2026, reaching 100% rejection by April 30 2026. After that, outlook.com/Exchange Online IMAP/SMTP require OAuth2 (XOAUTH2) — plain username/app-password IMAP/SMTP is not a viable path for Microsoft mail going forward. This forecloses the "just do IMAP like iCloud" shortcut that works for Apple.
  Source: https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-basic-authentication-exchange-online , https://www.getmailbird.com/microsoft-modern-authentication-enforcement-email-guide/
- **ICS calendar publishing**: standard read-only ICS feed subscription is still a viable, OAuth-free fallback for *reading* a Microsoft/Outlook calendar (publish a link, we poll/parse the .ics) — not explored in depth this pass, but architecturally unaffected by the Basic-auth shutdown since it's not a login at all. Not useful for writing/creating events or for mail.

### A5. Windows-native paths

- **WinRT Appointments API (`Windows.ApplicationModel.Appointments`) from Node/Electron**: reachable via the community **NodeRT** project (auto-generated native Node addons from WinRT metadata; needs recompiling as a native addon for Electron, and per NodeRT's own notes, from Electron v14+ these modules must be required in the **main process**). Microsoft also has a newer, official **dynamic WinRT projection for Node.js** (public preview) letting Electron/Node call WinRT APIs directly from JS/TS without a native-addon build step — likely the better long-term bet if it matures, but it's preview-stage as of mid-2026.
  Sources: https://www.npmjs.com/package/windows.applicationmodel.appointments , https://github.com/NodeRT/NodeRT , https://devblogs.microsoft.com/ifdef-windows/a-new-way-to-bring-native-windows-apis-to-javascript-introducing-dynamic-api-projections-for-node-js/ , https://www.theregister.com/devops/2026/07/27/microsoft-lays-out-a-buffet-of-windows-goodies-for-javascript-developers/5279244
  Caveat: this only reaches calendar/contacts *accounts the Windows Mail/Calendar app itself is configured to sync* — it's not a Graph API replacement, and it's Windows-only (no parity story for Mac/Linux/Android), which cuts against YouCoded's cross-platform design unless treated purely as an optional Windows-only bonus path.
- **Outlook COM automation**: **classic Outlook still supports COM/VBA**, but Microsoft has moved "new Outlook for Windows" to the default for enterprise M365 subscribers as of April 2026, and **new Outlook has no COM/VSTO/VBA support at all** (WebView2/Office.js only) — with classic Outlook now formally on a deprecation path (support window extended to 2029, per the search results, but no further feature investment). Server-side, Exchange Web Services (EWS) — which some COM/legacy integrations lean on — is slated to begin disablement in Exchange Online starting **October 2026**. Net: COM automation is a shrinking, already-legacy target; not a sound long-term bet for a product being built now.
  Sources: https://www.getmailbird.com/outlook-classic-extended-power-user-transition-guide/ , https://www.mckennaconsultants.com/why-you-must-migrate-your-vsto-add-ins-before-april-2026/ , https://guidy.ai/blog/new-outlook-vs-classic-outlook/

## PART B — APPLE

### B1. macOS native (EventKit/Contacts/AppleScript/JXA/Shortcuts/TCC/notarization)

- **TCC attribution**: macOS grants Calendar/Reminders/Contacts/Automation permissions to the **process that macOS considers "responsible"** for the request — for a CLI tool run from a terminal, that's the terminal app; for something spawned by an Electron app via a helper binary, the grant needs to land on a *stable* identity. Multiple real-world MCP-server projects (`apple-native-mcp`, `vicinaehq/vicinae`) report TCC prompts being silently denied or granted to the wrong app when the helper's signing identity isn't stable across rebuilds, or when the Info.plist is missing the correct `NSRemindersUsageDescription`/`NSCalendarsUsageDescription`/privacy strings. Best practice from `bite-mcp` and similar: ship the Swift/EventKit helper to a **fixed path** (e.g. `~/Library/Application Support/<app>/bin/`) with a **stable, notarized code signature**, so upgrades don't re-trigger the permission dialog or misattribute the grant. This matches and validates what YouCoded's existing vendored Swift/EventKit helper approach should already be doing — worth auditing that our helper's signing/path is stable across app updates.
  Sources: https://github.com/that-mathevs/apple-native-mcp/issues/4 , https://github.com/vicinaehq/vicinae/issues/1922 , https://github.com/Ktesio/bite-mcp
- **Shortcuts CLI**: `shortcuts run "<name>"` runs a named Shortcut from the terminal; there's also a `shortcuts://` URL scheme and a scriptable background "Shortcuts Events" process. No built-in scheduler (would need launchd/cron or an Automator wrapper), and it only runs Shortcuts the *user* has already built/installed — not something we could ship a canned automation through without asking the user to import a Shortcut first. Useful as a power-user escape hatch, not a primary integration path.
  Sources: search results (Shortcuts CLI/Mac Shortcuts Automation reference, macworld, medium)
- **Existing tools, quality/maintenance signal**:
  - **steipete/remindctl** — actively documented, wraps EventKit, requires macOS 14+, syncs normally through iCloud; has a dedicated site (remindctl.sh) — looks well-maintained.
  - **steipete/imsg** — send/read/stream iMessage & SMS, same author.
  - **icalBuddy** — long-standing but effectively superseded by **icalPal** (ajrosen/icalPal), a modern, compatible replacement; icalBuddy itself looks stagnant.
  - **apple-mcp (supermemoryai/dhravya)** — was the most popular Apple MCP server, covering Messages/Notes/Contacts/Mail/Reminders/Calendar/Maps via AppleScript+JXA (SQLite directly for Messages). **Archived January 2026** — no longer maintained upstream, though forks (`that-mathevs/apple-native-mcp`, others) continue it. Treat the original as dead; any fork needs its own maintenance-quality check before we'd depend on it.
  - **mcp-server-apple-events (FradSer)** — EventKit-based Reminders/Calendar MCP, ships a pre-built universal *code-signed* binary via npm so users don't need Xcode/Swift toolchain — a good template for how our helper distribution should look.
  Sources: https://github.com/steipete/remindctl , https://remindctl.sh/ , https://github.com/ajrosen/icalPal , https://github.com/supermemoryai/apple-mcp , https://github.com/that-mathevs/apple-native-mcp , https://github.com/FradSer/mcp-server-apple-events

### B2. Cross-platform iCloud via CalDAV/CardDAV + IMAP/SMTP (app-specific password)

This is the standout option because it is the **only Apple path that works on Windows/Linux/Android, not just Mac**.
- **Setup UX**: user must sign in at account.apple.com, enable 2FA (mandatory since 2020), and generate a 16-character **app-specific password** — a manual, one-time, non-technical-but-unfamiliar step. Not OAuth, so no publisher-verification analog and no consent-warning risk, but it does require walking a non-developer user through a somewhat "hidden" Apple ID security page.
- **CalDAV/CardDAV endpoints**: `caldav.icloud.com` / `contacts.icloud.com`, Basic Auth over TLS with Apple ID + app-specific password. Libraries: **tsdav** (natelindev/tsdav, actively maintained, used by Cal.com's fork `calcom/tsDAV`) is the standard Node/TS client for both CalDAV and CardDAV; **ts-caldav** is a lighter CalDAV-only alternative.
  Sources: https://github.com/natelindev/tsdav , https://github.com/calcom/tsDAV , https://github.com/KlautNet/ts-caldav
- **IMAP/SMTP for iCloud Mail**: `imap.mail.me.com:993` (SSL) / `smtp.mail.me.com:587` (STARTTLS), same app-specific password. Notably **Apple has NOT deprecated Basic-auth IMAP/SMTP the way Microsoft has** — this remains a stable, simple path. Gotcha: IMAP username is the local part only (`name`, not `name@icloud.com`) while SMTP wants the full address.
  Source: https://support.apple.com/en-us/102525
- **Reminders limitation (important, confirms the prompt's note)**: since **iOS 13/macOS Catalina**, Apple's own Reminders app migrated to a **private, non-CalDAV sync store** — CalDAV itself still works fine for calendars and for third-party to-do apps that never used Apple's Reminders app, but **Apple's own Reminders lists/items are no longer reachable over CalDAV at all**. So a cross-platform CalDAV integration gets iCloud **Calendars** but **not Reminders** — Reminders access is Mac-only (via EventKit/our existing helper). This is a real coverage gap to flag: "iCloud reminders on Windows/Linux/Android" is not achievable via CalDAV; only Calendar/Contacts/Mail are.
  Sources: https://support.busymac.com/blog/112990-reminders-in-ios-13-and-macos-catalina-drops-support-for-caldav , https://discussions.apple.com/thread/253490589
- **Notes**: no API of any kind (confirmed by absence — nothing found contradicting this, consistent with common knowledge); Mac-only via AppleScript/JXA against Notes.app, as already implemented.

### B3. iMessage

Only reachable on a Mac: reading requires **Full Disk Access** to `~/Library/Messages/chat.db` (cannot be granted programmatically — user must do it by hand in System Settings), sending goes through AppleScript driving Messages.app. **2026 risk signal, directly relevant**: OpenAI shipped a ChatGPT-for-Mac iMessage plugin in August 2026 that drew significant press criticism (Forbes, Fortune, TechTimes) because Full Disk Access is an all-or-nothing grant that *also* exposes Mail, Safari history, and Time Machine backups — not just Messages — and because OpenAI's own "persistent approval" setting lets the AI send messages without per-send confirmation, which OpenAI itself discourages. If YouCoded ever ships iMessage read/send, this is the exact reputational trap to avoid: require FDA with very explicit user-facing explanation of its true scope, and never offer a "skip confirmation" toggle for outgoing messages.
Sources: https://fortune.com/2026/08/26/chatgpt-apple-messages-plugin-privacy-security/ , https://www.techtimes.com/articles/325157/20260821/chatgpt-imessage-plugin-grants-full-disk-access-mail-safari-backups.htm , https://www.forbes.com/sites/gabrielalinzainescu/2026/08/21/chatgpt-can-now-send-your-imessages---and-test-apples-privacy-brand/

### B4. Android

Confirmed the basic model: **`CalendarContract`** (needs `READ_CALENDAR`/`WRITE_CALENDAR` runtime permission) and by extension `ContactsContract` expose **whatever accounts the phone's own sync adapters have already set up** — Google, Exchange, Samsung, etc. — as one unified content-provider surface, with a single Android runtime permission grant (no OAuth on our side at all, since the OS already did the account linking). This is architecturally the simplest, lowest-maintenance Microsoft/Google/anything calendar-contacts path we have, but it's Android-only and depends entirely on the user already having synced the account at the OS level. Generic CalDAV (e.g. iCloud, self-hosted) also works identically on Android as any other platform via the same tsdav-style client.
Source: https://developer.android.com/identity/providers/calendar-provider (cross-account enumeration details not fully confirmed in this pass — reasonably well-established Android behavior but flagged as not independently verified beyond the official provider-overview doc).

## Flags / unverified items
- Composio's Outlook/OneDrive/Word/Excel/To Do coverage was not independently confirmed (only Teams was).
- Android's cross-account (Google/Exchange/Samsung) enumeration behavior via CalendarContract is based on general provider docs, not a source explicitly confirming multi-account enumeration mechanics.
- Softeria's actual built-in client ID value was not disclosed in its README (only that a built-in app exists).
- The publisher-verification timeline ("minutes" per Nylas) assumes the business-verification step is already satisfied; that step is exactly where the LLC previously had trouble, so real elapsed time could be much longer.
