- F1 — `desktop/src/renderer/components/project-view/ProjectView.tsx:212-224` — `PROJECT_VIEW_OPEN_SKILLS_TAB` silently fails to select the requested project (and therefore scrolls nowhere useful) whenever Project View is already open when the request arrives. The effect that consumes a pending project path (`pendingSkillsProjectPathRef`) only runs on `[projects, indexLoaded]` changes (line ~218-224); the project list is only re-fetched by the effect at line ~396-420, which is keyed on `[projectViewOpen]` and re-fetches only on a `false→true` transition. `PROJECT_VIEW_OPEN_SKILLS_TAB`'s reducer case (`artifact-tracker.ts`) unconditionally sets `projectViewOpen: true`; if it was already `true` (Project View already open — e.g. the user is already browsing one project and something dispatches this action for a different project), the selector value doesn't change, the fetch effect never re-fires, `indexLoaded`/`projects` never change, and the second effect that would apply `pendingSkillsProjectPathRef.current` never re-runs. The ref is silently discarded and Project View stays on whatever project was already active — wrong project shown, and `scrollToNeedsSetup`'s target (`#project-tools-needing-setup`) will usually not exist there (or exists but has nothing to do with the request), so the promised "opens Projects on Skills & tools, scrolled to that missing item's row" (contract R14, T5's caller) silently degrades to "opens Skills & tools for whichever project you were already looking at." — Confirmed by reading the full effect chain and the reducer (`artifact-actions.ts`/`artifact-tracker.ts`): `PROJECT_VIEW_OPEN_SKILLS_TAB` case does `{...s, projectViewOpen: true, ...}` with no transition guard, and the two consumer effects have disjoint, non-overlapping dependency arrays that only intersect via `projects`/`indexLoaded`, which don't change on this path. Not runnable as a repro from a unit test without also wiring up `useArtifactSelector`/dispatch plumbing, but the logic is unambiguous from the code alone.

- F2 — `desktop/package.json:20` / `desktop/src/renderer/components/project-view/SkillsToolsTab.tsx:31` — the design-lint ratchet was raised (542→551) with a false justification, and a cleaner fix exists that wouldn't need raising it at all. The commit message says the `!whitespace-normal` override is "the same escape hatch `ContextSettings.tsx` already uses in production" — but `desktop/src/renderer/components/assistant-settings/ContextSettings.tsx` contains no `whitespace-normal` and no `descriptionClassName` usage at all (`rg` confirms zero hits). The *only* prior use of this exact `!whitespace-normal` pattern is `dev/workbench/mockups/ProjectPluginControls.tsx`, which is explicitly exempt from `lint:design` (`ignorePatterns: ["src/renderer/dev/**"]` in `.oxlintrc.design.json`) — i.e. there is no actual production precedent, only a workbench mockup the design-lint config was never checking. Separately, the root cause is in the primitive itself: `SettingRow.tsx:211` does `` `${d.desc} -mt-0.5 ${variant === 'nav' ? 'truncate' : ''} ${descriptionClassName ?? 'text-fg-muted'}` `` — plain string concatenation, not routed through the `mergeClasses`/conflict-group mechanism the rest of the primitives use (per `react-renderer.md`: "a caller's `className` REPLACES base tokens per conflict group via `mergeClasses`"). Because `truncate` and a wrapping override are both plain Tailwind utility classes with no conflict-group resolution between them, callers are forced into `!important` to win, which is exactly what trips `shadcn/no-restyle` and required raising the ratchet. A fix inside `SettingRow` (e.g., skip appending `truncate` when a `descriptionClassName` explicitly requests wrapping, or route `description`'s classes through the same conflict-group merge used elsewhere) would let both this file and the mockup drop `!important` entirely, without touching the ratchet. — Confirmed by reading `SettingRow.tsx:196-215`, `.oxlintrc.design.json`, and `rg` for `whitespace-normal`/`descriptionClassName`/`ContextSettings` across `desktop/src`.

- F3 — `desktop/src/renderer/components/project-view/SkillsToolsTab.tsx:219-239` (`commit`) — rapid toggling of two different rows before the first `project-extensions:set` round-trip resolves can silently drop or corrupt one of the two optimistic updates. `commit` captures `prev = viewRef.current` synchronously, but `viewRef.current` is only advanced by a `useEffect` (`state.kind === 'ready'` → `viewRef.current = state.view`) that runs after React commits/paints — it is not updated synchronously inside `commit` itself. If a second `commit` call fires before that effect has run (e.g. two toggles in the same tick, or in a fast double-click), both read the same stale `prev`, so the second optimistic view is computed from a base that doesn't include the first toggle's in-flight change — the first toggle's visible optimistic state gets silently overwritten by the second `setState`. Whichever request's response resolves second will win and paper over the other's optimistic view with only its own change reflected in `res.view` (a real server response, so eventually consistent, but with a visible flicker/regression window), and if the first request fails, its revert-to-`prev` will revert to a snapshot that predates the second toggle too. — Confirmed by reading the full `commit`/`viewRef` implementation; not reproduced with a timed test (would need fake timers or unflushed-effect microtask control), so marked [PLAUSIBLE].

- F4 — `desktop/src/renderer/components/project-view/ProjectView.tsx:1046-1054` — `SkillsToolsTab` is now unconditionally mounted alongside `FilesTab` whenever `activeProject` is set, regardless of which tab is active, so `project-extensions:get` fires on *every* Project View open for *every* project browsed — even when the user never opens the Skills & tools tab. Before this commit, this data-fetching component didn't exist in production (only the workbench-only demo did), so this is a new IPC round trip added to the default/first-tab path unconditionally. This matches the same pattern already used for `FilesTab` (also eagerly mounted) so it isn't a departure from precedent, but it's a real, measurable additional per-open cost that a mockup replacement didn't previously pay. Likely an accepted tradeoff (the same one FilesTab already makes, in exchange for zero-latency tab switches), not a regression against a stated rule, so severity is low. — Confirmed by reading the JSX around `activeProject && (<FilesTab .../>)` and `activeProject && (<SkillsToolsTab .../>)`, both unconditional on `tab`.
