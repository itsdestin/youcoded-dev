# Mesh chat store: data-loss and correctness review

Subject: commit `9221e279d`, `desktop/src/main/mesh/store/` (S1 adapters, S2 store). Reviewer did not write the code. Review-only; nothing in the repo was changed.

**Verdict: SAFE TO BUILD ON: yes-with-fixes.** Nothing calls the store yet, so the fixes cost little now. Findings C1, C2, H1, H2 should land before any caller is wired in. Counts: critical 2, high 4, medium 7, low 9.

## How this was run

The store sources were copied from `git show 9221e279d` into the scratchpad, compiled with the worktree's own `tsc` (same flags as `tools/run-tool.sh`), and driven by plain node scripts (`e1.js` to `e4.js`, in `/tmp/claude-1000/-home-destin-youcoded-dev/1d94ee8c-71e6-4c05-afdb-68b45dbe9211/scratchpad/store-review/`). All run on tmpfs with synthetic lines only. The builder's `validate-chat-files.mjs` was run read-only over `~/.claude/projects` (3 workers, 15 s): 1,360 files, 7.8 GB, 1,486,971 lines, 0 rewrites, 0 scrub failures, 0 torn final lines, 62 files ending on an unconfirmed reply, 20 invalid-JSON lines in 2 files (counted as conversation lines). No contents were read or printed. "Demonstrated" below means a script produced the stated output.

Seed check: `chain.ts` `defaultChainSeeds` computes `h[0] = SHA-256(utf8 chat id || uint32be 0)`, matching T12b F3 / design 5.3, ignores the version id, and is replaceable through `StoreOptions.seeds`. Segment other than 0 is rejected. Chain steps are `SHA-256(32 raw bytes || line incl. newline)`; with the fixed-width previous value and a line that must contain exactly one 0x0a (at its end, `asLine` store.ts:991), I found no encoding ambiguity between different line sequences. The idempotent overlap check compares chain values, so it returns `not-a-prefix` for any differing byte and `ok` for any identical prefix (store.ts:494-516); I found no counterexample, but see H3 for what it cannot see.

## Critical

**C1. A single damaged index record deletes every later acknowledged line AND their body bytes, silently. Demonstrated.**
Evidence: store.ts:271-279 verifies the last 4,096 records, stops at the first one whose CRC fails or whose offset breaks, and truncates the index there. Then store.ts:305-308 truncates the body file to match, and store.ts:296 unlinks body chunks past the end. This treats bit rot like a torn tail. Run `e1.js` E1: 100 lines, flip one bit in record 50, reopen: `head().lines = 50`, body file 12,490 to 6,240 bytes, `verify()` says ok. Fifty acknowledged lines are gone with no aside copy. Case E7 in the same script: delete `index.bin` and reopen: head 0 lines, the body chunk is unlinked (store.ts:296). `truncation.test.ts:103-113` asserts this destructive behaviour as correct. A real torn append only damages the final record or two, never a record followed by good ones.
Fix: auto-trim only when the damage is a pure tail (the bad record is the last one, or everything after it is short, zero or garbage with no whole valid record after it). If a good record follows a bad one, mark the version `corrupt`, refuse appends, keep all bytes, and offer `setAsideDamaged`. Never unlink or truncate body bytes during load; move surplus to aside. Never treat a missing `index.bin` as "no lines" when body chunks exist. The same pattern is in control.ts (M3).

**C2. Two opens of one store root silently lose an acknowledged append. Demonstrated.**
Evidence: no lock file; state is cached per process (store.ts:144, 241-248) and the write goes to `recPos(st.count)` from the cached count (store.ts:557). `e2.js` E6: process A and B both open the root and load the version at 10 lines; A appends 1 line (ack `ok`), B appends 2 different lines at the same position (ack `ok`). Reopen: 12 lines, A's acknowledged line is gone, `verify()` ok, no error anywhere. `sweepTemps` also deletes a second process's in-flight temp files (fsio.ts:123), turning its rename into a failure.
Likelihood in the app: `grep requestSingleInstanceLock desktop/src` finds only the headless shim (`headless/electron-headless.ts:72`, which just returns true), so I found no single-instance guard in the desktop main process. Whether Electron/Chromium's own profile lock stops a second instance on the same data folder is UNVERIFIED. Main process plus a headless backend on the same root is the realistic trigger; a dev instance uses its own profile, so it is not.
Fix: take an exclusive lock at `open()` (O_EXCL lock file holding pid and start time, stale-lock detection; or flock where available) and fail loudly when held. Defence in depth: before writing, compare `index.bin` size with `recPos(st.count)` and throw if another writer moved it.

## High

**H1. `setAsideTail` replayed with the same takeover id cuts lines that arrived after the first call. Demonstrated.**
Evidence: store.ts:725-728: when the tail file already exists, the code runs `cutTo(fromLine)` whenever `st.count > fromLine`, without checking that the lines beyond are the tail it saved. `e2.js` E5: set aside a tail at line 10 of 20, append 5 new lines from the new host at 10..14, call `setAsideTail` again with the same id (an at-least-once redelivery or a restart retry): head goes 15 to 10, the new host's acknowledged lines are deleted. Related (E5b): a legitimate retry after `fromLine` was clamped throws `bad-argument` because the saved `fromLine` differs (store.ts:726 vs 731).
Fix: on an existing tail, cut only if the current chain value at `fromLine + tail.lines.length` equals the saved `headHash` (i.e. the lines beyond are exactly the saved tail); otherwise return without cutting. Compare against the requested value before clamping.

**H2. A crash inside `setAsideDamaged` destroys the aside copy's index. Demonstrated.**
Evidence: store.ts:834-841. `finishAside` renames `index.bin` etc. into `aside/<name>`, then `ensureIndex` creates a fresh `index.bin` in the version folder, then deletes `aside.intent`. A kill between those leaves the intent file plus a new empty `index.bin`; the next `load()` re-runs `finishAside`, whose rename loop moves the new empty `index.bin` over the aside copy's index (rename overwrites). `e2.js` E4 sweeps every kill point of 18 operations: ops 13 to 17 leave `aside/<name>/index.bin` at 0 or 16 bytes (header only) next to intact body chunks. Bodies remain, but offsets, chain values and the kept "damaged" evidence are gone. `crash.test.ts:184-209` only checks that `index.bin` exists and body bytes are present.
Fix: unlink `aside.intent` before creating the fresh index (the moves are complete once the renames are fsynced), or skip a rename when the target already exists, or write the new index only after the intent is gone. Make the test assert the aside index size.

**H3. Body bytes are never checked against the chain on read, open or idempotent append; old index damage goes unnoticed. Demonstrated.**
Evidence: `readRange` (store.ts:430-457) checks only lengths and index CRCs. `applyLines` compares chain values from the index alone (store.ts:499-511). `e1.js` E3: flip one bit in a stored body: `read()` returns the corrupted line, and re-sending the correct bytes returns `ok` (idempotent), so the damage is never healed or flagged; only `verify()` reports `chain mismatch`. E2: 5,000 lines, corrupt record 5 (older than the 4,096 window): open succeeds, `head()` is normal, `append` at the end returns `ok` and extends past the damaged history; reads and overlapping appends throw `corrupt`. Nothing schedules `verify()`.
Fix: verify the chain over bytes when serving a range to a peer or the UI (cost is one SHA-256 pass over bytes already read); in `applyLines` for non-evicted overlap, compare bytes too and, on a match with the index but a mismatch with the body, rewrite or flag the body from the incoming correct line; run a background scrub that sets a persistent `damaged` flag; make `open` also check the index chain linkage of the last window, not only CRC and offsets.

**H4. The eviction "proof" is a self-asserted token; the store's last copy can be dropped by any caller. Demonstrated.**
Evidence: `validateProofShape` (store.ts:997-1004) and the hash match (store.ts:859-863) only check shape and that `hash` equals the store's own chain value, which `hashAt` hands out. `e4` snippet: a proof with holders `['nobody']` and `hash = hashAt(2)` evicts both lines (`freedBytes 32`), after which `read` returns `evicted`. Nothing binds the proof to a holder, a signature, a version, a store, or a time, and it is replayable across stores and versions that share a prefix (the default seed ignores the version id). Policy is said to live in S9, but this is the only gate over INV-4/INV-9 style loss.
Fix: make the proof carry per-holder acknowledgements (holder device id, chain value, signature verified by a callback supplied at open), reject unverified proofs, record who confirmed in `evicted.json`, and rename the current check so nobody mistakes it for the proof. Cap eviction to lines whose bytes pass `verify` first.

## Medium

**M1. The adapter's cheap poll misses a same-size edit in the middle of a file, even after the file grows. Demonstrated.** adapter.ts:295-305 compares inode, size, first 4 KiB and last 64 KiB before the offset only. `e3.js` E8: 536 KB file ingested, one byte changed at line 1000, `cheapCheck` says `unchanged`; after one new line is appended, `poll` returns the new line with no `rewritten` flag, while `scrub` says the prefix is no longer intact. The store would keep the old bytes of the edited line forever. T21 found in-place edits in 2 native chats. The code comment admits the blind spot; nothing schedules `scrub`. Fix: poll must, on every call where mtime moved and size grew, also sample a rotating 64 KiB window of the older prefix, plus a scheduled full `scrub` (300 MB read is about 0.5 s on this machine); on `scrub` failure treat as `rewritten`.

**M2. Directory-entry durability is unmodelled and partly missing.** `realFs.mkdir` (fsio.ts:91) never fsyncs the parent. New directories whose parent is not fsynced afterwards: `parked/` (store.ts:572), `tails/` (741), `rejected/` (609, only the dir itself and `parked/` are synced), `extras/<aa>/` (972), `aside/<name>/` (833, 839 syncs target and version folder but not `aside/`), `control/<hash>/` (control.ts:67, 86), and the store's first `versions/`, `aside/`, `extras/`, `control/` folders (store.ts:166-168 run after the FORMAT write has already fsynced the root). On ext4 the journal usually makes this safe, but POSIX does not promise it; the acknowledged result (`parked`, `stored`, first control entry) could vanish after a power cut, and an aside copy could be orphaned in H2's window. `fault-fs.ts` does not model directory entries, rename without directory fsync, reordered writes, or an unsynced truncate (its power-loss step cuts files to the last synced length and would zero-extend a truncated file), so tests cannot see any of this. UNVERIFIED on macOS (Node `fsync` is not `F_FULLFSYNC`) and Windows (directory fsync is a no-op, fsio.ts:97-103; `fsyncDir` also swallows `EINVAL/ENOTSUP`, L1). Fix: fsync the parent after every `mkdir`; extend the shim with a "durable namespace" model that applies at power loss only to directory ops followed by a directory fsync.

**M3. Control log.** (a) control.ts:75-84 truncates at the first bad record, deleting all later entries, same defect as C1. (b) Parked entries have no count or size cap, and every append and load re-reads all of them (control.ts:146-160): O(n^2) and unbounded disk. (c) The caller-supplied `id` is not checked against the body hash, so an early forged body filed under a real id wins and the real entry later returns `duplicate`; the log header says verification is elsewhere, but the store is where dedup is decided. (d) An entry whose `seen` contains its own id, or a cycle, parks forever. Fix as C1; cap parked entries; require `id == SHA-256(body)` (or document and test that the caller verified it).

**M4. Parked appends are quadratic and effectively unbounded. Demonstrated.** `park()` lists the parked folder and opens every file to total its size (store.ts:578). `e4`: 1,000 parks took 14 s, the next 1,000 took 28 s, on tmpfs where fsync is free, and the run was stopped after 2,000 of 4,000. The cap is bytes per version (256 MB, store.ts:154), not file count (a 13-byte line gives about 20 million files), `rejected/` and `tails/` have no cap at all, and `fromLine` up to 2^53 is accepted (names beyond 12 digits break the `parseInt(name.slice(0,12))` ordering at store.ts:591). An off-by-one `fromLine` (count+1) is not an error: `e4` shows `append` returns `parked`, head stays at 0 lines. Fix: keep an in-memory parked byte total, cap file count, reject `fromLine` more than a sane distance past the head (or require the caller to pass a `maxGap`), and surface `parked` older than a timeout.

**M5. The conversation chain depends on an unversioned classifier.** `c` is computed from `analyseLine` at append time and stored per record (store.ts:529, records.ts). The native allow-list is a "replaceable constant" (classify.ts:54-57) and `c[0]` is a label the builder invented (chain.ts:33-36, not in the design). Any change to the classifier makes two devices on different app versions produce different `c` for identical bytes, which T21 treats as "copies differ". Nothing stamps a classifier version into `meta.json`, the index header, or `Head`. Fix: store a `classifierVersion` in the version's meta and in `Head`; refuse to compare `c` across versions; document `c[0]` in the design.

**M6. Reply-end tracker misjudges lines without a message id. Demonstrated; real-data frequency UNVERIFIED.** classify.ts:145-155 confirms a candidate only when a later assistant line has a different id. `e3.js` E9: two consecutive end-of-turn assistant lines with no `message.id` give confirmed `[1]`, not `[0,1]` (first reply end lost). E9b: an interrupt marker (candidate with id null) followed by a no-id assistant line stays pending and is never confirmed. Also counted as ends: `max_tokens`, `pause_turn`, `refusal` (classify.ts:107), and `apiErrorsEndReplies` defaults to true while the design says "proposed no". T2 reports 0 sidechain lines in main chats, so sub-agent interleaving was not a finding. Fix: treat a null id as "different from everything" (confirm on any later assistant line), and decide the stop-reason list explicitly.

**M7. Tests prove less than they appear to.** All tests and the benchmark run under `os.tmpdir()`, which is tmpfs here (fsync is free), so the performance numbers say nothing about sync cost on disk; `truncation.test.ts:103` asserts C1's destructive behaviour; `crash.test.ts:184` omits the aside index check (H2); there is no test of two instances, tail replay after new appends, body bit-flips, deleted index, or missing middle chunk (a deleted middle chunk raises a raw ENOENT, not a `StoreError`); property tests use fixed seeds (`property.test.ts` `SEEDS.slice(0,15)`, `rng(500+seed)`) over fixture-shaped lines only. I did not run the test suite.

## Low

L1. `fsyncDir` swallows `EPERM/EINVAL/EACCES/ENOTSUP` (fsio.ts:97-103): on a file system without directory sync every directory-durability promise silently lapses.
L2. API error style is mixed: `append`, `evictBody`, `restoreBody`, `putExtra` and others throw synchronously on bad arguments (`keyOf`, `asLine`; demonstrated `bad-line` thrown, not rejected) while state errors reject; `.catch()` callers miss the first kind.
L3. Adapter defaults: any inode change returns `replaced` (adapter.ts:296) even if bytes are identical, unless `verifyReplaced` is set; copy-then-rename editors and restores would start new versions needlessly. The adapter follows symlinks and would block on a FIFO (`fsp.open(path,'r')`); it only reads, but a planted link would let the ingest read another file. Windows/exFAT inode behaviour UNVERIFIED.
L4. `read()` silently clamps `to` and returns `[]` past the end (store.ts:387-388); `conversationLines` throws `evicted` on the first conversation line if any prefix is evicted and does not validate a negative `fromLine`; `hashAt` returns null beyond count.
L5. `restoreBody` verifies nothing when the first chunk survived (S = 0, store.ts:916 comment) yet clears the marker and reports `restoredLines`; a crash after the chunk write re-deletes it at next load (store.ts:325); harmless but misleading.
L6. Tail file header JSON has no checksum (store.ts:760-769); `tail()` scans every version and returns the first match.
L7. Conflicting parked chunks at the same `fromLine` are applied in order of the hash in the file name (store.ts:588), so two devices could keep different winners; the loser goes to `rejected/` (kept, good).
L8. Adapter memory: an unterminated or giant line is held whole (carry grows by repeated `Buffer.concat`, adapter.ts:348, 367); tested 200 MB line 1.2 s and 200 MB torn 0.9 s, acceptable, but there is no cap and a 2 GB line would exhaust memory; `store.append` has no per-call size limit either (`Buffer.concat` of the whole batch, store.ts:547).
L9. Extras: `putExtra` hashes the whole buffer before taking the lock (fine), but there is no size cap and `extras/` never sweeps its own temp files except at root level.

## Gaps against the spec (not defects)

T12b amended 5.3 to say the store "records, per line, which device wrote it and under which host entry" and "re-keys a version when `decide` renames it". The store has no provenance field and no re-key operation. Both will be needed before Phase 5.

## Checked, no finding

- Torn index record, truncation at every byte of the last record, and kill at each operation of plain append (body fsync before index fsync, index fsync before acknowledgement, new chunk and index creation followed by directory fsync): ordering is sound for process kills on a journaling Linux file system.
- Writes outside the supplied root: every path is built from hex-validated ids, a hex-only takeover id, `aside` names matching `^[0-9a-f]+-\d+$`, 64-hex extras and SHA-256 control folder names. The adapter opens runtime files read-only only. Nothing writes into a chat folder unless the caller passes one as `root`; the store does not guard against that.
- Chain values and line splitting on 0x0a only; `\r\n`, U+2028 and invalid UTF-8 are carried as raw bytes (classification of invalid JSON fails toward "conversation").
- Eviction keeps chain values; `restoreBody` checks every restored line against the kept chain before writing (when it has anything to write).
