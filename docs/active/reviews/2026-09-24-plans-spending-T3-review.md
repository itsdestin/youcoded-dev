# T3 "Executor" — code review (`a18758b2b`)

Scope: `desktop/src/main/harness/plans/plan-executor.ts` + `desktop/tests/plan-executor.test.ts`, checked against design `docs/active/design/2026-09-24-specialists-plans-spending-backend-design.md` §3 "Executor"/"Concurrency" (Revisions 1–3) and decisions 34/37 in `docs/active/design/2026-09-05-specialists-plans/decision-log.md`.

- X1 accepted — fix after T4 lands (same file) — [high] — a drain halt can lose the "first reason wins" race to an unrelated halt, so the plan can pause with the wrong `kind`/`reason` even though it truly did cross its spend limit — evidence: `markLimitReached` (`plan-executor.ts:1237-1241`) sets `run.limitReached = true` synchronously, then calls `requestSpendLimitDrain` (`plan-executor.ts:718-726`), which is a detached `void (async () => {...})()` that `await`s `this.load(run)` (a journal read) before ever calling `requestHalt`. Any OTHER call to `requestHalt` that fires synchronously in that gap — e.g. a sibling's `memberEnd` reaching `outcome.kind === 'interrupted'` (`plan-executor.ts:1380-1385`, "specialist-stopped") or `'specialist-error'` — wins `requestHalt`'s first-reason-wins guard (`plan-executor.ts:683-684`) before the spend-limit request ever lands. The journal's `usedTokens`/`usedUsd` are still correctly over the limit, but the user-visible `paused.kind`/`paused.reason`/`paused.limit` (design §7's "Reached your $5 limit.") is whichever reason won the race, not necessarily spend-limit. No test exercises two live siblings where one crosses the limit and another halts for an unrelated reason in the same tick.
  - Fix: don't make the halt request depend on an awaited read. The crossing write in `plan-spend.ts` already knows `plan.spendLimit` at write time (`crossedLimit`, `plan-spend.ts:82`) — thread it through `markLimitReached(limit)` so `requestHalt` can be called synchronously from inside `markLimitReached`, with no intervening `await`.

- X2 accepted — fix after T4 lands (same file) — [medium] — `requestSpendLimitDrain`'s bare `catch {}` swallows every `this.load(run)` failure, including lease loss, instead of routing it through the file's own `onJournalError` handling — evidence: `plan-executor.ts:721` — `try { limit = (await this.load(run)).spendLimit; } catch { /* the run may already be gone; pause with no limit named */ }`. `load()` throws `PlanFenceError` when another process now owns the lease (`plan-executor.ts:760`); every one of the other 14 call sites of `this.load(run)` in this file lets that propagate up to `drive()`'s `catch (e) { this.onJournalError(run, e) }` (`plan-executor.ts:769-777`), which correctly turns lease loss into `requestHalt(run, {kind:'lost'})` and stops writing. This one site instead still calls `requestHalt(run, {kind:'pause', why:'spend-limit', ...})` with `limit: undefined` even when the real cause was losing ownership — the comment's "the run may already be gone" doesn't distinguish "gone" from "another process owns it and is driving it right now," which is exactly the case `onJournalError`/`kind:'lost'` exists to handle safely.
  - Fix: `catch (e) { this.onJournalError(run, e); return; }` (mirroring every other journal-read site in this file) instead of a bare swallow.

- X3 accepted — fix after T4 lands (same file) — [low] — settle's busy-wait phase (step 0) doesn't get the drain deadline — evidence: `plan-executor.ts:1652` (`const busyDeadline = Date.now() + this.settleDeadlineMs;`) always uses the short settle deadline, even when `run.halt` is already a drain pause; only step 1 (`plan-executor.ts:1681`) branches on `draining` to use `this.drainDeadlineMs`. A launch that "lands a little later" during a drain is explicitly allowed to keep running (`memberStart`'s `stillDraining` branch, `plan-executor.ts:1305-1317`), but the `track()`-wrapped launch handshake it's waiting on (`plan-executor.ts:1193`) is only ever given the ordinary settle window before settle logs "still busy" and moves on without it. Low-probability (a launch handshake is normally fast) but inconsistent with "every live specialist keeps running... until settle's drain deadline" (design §3).
  - Fix: compute `draining` before step 0 and use it for `busyDeadline` too, or accept and document that step 0 is intentionally exempt.

- X4 accepted — fix after T4 lands (same file) — [low] — the two new drain tests simulate in-flight specialist work with fixed real-time sleeps rather than waiting on a signal, which `.claude/rules/test-suite-hygiene.md` ("Never let a fixed sleep... stand in for a signal") flags directly — evidence: `plan-executor.test.ts:1868-1877` (`await new Promise((r) => setTimeout(r, 10))` / `setTimeout(r, 20)`) and `:1902` (`setTimeout(r, 5)`). The margins are generous (10–20ms of simulated work against a 5,000ms `drainDeadlineMs` in the first test) and the second test's real assertion is a log-order check (`plan-executor.ts` test `log.indexOf('dispose:...') > log.indexOf('settle-deadline')`) rather than a raw-duration one, so practical flakiness risk is low — but `drainDeadline.fired()).toBe(false)` in the first test is only true because the sleeps happen to resolve well inside the deadline, not because the test waits on the actual event.
  - Fix: none required to land, but a follow-up could replace the plain sleeps with a small resolvable gate the test controls directly (matching the existing `honorsAbort`/`stayUntilAborted` pattern already used elsewhere in this file for the "never resolves until aborted" case).

- X5 accepted — fix after T4 lands (same file) — [low] — local-engine serialization has only one test (a plain `map` step), not the retry or repeat-body cases the design commit message claims are "included" — evidence: commit message says "Tests... local-engine ×1"; the only local-engine test is `plan-executor.test.ts` "a 4-item local split step on a cloud-model parent never runs two local children at once" (a bare `map`, no retries, no repeat). The mechanism itself is sound by construction — `local`/`width` are recomputed fresh from a freshly-loaded `plan` at the top of every `runStep` call (`plan-executor.ts:1040,1061-1062`), and `runStep` is called once per repeat round and reads the current wave's `needed` items after any retries are folded in — so this is a coverage gap, not a known defect.
  - Fix: add a repeat-body local-engine test and/or a local-engine test where one item's attempt fails and is retried within the same wave, to pin the "included" claim rather than leave it implied by the general mechanism.

**Verdict:** The wave-start spend-limit check (§3's `used ≥ limit`) is implemented exactly as designed and correctly unit-selects USD vs. tokens (`spendLimitCrossed`, `plan-executor.ts:440-444`); the local-engine headcount serialization correctly reads the step's frozen manifest binding rather than re-deriving pricing, degrades safely on anything not recognizably `{kind:'local'}`, and is proven with a generous-cap test that isolates the rule from the cap; the `currentHalt()` helper is a legitimate (if slightly novel) TypeScript narrowing workaround, not a masked logic error — it returns `run.halt` verbatim through a function boundary specifically because `tsgo`'s control-flow analysis can't see that an awaited call may have mutated the property; and the recovery/resume paths are correctly inert on spend (confirmed by dedicated tests). The real risk is concurrency around the drain halt itself: the detached async gap between "limit crossed" and "halt actually requested" (X1) means the design's implicit promise — that a genuine spend-limit crossing is what the user sees — isn't fully guaranteed under concurrent siblings, and the same gap's error handling (X2) diverges from this file's own established convention for journal-read failures. Both are narrow-window races rather than everyday bugs, and X1 is the one worth fixing before this is considered done, since it's precisely the scenario item (1) of this review was asked to rule out. X3–X5 are minor and can be follow-ups.
