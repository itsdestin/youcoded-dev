# Cloud download consent — first-time UX review 1

Tested on 2026-09-15 at 1440 × 900, Midnight theme, using only the isolated address `http://127.0.0.1:5633/?mode=workbench&child=1&latency=150&scenario=default&cloudConsent=ask`. This is a simulated-backend review; fake data and lack of real download completion are not findings. Screenshots below are relative to this review file.

- U1 accepted — Clarify the next step. Automatic continuation and abandoning a pending request are behavior proposals to show explicitly in the review deck, not silently approved requirements. Do not claim OneDrive cancellation. Original finding: I expected the waiting notice to explain what happens next and let me abandon the pending action / “Waiting for OneDrive” and “You can keep using YouCoded while this waits” explain why I can leave, but not whether my file will open or my conversation will start automatically, whether I must return and click again, or how to cancel the pending request; the notice has no actions. Add a truthful next-step sentence, such as “Your conversation will start when this file is ready” if that is the behavior, and a “Cancel request” action — Projects, after allowing downloads for New Conversation — [conversation-waiting.png](2026-09-15-cloud-download-consent-ux-review-1/conversation-waiting.png).
- U2 accepted — Replace native-startup jargon with conversation and project-instruction wording. Original finding: I expected an explanation about my new conversation / “Native assistant startup is paused until YouCoded can read CLAUDE.md” exposes unfamiliar technical terminology and an unexplained filename. The next line repeats the filename and unavailability. Prefer “Your new conversation is waiting for a project instructions file (CLAUDE.md). You can keep using other conversations.” Keep the provider name in the heading — Projects, new-conversation waiting notice — [conversation-waiting.png](2026-09-15-cloud-download-consent-ux-review-1/conversation-waiting.png).
- U3 accepted — Remove prototype annotation from app copy; explicitly ask about the proposed app-run permission lifetime in the review deck. Retain 'YouCoded' in permission scope copy to distinguish external tools. Original finding: I expected a definite permission duration before agreeing / “Proposed duration: until you close YouCoded” sounds negotiable or unfinished, but there is no duration choice. Prefer “Permission lasts until you close YouCoded.” The nearby sentence can also be shortened from “Only files needed by YouCoded will download, not the whole folder” to “Only needed files will download—not the whole folder” — Projects, initial and reopened permission request — [ask.png](2026-09-15-cloud-download-consent-ux-review-1/ask.png).
- U4 accepted — Make changing the declined choice explicit and shorten explanation without dropping unknown-availability protection. Original finding: After declining, I expected an obvious way to change my download choice / “Review permission” works, but sounds like a read-only explanation rather than changing a decision. Prefer “Change download permission.” The recovery notice can be shorter: replace “Files already on this device remain usable. Cloud-only files won’t preview or open until you allow downloads” with “You can still use files on this device. Allow downloads to open online-only files” — Projects, “Local files only” notice — [declined.png](2026-09-15-cloud-download-consent-ux-review-1/declined.png).
- U5 accepted — Use 'Online-only' and explain that opening may need a download. Reject 'Location not checked' and a new checking action: unknown does not establish why the probe failed or that another check is safe/useful. Do not add per-file approval conflicting with the selected folder grant. Original finding: I expected file labels to say what I can do / “Availability unknown” above “Preview not loaded” leaves me unsure whether the file is missing, offline, or waiting for permission. “Cloud-only” is also less direct than “Online-only.” Prefer “Location not checked” only if that is the actual state, with an appropriate action such as “Check availability”; for known online files, “Online-only · Download to preview” would explain the next step — Projects, file cards before consent — [ask.png](2026-09-15-cloud-download-consent-ux-review-1/ask.png).
- U6 accepted — Use normal-size primary and outlined secondary consent buttons for readable, accessible choices. Original finding: I expected the two consent choices to have similar readability to other important actions / “Not now” and “Allow downloads” use noticeably smaller text and controls than “New Conversation”; “Not now” is particularly faint and visually understated. Make both choices easier to read and target, while keeping Allow as the primary action. There was no clipping or overlap in this notice at the tested size — Projects, file-specific consent request — [file-consent.png](2026-09-15-cloud-download-consent-ux-review-1/file-consent.png).

## Task outcome

I completed the browse/decision/waiting portion of the task: opened Projects, saw online-only files without previews alongside a readable local file, declined with “Not now,” reopened consent both through “Review permission” and by clicking an online file, then allowed downloads. I also started a new conversation and saw its separate file-related waiting explanation. The app remained usable: I opened the local README preview while an online file waited, left Projects for chat, successfully typed a study-planning draft, and returned to a preserved waiting notice. The most confusing moment was allowing the new conversation and remaining in Projects with “Native assistant startup” text: I could tell something was waiting, but not whether a conversation now existed or what would happen when the file became ready. I did not verify eventual download completion or automatic continuation, actual sending of the chat draft, other themes, touch input, or high-density rendering. No app error was logged in the completed capture manifests. Testing stayed within the 15-minute budget.
