- F1 — `desktop/src/main/project-extensions/store.ts:450-458` (`markPluginRemoved`) — The uninstall cascade silently fails to tombstone a plugin whose only record of that plugin lives in an *unfolded conflict copy* (i.e. the canonical `<name>.json` file itself has no `plugins[pluginId]` entry, but a `<name> (from other-device, ...).json` copy does). `markPluginRemoved` decides whether to attempt a project using the FOLDED record (`readSyncedRecord`, which merges conflict copies), but the actual write goes through `mutateSyncedRecord`, whose `mutateFileUnderLock` callback re-reads only the raw canonical file (`parseProjectExtensionsRecord(onDisk)`) and hands that *unfolded* value to `applyPluginRemoved`. `applyPluginRemoved` returns `null` (no-op) whenever `cur.plugins[pluginId]` is absent — which it is here, even though the folded record (used for the gate) has it. Net effect: the write never lands, so a future read keeps folding in the old, non-removed conflict-copy entry forever — the plugin is never actually hidden from "needs setup" on any device, for exactly the scenario (conflict copies) `store.ts`'s own comment above `markPluginRemoved` claims is handled ("The synced side checks the FOLDED record ... so a plugin entry that currently exists only in an unfolded conflict copy still gets tombstoned"). This directly contradicts the code under it. — **Confirmed**: added a temporary test (canonical file with empty `plugins`, a conflict-copy file with a `civic` plugin entry, then `markPluginRemoved(stores, 'civic', ...)`); it failed — `getProjectExtensions` still returned `{on: true, partsChosen: true}` for `civic`, not the expected tombstone. Restored the test file afterward with `git checkout --`.

- F2 — `desktop/src/main/project-extensions/store.ts:100-124` (`parseProjectExtensionsRecordValue`) — The top-level record parse rebuilds the object from only the four known fields (`schemaVersion`, `seededAt`, `plugins`, `items`), so any future top-level field added by a newer build is silently dropped on the next read-modify-write from an older build. This is the exact "rebuild on every read... any field we added there would be dropped by the next rename or description write" anti-pattern the technical design (§ "Source facts", `ProjectSync/<name>.json`'s `parseEntry`) names as the reason this feature got its OWN sibling file instead of a field on that record — the same failure mode has now been reproduced one level down, inside the new file's own top-level shape. Per-entry (`plugins[x]`, `items[x]`) fields ARE preserved (tested), just not top-level ones. — **[PLAUSIBLE]**: no top-level field is added anywhere in this codebase yet, so nothing observably breaks today; this is a latent forward-compat gap, confirmed by reading the parse function, not by a failing scenario.

- F3 — `desktop/tests/project-extensions-store.test.ts:106,159,187,236` — Each `afterEach` calls bare `fs.rmSync(root, { recursive: true, force: true })` with no `maxRetries`, which `.claude/rules/test-suite-hygiene.md` ("Real output goes to a temp dir, and its teardown retries") requires ("remove the root with `maxRetries`, not bare `rmSync` — a late write throws `ENOTEMPTY` into a passing test"). — **[PLAUSIBLE, low severity]**: confirmed by reading the rule and the test file; not confirmed as an actual observed flake in this run. Mitigating: this exactly mirrors the pre-existing pattern in `desktop/tests/native-home.test.ts:17` (bare `rmSync`, no `maxRetries`), which this new file's header comment explicitly says it copies the style of — so this is inherited precedent, not a new deviation invented by this commit.
