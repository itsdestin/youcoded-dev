# Mesh store review 7: round-6 fixes (22b666f71..49f21d81e)

Reviewer worked read-only. Harness: `docs/active/prototypes/2026-11-14-mesh-phase0/store-review-7/` (README.txt there). Repo suite at head: 369 pass (I ran it).
Method note: the fuzz builds a disk image with the NEW code, then reads the same image with OLD (22b666f71) and NEW code, so "before vs after" is on identical bytes. Old cannot read the new park format, so park-drain comparisons use probes built and read by the same code.

## Findings, by severity

### F1 (medium, new in this diff): two older files put back together are now accepted silently; before they were quarantined
What a user experiences: after a takeover, a restore tool (or sync tool) that puts back an older `index.bin` AND the older body file (but leaves the newer `checkpoint.bin`) used to make the chat "damaged" (kept aside, loud). Now the chat opens fine with the OLD history's lines (the lines after the takeover point are the wrong ones), no flag, and the lines written since the takeover are gone.
Repro (real disk, `probe1.test.ts`): 20 lines of history A, copy the folder, takeover at line 10, append 6 lines of history B, close, put back `index.bin` + `body-0000000000000000.bin` from the copy. Old: throws `damaged`. New: `head=20, damagedFrom=null, rolledBack=null`, 10 wrong lines served (A's lines 10..19), the 6 B lines gone.
Second form (`ck+body`, checkpoint and body older, index newer, old checkpoint count below the head; `probe2`: 20 lines, takeover at 5, 25 new lines): old throws `damaged`; new serves 20 lines of history A, reported only as `rolledBack{from:20,had:30}` (and only because the high-water record saw 30; `from:20` is also wrong, lines 5..19 are not the current history). With head at or above the high-water value it is silent.
Cause: the author's reasoning "time only runs one way" holds for an older index or older checkpoint ALONE (both fixed correctly, see item 1), but the code cannot tell "index older, checkpoint+bodies newer" from "index newer, checkpoint+bodies older", and "checkpoint newer, index+bodies older" from "checkpoint older, index+bodies newer". Relaxation (i) (recovery.ts:341, `atCk`) and relaxation (ii) (recovery.ts:431) each pick the answer "the lone odd file is the old one", which is wrong whenever the lone odd file is the new one.
Fuzz: 16,500 mixed seeds and 20,000 single-file-biased seeds: every one of the 183 seeds where new misbehaves and old did not is a two-file older fault (`idx+body` or `ck+body`). Zero in any single-file fault family. Whole-folder rollback behaves the same before and after (still silent when the old head is at or above the high-water value; that is documented limit (4)).
Existed before: no, this is new. (The `ck+body` silent form with a SHORTER current index existed before and is unchanged.)
Cheap fix I can see: the tails already hold the old history. A checkpoint (count, value) is provably "older, from before takeover T" when its value equals the chain value at its count along `fromHash + tail lines` of some tail; only then rewrite it. Same test for an index record. Anything else stays a quarantine.

### F2 (medium, existed before; the B1 invariant is still false for set-aside): a park drains onto a recopied different history
`setAsideDamaged` (asides.ts:90) moves index, bodies, checkpoint, marks but leaves `parked/` and `tails/`, so the epoch is unchanged and parks stay drainable. `probe3`: 10 lines of A, park A-lines 12..13, `setAsideDamaged`, peer recopies history B lines 0..11. Result old AND new: `head=14`, 2 wrong lines (A's) after B's 12, no flag. The header of inventory.ts says quarantine and recopy "refill the SAME lines"; that is only true if the peer's history is the one the park was made against, which the store cannot know. (With a takeover in between, new code correctly refuses the park: `takeoverThenSetAside` gives head=12.) Needs: a quarantine plus a history change this device never saw as a takeover plus a park beyond the head. Fix: set-aside should move parks to `rejected/` (or write a marker that changes the epoch).

### F3 (low-medium, existed before, unchanged): losing the tail AND its marker(s) still writes an empty tail over the loss
Tail + `.begun` lost together (or `tails/` as a whole lost or put back older: tail + `.begun` + `.done`) after the cut happened: a retry sees no marker, writes an empty tail, returns `{lines:0}`; the cut lines are gone with no signal. Same in old. This is two files lost (or one directory lost). B2's promise ("lost tail with either marker is reported") holds for one file. An older/missing `tails/` directory is the single fault that does it, and the inventory row does not list it. Fix idea: record the cut's intent inside the version's own checkpoint/marks file (a file that is not in `tails/`), or refuse an empty tail when the head is below the stated `fromLine` is impossible to know... simplest is a second copy of the marker outside `tails/`.

### F4 (design note for the next layer, not a defect): a park is sealed with the epoch at the moment the store receives it
`parkId(name, st.epoch)` (parked.ts:51) uses the store's current epoch, not one supplied by the caller. A late park from a deposed host that arrives AFTER the takeover is sealed with the NEW epoch and will drain onto the new host's history. B1 therefore fences "parks made before the takeover", not "parks made by the old host". The replicator must reject the deposed host before it reaches `append`.

### F5 (info): rejected parks are reported only by polling
`rejectedList(version)` (store.ts:946) is the only way to learn lines were rejected; `append`, `head()` and `verify()` say nothing, and the list has no reason (old history vs bad hash vs wrong version). Nothing acknowledged is destroyed (a park is only ever "parked", never acknowledged; the caller keeps ownership). Two small exceptions at the `rejected/` cap (1024 files / 256 MiB): `park()` ignores a failed `moveAway` (parked.ts:56) and then overwrites the old park file; and at the cap a stale park stays in `parked/` where only the epoch refuses it (a lost `.begun` plus a full `rejected/` would make it drainable again: two faults and a cap). The next layer must poll `rejectedList` after every takeover and resend from the head.

## Item results

1. Recovery relaxations. Single damaged file: improved, not weakened. `probe1`/`probe2`: old index alone: old quarantines, new serves the correct current history (head 16, 0 wrong lines); old checkpoint alone with lower count: old quarantines (probe2) or flags damaged (probe1), new serves the right lines. Flip/truncate/delete/older of any single file, all body chunks older, `tails/` older, `.begun` lost or put back, `.done` lost, tail lost or older: 0 data violations in ~17,000 seeds each for new and old. Two-file combinations and (i) accepting old-history bodies: see F1. Rollback of the whole folder: no change (silent when old head is at or above the high-water value, as documented; probe4 shows the whole-folder rollback also brings back the older folder's parks and they drain onto a resent history, in old and new alike). Relaxation (i) on its own does not accept the OLD history's bodies as the new one when the checkpoint is newer: it needs the bodies to hash exactly to the checkpoint's value.
2. B1 class. Epoch changes only through `.begun` names (confirmed by reading and by crash enumeration). Crash at each of the 55,200 disk-operation points (see 3) with 2 parks present and a prior takeover or not, then a new host's 7 lines landing exactly on the park position: no stale park drained once the retry finished, in any single-fault variant. A lost `.begun` makes valid new parks refused (findable in `rejected/`), and does not make old parks drainable, because old parks are moved to `rejected/` at cut time before the cut. Gaps: set-aside/quarantine (F2), the cap case and late parks (F4, F5).
3. B2 class. Enumerated every disk operation of `setAsideTail` as the crash point x 3 tear modes x kill/power x faults {none, tail lost, `.begun` lost, `.done` lost, tail flipped, tail truncated, tail zeroed, tail+`.done` lost} x 0-3 retries (random crashes) x with/without a prior takeover x with/without parks: 55,200 scenarios on new, zero failures; every end state is "complete tail and cut finished" or a typed `corrupt`. Only failures: tail+`.begun` lost and all three lost (F3), the first never reported. On old the same enumeration fails for a single lost tail (2,136 scenarios), so B2 is really fixed for one file.
4. Rejected parks: nothing acknowledged is destroyed; caller learns only by polling (F5).
5. Fuzz oracle changes. `stale-history-head-reported` (fuzz.test.ts:162) is honest in what it accepts (a head of another history only when the store flagged damage from at or before the first divergence, and the read oracle stays strict) but it does not check the cause it names. The "pending takeover dropped after quarantine/rollback" exemption is sound (the retry would be a fresh takeover on an older state). `lines may shrink while pending` is sound but wide (excuses any loss at or after `from` until the retry finishes). The thing that hides the most is `!diverged` (fuzz.test.ts:361): after the first divergent takeover the fuzz stops dealing whole-folder rollbacks at all, and partial rollbacks are never dealt, which is exactly where F1 lives. That is why the author's fuzz could not see F1.

- `b2` crash enumeration: 55,200 (new) and 44,400 (old) scenarios.

## What I did not cover

## Conditions for building the replicator on this
1. Treat F1 as a known weakening: do not rely on "a damaged chat is always quarantined" for partial restores; fix with the tail-based proof described in F1 before the replicator relies on rollback detection, or accept it explicitly.
2. Do not let a deposed host reach `append` after a takeover (F4); poll `rejectedList` after takeovers (F5).
3. Fix F2 (move parks at set-aside) before recopy-from-peer is built.
4. Keep `tails/` out of any restore or sync scope until F3 has a marker outside it.
