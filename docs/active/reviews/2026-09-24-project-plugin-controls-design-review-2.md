# Review round 2: 2026-09-24 project/plugin controls technical design — renderer (§5)

D1 — §5 "Drawer chips" — The drawer cannot render a red "Unavailable" card for a real missing item: `CommandDrawer`'s grids (`favsSorted`/`othersSorted`/`searchFiltered`) all map over `drawerSkills`, which is `SkillContext.installed` (`skill-context.tsx:145`), populated only from `window.claude.skills.list()` — a skill that is "on in the project, missing on this device" by definition has no `SkillEntry` and cannot appear there. Confirmed the ONLY existing "unavailable" card is hand-written static JSX in `CommandDrawer.tsx:357-364`, entirely outside the render loops (fixed sample text "Writing helper"), and `SkillCard`'s own prop type doesn't even admit the state (`availabilityPreview?: 'automatic' | 'manual'`, `SkillCard.tsx:27`, though the color map it draws from, `AVAILABILITY_PREVIEW`, does define `unavailable`). §5 never specifies the synthetic entry's shape (no local `SkillEntry` exists to reuse), how it sorts into Favorites/All-installed, or how `SkillCard`'s single shared `onClick` (today always "invoke this skill") gets overridden for exactly these rows to instead open Projects → Skills & tools. This is real net-new component-contract work, not a wiring change, and it's absent from §4's IPC table and §6's test list.

D2 — §4/§5 data flow — `CommandDrawer` is mounted ONCE at the App shell (`App.tsx:3903`, inside `currentViewMode === 'chat'`), not per session, and its `Props` interface carries no `sessionId` today — its skills/commands come from the singleton `SkillContext`. The design's `project-extensions:for-session` channel and "drawer chips … from the open conversation's own session id" (§5) require CommandDrawer to know which session is active and to react when the user switches sessions (Shift+arrow session-switcher, tab click) while it's mounted. Confirmed by reading `CommandDrawer`'s Props (no `sessionId`) and its single call site in `App.tsx`, which has `sessionId` in scope for other children (`TrustGate`, `MovedGate`) but does not pass it to `CommandDrawer`. Nothing in §5 says a `sessionId` prop is added, where the frozen-set data would live (a new context vs. a prop), or what happens to already-fetched chips when the active session changes while the drawer stays open.

D3 — §5 "Drawer chips" vs. `performance.md` rule 3 — The natural implementation (fetch `for-session` keyed by `sessionId`) risks becoming a per-session-switch IPC round trip on a component that isn't gated the way its sibling already is: `useMarketplace(open)` is deliberately called with `open` so "only OPENING it asks the marketplace to load" (`CommandDrawer.tsx:42`, explicit WHY comment citing "audit W16"). §5 doesn't say the new fetch follows the same `open`-gated precedent, and given D2 (no sessionId today, single always-mounted drawer under every session), a naive effect keyed on the active session id — rather than on `open`+session — would re-fetch on every session-strip switch even while the drawer is closed, which is exactly the per-event/per-switch cost class `performance.md` rules 2–4 exist to prevent on a component that lives for the whole app run. [PLAUSIBLE — describes a foreseeable naive implementation given the confirmed absence of a stated gating rule, not code that exists yet.]

D4 — §5 "Marketplace post-install" — Describes reusing "the existing overlay," but the only code that resembles this step is workbench-only and hardcoded to one fixture plugin id. Confirmed in `MarketplaceDetailOverlay.tsx`: `setSetupPreview(true)` fires only when `isWorkbenchMode() && entry.id === 'youcoded-inbox'` (lines 109-113), `showSetupPreview` repeats the same double gate (line 150), and the rendered content is `ProjectPluginControlsDemo` imported from `dev/workbench/mockups/ProjectPluginControls.tsx` (line 30, rendered lines 152-155) — a mockup component taking fixture props (`previewPlugin`, `previewProjects: string[]`) whose choices the decisions doc itself says "are in-memory and cannot persist across closing the detail panel." Shipping this for real means: dropping both gates, building a genuine production component that takes the real installed entry + the real project list and writes through `project-extensions:set` instead of local `useState`, and replacing the mockup import — the single largest net-new renderer surface in the feature, and it isn't broken out as its own line in §4's IPC table or §6's test list the way the Skills & tools tab explicitly is ("production component replaces the workbench demo").

D5 — §3 project resolution vs. `ProjectView.matchProjectByPath` — Two different, inconsistent "which project owns this cwd" algorithms will coexist. `ProjectView.tsx:162-170`'s `matchProjectByPath` — which `.claude/rules/artifacts.md` documents as re-homing Project View "to the FOCUSED conversation's project on every open" — matches by EXACT path equality only (`p.path === cwd`, or the same with slashes normalized/lowercased), with no ancestor matching. The design's new §3 `resolveAvailability` project resolution does the opposite on purpose: "the LONGEST saved folder that contains it (a conversation started in a subfolder of a project belongs to it)." So a conversation whose cwd is a subfolder of a saved project gets that project's skill/tool policy (ancestor match) while opening Project View from that same conversation will NOT land on that project (exact match only) — a directly observable inconsistency between the drawer's "Automatic"/"Unavailable" chips and which project Project View shows as active for the identical conversation. Confirmed both algorithms from source; their interaction/user-visible effect is inferred, not executed. Not raised in round 1.

D6 — §5 "Needs setup" / Q-3 "Choose skill file" — Assumes copying a single file is sufficient, but personal/self skills are DIRECTORIES on disk: `skill-scanner.ts` documents `~/.claude/skills/` as "USER-authored local skills (source: 'self')" and reads `path.join(skillDir, 'SKILL.md')` — i.e. a folder that commonly holds more than one file (references, scripts, assets, as several skills available in this very session demonstrate). The only file-picker IPC found, `DIALOG_OPEN_FILE` (`ipc-handlers.ts:1188`, `properties: ['openFile', 'multiSelections']`), selects individual files, not a folder; `DIALOG_OPEN_FOLDER` exists (line 1209) and is the shape that would actually match a skill's real structure. The app already has the right precedent for this operation — `plugin-installer.ts`'s `copyDirSync` (line 175, used at 326/435/572) recursively copies a whole plugin directory on local-source install — but it's a *Sync* fs call, so reusing it verbatim from a new IPC handler on a user click would need an async wrapper to satisfy `performance.md` rule 1 ("no `*Sync` fs … on any path a click … reaches"). §5's "opens the existing file picker and copies the file" describes neither the folder-picker nor the directory-copy precedent, and would silently produce a broken skill (a lone SKILL.md, missing everything else) for any personal skill that isn't a single file. [Confirmed: skill directory shape, dialog capabilities, and the sync copy precedent. PLAUSIBLE for the "silently broken" outcome, since the actual copy code doesn't exist yet.]

D7 — §6 test list — The one property the round-2 brief calls most safety-critical for this surface — "the tab and chips must not subscribe to chat state" — is stated only as prose in §6, with no named guard, unlike every other `performance.md` invariant in this codebase, each of which cites an actual pinning test or ast-grep rule (`filestab-*`, `root-selectors-skip-token-rerenders`, `mascot-rig-pauses-when-hidden`, etc.). Given D2 (CommandDrawer has no `sessionId` today) and D3 (no stated open-gating for the new fetch), this is precisely the class of regression rule 2/3 exist to catch, and as written the design has no mechanism (busy-app-render-budget scenario addition, new unit test, or ast-grep rule) that would fail if it shipped ungated — only a sentence saying it shouldn't.

D8 — §3 scope note (over-build check) — Everything else in §1-§4 tracks the approved decisions closely; no clear over-build found there. One thing worth double-checking against the "Open for Destin #1" answer: §3 says the frozen `{skillIds, mcpIds}` is written into every native session's on-disk header at `create()` unconditionally, including sessions outside any project, where the design's own proposed interim behavior is "keep today's behaviour" (i.e., there's no real policy to freeze yet, since incognito doesn't exist). Writing a frozen-set marker there before that question is settled is low-risk (the header format is tolerant of extra fields — confirmed via `session-store.ts`'s `validateHeader`, which passes unknown keys through rather than whitelisting them, so Resume Browser and specialist-title lookups that also read `NativeSessionHeader`/`NativeSessionListEntry` are unaffected) but is scope slightly ahead of a decision Destin hasn't made yet; worth a one-line callout in §3 rather than silently building it in.
