# Review round 3: 2026-09-24 project/plugin controls technical design

D1 — §2/§3 (B-1 "none-outside") vs. the existing Home-folder seed — **B-1's "nothing automatic outside a project" will almost never fire for a new or casual user, because the app already auto-creates a real saved-folder "project" pointing at the user's actual home directory, and auto-selects it as the default new-session cwd.** Confirmed the full chain: `folders-service.ts`'s `listPickerFolders()` and `artifacts/projects-index.ts`'s `listProjectsIndex()` both seed `[{ path: os.homedir(), nickname: 'Home', addedAt: Date.now() }]` whenever the saved-folders file is empty, and `listPickerFolders` additionally **persists** that seed to `~/.claude/youcoded-folders.json` via `writeFolders(...)` (`artifacts/projects-index.ts:70-93`, `folders-service.ts:24-30`) — so it isn't an ephemeral display fallback, it becomes a real saved folder from that point on. `FolderSwitcher.tsx:82` (`if (autoSelect && !value && list.length > 0) { onChange(list[0].path); }`) auto-selects that first entry for the new-session form, and `SessionStrip.tsx:575`'s own comment confirms it in plain words: "Home path is now auto-selected by FolderSwitcher on mount." `saved-folder-projects.ts` — the exact module the design's own "Source facts" section cites for "Projects are the saved folders" — says explicitly "A folder shows up here because the user added it to the picker," and this seeded Home entry is indistinguishable from one the user deliberately added. Separately, `projects-index.ts`'s own `isGatedRoot()` already special-cases the home directory as "the user's whole home directory... trees so large that discovery ALWAYS hits its caps" — i.e. the codebase already treats Home-as-project as a known, non-hypothetical situation, not an edge case. Net effect: §3's project resolution ("exact match, else longest containing saved folder") will match nearly every conversation a first-time or folder-picker-default user starts (since almost everything lives under `$HOME`) to this seeded "Home" project, not to "no project" — so B-1's decided behavior change (no automatic skills/MCP outside a project) silently never applies to this population, while the "Home" pseudo-project also appears as a real row in the new Skills & tools tab and the marketplace post-install project list, labelled "Home," with no acknowledgment anywhere in the design that it is the user's actual home folder rather than a folder they chose. Not raised in rounds 1–2.

D2 — §2 seeding trigger ("listing it, opening its tab, or starting a conversation in it") — **the design does not say seeding is idempotent or gated, and "listing it" reads as firing for every project the first time the Projects overview renders its rows, which is a real cross-device sync-churn risk the task explicitly asked about.** As written, a user with N saved/synced projects who opens the Projects page once after upgrading would have all N projects "touched," each writing a full materialized `ProjectExtensions/<name>.json` (§1) that syncs to every other device. §6's test list covers "materialised seeding" and "conflict-copy fold" as one-shot correctness properties but has no pinning test for "seeding a project it has already seeded is a no-op" or "listing all projects fires at most one write per project, not one per render." If the seeding check the implementer writes is anything looser than "skip when `seededAt` is already present," repeatedly opening the Projects tab (or having it re-render, e.g. after a favorite/rename) could re-materialize and re-write identical records over and over, each one a sync event across every linked device. [PLAUSIBLE — this is a specification gap, not reproduced code, since `project-extensions/store.ts` doesn't exist yet; but the design's own §1 already anticipates concurrent-seed races between devices (D3 of round 1, accepted) without similarly anticipating repeated-seed churn from one device re-listing.]

D3 — §1/§4 vs. plugin uninstall — **the design never says what happens to a project's `plugins[pluginId]`/`items[itemKey]` entries when that plugin is uninstalled, even though the codebase has an established "cascade cleanup on uninstall" precedent this design doesn't extend.** Confirmed `skill-config-store.ts`'s `removePackage(id)` (invoked by `LocalSkillProvider.uninstall`, `skill-provider.ts:521-543`) already deletes the package record and cascades cleanup to `favorites`, `chips`, and `overrides` for exactly this reason — its own neighbouring comment about theme slugs even flags "revisit whether we want to strip seeded defaults... on uninstall" as a live concern for this class of bug. The new project-extensions store adds a **third, per-project, cross-device-synced** place that references a `pluginId`, and nothing in §1 (storage), §3 (enforcement) or §4 (IPC) mentions clearing or marking it on uninstall. Left as designed, every project where the plugin was ever toggled keeps a permanent, syncing `plugins[pluginId]` entry after the user uninstalls it. This also collides with §5's "needs setup" rule: that rule can only express "installed elsewhere, not here" (Install action) — it has no way to represent "the user uninstalled this everywhere," so an uninstalled plugin's stale `on` entries would keep surfacing "needs setup" / Install rows for something the user explicitly removed, in every project that referenced it, forever. [Confirmed: no uninstall-side cleanup is mentioned anywhere the plugin-controls design touches its own store; the "silently broken/never cleaned up" outcome is inferred from the store's own last-writer-wins-forever design, since the store code doesn't exist yet to execute against.]

D4 — §5 "Needs setup" vs. §3's B-1 default — a project resolved as "no project" (true incognito-style cwd, once one exists, or any cwd genuinely outside every saved folder) has an empty frozen `{skillIds, mcpIds}` by design (§3), but §5's drawer only describes `missing[]` cards for items "on in the project but absent here" — it does not say whether, for a session with **no project at all**, every installed skill/server renders as a `missing[]`-style dimmed/unavailable card (consistent with "Manual use" per B-1's own wording: "The drawer shows every skill amber 'Manual use' there") or is simply omitted from the grid. B-1's prose says amber "Manual use," but §5's chip taxonomy for `for-session` is Automatic (green)/Manual use (amber, installed-but-not-frozen-in)/Unavailable (red, missing-on-device); a no-project session's items are installed AND not in the frozen set, which is exactly the amber case per §5's own definition — so this is likely consistent, but the design never states it for the no-project case explicitly, only for the missing-on-device case. [PLAUSIBLE — wording gap only; the amber definition in §5, read literally, already covers it, so this is a clarity note more than a functional bug.]
