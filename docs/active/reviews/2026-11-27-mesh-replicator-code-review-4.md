## Verdict

**NOT SAFE to switch on for real users' chats as it stands. Two local fixes (F1, F2 below) away from SAFE WITH CONDITIONS.**

The new self-fork backstop turns what used to be a LOUD permanent fault into a QUIET LOSS in two reproduced cases: (F1) a second rollback while the writer already holds the second version, (F2) a self-fork that takes longer than the 120 s step ceiling. In both, lines the user was told were `saved` end up in no live version on any device, and in F1 the writer then signs and replicates a history that is a mixture of two. Both are on the rare path (a writer restored from an old backup that chatted before it heard the others), but that path is exactly the one the backstop exists for, and the governing principle allows no quiet loss. Everything else I found is loud (named states) or needs a hostile roster device.

What held: I could not make a non-writer roster device put a line into anyone's copy, forge, replay or pre-empt a self-fork announcement, or make a peer set aside a copy (token binding, derived id, writer equality and the hash/line-count checks in `resolveSelfFork` are sound by reading and by the mutants that were killed). Over about 870 randomized schedules (below) there was no lost acknowledged line, no duplicate, and no in-sync mismatch outside F1/F2; the product directory (root-id binding on) runs the second-rollback flow correctly (`s1b`).

## Findings, most severe first

### F1. QUIET LOSS plus a quietly wrong history: a self-fork copies onto a second version that already holds other lines
- User experiences: the user restores the same old backup twice. After the second time, three lines they were told `saved` exist nowhere on any device, and the second version now reads `NEW5 NEW6 NEW7 THREE8` (a splice of two different histories). Peers accept the spliced extension because the writer signs it.
- Trigger: `selfForkNow` derives V2 from (V, p, chain value at p, writer token), so the same divergence point always gives the SAME V2 id. If the writer already holds V2 (heard from a peer, filled with the first rollback's lines) when a second conflict at the same `p` is found, the copy loop (`replicator.ts` ~line 238, `if (h2.lines >= head.lines) break; ... append(v2, h2.lines, read(V, h2.lines..))`) appends V's lines from V2's current length on top of V2's other content, never checking that V2's first `h2.lines` lines equal V's. Then step 3 sets V aside, so the skipped lines survive only in the store's aside folder (not findable under V or V2).
- Repro: `$S/s2.test.ts` (`./run.sh s2`). Output: `A/c749e535 9 old0..old4,NEW5,NEW6,NEW7,THREE8` on both A and B; `MISSING acknowledged lines: 3 [THREE 5, THREE 6, THREE 7]`; test fails. Caveat stated plainly: to put the writer in the "already holds V2" state at the right moment I injected V2's saved announcement through the private `onIntro` and appended the three first-rollback lines from B's store (that is what pulling them does). The natural run (`s1`) usually reaches V's conflict before V2 is filled and then builds a third version correctly, so random schedules (below) never hit it. I judge the state reachable (peer answers V2's announcement before it answers V's lines) but did not make the network order happen unaided.
- Smallest fix: before copying, require `hashAt(V2, h2.lines) === hashAt(V, h2.lines)`; if not, derive the id from a token that also carries a counter or the chain value at V's head (peers only check that the token starts with the writer id) and journal that id. Add a pinning test of this exact order.

### F2. QUIET LOSS: a self-fork that outlives the 120 s step ceiling releases the version's queue while it is still copying
- User experiences: on a big chat or a slow disk, lines saved while the move is running disappear (not in V, not in V2). A second conflicting batch also starts a second overlapping self-fork (counter `writer-self-fork` went to 3).
- Trigger: `guarded()` rejects the step at `stepLimitMs` (`stuck(store-call-blocked)`) and lets the queue run the next step while the original function keeps going. `selfForkNow` runs as ONE queued step (copy loop in 200-line slices, then retire). `appendLocal` is not refused meanwhile, its line lands in V after the loop read `head`, and step 3 then sets V aside.
- Repro: `$S/s4.test.ts`: ceiling 100 ms real, reads of A's store slowed to 400 ms. Output: `append during self-fork: saved` twice, then `MISSING 2 [LATE0, LATE1]`; test fails. With the production ceiling this needs a chat whose move takes over two minutes (hundreds of thousands of lines, or a phone-class disk); I did not measure how big. Android runs this backend.
- Smallest fix: a per-version `selfForking` flag set when the journal is written and cleared when it is removed; `appendLocal` refuses (`writer-self-fork-in-progress`) and `selfFork` returns at once while it is set; run the copy as many short queue steps (or exempt it from the ceiling).

### F3. Hostile roster device freezes the writer for good (review 3 finding 6 is NOT closed)
- User experiences: the chat refuses every message (`writer-behind-peer-holds-more`, status `pulling peer-claims-more`), indefinitely.
- Trigger: a device (not the writer) says it holds 500 lines; after 10 minutes the writer discounts it, but any applied batch from that device deletes the clock (`receive.ts` `peer.claimSince.delete(sk)`). A device can replay ANY genuine old signed batch (it holds them) every 9 minutes; replaying already-held lines appends `ok`.
- Repro: `$S/h1.test.ts` (`-t H1`). Output: `attempts over 80 minutes with replay each 9 min: REFUSED x8`; control without replay: `REFUSED | saved | saved ...` (discounted at 10 min); after the attacker stops, 15 quiet minutes later `saved`. The writer's own pull from that device just stalls (`pull-stalled 144`).
- Smallest fix: reset the clock only when the batch backs the claim (`b.head.lines >= claimed lines` and the claimed chain value matches); otherwise leave it running.

### F4. Hostile or buggy roster device keeps a restarted writer refusing (the gate waits on a device forever)
- User experiences: after an app restart the writer refuses (`writer-waiting-for-peers`, status `comparing`) for as long as that device keeps sending anything.
- Trigger: "reachable" = any `rep.*` frame from the device within 120 s (`lastSeen`), including a bare summary; the gate needs that device's COMPLETE heads. A device that sends a summary a minute and never heads is reachable forever. No timeout for "reachable but silent".
- Repro: `$S/h1.test.ts` (`-t H2`): `H2 results over 20 min: REFUSED writer-waiting-for-peers`. Honest devices answer heads, so this needs a hostile or broken sender (e.g. a replicator stuck mid-update).
- Smallest fix: a reachable device that has not completed heads within about 60 s of first being heard stops counting for the gate (the self-fork is the backstop for what that skips).

### F5. LOUD but permanent: a peer is frozen on a chat whose writer now agrees with it (sticky fault never clears)
- User experiences: on device B (and C) the chat stops updating for good; its state reads `diverged(writer-two-histories ..., waiting for the writer)`, while the writer's own device reads `in-sync` and keeps chatting.
- Trigger: the writer signed a second history that reached B (B faults), and that second history later no longer exists on the writer (restored again, or lost) so it never announces a V2. B refuses every later batch (`lines-refused-faulted` 14).
- Repro: `$S/s3.test.ts` (clean, deterministic: A's genuine signature over three other lines at 5..7 is delivered to B, then A keeps chatting): `LATER A serving 12 lines; B diverged(...) 10 lines`; test fails. Found by fuzz first: seeds 2068, 3056 (3 devices: B and C both frozen), 11064, 11092, 12124, 14100, 14134 (`DUMP=1 SEED0=<n> NSEEDS=1 NDEV=<2|3> ./run.sh fuzz`).
- Smallest fix: in `applyLines`, when the copy is faulted with `writer-signed-two-histories` or `unsigned-lines-contradicted` and a verified writer-signed batch starts exactly at my head with my own chain value as base, clear the fault and append (the writer's current history contains my lines).

### F6. LOUD but permanent: same-count divergence nobody resolves
- User experiences: writer and a peer both hold N lines with different content; both say `diverged`, the writer refuses (`writer-diverged-from-peer` or `writer-recopy-not-confirmed`), no self-fork happens.
- Repro: `$S/fuzz.test.ts` seeds 12088 (`NDEV=2`: A and B both 15 lines, last four lines differ) and 2061 (`NDEV=2`: the writer's recopy waits for lines the peer holds but cannot serve, `saved-point-not-on-my-chain 37`, `nak-unavailable 37`, while V2 is healthy); also 11080, 13535. I confirmed the symptoms; I did not isolate the root cause (suspected: after repeated restores the lines a peer holds are signed at points off its own chain, so it answers `unavailable`, and the one-time restart-from-zero ask per peer per hello does not break the tie).
- Smallest fix I would accept: none small. Name it in the status for the user and give the writer a way out (offer V2 as the current version) instead of an endless refusal.

### F7. Hostile roster device makes any device do unbounded disk and memory work (review 1 F6 not closed)
- Trigger: any roster device can announce brand-new root versions it writes (documented interim limit in `directory.ts`); each one gets a store folder, two announcement files, a `runs` entry, a link follow and a line in every summary.
- Repro: `$S/h3.test.ts`: 1500 announcements from one device -> 1500 versions, `runs: 1500`, 3002 files / 658 KB under `replicator/`, 7507 files / 1.4 MB under `store/`, all kept for good (6 s).
- Smallest fix: a per-device cap on announced versions with a named refusal until the control log exists (e.g. 1000).

### Lower
- F8 (false alarm, not quiet): an unsigned `nak not-a-prefix` from any roster device flips the WRITER's status to `diverged` (appends still work). `$S/h4.test.ts`.
- F9: `Replicator.selfForks()` and the `onSelfFork` callback are in-memory only and fire after the journal is removed; a crash between loses the notice (V2's announcement on disk still names it, so it is findable, but nothing says so). Suspected from reading, not reproduced.
- F10: status during a running self-fork is not marked; with peers that claim fewer lines the writer can read `in-sync` for V mid-move (suspected from `statusNow`, not reproduced). Peers that wait are named (`diverged`), and the writer reads `in-sync` while they wait (seen in seed 3056).
- F11: test honesty: `replicator-hostile.test.ts:86` ("claiming far more lines schedules a request and proves nothing") failed once under load in my baseline and spuriously killed 8 mutants in the first mutation pass; it must be made deterministic.
- CRC-32 is used only as an integrity check on the own record (the value is then compared with the store's chain) and on the saved-points file, never as authentication. A record that passes CRC by chance is trusted to sign a `cover`; only a local writer or a 1 in 2^32 rot can do that. Fine.
- Set-aside is non-destructive everywhere I looked (`asides.ts` moves, never deletes; retire count is capped at 32 incarnations and only writer-signed material or the writer's own events can cause one). Growth from hostile roster devices is F7 only.

- `in-sync` while a self-fork is pending: yes on the writer while peers wait (F5, F10).
