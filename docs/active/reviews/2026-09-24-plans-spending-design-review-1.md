# Specialists plans spending backend — design review 1

## Findings

- D1 accepted — see design "Revision 1" — [severity: high] — Two independently-computed running totals for "what has this plan spent" are never shown to share an event set. `plan.usedUsd` is fed by the NEW `planSpend.afterReply()` hook, called only from inside `harness-session.ts`'s per-step loop (and from `priceSummaryUsage`, called at two more sites). The conversation's Cost chip total for the same plan child is fed by the EXISTING, separate `emitSubagentUsage()` call in `native-session-host.ts`'s `runPlanChild`, which accumulates usage from `turn-complete`/`session-error`/`user-interrupt` transcript events via `addSpend()` and reports ONCE, in a `finally` block, after the whole child run ends. The design's only proof these stay equal is one sentence about compaction ("so both stay equal") — it never enumerates the full set of usage-bearing events on each side and shows they match. A `session-error` or `user-interrupt` mid-step is exactly the kind of non-normal-completion path most likely to be captured by one accumulator and missed by the other. — evidence: `desktop/src/main/harness/native-session-host.ts:5304-5360` (`addSpend`/`onEvent`/`emitSubagentUsage`, the chip path) vs `desktop/src/main/harness/harness-session.ts:3111-3123,1409-1415,2160,2412` (`turnUsage`/`priceSummaryUsage`, the proposed `afterReply` call sites) — proposed fix: before building `plan-spend.ts`, write out the exact list of call sites that will invoke `afterReply` and the exact list of events `runPlanChild.onEvent` still accumulates for the chip, and add the integration test the design already promises ("summed subagent costUsd equals plan.usedUsd") as a table covering normal completion, `session-error`, `user-interrupt`, and a compaction mid-run — not just the happy path.

- D2 accepted — see design "Revision 1" — [severity: high] — Deleting `localPoolTokens` removes a real, distinct safety check and the design's justification doesn't cover the failure mode it guarded. `plan-budget.ts:373-490` uses `localPoolTokens` (= local engine `contextLength × totalSlots`, computed in `plan-host-bridge.ts:767-774`) to REFUSE a wave that would make concurrently-reserved local specialists collectively need more context than the local llama-server's one shared pool can serve (`plan-budget.ts:487-490`, with an explicit user-facing message). This is a TOKEN-POOL cap, not a headcount cap. The design deletes it with the note "Local-engine concurrency is already bounded by the host's specialist slots" (max 4) — but 4 concurrent local specialists each needing near-max context can still exceed the shared pool even though the count is within budget; nothing in the new design replaces this check. — evidence: `desktop/src/main/harness/plans/plan-budget.ts:373,483-490`; `desktop/src/main/harness/plans/plan-host-bridge.ts:767-774`; design §1 "Deleted entirely" bullet for `plan-executor.ts`. — proposed fix: either keep a pool-capacity check at wave-reservation time for local-engine specialists (it doesn't need the rest of budget-adapter.ts's machinery — it's a single arithmetic comparison against a live number), or, if intentionally dropped, get an explicit product ruling that a plan fanning out several local-model specialists may now fail/degrade at the local engine instead of being pre-empted with a clear message.

- D3 accepted — see design "Revision 1" — [severity: medium] — `afterReply`'s fenced journal write is chained onto a per-attempt `pending` promise, but the design never states what awaits or catches that promise after the LAST reply of a run, when no further `beforeRequest()` call exists to surface a rejection. "The write overlaps tool execution; no `*Sync`" and "beforeRequest awaits pending... returns a stop reason if... the write failed" together imply the ONLY consumer of a write failure is the next `beforeRequest`. If a plan step's final reply's `afterReply` write fails (lock exhaustion — `NativeHome.mutateJson`/`mutateFileUnderLock` explicitly THROWS on lock exhaustion, `native-home.ts:100-107,164-166`) and the run ends without another request, that rejection has no consumer — an unhandled rejection in the Electron main process is a whole-app risk, not a per-plan one. — evidence: design §3 "Implementation" paragraph; `desktop/src/main/native-home.ts:100-107,164-166`. — proposed fix: `plan-spend.ts` must await/catch `pending` on every exit path of an attempt (normal completion, stop, dispose), not only from the next `beforeRequest`; add this as an explicit `plan-spend.test.ts` case ("a write failure on the last reply of a run never produces an unhandled rejection").

- D4 accepted — see design "Revision 1" — [severity: medium] — Task ordering: T2 and T4 are marked parallel-safe ("T4 — Manifest + step models (after T1, parallel with T2)") but both tasks rewrite the same function. T2 is "the harness hook; ... launch() wiring"; T4 is "the resolver providerId" and the design's own §5 text says "launch() reads manifest.steps[input.stepId].binding" — i.e. both tasks touch `plan-host-bridge.ts`'s `launch()` (currently `desktop/src/main/harness/plans/plan-host-bridge.ts:776-815`, which already does credential/manifest lookups in the exact region T4 would change). Two subagents editing the same ~40-line function concurrently is a realistic merge conflict or silent drop of one side's edit. — evidence: design §11 (task table), §5 ("launch() reads..."); `desktop/src/main/harness/plans/plan-host-bridge.ts:776-815`. — proposed fix: re-sequence so T4's `launch()` change either precedes or is folded into T2, or split `launch()`'s manifest-binding lookup into a separate helper each task can own without touching the other's lines.

- D5 accepted — see design "Revision 1" — [severity: medium] — IPC parity is precisely specified for the two NEW channels but not for removing the OLD one. Design §6 lists exact line numbers for adding `plans:set-limit`/`plans:set-step-model` across preload.ts, ipc-handlers.ts, remote-shim.ts, remote-server.ts, `PlansBridge.kt`, `SessionService.kt`. For the removed `plans:add-budget`, the table just says "removed... —" with no file list, even though it is currently present on every one of those same surfaces: `PlansBridge.kt`'s `CHANNELS` set (`app/src/main/kotlin/com/youcoded/app/runtime/PlansBridge.kt:24-32`), remote-shim.ts's `RESOLVE_UNSUPPORTED` set and its `REMOTE_ACTION_CATEGORY` map (`desktop/src/renderer/remote-shim.ts` — verified present at the map and near line 3154), and remote-server.ts's case list (`desktop/src/main/remote-server.ts:2320`). A stale channel string left on any one of these (while the main-process handler is deleted) breaks that surface silently for a remote/Android caller that still references it, or leaves dead code the parity tests don't catch since they check presence, not correctness of removal. — evidence: `app/src/main/kotlin/com/youcoded/app/runtime/PlansBridge.kt:24-32`; `desktop/src/renderer/remote-shim.ts:784,3154` (`RESOLVE_UNSUPPORTED`, invoke object); `desktop/src/main/remote-server.ts:2320`. — proposed fix: add `plans:add-budget` removal, by name, to the same file list the design gives for the additions, and extend `ipc-channels.test.ts`/`mock-shim-window.test.ts` assertions to fail if the string survives anywhere.

- D6 accepted — see design "Revision 1" — [severity: medium] — Crash-recovery risk #1 is self-flagged by the design ("Removing request phases changes crash recovery... needs explicit tests") but §10's test list only promises "crash recovery charges nothing" — it does not name a test for the specific scenario the risk describes: an unanswered EXTERNAL (side-effecting) tool call surviving the collapse of `phase: 'prepared'|'launched'|'committed'` (dropping `request-sent`/`ambiguous`) without being replayed. The current code's `recoverAttempt` (`plan-executor.ts:704-`) treats `request-sent` specially (charges unresolved, marks `ambiguous`, requires the user to have seen it before auto-continuing); the new design folds that entirely into `classifyChildTranscript`'s `dangling-effect` verdict for any `launched` attempt. That's plausible but is exactly the kind of behavior-preserving refactor that needs a named pinning test, not just "recovery charges nothing." — evidence: design §12 Risks (1); §10 Tests ("crash recovery charges nothing"); `desktop/src/main/harness/plans/plan-executor.ts:704-722` (current `recoverAttempt`), `:229-249` (`classifyChildTranscript`). — proposed fix: add an explicit `plan-executor.test.ts` case: a `launched` attempt whose transcript ends on an unanswered external tool call (e.g. a message-send) is paused, not replayed, under the new two-phase model — matching the "Kept" list's promise that "an unanswered EXTERNAL call is never replayed."

- D7 accepted — see design "Revision 1" — [severity: low] — The new history-index cache (`~/.youcoded/specialist-usage.json`) has no stated eviction, rotation or size cap, and `NativeHome.mutateJson`'s write does a synchronous whole-file `JSON.parse`/`JSON.stringify` (`native-home.ts:109-130`) inside a "debounced cache write" — i.e. a timer-triggered path, which `performance.md` rule 1 explicitly calls blocking ("no... whole-file parse on any path a... timer reaches"). With one entry recorded per completed specialist run and no pruning mentioned, this file grows without bound over the life of the app; the risk is small today (297 runs ≈ a small file) but the design gives no reason it stays small, and the main-blocking-calls ratchet likely won't catch a `JSON.parse` call the way it catches `*Sync` fs calls. — evidence: design §4 ("Cache `~/.youcoded/specialist-usage.json`... debounced cache write"); `desktop/src/main/native-home.ts:109-130`; `.claude/rules/performance.md` rule 1. — proposed fix: cap the index (e.g. keep only the newest N runs per agentType/model, or age out entries older than the estimate ever needs), and note the cap explicitly so a future session doesn't have to rediscover the unbounded-growth question.

- D8 accepted — see design "Revision 1" — [severity: low] — Images become allowed in plan specialists for the first time as a side effect of deleting the reservation machinery, and this isn't a decision 33–37 ruling. `imagesAllowed`'s plan-child carve-out exists ONLY because "an image has no certified token bound (budget-adapter.ts)" (`harness-session.ts:1015-1019`); design §1 deletes that clause, and §3 confirms plan children now get "images" through the ordinary request path. Reasonable given the stated rationale disappears, but it's a genuine behavior change (a plan specialist could not see images before; it can now) that none of decisions 33–37 discuss, and the surrounding code comments ("Read never promises pixels", "wire replaces any stored image with a named placeholder") suggest other assumptions about plan children being non-vision may exist elsewhere in the harness. — evidence: `desktop/src/main/harness/harness-session.ts:1015-1019`; design §1, §3. — proposed fix: confirm with Destin that plan specialists seeing images is an intended, wanted change (not just an accepted side effect of a budgeting deletion), and grep for other `!isSpecialistChild`/`planChild`-gated vision assumptions before shipping.

- D9 accepted — see design "Revision 1" — [severity: low] — No test in §10 covers the design's own self-flagged risk #2 ("`withRetry` may resend a failed request the provider billed without reporting usage; uncounted"). It's explicitly accepted as matching the chip's existing blind spot, but an accepted risk with zero test coverage is easy to silently regress further (e.g. if `withRetry`'s retry conditions widen later, this blind spot widens with it, and nothing would notice). — evidence: design §12 Risks (2); §10 Tests (no matching entry). — proposed fix: at minimum, a comment at the `withRetry` call site inside the plan-child path naming this known gap, so a future change to retry conditions is forced to re-read it.

## Verdict

The accounting design is sound in its stated arithmetic (`costForUsage` reused unchanged, same price card, cache-read discount matches decision 22) and its crash-safety story is a real simplification over the deleted request-phase machinery — but three things need resolving before build: the plan's own spend total and the conversation's chip total are asserted, not shown, to stay in sync across error/interrupt paths (D1); a genuine safety check for shared local-engine context capacity is dropped with no replacement or explicit sign-off (D2); and one task-ordering conflict (D4) plus one incomplete IPC-removal spec (D5) risk build-time breakage rather than runtime bugs. None of the eight kept behaviors from decisions 33–37 are contradicted by the design as written.
