- D1 accepted — major — Holder-takeover destroys a session by calling `sessionManager.destroySession()` directly, bypassing every place the design wires `untrack()` (the `SESSION_DESTROY` IPC handler and the window-close handler) — so a conversation moved to another device stays in `open`/gets offered back by Welcome Back on this device even though it is "no longer open HERE," exactly the case §2 flags with "should untrack" and "→ verify in build" but never resolves. A user could be offered — and attempt to resume — a conversation that's now live on another device, which is precisely what the lease/takeover system exists to prevent. — evidence: `desktop/src/main/conversations/takeover.ts:141` and `:225-232` (`deps.sessionManager.destroySession(id)`/`destroySession(desktopId)` called straight from the takeover flow, never through `ipcMain.handle(IPC.SESSION_DESTROY, ...)` at `ipc-handlers.ts:1084` or `remote-server.ts:1805`); design §2 table row "destroySession, session-exit, destroyAll, crash → nothing (that is the point)" would otherwise silently swallow this case too. — suggested fix: give holder-takeover its own explicit `untrack(desktopId)` call at the same point `pushMoved`/`destroySession` run in `takeover.ts`, and add a test asserting a takeover-destroyed id is removed from `open` (not just an ordinary crash-exit id, which must stay).

- D2 accepted — major — Race between an in-flight per-window "Resume on Next Launch?" prompt and a concurrent whole-app quit. `app.on('before-quit')` fires before any window's `close` event and, on its first pass, unconditionally calls `e.preventDefault()` + `shutdownApp()`, which runs `sessionManager.destroyAll()` for every window's sessions immediately — including the sessions a currently-open `QuitSessionsPrompt` is still asking the user about. Two bad outcomes follow: (a) if the pending prompt's eventual answer is `{close:true, reopen:false}` (the default), the handler's `untrack()` call strips those ids from `open` even though the actual end was a whole-app quit (S-other-quit, which is supposed to "keep it" silently with no ask at all) — so the user loses a resume offer they never consciously declined; (b) Electron's second `app.quit()` pass (after `shuttingDown` is set) will try to close that same still-open window again, re-entering the "second close press" branch, so the quit sequence stalls behind a dialog describing sessions that are already dead. The design's §4 never accounts for `before-quit` racing ahead of a pending window-close request. — evidence: `main.ts:944-970` (existing per-window close handler the design replaces), `main.ts:2474-2480` (`before-quit`: `if (shuttingDown) return; e.preventDefault(); void shutdownApp().finally(() => app.quit());`), `main.ts:2407-2429` (`shutdownApp`/`runShutdown` call `sessionManager.destroyAll()` with no coordination with any pending window-level close request). — suggested fix: have the `before-quit` handler check for/await any pending `window:close-request`s (or short-circuit them with an implicit "keep tracked" answer) before running `shutdownApp()`, so a race never lets a stale answer downgrade a S-other-quit into an explicit "don't resume."

- D3 accepted — major — "Only one window may show Welcome back" (leader-window gating) is explicitly still-to-be-added (§5: "Add: skip in remote mode..., on Android, and in any window that is not the leader main window") and is NOT present in the built renderer: the `welcomeBackAsked` effect only checks `isFirstRun`, `sessionListLoaded`, `remoteCatchingUp` and `sessions.length` — no leader/window-id check exists. Until it lands, every open main/detached window independently calls `reopenList()` and can render its own Welcome Back screen whenever its own strip is empty (e.g., two blank windows at launch, or a torn-off window whose strip emptied). Because main only removes ids from `offer` on an explicit `forgetReopen` (never on read), resuming a row in one window does not update the other window's already-fetched list, so the second window keeps showing already-actioned rows as available. `resumeAdmission`'s coalescing (`conversations/resume-admission.ts:36-39`) likely prevents an actual double-spawn/corrupted-transcript outcome, but the user-visible result is duplicate simultaneous screens and a click that silently does nothing or throws a lease-denied error with no explanation. — evidence: `App.tsx:3496-3506` (the effect's guard list), design §5 "Add:" line. — suggested fix: gate on `windowRegistry`-reported leader id (already pushed to renderers via the directory) before fetching `reopenList()`, and treat this as launch-blocking for the feature, not a follow-up.

- D4 accepted — minor — The 5-second close-request timeout branch ("Timeout → close, and keep the sessions tracked") doesn't say whether it also runs the destroy+`releaseSession` loop that the `close:true` branch explicitly calls out, or just calls `win.close()` on its own. Read literally, a frozen/crashed renderer that never answers would have its window closed while the underlying PTY/native sessions are left running with no owning window (windowRegistry ownership is cleared by `unregisterWindow` on `closed`, but nothing there kills the process) — invisible zombie sessions until the whole app quits. — evidence: design §4 steps 2–3 (only step 3's `close:true` branch names "the existing destroy + releaseSession loop"); `window-registry.ts:78-101` (`unregisterWindow` releases ownership bookkeeping only, never touches `SessionManager`). — suggested fix: state explicitly that the timeout path also destroys the window's owned sessions (just skips `untrack`), matching "same as a crash" intent, and add a test for it.

- D5 accepted — minor — §1's "the startup read is one `fs.promises.readFile` before `createWindow`" doesn't match `createWindow()`'s actual shape: its first statement already synchronously constructs the real `BrowserWindow` (`mainWindow = createAppWindow({ maximize: true })`, `main.ts:976`), with `registerIpcHandlers()` (where `session:reopen-list` would live) called ~100 lines later in the same function. "Before createWindow" therefore can't mean "before this function is entered" without restructuring `app.whenReady()`'s call site instead — worth pinning down explicitly so the union/reset logic doesn't end up racing the renderer's first `session:reopen-list` call in an unusual boot order (slow disk, antivirus scan on the userData file, etc.). — evidence: `main.ts:975-976`, `main.ts:1075` (`registerIpcHandlers(...)` call inside `createWindow`). — suggested fix: name the actual hook point (e.g., "before `createWindow()` is invoked from `app.whenReady()`", not "before `createWindow`" read as the function body), or make the `session:reopen-list` handler await the startup read's completion explicitly rather than relying on timing.
