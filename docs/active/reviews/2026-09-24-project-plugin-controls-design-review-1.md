# Review: 2026-09-24 project/plugin controls technical design

D1 — §4 IPC / Scope — The design lists only four IPC surfaces (`preload.ts`, `remote-shim.ts`, `ipc-handlers.ts`, `SessionService.kt`) for the three new channels, omitting `remote-server.ts` entirely, even though Scope explicitly promises "remote-browser access to all of it... Remote browsers use the desktop backend and get the full feature" — confirmed `remote-server.ts` is a distinct, required 5th surface that already carries the sibling `artifacts:*`/`project:*`/`syncspaces:*` channels (`youcoded/desktop/src/main/remote-server.ts:3728-3760`), and the workspace's own `ipc-bridge.md` rule states plainly "A channel has FIVE surfaces, not four... `remote-server.ts` is the desktop's WS host for a remote browser... so a channel skipped there is dead over remote." As written, a remote-browser user opening Skills & tools would hit an unhandled/`unsupported:true` response instead of the promised full feature — a silent break of the design's own scope claim, not just a missing test.

D2 — §2 rule 2 ("A marketplace plugin... whose `installedAt` is AFTER the project's `seededAt` → off") — This compares two differently-typed clocks that the design never reconciles: `seededAt` is documented as "ms" (§1), but `installedAt` is a `string` ISO timestamp (`desktop/src/shared/types.ts:1116,1237`; written via `new Date().toISOString()` at `desktop/src/main/skill-config-store.ts:47,370`). A literal `installedAt > seededAt` in JS coerces the ISO string via `ToNumber` to `NaN`, and any comparison against `NaN` is `false` — so the "new download starts inactive" rule would silently never fire unless the implementer remembers to `Date.parse()` first, which the design doesn't call out anywhere (not in §2, not in the pinning-test list in §6). Confirmed by reading both fields' real types/writers; the failure mode itself (silent `false`) is derived from JS semantics, not executed.

D3 — §1 storage record — `seededAt` is a single scalar field on the record, but §1 only defines a merge rule for `plugins[p]`/`items[k]` ("per entry, last-writer-wins by `at`"); no merge rule is given for the record's own scalar fields (`schemaVersion`, `seededAt`). If two devices both first touch a newly-synced project before either has pulled the other's write (plausible — this is exactly the race `sync-spaces/project-registry.ts`'s fold-on-read exists to handle for the sibling `ProjectSync` store), each writes a full record with its own `seededAt` and its own device-local materialized items. Nothing in the design says which `seededAt` wins on fold, so the "AFTER `seededAt`" rule in §2 can give different verdicts depending on which record's `seededAt` a later read happens to keep. [PLAUSIBLE — this is a documentation gap in the design, not a reproduced bug; the sibling store it patterns itself on (`project-registry.ts`) does define an explicit per-field merge for every field it has, which this design does not do for its own top-level fields.]

D4 — §3 "Tool connections" — Achieving "a turned-off server is not even spawned for that session" requires changing `McpManager.acquire(sessionId)`'s signature/behavior, since today it unconditionally calls `this.registry.resolveAllEnabled()` and connects to every enabled server before any caller-side filtering (`desktop/src/main/harness/mcp/mcp-manager.ts:143-146`) — confirmed by reading `acquire()`. The design's sentence ("filter `mcpLease.servers` to `mcpIds`... and pass the allowed ids into `McpManager.acquire`") describes the desired outcome but not the actual code change needed, and doesn't address how a per-project allow-list composes with the existing "whole-server, in registry order, dropping from the END" attachment-budget rule (`.claude/rules/harness-tools.md`) — i.e., which filter applies first when a project's allowed set plus the model's context budget both want to drop servers. Not necessarily wrong, but under-specified for something in the "Enforcement" section rather than "Open for Destin."

D5 — §3 "Skills" — "resolves the conversation's project from its cwd (saved folder match by canonical path; nearest ancestor wins)" cites no existing mechanism, and a repo-wide search for cwd→project resolution (`nearest ancestor`, `findProjectForCwd`, `projectForPath`, `resolveProjectForCwd`) found nothing — this appears to be entirely new logic the design describes in one clause without saying how it handles a saved folder nested inside another saved folder, or a specialist/sub-agent cwd that differs from the root session's cwd. [PLAUSIBLE — absence of a hit is not proof no such helper exists under another name, but the closest analogous existing code (`native-permissions.md`'s `nativeStoreSlug(entry.cwd)`) matches by slug equality, not ancestor search, so this would be new comparison logic, not reuse of a precedent.]

D6 — §1 "Source facts" — The stated reason for the sibling-file design ("an older build rewriting it (a rename) would drop any field we add") is imprecise: `project-registry.ts`'s `parseEntry` (`desktop/src/main/sync-spaces/project-registry.ts:62-86`) rebuilds the record from an explicit whitelist of fields on *every* read, on *every* build, including the current one — so an added field would never survive a single write/read cycle through this store even without a version skew. The conclusion (use a sibling file, not a field) is still correct, but the justification undersells the risk as a legacy-device problem when it's actually true unconditionally.

D7 — Open for Destin #1 — The stated fact ("The app has no incognito conversation yet") is confirmed: a repo-wide search for "incognito" only turns up the unrelated game-presence feature (`desktop/src/main/prefs-service.ts:113-119`), not a conversation concept. The proposal (keep today's full-access behavior outside any project until incognito exists, defer "none" to incognito only) is a reasonable reading of the tension between two decisions-doc lines ("no-project/incognito gets no automatic skills" vs. "don't turn off what works today"), but it is a real, literal deviation from the decisions doc's flat statement that a no-project conversation gets none — worth Destin explicitly re-confirming rather than treating the proposed default as settled, since as written it reads as already-decided in the decisions doc.

D8 — Open for Destin #2 — Facts check out: `SessionService.kt` answers `not-implemented-on-mobile` for every `artifacts:*` Projects channel (confirmed, 24 occurrences, e.g. `app/src/main/kotlin/com/youcoded/app/runtime/SessionService.kt:4025-4046`), so there is indeed no Android Projects screen to hang Q-4's "show with note" on yet. The proposal (no Android work this build, ship the note when Projects lands on Android) is sound and consistent with the decisions doc's own "Still open" item 3 caution about not falsely claiming to affect Claude-Code-based Android sessions.
