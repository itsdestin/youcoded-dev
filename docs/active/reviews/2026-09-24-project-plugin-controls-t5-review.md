## Answers to the assigned questions
1. Chip wording/shape matches the approved screenshot exactly: green "Automatic", amber "Manual use", red "Unavailable" dot-and-label pill (`SkillCard.tsx` `AVAILABILITY_STATUS`), and the dimmed "Unavailable" card renders under a "Needs setup here" heading with per-kind subtitle text ("Choice saved for this project; skill file missing here" for a personal skill) — confirmed against `docs/active/design/2026-09-23-project-plugin-controls/images/.../drawer-chips--midnight--after.png`, which shows the identical card/copy/chip for "Writing helper". No mismatch found.
2. `catalogKeyForSkill` (`skill-catalog-key.ts:19-22`) is byte-for-byte the same three-line rule as main's `itemKeyForSkill` (`desktop/src/main/project-extensions/resolve.ts:86-90`): `self:<id>`, `project:<id>`, else raw id — verified by reading both functions side by side. `SkillEntry.source` (`shared/types.ts:1105`) has exactly 5 values (`youcoded-core | self | project | plugin | marketplace`); all 5 are covered (the two named branches plus the fallthrough for the other 3), and the new test (`skill-catalog-key.test.ts`) exercises all 5. It is a real duplication risk (a future change to either copy without the other silently breaks every chip, since a mismatched key means every installed skill reads "Manual use" instead of its real status) — the code's own WHY comment concedes this and blames the renderer/main process boundary, not a technical impossibility of a shared file: `shared/types.ts` is reachable from both sides already (it's how `SkillEntry`/`ProjectExtensionsForSessionResult` cross the boundary today), so a plain, side-effect-free `itemKeyForSkill`-shaped function could live in `shared/` and be imported from both places instead of hand-mirrored. This is a design choice the branch's own comment flags rather than hides, so I'm surfacing it as a "weird but documented" item rather than a bug.
3. Hook is IPC-clean while closed: `if (!open || !sessionId) { setResult(null); return; }` (`useSessionAvailability.ts:44`) runs before the `window.claude` call, so no `forSession` call fires until `open` is true and a `sessionId` exists — pinned by `useSessionAvailability.test.ts`'s "makes zero calls while the drawer is closed" case, which I re-ran (part of `verify.sh`'s full suite, PASS). Stale responses are dropped via the `generation` ref bumped at the top of every effect run and checked before each `setResult` — pinned by the "ignores a slow response" test, also PASS. `not-implemented-on-mobile` and any other `{ ok: false }` shape both fall into the same `if (!res.ok) { setResult(null); return; }` branch — hides chips rather than guessing, matching design intent, pinned by both error tests, PASS.
4. `SkillCard` receives `status` as a plain string (`'automatic' | 'manual' | 'unavailable' | undefined`) from `skillStatus(skill)`, a `useCallback` keyed on `frozenSkillIdSet` — no fresh object/closure reaches the memoized `SkillCardImpl` per render beyond what already existed pre-T5 (`handlersRef` pattern is untouched). `CommandDrawer` itself is not memoized (same as before this commit), and `useSessionAvailability`'s effect only fires on `[sessionId, open]` changes; while closed, a `sessionId` change still runs the effect but calls `setResult(null)` when state is already `null`, which React bails out of (`Object.is` same-value check) — no additional render from a background session switch while the drawer is closed. I did not find new re-render pressure beyond the drawer's existing patterns.
5. The dimmed missing card is a native `<button>` (`CommandDrawer.tsx:365-390`): keyboard-focusable by default, `aria-label` states the row's name + destination, `focus-visible:ring-2` and `hover:opacity-100`/`focus-visible:opacity-100` both lighten the dimmed card, and the chip inside has `group-hover:brightness-125`/`group-focus-visible:brightness-125` (no separate interactive element nested inside — the chip is a plain `<span>`, so no nested-button a11y violation). This matches `narrow-viewport.md`'s "hover-only affordances have no touch path" concern only partially: the card's own visual brighten-on-hover is also triggered by `focus-visible`, so keyboard/touch users get the same affordance via focus, and there's no load-bearing `title=`-only text (the `title` attribute duplicates the `aria-label`'s content rather than carrying unique information).
