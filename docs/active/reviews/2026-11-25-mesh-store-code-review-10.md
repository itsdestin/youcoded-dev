## What a person would experience (plain language)
- An old backup of one chat folder put back: the chat now says "rolled back" and refuses to show the lines from the cut onward until the app has received them again; nothing different is ever shown. This holds in every run where the store's separate memory of "how far this chat ever got" survived.
- A plain crash or power cut (no damage): the chat reopens fully readable, no warnings. Zero exceptions in 6,000 + 5,000 crash-only sequences and 1,872 crash points tried by hand.
- Worst cases left: (a) a whole-backup restore (chat folder AND the memory file back together) plus a chat that once received a conflicting "waiting" batch: two lines can be shown that differ from what the chat acknowledged (F-B); (b) a chat that was retired after a crash mid-retirement can come back as an empty chat under the old id if someone deletes both of its folders (F-A).

## Findings, ranked

### F-A (LOW-MEDIUM) The store-root retirement record is not written when a retirement is finished after a crash
Claim 5 ("deleting both the aside folder and the retired folder cannot bring an id back") holds only for retirements that did not crash midway.
Cause: `asides.ts` `setAside` returns early when `retiredName` already finds the aside folder (it "changes nothing"), and `finishAside` (also run at load) writes `retired.json` and moves the files but never writes `retired/<vhex>.ret`. `retire()` writes the root record only on the fresh path. A crash after the aside folder is made and before `.ret` is durable (or a disk-full at that point, which `quarantineOrReport` tolerates) leaves an id with two witnesses for good.
Reproduction (`probe_retire3.test.ts`, deterministic): version with 20 lines; arm a crash at disk operation k of `setAsideDamaged`; reopen; call `setAsideDamaged` again (returns the aside name); delete the aside folder and the version folder (directories too, as a retention job would); reopen. k=1 and k>=7: `head` refuses, `registerVersion` refuses (record present). k=3, 5, 6: no `.ret` file exists, `head` refuses but `registerVersion` is ACCEPTED, i.e. a fresh empty version under the retired id. Crash points 2-6 of about 60 (roughly 8%). Reaching it needs a crash during retirement plus a retention job that deletes both witnesses, so it is rare, but it is exactly the case the new record exists for.
Why the earlier fuzzes did not see it: deleting files leaves empty directories in a test disk, and the aside folder's own existence is one of the witnesses. My first retire fuzz missed it the same way until I removed directory entries too. After fixing that, 2,699 seeds of retire-heavy fuzz with deletions of every single witness or any pair that left at least one witness: 0 un-retirements (about 6,000 single or pair deletions with a witness left); deleting all three: the id returns (documented limit 5).
Fix: in `finishAside` and in the early-return branch of `setAside`, write the root record when it is missing (existence only). Also the inventory line "(5) a retired id whose aside folder AND retired.json are both deleted is two faults" is now stale next to rule (ii).

### F-B (LOW) Limit 4 says "Fewer lines, never different lines"; that is false for one two-fault shape
Shape: the chat folder AND its high-water record are put back together (a whole-backup restore, or the record lost/older at the same time), and the old folder holds a stale waiting batch whose lines differ from lines the chat acknowledged later. After the head reaches the batch's start (the replicator resends the true earlier lines), the batch drains and is served at positions that were acknowledged with other bytes; the replicator's own resend of the true lines answers `not-a-prefix`.
Reproduction (`probe_twofault.test.ts`): true lines 0..1, a different sender parks lines 4..5, snapshot folder and record, acknowledge true 2..29, put the snapshot back. Mode "folder only (record intact)": reported rolledBack from 2 had 30, park held, everything clean after a resend (F1 closed). Mode "folder + record back together" and "folder + record deleted": no report, head 2; after resending lines 2..3 the park drains; read(4), read(5) return DIFFERENT lines, resend of true 4..29 answers `not-a-prefix`.
Evidence at scale: in my fuzz 20,000 seeds (batch B) gave 20 seeds with 193 WRONG-LINE records (plus 34 inherited by forks, because a fork copies what the parent serves), all with fault `folder-old` + record also put back or deleted; zero with the record intact. Disabling the park drain makes all 20 seeds clean (classification proof). Earlier batch A: 31 seeds of 48,000, same class, same proof.
Needs: a diverged sender that parked lines (replicator rule (i) says it should not exist) plus a whole-backup restore, so narrow. Not a bug the store can fix without a second record; fix is wording plus a replicator rule: after any restore of files, release all parked files of that version (`releaseParked`) before resending, and treat `not-a-prefix` on its own acknowledged lines as "this device holds a diverged history: retire the version". Keep the inventory limit 4 honest.

### F-C (LOW) "A folder whose chain value contradicts the record is retired at load" is narrower than stated
`highwater.ts` `rolledBack` compares only when head < record AND a ladder point at or below the head exists. Probe (`probe_contra.test.ts`, a different history under the same id from another store, record 20): head 10 (record 20): reported rolledBack, NOT retired (the ladder had only the seed and the newest point, because the 20 lines came in one call, so the only point <= 10 is the seed); head 20 equal and head 25 longer: not compared at all, the foreign lines are served. This is the "two histories under one id" case that rule (i) puts on the replicator, so impact is low, but the sentence in the commit and header overstates. Cheap improvement: also compare the newest ladder point when head >= record count (the chain value at the record's count is available).

### F-D (INFO / usability) The record and the partial marker count lines that were never acknowledged to the caller; the replicator cannot see how far to refill
The checkpoint is the commit point, so the lines of a call that finished durably but crashed before returning count as acknowledged by the store (and the record). After a rollback or a set-aside, reads are refused from the report start until the head reaches the recorded head with the recorded chain value, so those lines must be re-supplied too. `head().rolledBack` gives `had`; the partial marker's end is NOT exposed (`damagedFromLine` only). Seen in fuzz as "LOCKOUT": the harness resent every line it had acknowledged, got `ok` each time, and the flag stayed (`damagedFromLine 3` with head 5, marker lines 3..7, the checkpoint had counted two unacknowledged lines). Re-supplying those lines (a replicator re-reads them from the source transcript) cleared every case: 0 unrecoverable in the final harness over 570 flagged seeds; they all cleared, so this is loud and recoverable, not a lock-out. User sees: correct early lines refused (typed `corrupt`) until the end of the chat is re-sent; an append whose lines differ from the recorded ones retires the version (loud). Suggest adding the marker's end to `Head` (like `rolledBack.had`).

### F-E (INFO) F5 residual is wider than the fixer states, and one in-repo fuzz seed fails

With the record lost or older (no chunk fault needed), the present bodies read as typed `evicted` (4 or 12 lines): loud, nothing wrong served, but the stated uncovered case ("older checkpoint + record lost + one chunk file") is really "older checkpoint + record lost/older".
