# T2 "Spend core" — code review (`ebe74b3e3` vs `a58ad20b9`)

Scope: `desktop/src/main/harness/{harness-session.ts,native-session-host.ts,pricing.ts,plans/{plan-spend.ts,plan-executor.ts,plan-host-bridge.ts}}` and the four new/updated test files. Checked against design §3 + Revisions 1–3 and decisions 33–37.

- S1 accepted — fixed, test seen red then green — [high] — a plan spend-write failure is misrouted into the invalid-report auto-recovery path instead of pausing cleanly for the user, violating design's "a failed write routes sensibly" — evidence: `commitReport` (`desktop/src/main/harness/plans/plan-executor.ts:1393-1398`) returns `{kind:'pause', why:'unexpected-error', reason: PLAN_PROGRESS_NOT_SAVED}` when `run.spendWriteFailed`; `memberEnd`'s gate (`plan-executor.ts:1210`) only checks `invalid.kind !== 'pause'`, never `invalid.why`, so this pause falls into `reportOnlyRetry` (`plan-executor.ts:1212`) exactly like a genuine invalid-report pause; `reportOnlyRetry` hardcodes `routePlanPause('invalid-report', { reportOnlyFundable: true, ... })` (`plan-executor.ts:1351-1361`), which on the first occurrence for that step/item/iteration returns `route: 'auto'` (`pause-routing.ts:110`) — so the executor AUTO-LAUNCHES a fresh report-only turn on the same specialist, handing it `planReportOnlyBrief({problem: "The plan stopped because its progress couldn't be saved."})` as if that internal journal-write failure were feedback on the specialist's OWN report, and records it as an `invalid-report` recovery (`plan-executor.ts:1359`) instead of surfacing the real cause to the user. This path is pre-existing (T1) machinery that T2's new `commitReport` early-return was never routed around — before T2, every pause `commitReport` could return WAS an invalid-report pause, so the unconditional fall-through was safe; T2 added a second, structurally-identical `kind:'pause'` case it doesn't belong in. No test exercises this (see S2/S3 below) — `plan-executor.test.ts` never sets `run.spendWriteFailed` and asserts on `memberEnd`'s routing.
  - Fix: discriminate on `why`, not just `kind`, at the gate: `if (run.halt || invalid.kind !== 'pause' || invalid.why !== 'invalid-report') { this.requestHalt(run, invalid); return 'done'; }` (`plan-executor.ts:1210`).

- S2 accepted — literal-number test added — [medium] — `billedEquivalentTokens`'s cache arithmetic (review item 2's "cache reads 0.1×, cache writes counted") has zero test coverage with a nonzero cache value anywhere in this commit, and the tests that do assert token totals are tautological about the formula — evidence: `billedEquivalentTokens` (`desktop/src/main/harness/pricing.ts:112-115`); every usage object passed to it across `desktop/tests/plan-spend.test.ts` (lines 81, 113, 130, 149, 169, 183) and `desktop/tests/harness-session-plan-spend.test.ts` uses `cacheReadTokens: 0, cacheCreationTokens: 0`; the assertions that DO check `spentTokens`/`usedTokens`/`p.usedTokens` (`plan-spend.test.ts:89-90,156-157,204`) compute their own expected value by calling `billedEquivalentTokens(usage)` — the SAME function under test — so a wrong coefficient (e.g. `0.1` applied to the wrong field, or a `round` instead of `ceil`) would pass silently. `harness-pricing.test.ts` (unmodified by this commit) has real cache-token cases but only for `costForUsage`, never `billedEquivalentTokens`.
  - Fix: add a direct unit test for `billedEquivalentTokens` with hand-computed expected numbers exercising nonzero `cacheReadTokens` and `cacheCreationTokens` (e.g. beside the existing `costForUsage` cache-mix cases in `harness-pricing.test.ts`).

- S3 accepted as disclosed — compaction parity covered at harness level — [low] — disclosed but real: no test proves the chip/journal parity claim (D1's core promise) across a forced compaction reached through the full `NativeSessionHost` stack — evidence: `desktop/tests/plan-spend-chip-parity.test.ts:184-197`'s own comment says engineering real compaction through the full native-host stack "proved too fiddly to do reliably here," and substitutes the harness-level `harness-session-plan-spend.test.ts` compaction test, which proves `afterReply` fires for a compaction's usage but does NOT prove that usage reaches `entry.planSpend.total()` and thus the chip via `runPlanChild`'s `finally`, for a plan child specifically. The three chip-parity scenarios that ARE covered (clean finish, provider error, interrupt) do exercise the real wiring, so the gap is narrow and honestly disclosed, not hidden.
  - Fix: none required now — flagged so a future compaction-touching change to `runPlanChild`/`startPlanChild` doesn't assume this case is pinned.

**Verdict:** The core mechanism is correct and well-tested where it's tested: chip parity for the clean/error/interrupt paths (S1 aside) is real and verified end-to-end against a live `NativeSessionHost`, `beforeRequest`'s "refuse only the next request" timing is precisely right and pinned (the crossing reply's tools run, no second `doStream`, clean `turn-complete` with no park), the journal-write concurrency (4 siblings, mid-run limit change, live vs. captured `spendSettled`) is verified against a real filesystem journal rather than mocks, and the `reportOnlyOf` childId fix is real and independently confirmed by asserting `resumeChildId === a.childId`. The one correctness bug worth blocking on is S1: a spend-journal write failure — precisely the crash-safety scenario this task exists to handle safely — currently causes the executor to auto-retry the specialist with a nonsense "problem" message drawn from an internal error string, instead of pausing the plan and telling the user their progress couldn't be saved. It's a small, mechanical fix (one added condition) but changes user-visible behavior on exactly the failure path Revision 1 D3 was written to make safe, so it should land before this task is considered done. S2 is a real coverage gap on a formula this task introduces and multiple other pieces (the estimate, T5) will build on; worth a quick follow-up test. S3 is acceptable as disclosed residual risk.
