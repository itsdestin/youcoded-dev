# Review 1 — Pages finish, step 2 (files) technical design

Design: docs/active/specs/2026-10-24-pages-finish-step2-files-technical-design.md (cited "D §n").
Paths are under youcoded/desktop/src unless noted. "unverified" = could not check from code.

1. **blocker** — The deny list does not protect "write" at all, and "all / readwrite" can plant code execution.
   Claim (D promise 3): the credential list is "applied to the real path" for reads and writes. Evidence: `main/harness/tools/credential-paths.ts:84-120` (`isPhoneDeniedPath`) is a list of secrets to not READ. It has nothing for places a write turns into code running later: `~/.bashrc`, `~/.profile`, `~/.zshrc`, `~/.config/fish/config.fish`, `~/.config/autostart/`, `~/.local/bin`, `~/.config/systemd/user/`, macOS `~/Library/LaunchAgents/`, Windows Startup folder, and `~/.claude/` hooks and settings, YouCoded's own `settings.json`, and a page's own folder (a page rewriting its approved HTML or `program` file; program hashing at `pages-service.ts:262-266` only detects it after the fact). `.ssh` is denied as a segment, so `authorized_keys` is covered, but nothing else is.
   Fix: a separate, longer WRITE deny list (the above plus `.claude/`, the pages folder, the userData folder) checked on the real path and on the parent's real path; make it default-deny for dot-directories directly under home at `all` level. Pin it with a table test.
   Triage: accepted — a separate WRITE deny list (shell start-up files, autostart and login items, ~/.local/bin, systemd user units, LaunchAgents, Windows Startup, ~/.claude/, YouCoded's userData and every Pages folder, the page's own folder) checked on the real path and the parent's real path; at `all` level every dot-folder directly under home is write-denied. Table-tested.

2. **blocker** — The read deny list does not cover several secret classes, and "all" reaches outside home where the list is not anchored.
   Evidence: `isCredentialPath` returns false for anything not under home (`credential-paths.ts:73`). Absolute paths at `all` level can therefore read `/proc/self/environ`, `/proc/<pid>/environ` (every API key the app holds in env), `/etc/*`, other users' homes, `/Volumes`, `C:\Users\Other`. `.env` / `.env.*` is explicitly NOT denied (comment, `credential-paths.ts:127-129`), so a page with folder level on a project reads every project's secrets. Not covered either: `~/.bashrc`/`.zshrc` (often hold tokens), `~/.config/rclone` dir variants, `.mozilla/.../cookies` only under the listed roots, Flatpak/Snap browser profiles (`~/.var/app/...`, `~/snap/...`), `~/.config/1Password`, `~/.local/share/Steam`, `*.keystore`, `*.jks`, `*.ovpn`, `wallet.dat`, `.env` family, `~/.kube/config` is covered, `~/.terraform.d`, `secrets.*`, `*.sqlite` of messengers (Signal, Slack).
   Fix: at `all` level refuse everything outside home, `/proc`, `/sys`, `/dev`, `/etc`, `/var`, and add `.env*`, `.var/app`, `snap`, `.keystore/.jks/.ovpn` to a files-specific list (a new function, not a change to `isPhoneDeniedPath`, which the phone tests pin). Say plainly on the card that `.env` files are readable, or deny them.
   Triage: accepted — `all` is confined to home (never /proc, /sys, /dev, /etc, /var, other homes, drive roots); a files-only READ deny list adds `.env*`, `.var/app`, `snap`, `*.keystore`/`*.jks`/`*.ovpn`/`wallet.dat`, messenger and password-manager folders, shell rc files, on top of the phone list (which stays untouched).

3. **blocker** — Path confinement is described but is a check-then-use race and misses links.
   Evidence: D §3 "then `realpath` ... must stay inside the folder" then (implied) `readFile(path)`. Nothing opens by descriptor. `isPhoneDeniedFile` itself is realpath-then-caller-opens (`phone-read-deny.ts:49-59`). Gaps: (a) TOCTOU: a program the person runs (or a sync client) swaps a file for a symlink between check and read/write; (b) writes of a NEW file check only the parent's realpath, then `writeFile(parent/name)` follows a symlink planted at `name` — use `O_NOFOLLOW`/`flag 'wx'` for creates, and for overwrite open then `fstat`/re-realpath the fd path; (c) hard links: a hard link in the folder to `~/.git-credentials` has an innocent name and the same inode, and `realpath` cannot see it — compare `stat.nlink > 1` on write/read at folder level and refuse, or check inode against deny-listed files; (d) the folder itself: a remembered `folders` path stored canonically is never re-checked, so if the folder is later replaced by a symlink to `~` it is followed — re-realpath the root each call and compare to the stored root; (e) case-insensitive disks (macOS/Windows): "inside the folder" must be compared lowercase there, and the stored root vs. `realpath` spelling can differ (8.3 names `PROGRA~1`, `\\?\` prefixes, junctions); D lists Windows stream names only as a test, but `normalizeTypedPath` (`phone-read-deny.ts:25-31`) strips streams for the deny check only — the file open must also refuse any `:` after the drive letter, trailing dot/space, and reserved device names (`CON`, `NUL`, `COM1`).
   Fix: one `openConfined(root, rel, flags)` helper: reject `:`, NUL, trailing dot/space, devices; `realpath` the root; open with `O_NOFOLLOW` where available; after open, `fstat` is a regular file with `nlink === 1` (folder level) and re-resolve `/proc/self/fd`-style path where possible; only regular files (refuse FIFOs/devices — a read of a FIFO blocks forever and `/dev/zero` fills memory).
   Triage: accepted — one `openConfined()` helper: refuses `:`, NUL, trailing dot/space, Windows device names; realpaths the root every call; opens with O_NOFOLLOW where the platform has it, else lstat before and fstat after must agree (dev+ino); only regular files; folder level refuses nlink>1; creates use 'wx'. Residual (said in the doc): a parent folder swapped between its realpath and the open.

4. **blocker** — A folder that IS home or root is not refused.
   Evidence: D §2 refuses only "a folder that is, or contains, a denied path's parent (`~/.ssh` itself)". `~` and `/` pass that test (they are "parents" only loosely), so the folder level could be given the whole account, defeating the difference between "folder" and "all" the approved card promises. Also a folder INSIDE a denied tree is not mentioned (`~/.ssh/keys`).
   Fix: refuse a chosen folder when it equals home, a parent of home, a drive root, or when `isDenied(folder)` or any denied path lives directly beneath it that would be listable; refuse the userData and pages folders. Tell the person in a sentence ("Pick a folder inside your home, not your home itself").
   Triage: accepted — a chosen folder may not be home, above home, a drive root, inside or containing a denied tree, YouCoded's userData or a Pages folder; plain sentence on the card.

5. **should-fix** — Handle design is under-specified (forgeable? scoped? lifetime?).
   Evidence: D §3 says "opaque handle ... lives in memory for that page and window until the page closes". Missing: handle format (use 128-bit random, never derived from the path); binding key must be (pageKey, owner key from the DOOR via `page-owner.ts:41-72`, line id) — the existing `ownerOf` in `main/ipc/pages.ts:36-42` is the pattern, but the request carries `id`, which a page could change to another approved page's id: the host (`PageHost.tsx:~490`) fills `pageId`, but a phone's raw socket message does not go through the host, so main must check the handle's recorded page equals `p.id` AND the owner. Reload: `did-start-navigation` handler (`page-owner.ts:46-53`) only closes sockets, so pick handles survive a window reload while "page closes" is the promise; wire `closeOwner` to drop them (and on page edit / html hash change, approval removal `removeConnection`, and phone disconnect `clientOwnerKey`). Pick handle at `pick` level must also record the access it was granted (a read-only pick can never `save`), and `save(handle)` must re-realpath and re-run the deny check (the file may have been replaced by a symlink since the pick). Cap live handles per owner (e.g. 200) or memory grows without bound.
   Fix: write the table of "handle → {pageKey, ownerKey, lineId, path, access, expires}" into D and test replay from another window, another page and after removal.
   Triage: accepted — handle = 128-bit random → {pageKey, ownerKey (from the door), lineId, path, access, expires}; checked against the request's page and door every call; dropped on closeOwner (reload/close/phone drop), approval removal, page edit; ≤200 per owner.

6. **should-fix** — Remembered files are re-opened by stored path with no identity check.
   Evidence: §1 stores `{id, name, path}` only. If the remembered file is deleted and a symlink to a secret is created at that path, the next `read(id)` follows it. Fix: re-run realpath + deny list + regular-file check on every use (not just at pick), optionally store inode/dev and refuse changed identity on write. Also `recent()` must drop entries whose file is gone rather than return stale names, and `name` shown must be the basename only.
   Triage: accepted — every use re-runs realpath, deny lists and regular-file checks; stores dev+ino at remember time and refuses a changed identity on write; recent() drops vanished files; names are basenames.

7. **should-fix** — `pages:list-folder` is gated only by "a pick is waiting", not by who is waiting or where.
   Evidence: D §4 "answered while that page has a pick or saveAs waiting for that same phone". The request body carries `id` and `folder`; the door's `ctx.clientId` is available (`pages.ts:36-42`), so the same-phone check is feasible, but the folder is free: any `~/<folder>` listing of the whole home tree (names, sizes, mtimes of private files) is available to a page that merely calls `pick`. The page controls when `pick` is pending and can keep it pending indefinitely, driving a crafted client to list anything. A hostile page on the PHONE sits in the phone's own browser; the listing goes to that phone. That is leak of file NAMES (e.g. `divorce-lawyer.pdf`), and the existing phone channels were deliberately limited to "known roots" (`main/ipc/file-gates.ts:25-31`).
   Fix: (a) the pending pick records the `types` filter and the listing is filtered to matching files plus folders; (b) rate limit and expire the pending pick (60 s, one per phone); (c) never accept `..`, absolute, `~`, backslashes or `:` in `folder` (same normaliser as D §3); (d) re-use `isPhoneDeniedFile` per entry AND hide denied directories entirely; (e) add listing to the phone-open fixture as a separate decision since it widens what a phone can browse beyond known roots — Q-remote-pick approved "YouCoded's own file chooser", not "browse the whole home" (unverified wording; check `pages-finish-step2d.choice.answers.json`). Also: `list-folder` is an extra channel for a UI that could be served by `pages:files {op:'pick'}` returning directory pages (see 14).
   Triage: accepted — list-folder only for a pending pick of that page and phone (60 s, one at a time), filtered to the pick's file kinds plus folders, normalised folder, denied entries and directories hidden, 1,000 entries per page. Covered by the approved chooser screens (browse from home), recorded in the fixture.

8. **should-fix** — The phone's returned choice `{ folder, file }` is trusted input.
   Evidence: D §3 "choice comes back as `{ folder, file }` relative to home; main resolves and checks it". A crafted socket message from a paired phone (the same threat the code already handles for `pages:approve`, `pages.ts:6-9`) can send `pick` with any folder/file without ever listing. Checks must be: a pick is actually pending for this phone+page; the choice's resolved path passes the §3 normaliser, deny list, `types` filter; the choice is consumed once. Otherwise a page + a hand-made message reads any non-denied home file at `pick` level, which is the weakest approval. Fix: store the pending pick at request time and accept only a choice for it.
   Triage: accepted — op `pick-choice` accepted only for the pending pick of that phone+page, consumed once, all checks re-run.

9. **should-fix** — Folder token for `chooseFolder` / `approve` is only partly specified.
   Evidence: D §2 "bound to the calling window/phone owner". `chooseFolder` is `desktopOnly` (D §6) but `approve` and `set-folder` are phone-open, so a phone can call `approve(id, keys, addresses, folders)` with a token: tokens are random so it cannot guess one, fine, but the token's owner binding must compare to the approving door (a phone owner never owns a desktop token). More important: the approval is recorded for the page id, but the token does not bind WHICH page/line it was chosen for, so token chosen for page A can be passed for page B by a script in the same window (renderer is trusted, a hostile page cannot reach `chooseFolder` — `PageHost` does not forward it; unverified for any other host path). Bind token to (page id, line id, owner). Also `setFolder` "without re-asking" lets a page's line move from `~/Taxes` to `~` via the same window flow only if Page settings is the sole caller; add the §4 folder rules (item 4) there too.
   Triage: accepted — folder token bound to (page, line, owner), 10 minutes, single use; set-folder applies the item-4 rules.

10. **should-fix** — Main-process blocking: sizes and base64 are bigger than the rule allows.
   Evidence: `.claude/rules/performance.md` rule 1 (`main-blocking-calls.test.ts` bans sync calls). D §3 caps read 25 MB "as base64" = ~33 MB string built on main, JSON-stringified, sent over IPC (structured clone copies again) and over the phone socket (`remote-server.ts:465` maxPayload 52,428,800 bytes, backpressure close at `:1398`) — a page can fire many concurrent reads: the `PageRateGate` is per request, not per bytes in flight. `Buffer.toString('base64')` of 25 MB blocks main roughly tens of ms and a 5,000-entry `list` with `stat` per entry is thousands of syscalls on libuv's pool (4 threads), starving other async fs work; `readFile` of a FIFO/huge-sparse file defeats the cap unless size is checked on the fd BEFORE reading.
   Fix: `fstat` size check on the open fd, then read; cap in-flight bytes per owner (e.g. 32 MB total, serial queue); lower the bytes cap for phone owners to ~10 MB and for IPC to a binary-safe path (Electron IPC clones `ArrayBuffer` without base64; phone path needs base64); list: `readdir({withFileTypes})` first, `stat` in batches of 32, cap 1,000 for the phone chooser and paginate; `write` caps must also apply to data arriving as a string (UTF-8 length, not `.length`).
   Triage: accepted — fstat size before reading; caps 25 MB a file on a computer window, 10 MB through a phone; 32 MB in flight per owner (queued); lists via readdir withFileTypes, stat in batches of 32, paged at 1,000; write caps on UTF-8 byte length.

11. **should-fix** — Thumbnails: the EXIF-preview approach contradicts what the approved screens show.
   Evidence: D §4 gives only embedded JPEG previews, "kind icon otherwise". The approved tiles-first chooser (pages-finish-step2d/2e) shows tiles; PNG/HEIC/WebP/screenshots (most phone-origin images) have no EXIF thumbnail, so most tiles are icons — the approved look is not delivered, and D defers it to "the next deck". Also parsing EXIF from untrusted files in main is a parser attack surface; a hand-rolled parser on 64 KB of attacker-chosen bytes needs strict bounds (unverified: no EXIF code exists yet in the tree).
   Fix: either (a) generate thumbnails with Electron's `nativeImage.createThumbnailFromPath` on desktop (async, OS-cached; on the headless Android backend it is absent — fall back to icons and say so) or (b) have the phone's browser render thumbnails itself from a small `pages:files {op:'thumb'}` capped at 20 KB with a per-folder concurrency of 4. Decide before building; tell Destin which promise changes.
   Triage: accepted, changed — Electron's thumbnail call is macOS/Windows only (Destin is on Linux), and decoding every photo on main breaks rule 1. Thumbnails: a JPEG's embedded preview (bounded, defensive parser) or the picture itself when it is a small image (≤ 1 MB, e.g. screenshots); others show the kind icon. Full thumbnails for every picture are a recorded follow-up card. Said to Destin.

12. **should-fix** — "Save asks before replacing" is only promised for the computer's window.
   Evidence: D §3: the system Save window confirms overwrites on desktop (`office-dialogs.ts:61,96` uses `showOverwriteConfirmation`; but note `resolveCopyTarget` at `:17-23` shows that names the code adds are NOT confirmed). The phone chooser's Save as and the Android path (D §5, "writes to Downloads") have no replace prompt specified; `save(handle, data)` to a remembered file replaces silently by design; `writePath` at folder/all level overwrites silently. Also on desktop, `dialog.showSaveDialog` is not available headless.
   Fix: say in D which saves replace silently (those the card already allowed) and add an in-chooser "replace?" step for the phone; for Android use a unique name ("name (2).ext") rather than DownloadManager's silent behaviour; for `saveAs` on the headless/Android backend return `unsupported` rather than hanging.
   Triage: accepted — the phone chooser asks before replacing; saves the card already allowed (save back, writePath at folder level) replace by design and say so in the builder skill; headless backends answer `unsupported` for computer-window dialogs.

13. **should-fix** — Android claims do not match the code.
   Evidence: (a) D §5 "Save-as writes to the phone's Downloads (the existing download path)". The only download path is `AppWebView.kt:63-69` / `WebViewUrlRouter.kt:128-137`, which accepts ONLY `http(s)` links on a paired host matching `MINTED_PATH` (a minted artifact download route). A page's bytes are not a minted URL, so this path would refuse it; saving page-made bytes needs a new minted-download route in main (store bytes briefly, mint a one-time URL, then the existing listener) or a `MediaStore` bridge. (b) D §5 "the WebView's own file chooser ... already used for attachments": `onShowFileChooser` (`AppWebView.kt:97-99`) calls `pickFiles(callback)` for ANY chooser the WebView raises, with no filter by `params.acceptTypes` and no way to tell it came from a page; the sandboxed page iframe cannot itself open a chooser (no user activation in the opaque frame, `PageHost.tsx:799` `sandbox="allow-scripts allow-forms"`), so the host must render a real `<input type=file>` and click it from a user gesture — gesture timing (the page's click is in another frame) is the same problem the session-start code works around at `PageHost.tsx:418`; design must say how (a visible "Choose a file" button the host draws). (c) The bytes then travel WebView → bridge → on-device Node backend; 25 MB base64 through `YouCodedHost`/the local WebSocket is fine up to 50 MB payload but doubles memory in a WebView; cap Android at ~10 MB (unverified on low-end devices). (d) Android's Node backend is headless: `shell.trashItem` exists as a move-to-userData-Trash (`headless/electron-headless.ts:114-123`), so D §3 "else refuses" is wrong there — it never refuses and a "remove" silently fills app storage with no way for the person to find it; and `dialog.*` has no headless implementation (unverified — grep `dialog` in `electron-headless.ts` returned nothing) so pick/saveAs on a "computer window" branch must be guarded by door, not by existence of Electron. (e) Folder/all/remember on Android are shown as "Not available" (D §5) — fine, but then `files` lines of those levels in a page are a dead end the builder skill must warn about.
   Fix: state the Android flow in two real paths (bytes in via a drawn input; bytes out via a minted one-time download URL), and make remove refuse on headless.
   Triage: accepted, narrowed — the Android app in step 2: pick-and-read through a host-drawn 'Choose a file' sheet (a real input pressed by the person) only. Save-as to Downloads (needs a minted one-time download route) joins card #203 with remember/folders. remove refuses on the headless backend.

14. **should-fix** — Phone-open channel additions need the fixture ritual, and four channels is more than needed.
   Evidence: `tests/fixtures/phone-open-channels.json` header: "Any change to this list is a decision for Destin" and `tests/phone-open-set.test.ts` compares it. D §6 cites two answers (Q-filesphone, Q-remote-pick) as covering `pages:files`, `set-folder`, `forget-file`, `list-folder`. `pages:files` (including `writePath`/`remove`/`makeFolder` at `all` level from a phone) is far wider than "remote access to desktop → desktop" suggests; a phone running a page that deletes files on the desktop is a new class. `pages:plaid` and `pages:run-program` are `desktopOnly` for exactly this reason (`pages.ts:97-113`).
   Fix: open `pages:files` to the phone only for ops `pick`, `read`, `save`, `saveAs`, `recent`, `list`, `readPath` (read-side) and keep `remove`, `makeFolder`, `writePath` allowed only at folder level (not `all`) from the phone, enforced in main by `ctx.door`; ask Destin once with the exact list. Make `forget-file` and `set-folder` desktop-only (set-folder needs the folder window, which a phone cannot show anyway — D §2 says `chooseFolder` is desktopOnly, so a phone `set-folder` token can never exist).
   Triage: accepted — from a phone: pick, pick-choice, read, save, saveAs, recent, list, readPath; writePath/makeFolder/remove only at folder level, never at `all`; set-folder and forget-file desktop-only. Enforced by ctx.door in main. Destin delegated this call (2026-10-24, 'build it however you think is best'); recorded in the fixture.

15. **should-fix** — Chooser flow through remote-shim / remote-server is not yet shown to work.
   Evidence: `renderer/remote-shim.ts:1326-1346` routes push events (`pages:socket-event`, `pages:changed`), and `pages:files` is request/answer, which is fine, but the design has one request (`pick`) that stays pending for minutes while the person browses and a separate `list-folder` and a "choice comes back" step: it is unspecified how the choice reaches main (a second call? the first call's answer?). If the host awaits `pick` on the phone and the chooser UI lives in the same host, the choice is a local result and main only sees a later `files {op:'pick-choice'}` — which is not in the op list. Also socket drops mid-pick: `closeOwner(clientOwnerKey)` (remote-server per `page-owner.ts` comment) must clear the pending pick. Phone request timeouts: unverified (not found a per-request timeout in the shim).
   Fix: add the op `pick-choice` explicitly (or fold into `pick` with a token), define pending-pick state `{ownerKey, pageKey, lineId, types, expires}`, clear on disconnect/reload, and add an end-to-end test over the fake socket.
   Triage: accepted — pending-pick state {ownerKey, pageKey, lineId, types, mode, expires}, cleared on disconnect/reload; `pick-choice` op; an end-to-end test through the fake socket.

16. **should-fix** — Approval changes do not revoke what is already handed out.
   Evidence: §1 says a line's remembered entries are dropped when its approval is removed; nothing says live handles die too; `pages-service.ts:504,540` re-read approvals for fetch/plaid on each call (good pattern) but D §3 says "re-reads the approvals" without the page-edit case: an edited page whose `files` line changes level/access gets a new fingerprint (`page-kinds.ts:379`) and is unapproved, but `types` changes are intentionally not in the fingerprint (fine). Level downgrade (folder → pick) leaves `folders[pageKey]` data behind, and a later re-widening back to `folder` silently reuses the old folder without a new yes, since the fingerprint matches only the level. Fix: on any change of level/access or removal, drop folder, remembered, handles, pending picks; test it.
   Triage: accepted — any level/access change or removal drops the line's folder, remembered files, handles and pending picks.

17. **should-fix** — Rate and abuse limits: `PageRateGate` is a per-page request rate (`pages-service.ts:73`); a files page can read thousands of files, so `all` + `read` is a quiet exfiltration channel to any network line the page also holds. The design's combined risk (D §7) says `combinedRisk` counts readable files; confirm it treats `pick` as low (one file) and warns on network + folder/all. Fix: cap files-per-minute and total bytes per page session, and include "reads files AND reaches the internet" in the card's combined line (unverified how `combinedRisk` counts today: `renderer/components/pages/page-connections.tsx`, not read line by line).
   Triage: accepted — per page: 600 files and 200 MB read per hour; combinedRisk already counts readable files (pick included) as private.

18. **nit** — `remove` via `shell.trashItem` can still delete a whole directory tree and, on Linux without a trash (headless, some desktops), the design says "refuses"; but on Linux with GVFS missing Electron throws; handle the throw as a refusal sentence. `remove` of a folder path should require folder level and refuse the folder root itself.
   Triage: accepted.

19. **nit** — `normalizeTypedPath` strips `:stream` from each segment, so a normal Linux/macOS file named `report: final.txt` is checked under another name for the DENY test only (harmless) but a `types` filter or `name` shown to the page must use the real basename.
   Triage: accepted.

20. **nit** — D lists tests for escape attempts but not: FIFO/device file, 0-byte and over-cap files, NUL byte in path, very long paths (>4096), unicode normalisation (NFC/NFD on macOS can make `é` two spellings that differ from the stored root), a root that disappears (unmounted drive), concurrent save/save, and write of a name equal to a denied name in an allowed folder (e.g. a page writing `.git-credentials` or `id_rsa` INTO the approved folder — the deny list is checked "every time" per D §3, which covers it for existing names; confirm it is checked on the NEW name too, not only the realpath of the parent).
   Triage: accepted — all listed cases added to the table tests.

21. **simpler design (suggestion)** — The same promises are met with less machinery by: (1) dropping `list`/`readPath`/`writePath`/`remove`/`makeFolder` from the page API at `all` level and giving `all` only `pick` without any dialog (i.e., "all" = the system chooser starts anywhere, no folder confinement) — most "all files" pages can be written with pick + remember; (2) making folder and all levels desktop-only for the first release (phone gets pick/remember through the chooser), which removes items 7, 8 and 14 for the phone; (3) one thumbnail source (OS thumbnails on desktop, icons elsewhere). This shrinks the part with the highest risk (writes at `all`) and keeps every approved screen except the blunt all-files line for phones.
   Triage: partly — items 7, 8 and 14 already narrow the phone; `all` keeps its API on the computer because a file-browser page (Destin's own example) needs list/write.
