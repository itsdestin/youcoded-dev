# Assistant Browser design: engineering review, round 2

Scope: only new problems from the revision, or round-1 fixes that are inadequate as written. Round-1 items that were accepted and are adequately specified are not repeated. Checked against `src/main/harness/harness-session.ts`, `tools/types.ts`, `session-manager.ts`, `voice/voice-handlers.ts`, `electron-builder.yml`. Items marked UNVERIFIED rest on my knowledge of Chrome/Playwright behaviour, not on code or a run.

## Findings

### 1. [blocker] The "app-level ask" has no delivery path in either runtime, and the policy engine lives in a process that has no UI
- **Problem.** The revision moves all asks out of the runtime permission systems into BrowserService. But BrowserService now runs in a utilityProcess (no UI). The spec never says how a tool call in the worker raises a card in the renderer, waits for the answer, and survives the answer arriving after a restart or disconnect. Native tools get no ask handle: `ToolContext` (`tools/types.ts:233`) carries `sessionId, cwd, signal, binding...` and no `askUser`; the only ask path is `harness-session.ts` `decide()` driven by `permissionSubject` (line ~4018), which the spec deliberately disables (`permissionSubject` undefined, always-allowed). So "native adapters only transport" is false: the adapter needs a new main-side channel to the chat UI keyed to the session, including the "the assistant's call blocks until the card is answered" and the "unanswered after 90 s -> withdrawn" timer.
- **Also.** The card UI reaches remote-web clients and phones attached to a desktop session. The spec says controls are desktop-only, so a remote user driving a desktop session gets a call that blocks 90 s and is withdrawn every time. Nothing says what a remote client sees.
- **Also.** Per-chat grants ("Allow for this chat") need a chat identity. A native session id is stable; a Claude Code relay id is per-launch. A resumed or `/clear`ed Claude Code chat silently loses its grants (harmless but unspecified) and, worse, a stale grant could attach to a reused id.
- **Evidence.** `tools/types.ts:233-260`; `harness-session.ts:4018` (`tool.permissionSubject`); spec section 1 "Asking first", section 2 Tools paragraph.
- **Recommend.** Specify one `BrowserAskBroker` in main (not in the worker): worker -> main request `{conversationId, kind, subject, deadline}`, main shows the card, answer returns; worker holds no policy state beyond "wait for verdict". Add an explicit ToolContext/ToolServices ask hook for native adapters and list it in the conformance tests. Define remote-client behaviour (show the card there, or return "needs the desktop" immediately instead of burning 90 s).

### 2. [major] The 90 s wait model ignores queueing, cold start and downloads, so Claude Code's 120 s auto-background still bites
- **Problem.** The 90 s cap is stated per wait. Total call latency is also: per-conversation serialization queue (calls wait behind each other) + utilityProcess spawn + browser cold launch + the 150 MB browser download ("the assistant's call continues once it finishes") + a restart's up-to-10 s drain + an ask (up to 90 s) + the action's own Playwright timeout. An ask of 90 s followed by a 30 s navigation is already past 120 s. Past 120 s Claude Code backgrounds the tool and the model sees a different result shape; for the download card the model never gets the continuation it was promised.
- **Evidence.** Spec section 1 (download "call continues"), section 2 (serialized calls, "waits up to 10 s"), tools table (BrowserAskUser <=90 s). Round-1 triage 7 only caps individual waits.
- **Recommend.** One call-level deadline (say 100 s) enforced in `browser-tools.ts` for every tool: on expiry return "still working / waiting for you, call BrowserSnapshot to continue" and keep the work going in the worker. Download and ask must be detached from the call: the call returns "waiting for the person to approve/download", and the card/progress lives independently. Queue wait counts toward the deadline.

### 3. [major] Ask timeout and decline look the same to the model, inviting retry loops
- **Problem.** An ask withdrawn after 90 s "and the action is NOT done" is indistinguishable from "Not now" unless the result text differs. A model that gets "not done" retries the same click, producing a new card every 90 s on a screen nobody is looking at (or a stack of identical cards). Final-step cards in particular are one-shot ("Allow this once"), so each retry is another prompt.
- **Recommend.** Distinct result strings ("The person did not answer; do not retry, ask them in chat" vs "The person declined"). After a decline or timeout, refuse the identical (host, target) action for the rest of the turn. Cap simultaneous open cards at one per conversation.

### 4. [major] The final-step heuristic is keyed on page-controlled text and misses the common ways a form actually submits
- **Problem.** "An action whose target reads like buy, pay, ... submit" is matched on the element's accessible name, which the page controls. A hostile or merely sloppy page names its pay button "Continue", "Next", "Yes", "Complete" or an icon with no name; non-English sites are not covered. `press_key` Enter in a focused field, `type` with a trailing newline, and clicking a link to `/checkout/confirm?...` submit or navigate without any "buy"-like target. Conversely "Submit search", "Send feedback" asks every time even on an allowed site, which trains the user to click Allow without reading, weakening the card that matters.
- **Evidence.** Spec section 1 "Final steps ask every time"; tools table lists `press_key` and `type` as separate actions.
- **Recommend.** Treat the keyword list as advisory only, as the spec already half-says, and add structural triggers that do not depend on page wording: Enter/newline while focus is inside a `<form>`; click on an element that is `type=submit` or a form's default button; click on a link whose resolved URL path matches the same word list; any action on a cross-origin payment frame. Say in Settings/tool copy that the assistant, not the card, is the primary guard. Tune false positives (search/feedback) with role context rather than words alone.

### 5. [major] Private-network ask is post-hoc where it matters, and "once per chat" is far too coarse
- **Problem.** (a) The landing check "stops" an unapproved private main-frame landing after the request was already made. A GET to `http://192.168.1.1/cgi-bin/reboot` or a router/IoT endpoint with side effects has then already executed; the spec admits it. Playwright can abort before sending (`context.route`, or `page.on('request')` is too late but `route.abort()` is not), so the pre-request block is achievable. (b) Subresource and redirect requests from an already-loaded public page to `http://127.0.0.1:port` (DNS rebinding, a public hostname that resolves to a private IP) are not covered by "model-initiated navigation". (c) "Asks once per chat" for the whole class means approving one localhost dev server also approves the router and the cloud metadata address.
- **Evidence.** Spec section 2 Navigation; round-1 triage 5 ("documented: the request itself was made").
- **Recommend.** Intercept at the context level (`context.route('**/*')` with resolved-IP classification) and block before sending for main-frame navigations and redirects; key approvals per host:port, never grant the metadata address (169.254.169.254, fd00:ec2::254) at all; classify by resolved IP, not hostname string. Keep subresources as stated limitation if that is the choice, but say so.

### 6. [major] Restart semantics collide with the sign-in flow they exist to serve
- **Problem.** "Open window to sign in" and Show window both restart the browser. The assistant's BrowserAskUser call is itself in flight (it waits up to 90 s), and a restart "waits up to 10 s for in-flight calls", so the card's own call either blocks the restart for 10 s or gets killed, and it is unspecified which. The restart reopens the tab "by address": a sign-in/captcha page the assistant stopped on is reloaded, not restored; a challenge token, a one-time 2FA step, a POST result page, or a half-filled multi-step form is lost, which is exactly the situation the card was raised for. The headless-to-headed switch is also a different fingerprint, so the same challenge may re-trigger.
- **Also.** Restart affects other chats using the browser (the confirm names them) but the spec does not say what happens to their in-flight calls after the 10 s drain (fail? retry?). Profile lock: relaunching on the same profile directory needs the old process fully exited; no wait-for-exit step is specified (round-1 11 mapped "profile in use" to a message, but a self-inflicted restart race would hit it).
- **Recommend.** Treat BrowserAskUser as non-blocking for restart (cancel it cleanly, card persists). For needs-you flows, launch the headed browser as a separate window on the same profile only if the profile is idle, or reopen on the exact URL and explicitly tell the model "state lost, redo the step". Define in-flight failure text for other chats. Wait for process exit + lock release before relaunch, with timeout and a specific error.

### 7. [major] utilityProcess packaging and plumbing are asserted, not specified; asarUnpack is no longer mentioned
- **Problem.** The only utilityProcess in the repo is the voice worker (`voice-handlers.ts:44`). Open points for the browser worker: (a) playwright-core must resolve inside a packaged app; `electron-builder.yml` `asarUnpack` (lines ~128-150) lists pdfjs/koffi/scripts only, and the revised spec dropped the round-1 note about it. Playwright spawns its own driver and the browser installer using `process.execPath` with `ELECTRON_RUN_AS_NODE`; inside a utilityProcess `process.execPath` is the Electron binary, and the installer needs real files, not asar entries. (b) Three hops (native adapter or relay socket -> main proxy -> worker), each needs request ids, timeouts and abort-signal forwarding; the spec says every Playwright call honours the abort signal but does not say how a signal crosses `postMessage`. (c) Worker death (crash, OOM on a heavy page): proxy must fail pending calls and reset state; the voice worker comment records a 1.14 GB leak from a missed respawn guard (`voice-handlers.ts:76`), same risk here. (d) Frames: base64 JPEG at 10/s through worker -> main -> renderer is two structured-clone copies; use a MessagePort transfer.
- **Recommend.** Add to the spec: asarUnpack for playwright-core (whole package) and a packaged-build smoke test that launches a stub browser and runs the installer path; a proxy contract (request id, deadline, abort message, crash handling, single-instance guard); frames via transferable buffer. Specify `utilityProcess.fork` `serviceName` and `stdio` so the worker's logs reach the app log.

### 8. [major] My Chrome is shipped with its core mechanism unverified, and Chrome's behaviour on the default profile is a likely blocker
- **Problem.** Triage 14 keeps it "verified against a separately launched Chrome only (the real chrome://inspect toggle is unverified and said so)". So the feature the user is offered (their own signed-in Chrome) has never run in the only configuration users have. UNVERIFIED but I believe: current Chrome ignores `--remote-debugging-port` / pipe when pointed at the default user-data-dir (since Chrome 136), and the user-enablable remote-debugging toggle appeared only in newer builds; older Chrome, Edge and Brave behave differently. A "Waiting for you to click Allow in Chrome" step may not exist on the user's version. Further: connecting over CDP exposes every open tab and the whole default browser context (all cookies/sessions), and the app's "own tabs" rule is bookkeeping in our tools only; the stricter asks are per site but a model sees all of the user's logged-in sessions through any page it opens.
- **Recommend.** Keep it out of the first release or label it Experimental behind a flag until it has been run once against Destin's actual Chrome on at least Linux; the Settings steps should be generated from a detected Chrome version with a clear "your Chrome version can't be used this way" state. Do not offer it by default. If kept, also block BrowserTabs from listing/selecting tabs it did not create (enforced in the service, not just hidden).

### 9. [minor] Page text can forge element refs
- **Problem.** `ariaSnapshot({mode:'ai'})` output puts page-controlled names beside `[ref=e12]` markers. A page can put the string `[ref=e3] "Allow"` inside a heading; `wrapUntrusted()` neutralises tag look-alikes but not this. The model's click maps refs to real elements, so forged text does not itself click anything, but it can make the model believe a different element carries a given ref, and it can make the card text and the model's stated intent disagree.
- **Recommend.** Neutralise `[ref=` sequences in page-supplied names in the same wrapper; have the card show the element name and role from the live element (as the spec does for frame host), not the model's description.

### 10. [minor] The registry.ts hardening is scope creep with test-pinning risk
- **Problem.** Changing `wrapUntrusted`/WebFetch output in `registry.ts` changes what every native session sends to models for fetched pages and may break pinned wrapper tests and the prompt cache prefix assumptions in `harness-tools.md`. Neutralising `<`-like sequences can corrupt fetched code samples and HTML the model is asked to reproduce.
- **Recommend.** Land it as a separate, tested change with before/after WebFetch fixtures, or keep the browser wrapper local first.

### 11. [minor] Idle timers can destroy a hand-off in progress
- **Problem.** "A conversation's tabs close 30 min after its last browser call." A needs-you card waiting on a person who stepped away (a sign-in, a captcha) has no browser calls in that time, and Claude Code's stdio idle is also 30 min. The tab with the half-completed sign-in is closed while the card is still on screen; "I'm done" then lands on nothing.
- **Recommend.** The idle clock does not run while a needs-you card is open for that conversation; closing tabs under an open card is refused. Show "paused until you answer" on the card.

### 12. [minor] Claude Code plan mode and read-only expectations
- **Problem.** All seven tools are pre-approved with `--allowedTools`. If the Claude Code session is in plan mode (or the person expects read-only behaviour) a previously granted "Allow for this chat" site grant lets BrowserAct click and type anyway; the spec says the asks "happen in every permission mode" but does not say that plan mode should forbid BrowserAct entirely, as Write/Edit are forbidden there. Native has only ask / auto-edit / full-auto, so the question is Claude Code only.
- **Recommend.** Decide explicitly: either BrowserAct is refused in plan mode (needs the session manager's known mode) or the spec records that it isn't, and the tool description says so.

## Not found / checked and fine
- The utilityProcess choice itself is sound and has precedent (`voice-handlers.ts`); the issues are packaging and protocol (item 7), not the approach.
- Seven-tool surface and profile-gating like `Skill` are consistent with the existing conditional-tool plumbing.
