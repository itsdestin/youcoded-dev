- D6 accepted — major — Design §4.5's D2 fix ("before-quit first settles every pending close request... Menu quit / SIGTERM / OS shutdown therefore never downgrade to 'don't resume'") is only wired into the `app.on('before-quit')` handler, but SIGTERM/SIGINT (the app's OS-shutdown/logout/`kill` route) never fires `before-quit` at all — it's a completely separate route that calls `shutdownApp()` directly. A `window:close-request` left pending when a SIGTERM arrives is never settled/cancelled by the described fix, so if the renderer's in-flight `{close:true, reopen:false}` answer (a real click made moments earlier) is still processed by the close handler's continuation before `app.exit(0)` lands, it will call `untrack()` and strip that session from `open` — exactly the downgrade D2 exists to prevent, for a cause the design explicitly claims is covered. — evidence: `desktop/src/main/main.ts:2474-2480` (`before-quit`, where the described fix lives) vs `desktop/src/main/main.ts:2486-2489` (`process.on('SIGTERM'|'SIGINT')`, calling `shutdownApp()` directly — the code's own comment at `main.ts:2395` says "An OS shutdown/logout SIGTERM bypasses Electron's quit events entirely, on every platform"); no `powerMonitor`/session-end handling exists anywhere in `main.ts` (grep returned nothing) so SIGTERM is the app's only OS-shutdown hook. — suggested fix: either (a) route the pending-request settle-and-cancel step through a shared function called from both `before-quit` and the SIGTERM/SIGINT handler before `shutdownApp()` runs, or (b) narrow §4.5's closing claim to menu-quit/`app.quit()` only and note that SIGTERM/OS-shutdown is safe only because nothing settles the pending promise at all (an unanswered prompt just hangs until process exit) — which is true today but fragile, and should say so rather than claim coverage it doesn't have.

- D7 accepted — major — §6 says "IPC: `ipc-channels.test.ts` parity (automatic)" for the two new `session:*` channels, but the test file has no generic mechanism that checks arbitrary new channel names against `remote-shim.ts` or `SessionService.kt` — only the two constant maps in `preload.ts`/`shared/types.ts` are diffed automatically. Every other namespace's cross-platform coverage (`voice:*`, `social:*`, `account:*`, `handoff:*`, `system:notify-stack-state`, etc.) is a hand-authored `describe`/`it` block naming the exact channel strings; `dev:*` is the ONLY namespace with an auto-derived list that walks `remote-shim.ts`/`SessionService.kt` for every new member. Nothing today would fail if `session:reopen-list`/`session:forget-reopen` were added to `preload.ts` + `shared/types.ts` + `ipc-handlers.ts` and the `remote-shim.ts` invoke or the `SessionService.kt` `[]`/`{ok:true}` stub were simply forgotten — the build would go green while Android silently timed out or threw on that channel, exactly the failure mode `.claude/rules/ipc-bridge.md` warns about ("a typo silently breaks that feature on one platform"). — evidence: `desktop/tests/ipc-channels.test.ts:126-131` (the only automatic check: preload-vs-types constant-map diff, with no reference to `remote-shim.ts` or `SessionService.kt`); the hand-written per-namespace blocks at e.g. `tests/ipc-channels.test.ts:1755-1830` (voice), `:505-565` (`system:notify-stack-state`); the `dev:*` auto-derived exception at `:156-238`. — suggested fix: change §6 to call for a new hand-authored parity block (same shape as the `voice:*`/`handoff:*` ones) asserting `session:reopen-list` and `session:forget-reopen` appear correctly in `remote-shim.ts` (`invoke(...)`) and `SessionService.kt` (the `[]` / `{ok:true}` answers), and drop the word "automatic."

- D8 accepted — minor — §1's coalesced ~200ms async write to `welcome-back.json` is flushed on the `before-quit`/shutdown path, but nothing flushes it on an actual process CRASH. A `track()`/`untrack()` call made within that ~200ms window right before a real crash (not a clean quit) never reaches disk, so on next launch that session silently isn't offered back — quietly breaking the explicit S-other-quit guarantee ("crash... keeps it") for that narrow slice of time. This isn't fixable without a synchronous write, which `performance.md` rule 1 (`main-blocking-calls.test.ts`) bans on any hot path, so the right fix is documentation, not code. — evidence: design doc lines 47-49 ("coalesced async write (~200 ms)... flush pending write" only listed under the `before-quit`/shutdown bullet, not under crash). — suggested fix: add one sentence to §1 naming this residual gap explicitly (accepted trade-off, ~200ms window, no fix without violating the main-never-blocks rule) so it isn't rediscovered as a bug later.

- D9 accepted — minor — Design §4.5 says `before-quit` "pushes `window:close-request-cancelled {requestId}` so the renderer drops its prompt," but neither the already-built renderer mockup nor its workbench mock exposes any way to receive that push: `App.tsx`'s `quitPrompt` state is only `{ sessions: number }` (no `requestId`) and its only subscription is `onCloseRequest` (`App.tsx:3542-3546`); `mock-shim.ts` only mocks `onCloseRequest` (`:2843`), with no `onCloseRequestCancelled` anywhere. §6's test list for the close flow doesn't call for a test of this behavior either. Impact is bounded — main is specified to ignore a late answer for an already-settled request, so no tracking corruption follows — but the dialog can visibly linger through the moment the app is already quitting, which is exactly what this half of the fix was meant to prevent, and as written it's easy to ship without it. — evidence: `desktop/src/renderer/App.tsx:3542-3549`; `desktop/src/renderer/dev/workbench/mock-shim.ts:2843`; design §6's close-flow test bullet lists only "answer false/true/reopen, timeout keeps tracked." — suggested fix: add `onCloseRequestCancelled` to preload/remote-shim's `window` namespace and the mock shim, have `quitPrompt` clear on it, and add that as an explicit §6 test.
