## Interfaces and compatibility

`AskUserQuestionCard` now keys choices, textarea content and textarea refs by the question's index within its pending request; the card itself is keyed by requestId so a subsequent pending request cannot inherit those indexes. The flat keyboard-option list carries the same index. The existing `respondToPermission(requestId, { decision: { behavior, updatedInput } })` envelope is unchanged. Only `native-` broker request IDs add `updatedInput.orderedAnswers: Array<{ answer: string; note?: string }>` in question order; the original legacy `questions`, `answers`, `notes` and `annotations` members remain. `formatAnswers` validates the entire ordered array (count, object entries, string/string-array answers and optional string notes), uses the original tool-call question array as authority, and otherwise falls back to the old text-keyed map without throwing. No IPC method/channel was added.

Claude Code's documented Agent SDK response keys `answers` by question text and documents no ordered identity field (`docs/active/reviews/2026-09-27-native-harness-question-transport-note.md`). For **ordinary unique wording**, the card sends byte-equivalent legacy updatedInput without `orderedAnswers`. For duplicate-worded Claude Code requests, the card disables Submit and explains that the questions must be reworded; Dismiss remains available. It does not silently collapse different answers, invisibly change the model's question wording, or send an unsupported field to Claude Code. Actual duplicate-wording CC submission remains blocked on a compatible upstream protocol or an explicit product/transport decision; this native fix does **not** claim to support that CC case. No F14/F15 changes were made.
