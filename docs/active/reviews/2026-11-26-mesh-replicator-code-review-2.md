## Findings, most severe first

### 1. CONFIRMED. QUIET then permanent loud: writer appends past a lost tail when its own record cannot help (F1 not fully closed)
`appendLocal` (replicator.ts:514-556) protects against its own lost tail with (a) `own` = the highest head it signed, in `<replicator>/own/<wire>` (replicator.ts:497-503, 531-538), (b) fresh peer claims (539-545), (c) `incarnation>0 && !caughtUp` (538). Gaps:
- own record missing, or rolled back together with the store (a restore of the whole user-data folder, which the store itself lists as undetectable, inventory.ts limit 4), at incarnation 0, and no peer has spoken yet since start: the append is accepted. Repro: `t1.test.ts` a1 (both folders restored, peer unreachable at append): `ACCEPTED lines=6`, then A and B both go `faulted(writer-signed-two-histories)` for good; the new line is never copied; B keeps the old 10. a4 same.
- own record cut short by rot (length != 40) is read as "no record" with no report (replicator.ts:501: `raw && raw.length === 40 ? ... : null`). Repro `t1` a5 (store rolled back, own cut to 39 bytes): `ACCEPTED`, same permanent fork. (A zeroed/garbled 40-byte record is refused loudly, so only the short case is quiet.)
- The `caughtUp` guard (538) is satisfied by an unsigned claim: a hostile paired device can echo the writer's own `rep.sum` digest (the digest is computed from public state; onSum equal-digest branch, replicator.ts:310-321, counts it as `inSyncPeers`). Only matters when `own` is missing; honest peers' fresh claims still block if they spoke. PLAUSIBLE (not run).
User-level consequence: after restoring a backup on the writing device, the first chat message typed in the first seconds is told "saved", then that chat shows a permanent fault on every device and the new messages never reach the others. In the fuzz (non-SAFE, 160 seeds x 100 ops) 16 seeds showed `QUIET-append-at-wrong-position`; each ended loud on all devices (faulted) but the adapter had already been told ok. Related: seed 547: writer `in-sync` at 0 lines while 21 acked lines were held by nobody (every copy set aside, writer's own record rolled back): the status is quiet-wrong.
Fix direction: a writer that has not heard a fresh heads claim from every roster peer that is online (or a named timeout) since process start refuses appends with a NAMED waiting state (not only at incarnation>0); a present-but-malformed own record is a named fault (`own-record-unreadable`), never null; write the own record before the first push and keep a second copy inside the store folder or the control log so a single-folder restore is visible; `statusNow` must not say `in-sync` for a writer whose copy is empty with acked history unknown.

### 2. CONFIRMED. QUIET: a device that knows its copy is damaged acks its full head (F2 not fully closed)
`applyLines` (receive.ts, after append `ok`) calls `sendAck`, which acks `head.lines`/`head.hash` without looking at `repairFrom(head)`. If the store has already reported damage (refilling, bytes unreadable) and new lines are appended at the end, the ack names lines the device cannot read; `onAck` then sets the sender's heads to `ok` at that count (serve.ts, onAck) and `peerAcks` lists it. Repro `t4.test.ts` e1: B rotted at line 20, then writer pushes 5 lines: A lists `B acks [45]`, A status `in-sync/45`; B status `refilling/45`; B `read` of those lines throws `corrupt`. Heals when B's next heads frame reaches A (a lost live frame, or up to the next hello at 60 s, or 10 min in a partition). An eviction decision in that window would drop the last good copy.
Fix direction: ack only min(head.lines, repairFrom) with the chain value there (what `myEntries` already does for heads); and an ack should not refresh `peer.heads` to `ok` unless the sender is not repairing.

### 3. CONFIRMED. CALM-FOREVER: lines stranded when a device's signed-points file is older than its store
A non-writer can serve only up to a signed point it holds (serve.ts buildBatch). If the points file is rolled back or rotted at its tail while the store keeps the lines, that device holds lines nobody can be given. Repro `t5.test.ts`: writer B and C lose lines 15..22 (store restored), A holds 22 lines but its replicator folder is older: after 400 virtual seconds A = `in-sync/22`, B = `refilling(behind-own-signed-head)` (named, good), C = `comparing/15` with no reason, `nak-unavailable` 20, `pull-stalled` 18, forever. The lines can only come back from the writer's own chat file (adapter). A's `in-sync` is by design (F7) but together with C's reasonless `comparing` it is a calm picture of a stuck system.
Fix direction: a holder with lines above its newest signed point should say so (advertise as `refilling`/`unsignable`), and a stall with `nak unavailable` from every candidate should turn into `stuck(no-peer-can-serve)` after N tries instead of `pulling`/`comparing`.

### 4. CONFIRMED (documented interim limit, but F4 did not remove it). Intro hijack splits a version between honest devices
A paired device that announces an existing version id with itself as writer, and reaches a device before the real intro does, wins first-wins there (directory.ts:accept). Fuzz (gg, 160 seeds): 3 seeds where one honest device holds M as the writer of a version and shows `faulted(directory-conflict)` (loud, sticky), while the other two honest devices show `in-sync`/`serving` (they cannot know). Also any paired device can make every other device show `faulted(directory-conflict)` for any version forever (conflict note is durable). Writer itself is not frozen (F4 intent held). Not exploitable for a line the named writer never signed (the victim's named writer is M), but a user-level result is "that chat is faulted on one device and calm on the others".
Fix direction: the control log; interim: an intro for an id this device already learned from a different peer first is held until the roster-listed creator of the chat confirms.

### 5. CONFIRMED mechanism, loud eventually. The endorsement record lives in a folder that can be older than the store
`endorsedByWriter` (receive.ts) and the sticky fault both live in the replicator folder. When it is rolled back but the store is not, a contradicting writer-signed history is not seen as endorsed-contradiction; the copy is set aside and recopied first. Repro `t3.test.ts` b2 rollB=true: B holds the 7 FORK lines (old 6 set aside), then ends `faulted(writer-signed-two-histories)`. The builder's claim "copy kept and served, never cleared" holds only while that folder is intact. Quiet window is short here; keep as hardening: keep a tiny endorsed-head record inside the store folder.

### 6. PLAUSIBLE/INFO. peerAcks semantics for the eviction design
- `onAck` writes `peer.heads` (`at=now`, `ok`) from the ack itself (serve.ts onAck), so "the holder's own heads agree" is partly circular: the ack is its own freshness witness. An ack has no nonce or time; it is a past signed statement valid for PEER_FRESH_MS (10 min) after the holder's last word. A holder that loses data silently and goes offline stays listed up to 10 min.
- No check that a later heads claim (more lines, other value) extends the acked chain value; only equal-count and fewer-lines are compared. A holder that retired and recopied a different history (needs a writer fork) and whose retire-advert was lost keeps its old ack listed.
- Wrong `peerAcks` entries I could construct: finding 2 (repairing holder). Not constructible: replay of an old ack by relay (the link's replay table refuses it, link.ts:142 QUIET 'replay'), ack for a different chain (onAck checks my chain value), ack from a retired copy after the holder's advert (F2 fix works when the frame arrives; `F2-onHeads-ack-delete` mutant survives, see below).
Fix direction: eviction should demand an ack taken after a `solicitAcks` round started (nonce or local receive time recorded separately from heads), plus a durable-readable check as in finding 2.

### 7. CONFIRMED, low. Status and API ambiguities

User-level: that chat's new messages stop copying to every device while a paired device keeps lying, and the screen says only "pulling". Fix: `stuck(writer-blocked-by-peer-claim)` plus the claim's source device.

### 8. CONFIRMED, low. Unknown-version head entries are never evicted
