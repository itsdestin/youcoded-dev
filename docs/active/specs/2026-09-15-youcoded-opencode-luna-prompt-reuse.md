# YouCoded vs OpenCode: GPT-5.6 Luna prompt-reuse experiment

## Scope and authorization

Compare YouCoded and OpenCode on ChatGPT-plan `gpt-5.6-luna`: ordinary multi-turn agentic work, a full client-process restart, and continuation of the same session without forced compaction. Use provider-reported usage, not HTTPS interception or a UI-only smoke test. Pin an isolated OpenCode **1.18.31** and verify the actual version before running; do not modify the installed OpenCode or the running built YouCoded app. Run three scored repetitions per client.

Offline preparation and content-free, experiment-only pre-dispatch request counting in **isolated client builds** are authorized; instrumentation may not alter prompts, model selection or the running/installed clients. An isolated OpenCode source download/build was separately approved and completed; authentication remains a separate gate. Obtain fresh approval before **any** ChatGPT-plan compatibility probe or scored request; these consume quota even if unscored. No OpenRouter, OpenCode Go/Zen, DeepSeek, production-app access or shipped product-behavior changes are in scope. ChatGPT-plan quota cannot be capped in dollars: enforce the quota safeguards below before live work.

## Question and scope

> During an equivalent multi-turn Luna coding task, how efficiently does each client reuse prior prompt input, and does that reuse and provider-native continuation survive a full client-process restart?

Compare real ChatGPT OAuth routes, not API-key or OpenRouter approximations. This is a **client-level** comparison: different system prompts, tools and agent trajectories remain part of each client's result. Judge reuse of *each client's own previous prefix*, not raw prompt size alone; do not attribute a difference to a cache algorithm in isolation. In scope: root chat requests, cache reads/writes where reported, fresh input, warm turns before restart, first and later turns after restart, accepted reasoning/item metadata survival where observable, correctness and task-state retention, timing, coverage and limitations. Distinguish (a) the ability to reopen and remember a session, (b) exact accepted-history/reasoning restoration, and (c) provider-reported cache reuse. None implies either of the others. Exclude forced compaction, specialists, model-quality ranking beyond fixture checks, UI changes, traffic interception, undocumented backend TTL claims, DeepSeek, and clients other than YouCoded and OpenCode.

## Arms and isolation

**YouCoded:** run the native harness from an isolated app worktree using the supported dev launcher, with a dedicated profile **and an independently isolated home/state root**. `--profile` separates Electron `userData` but not everything under `HOME`: dev and built instances otherwise share `~/.claude/` and `~/YouCoded/`. Before launch, enumerate effective paths for Electron state, `NativeHome`, transcript and project roots, auth, toolkit state, instructions/skills, diagnostics and continuation; prove none can read or write real user state. If the launcher cannot honor a private home without modifying the built app or loading real credentials, stop for design review. Do not attach to, message, reload, signal, or inspect held-open state of the built app. Read only the dedicated profile's content-free ChatGPT request diagnostics. Their HMAC/fingerprint comparison state is **process-local**: the first post-restart row is a fresh baseline, never direct prefix proof against a pre-restart row. The accepted-history checkpoint is a separate sensitive private store; record whether exact restore succeeded or fell back to transcript reconstruction without exporting ciphertext. A full restart must exit the experiment's process tree and reload the same persisted session; an object reset is not a restart.

**OpenCode:** use an isolated 1.18.31 installation and dedicated HOME and XDG config/data/cache roots, never the existing installation or its auth directories. Validate the effective merged config, instruction ancestry and environment rather than trusting XDG variables alone. Explicitly disable sharing, external plugins, MCPs, inherited provider keys, auxiliary model calls where configurable, and automatic compaction/pruning. Authenticate only the isolated profile through supported ChatGPT Plus/Pro OAuth after a new go-ahead. Before live requests, establish from the pinned version's schema whether root-chat provider requests, retries and their input/cache-read counts can be distinguished; aggregate `stats` or a sanitized session export alone is not proof of per-request coverage. Collect allowlisted fields only; inspect continuation metadata as booleans/counts without copying opaque values. Restart the actual process/backend, then resume the same session ID without forking.

**Both:** exact model `gpt-5.6-luna`, independently authenticated on the same ChatGPT account only after authorization, comparable reasoning effort and text verbosity where supported, default first-party tools only (with tool network access denied), identical disposable fixtures and ordered user turns. Pin and record effective project/global instructions, tool list and ordering, model variants, context/compaction settings and auxiliary lanes; use the same instruction text through each client's supported loading mechanism, without double-loading it. Verify all file access stays in the synthetic fixture/private home, including through symlinks or shell calls. Run sequentially with balanced order if repetitions permit (three per client yields six starts, so alternate YouCoded/OpenCode then OpenCode/YouCoded then decide the third order with a recorded random seed and acknowledge residual imbalance). Record restart gaps and settings. One separately authorized, unscored one-line Luna compatibility probe per client confirms routing; it consumes quota and must not silently warm or contaminate scored session lineage. On failure, report compatibility failure, not a cache score; never substitute models.

## Fixture and six-turn workload

Create an immutable template, cloned byte-for-byte into six disposable roots. It contains a small deterministic application, one identical project-instruction text with verified client-specific loading, a seeded configuration disagreement with one intended fix, a second independent mechanically checkable change, local tests with meaningful initial/final states, and stable marker facts for the restart check. No secrets, network dependency, package installation, or shared-checkout dependency. Keep it big enough for realistic reads/tool outputs and a cache-eligible prefix where observed, small enough to avoid compaction; do not pad it solely to inflate cache hits. Offline tests must prove identical initial clones, that the verifier distinguishes required final states, and that neither fixture nor prompts reference real user paths. Record any divergence in tool path or fixture content rather than silently repairing it between arms.

Send exactly the same six user prompts per repetition:

1. Read project instructions, inspect the app, and report structure and marker facts.
2. Diagnose the seeded configuration disagreement without changing files.
3. Apply the specified fix and run relevant tests.
4. Recall two earlier facts, make the second independent change, and run its focused check.
5. **After a full process restart**, inspect state, say what was completed before restart, and recover both facts without being retold.
6. Run the full fixture verifier and summarize both changes and test outcomes.

Prompts constrain outcomes, not exact tool calls; the real agent path matters. Mechanical checks, not polished prose, determine correctness.

## Normalized observations

Record arm, repetition, client/version/model/provider route, opaque experiment-local session label, phase (`compatibility`, `pre-restart`, `post-restart`), user turn and provider-request sequence, purpose when known, outcome, nullable input/output/reasoning/cache-read/cache-write counts, nullable duration, nullable expected-rebuild flag, optional within-process item-prefix classification/counts, and **source/meaning** of each field. Preserve failed/aborted attempts and unknown-usage requests separately. Validate counts as non-negative integers (not booleans), cache read ≤ input, and whether each client's `input` includes cached tokens; incompatible semantics block a comparative verdict. Missing cache counts are **null**, never zero. No raw request content, real session ID or provider-native opaque material belongs in the normalized report. If OpenCode only exposes per-message aggregates, record that limitation and decline the per-request primary comparison rather than manufacturing request rows.

The primary comparable subset consists of successful root-chat provider requests with valid input and cache-read counts. Exclude the unscored probe, each scored session's cold first request, auxiliary title/naming/summary lanes, failed/aborted attempts, and records lacking cache detail. Show excluded requests, retries, error consumption, unknown usage and auxiliary usage separately. For the **operational/quota** view include all observed provider consumption, successful or not; report its coverage and never imply the clean subset is total spend.

## Metrics and verdict

Report all three repetitions, then their median:

1. **Warm reuse rate:** `sum(cacheReadTokens) / sum(inputTokens)` on comparable requests; zero-denominator runs are invalid.
2. **Clean-subset fresh input per completed turn:** `sum(inputTokens - cacheReadTokens) / completedScoredTurns`, using successful requests with valid cache detail. Label this as a *partial* burden, not the account's total quota usage. Separately show all observed input/output and estimated uncached input per assigned turn, including errors, retries and auxiliaries where reported, with unknowns explicit.
3. **Restart observations:** show the first valid post-restart request's input, cached count and rate beside the last pre-restart request and pre-restart warm distribution, plus exact elapsed gap, pre/post prompt settings and a same-session resume attestation. These requests differ in content/length, so this contrast is descriptive, **not** a causal restart effect. If attributing a cache change to restart is important, design a separately authorized matched no-restart control.
4. **Unexpected misses:** substantial input with zero or materially low reads absent a *known* expected prefix change; lower confidence after restart because YouCoded's diagnostic HMAC key and lane baseline reset. OpenCode's unknown is not `false`, and metadata presence alone cannot establish a provider hit.
5. **Continuation and correctness (separate gates):** verify the same session ID and both pre-restart facts/work state; classify exact accepted-history restoration, ordinary transcript reconstruction, or unknown per arm using evidence the client exposes. YouCoded restore is conditional on transcript digest, model/account credential era and assembled prompt matching; successful recall does not prove reasoning restored. Score verifier result, final file state and tests separately. Reuse cannot win if context was dropped or task correctness is worse.

Also report total input/output/reasoning, cache writes where reported, request and token reporting coverage, requests per turn, latency/elapsed time, retries and errors, continuation-metadata presence before/after restart as booleans/counts where available, and YouCoded **within-process** prefix-change distribution. Raw prompt size is context, not a reuse score.

Correctness gates the efficiency verdict: a client with fewer correct repetitions cannot be named the winner. With equal correctness and comparable token semantics, call YouCoded **clearly better** if median warm reuse is at least 10 percentage points higher *or* median clean-subset fresh-input burden at least 20% lower, and the other efficiency metric and all-observed quota burden are not materially worse; call it **clearly worse** for the inverse, or repeated *evidenced* same-session/continuation loss while OpenCode retains it. **Roughly equivalent** means below both thresholds or opposing effects without consistent practical advantage. **Inconclusive** means fewer than two valid repetitions per arm, cache-detail **root-request** coverage below 70% in either arm, inability to count provider requests, incompatible token semantics, inadequate evidence for claimed exact restoration, or inconsistent run direction. Do not score unknown continuation as loss. **Compatibility failure** is separate: the arm cannot complete the Luna probe. Three repetitions and these practical thresholds do not establish statistical significance or isolate client caching from differing agent paths.

## Repetition and quota safeguards

Three scored repetitions per client, fresh session identity per repetition. Do not intentionally reuse another run's provider cache lineage; independent cache residency is best-effort, so record order, gap and any unexpected warm first request. Preserve and report every attempt. Retry a repetition **once at most**, solely for identified infrastructure failure such as launcher crash before scored dispatch or OAuth expiry before dispatch; wrong edits, tool choices, excess exploration, and failed tests are outcomes, not grounds for rerun.

Before any OAuth probe, read the plan's current five-hour and weekly remaining allowance/reset times without copying account identifiers into the report. The implementation plan must set numerical **per-turn wall-clock, per-turn provider-request, per-repetition provider-request and whole-experiment** ceilings and a stop threshold against the *observed* remaining allowance; obtain approval of those numbers before live use. Count all provider requests, including retries and auxiliary requests, from a controller-visible source; if either arm cannot be counted and stopped reliably, do not run it. Enforce six user turns per repetition and identical ceilings. Stop immediately on repeated transport failures, `model_not_found`, authentication refusal, apparent agent loop, quota warning or exhausted allowance; no automatic fallback to API key, another model or paid credits. Hitting a ceiling yields an incomplete/failed repetition, not permission to extend quota. No automatic compaction/specialists/additional models. Unlike the OpenRouter evaluator, ChatGPT-plan quota cannot be protected by a dollar cap; published message estimates are not guarantees.

## Privacy and failure handling

Permitted report material: synthetic fixture content/diffs and the authored six prompts, sanitized errors, settings/versions, normalized token/timing/outcome records, opaque session labels, and booleans/counts for metadata restoration. Forbidden: access/refresh tokens, account IDs, auth headers, raw backend request/response bodies, raw cache keys or real session IDs in the final report, encrypted reasoning or its fingerprints, non-fixture conversation data, and files from live or existing profiles. Use private isolated directories and capture only allowlisted fields **before** writing the normalized report; do not redirect raw CLI JSON, session exports, debugger logs or auth output into a report file. Any unavoidable raw working stores remain local with restricted ownership/modes and a retention/deletion schedule. YouCoded's private accepted-history manifest contains encrypted reasoning even though syncable transcripts do not; its diagnostics can retain rotated files with linkable request metadata. Never copy either into deliverables or commit auth stores. OpenCode sharing must be explicitly `disabled`, not merely left at its default manual setting.

If Luna is unavailable, stop the arm without fallback. If OAuth is needed, pause for browser authorization, never ask for credentials in chat or copy existing profiles. Treat missing detail as unknown and lower coverage. If restart cannot resume the same session, score a continuation failure, not a substitute fresh chat. If the session resumes through transcript reconstruction rather than exact accepted-history restore, score *task continuity* but not exact metadata restoration. Preserve fixture divergence and score correctness failure. Report diagnostic writer losses instead of fabricating counts. If private data appears in collected output, stop, restrict/quarantine that output locally and correct the collector before more live work. If client modification is required, report a blocker; never patch one arm after scoring starts.
