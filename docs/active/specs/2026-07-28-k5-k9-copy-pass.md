## Decisions I need from you

### 1. `'Setup failed'` — a hardcoded guess replacing a real error 🐛

```tsx
<p className="text-xs text-destructive-fg text-center">{setupError || 'Setup failed'}</p>
```

When the Tailscale install fails without setting `setupError`, the user gets the words "Setup
failed" and nothing else — no reason, no next step. That is the exact pattern
`error-message-standards.md` forbids: *never `catch` and replace the real error with a hardcoded
guess.*

The standard already prescribes the fix — `<ErrorState mode="general">`, which renders a
non-committal title plus **Report bug** and **Diagnose with Claude**. Proposed:

> **title:** "Unable to set up remote access."
> **explainer:** "The Tailscale installer didn't report a reason. Diagnosing will collect the setup
> log so Claude can look at what happened."

When `setupError` *is* set, keep `<ErrorState mode="recoverable">` with the real message + Retry, as
today.

**→ Approve, or give me your own wording?**

### 2. "Loading Tailscale…" during an install ✏️

`LoadingState` hardcodes the verb, so an install reads "Loading Tailscale…" and the sign-in wait
reads "Loading the Tailscale sign-in…". Both are wrong about what is happening. This is already on
the residue list from tranche 1.

Proposal: add an optional `verb` prop to `LoadingState` (default `"Loading"`), then:

- installing → "Installing Tailscale…" · "This may take a few minutes"
- authenticating → "Waiting for Tailscale sign-in…" · "Check your browser to sign in to Tailscale"

**→ Approve, or different verbs?**

### 3. "Tailscale installed and connected!" ❓

The only exclamation mark in the settings family. Everything else states facts flatly. Options:

- Keep it — it is a genuine success moment and the app is allowed to be warm.
- Drop the mark: "Tailscale installed and connected."
- Say what it means for the user: "Tailscale is connected. You can pair a device now."

**→ Which?** My preference is the third — a status strip should say what you can do next — but this
is tone, and tone is yours.

### 4. The empty state, branch 11 ❓

Today it is a bare "Set Up Remote Access" button with no message. As a K5 status strip it wants a
line beside the action. The intro callout above already explains what remote access *is*, so this
should say what the *state* is.

Proposal: **"Not set up yet."** (dot: muted)

**→ Approve, or your own?**

### 5. Where the Skip Permissions danger zone lives ❓

K9 says the danger zone is **always last in the menu**. Skip Permissions currently sits in the
middle of Session Defaults, above Project Folder and Close-session prompt, with its Advanced
sub-block attached.

- **(a)** Move it last, as K9 says. Consistent, but it is arguably the most important setting in
  that menu and moving it down de-emphasises it.
- **(b)** Leave it where it is and give it the danger-zone *shape* without the placement rule.
  Then K9's "always last" holds for Account and Local Models only, and Skip Permissions is a
  documented exception.

**→ (a) or (b)?** I lean (b) — the placement rule exists so destructive actions are not stumbled
into, and a toggle you must deliberately flip is a different risk from a Delete button. But it
weakens the rule, so it is your call.
